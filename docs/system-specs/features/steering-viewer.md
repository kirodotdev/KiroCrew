# Steering Viewer

The Steering tab under Agent Capabilities lists the standard user and workspace steering roots and reads, creates, edits, and deletes their Markdown files; `POST` / `PUT` / `DELETE` are filesystem mutations, not a read-only viewer. `handlers/steering.py:api_steering`, `api_steering_create`, and `api_steering_detail` enforce the surface.

## Policy

Two locations are shown, with provenance, because two different mechanisms load them:

| Source | Location | Loaded by |
|--------|----------|-----------|
| `user` (Global) | `~/.kiro/steering/**/*.md` | kiro-cli for every session; also what the CC-backend injection in `context.py:_load_steering_resources()` reaches, since its `file://.kiro/steering/**/*.md` resource globs against `$HOME` |
| `workspace` (Workspace) | `<project>/.kiro/steering/**/*.md` | kiro-cli, because the session subprocess runs with the slot's project directory as cwd |

`handlers/steering.py:steering_roots()` offers a missing standard root as an empty root so the first file can be created, but omits a sensitive root. `list_steering_blocking()` recursively lists Markdown files whose LEAF name is not dot-prefixed — the filter tests `entry.name`, so a dot-prefixed intermediate directory is still traversed and a file inside one is listed — records their source-qualified keys, and redacts the display metadata; `TestListing` in `test/test_steering_api.py` pins those discovery rules.

The active project comes from `_ChatSlot.project` via `handlers/_shared.py:active_project_dir()`, which resolves deterministically: the slot named by the request's `X-Session-Key` if it has a project, else the single project shared by slots that have one, else nothing. That last case matters for mutations — with two chats open on different projects there is no defensible "active" project for a settings page, and picking the first-inserted slot would create, overwrite or delete files in the wrong project.

`GET /api/steering` reports `project_state` (`set` | `none` | `ambiguous`) from `handlers/_shared.py:active_project_state()` — the same resolution, with the reason for an absent project preserved instead of collapsed to `None`. "No project is set" and "your open chats are on different projects" are different problems with different remedies (bind a project, or close the chat that disagrees), and a client told only that the project is absent reports the first when it means the second. With no resolvable project only the global root is offered, and `POST /api/steering` with `source=workspace` is a 400 with `code: "steering_workspace_unavailable"` whose message names the cause, so the create dialog can state which fix applies rather than reporting an unexplained rejection.

Project precondition on workspace writes (`handlers/steering.py`):

- The listing also returns `project_key`: an opaque SHA-256-derived fingerprint of the selected project path, empty when there is no project. A digest rather than the path itself, because its only job is equality — the display path is lossy (`~` collapsed, credential-redacted) and needlessly revealing for that. `TestWorkspaceProjectPrecondition.test_listing_publishes_a_project_key` pins the representation.
- Every **workspace-scoped write** must echo the `project_key` it was listed in a required `X-Steering-Project` request header: `POST /api/steering` with `source=workspace`, and `PUT` / `DELETE /api/steering/{key}` where the key's source is `workspace`. A header rather than a body field because `DELETE` carries no body.
- The precondition exists because a chat slot's project is **mutable**, so the session key cannot close this on its own — it names a slot, and the slot is exactly what moves. List project A, let the slot be re-pointed at B, and a delete issued from the still-visible listing resolves B and unlinks B's file of the same name. A workspace write must therefore state which project it believed it was acting on.
- Mismatch **or absence** returns `steering_project_changed` with 409. Absence fails closed for the same reason the resolver refuses an ambiguous project: a caller that cannot say which project it meant has not earned a write to one. `TestWorkspaceProjectPrecondition` pins refusal of moved and headerless writes, including preservation of both files.
- The denial emits `sel().log_api_access(operation="steering.create|update|delete", outcome="denied", resources="steering_project_changed")`, audited like any other refusal to write — a stale-header burst is the shape a confused, or hostile, client produces, and a denial nobody records is one nobody can review. Enqueued rather than synchronous: the write is already refused, so the record gates nothing and reports a decision already made.
- `user/` keys are **not** gated — they anchor on `$HOME`, which no project can move under. **Reads** are not gated either: a stale read shows the wrong file but destroys nothing, and the save that would act on it comes back through the guard.

Every steering filesystem transaction — the two-root scan, the single-file read, and each create / update / delete — runs as one complete blocking function on `discovery_executor()`. A project on a slow or network filesystem must never stall the event loop, and with it every chat and the heartbeat, for the duration of a write. `handlers/steering.py:_offload()` dispatches the transactions.

Path policy (`handlers/steering.py`):

- A file handle is `"<source>/<relpath>"`. `_split_key()` rejects a missing/unknown source, absolute paths, `~`, `..` segments, backslashes, NUL, and any suffix other than `.md`.
- Containment is anchored on the **trust base** (`$HOME` for `user`, the project dir for `workspace`), not on the steering root: `_contained()` resolves the deepest *existing* ancestor and requires it to sit at or under the resolved base. This is what rejects a `~/.kiro/steering` symlink pointing at `/etc` — comparing against the root itself would follow such a link.
- `is_sensitive_path()` gates every root, listed entry and resolved target; writes additionally gate on `is_sensitive_write_path()`.
- A symlink at the **leaf** is rejected outright and never listed — not merely one that escapes the base. `.kiro/steering/rules.md -> ../../README.md` satisfies base containment, so without this a `PUT` would truncate (and `DELETE` unlink) a file that is not a steering document.
- Update replaces the file (`atomic_write()`: unique temp file in the same directory, then `os.replace`) rather than truncating in place — on a nearly full filesystem a truncate followed by a failed write would destroy the user's document. `os.replace` swaps the leaf directory entry rather than writing through it, so a leaf symlink raced into place is replaced rather than followed.
- Update preserves the target's existing permission bits (`mode=stat.S_IMODE(pre.st_mode)`) rather than forcing `0o600` — the old in-place write inherited them, and a project steering file checked out group-readable must not be silently tightened by a save. Create uses owner-only mode, which is correct for a file this endpoint is bringing into existence. `TestUpdateDeleteEndpoints.test_update_preserves_existing_file_mode` pins the preservation rule.
- Update also carries the target's access-control extended attributes across the replace. The replace installs a fresh inode, so `mode=` alone reproduces permission bits only; a named POSIX ACL (`system.posix_acl_access`, or `system.posix_acl_default`) would otherwise be dropped, handing back a file protected more narrowly than the one it replaced. Update opens the existing file `O_NOFOLLOW` and passes that descriptor to `atomic_write(preserve_access_control_from=…)`, which reads the source's xattrs off the descriptor and reproduces them on the replacement — refusing the write if an access-control attribute cannot be carried, treating `user.*` attributes as best-effort, and treating a filesystem with no xattrs (`ENOTSUP`/`EOPNOTSUPP`/`ENOSYS`) as nothing to carry. `TestUpdateDeleteEndpoints.test_update_routes_acl_preservation_through_atomic_write` pins the routing.
- The carry is an **allowlist** — the two `system.posix_acl_*` names plus `user.*` — and nothing else, because the replacement holds content the *caller* supplied. Replaying `security.capability` would attach the old file's capabilities to that new content, and replaying `security.ima`/`security.evm` would forge an integrity signature over bytes that were never measured. `security.selinux` is excluded too: a fresh inode already gets its type from the parent directory's transition rule, and writing that attribute needs `relabelfrom`/`relabelto` the dashboard process usually lacks on an enforcing host, which under the fail-closed rule above would refuse every save there. A denylist would close today's three names and re-open on the next privileged namespace, so the policy names what it needs instead.
- Both write paths pass `newline=""`. Text-mode writes translate `\n` to `\r\n` on Windows, so a document read back and saved again would accumulate carriage returns on every cycle (CRLF → CR CR LF → …). Content lands on disk exactly as the editor sent it. `TestUpdateDeleteEndpoints.test_crlf_content_round_trips_byte_exact` pins the behavior.
- Create uses `os.open` with `O_EXCL` and `O_NOFOLLOW` where the platform provides it; `O_EXCL` refuses a pre-planted leaf, including a symlink. Update first rejects a symlink or non-regular leaf with `lstat`, then delegates replacement to `atomic_write()`; it does not use an open-then-`fstat` identity comparison. `TestUpdateDeleteEndpoints.test_update_is_atomic_and_preserves_content_on_write_failure` pins the no-truncate failure behavior.
- Create sanitizes the user-supplied name (`_safe_rel_name()`): disallowed characters become `-`, `.`/`..` segments are dropped, and a `.md` suffix is appended. A traversal attempt lands inside the steering root or is rejected — never outside it.
- Listing and document-size bounds are enforced by `STEERING_MAX_FILES` and `STEERING_FILE_MAX_BYTES`; `TestListing.test_file_cap_enforced`, `TestReadEndpoint.test_growth_past_cap_mid_read_is_413_not_500`, and `TestCreateEndpoint.test_oversize_content_is_413` pin them.
- Read responses return content **verbatim** — no credential redaction. The response populates the editor and is written straight back on save, so redacting it would overwrite the user's own file with `[REDACTED]` markers — a data-loss bug in exchange for partial confidentiality. The tradeoff is real rather than free: verbatim content is served to any authenticated dashboard session, which is not necessarily the local OS user who owns the file, because a remote browser reaches the dashboard through the ordinary token flow. `TestMetadataRedaction.test_detail_content_is_verbatim` pins this behavior. Listing **metadata** — the first-heading description, display paths, the project path — is run through `redact_credentials()` + `redact_exfiltration_urls()` via `_redact_meta()`; metadata never round-trips, so redacting it is free. Paths also collapse the real home to `~`.
- The single-file read is one offloaded transaction, `_resolve_and_read_blocking()`: it resolves, then reads through `hooks.safe_read_file_bytes_nolink()` with `within_root` set to the steering root. That helper opens with `O_NOFOLLOW`, `fstat`s the descriptor (rejecting hardlinks and non-regular files), and verifies the **opened** descriptor's real path resolves inside the root and is not sensitive — `O_NOFOLLOW` alone guards only the final path component, so an ancestor directory swapped for a symlink between resolution and open would otherwise escape. Resolution and read are not split, to keep the check-to-use window minimal. The pre-read `lstat` only supplies the size for the 413 message; a file that grows past the cap before the descriptor read makes the helper raise `FileTooLargeError`, which is caught and mapped to 413 rather than a 500.
- Every filesystem touch goes through `_offload()`, including `resolve_steering_file()` — resolution is itself `is_dir`/`lstat`/`resolve` metadata work, and on a network-backed project a stat storm alone is enough to stall the loop. Nothing in these handlers stats, reads, writes or unlinks on the event loop.
- Restricted (incognito / temporary / guest) sessions may read steering but never create, update or delete it (`_is_restricted_session` → 403). Every mutation emits `sel().log_api_access(operation="steering.create|update|delete")`; reads emit `log_tool_invocation(tool_kind="steering")`.

Behavior is pinned by `test/test_steering_api.py`, `website/src/test/SteeringTab.test.tsx` and `website/src/test/ApiClient.coverage.test.tsx` (which scope of write sends the header, and that a user-scoped write does not).

## Wiring

- `src/kiro_crew/dashboard/handlers/steering.py` — `steering_roots()`, `list_steering_blocking()`, `resolve_steering_file()`, the blocking transactions `_resolve_and_read_blocking()` / `_create_file_blocking()` / `_update_file_blocking()` / `_delete_file_blocking()` (all dispatched through `_offload()` onto `discovery_executor()`, the same pool as `/api/skills`), the precondition pair `_project_key()` / `_project_precondition()` with the `STEERING_PROJECT_HEADER` constant, and the handlers `api_steering`, `api_steering_create`, `api_steering_detail`.
- `src/kiro_crew/dashboard/handlers/_shared.py:active_project_dir(state, session_key="")` — shared, deterministic project-dir resolution; `_resolve_skill_root()` and `api_skills` route through it too. `active_project_state()` is the same resolution returning `(project, "set" | "none" | "ambiguous")`, for callers that must explain an absent project rather than only handle one.
- `src/kiro_crew/dashboard/routes/skills.py` — registers `GET/POST /api/steering` before the catch-all `GET/PUT/DELETE /api/steering/{key:.+}`.
- `website/src/pages/overview/SteeringTab.tsx` — list-detail layout (React Query keys `['steering', slotKey]`, `['steering-file', key, slotKey, projectKey]` — `project_key` is part of the file's identity, since `workspace/api.md` names a different file in a different project), `MarkdownRenderer` for view, textarea for edit, `Modal` for create with a scope selector. Workspace writes send the listed `project_key`; an in-progress edit sends the key **captured when the draft loaded**, not the live one, so a draft typed against project A fails the precondition for B (409, draft still on screen) instead of satisfying it and overwriting B's same-named file.
- `website/src/pages/CapabilitiesPage.tsx` — the `steering` tab (Compass icon) between Skills and Hooks.
- `website/src/api/client.ts` — `steeringFiles`, `steeringFile`, `createSteering`, `updateSteering`, `deleteSteering`; the three write helpers take the project key and set `X-Steering-Project` from it.

## Non-goals

- Editing the agent config's `resources` globs — that already exists at `GET/PUT /api/agent/config`; this tab shows the files those globs reach, not the globs.
- Showing the truncation state of the context budget enforced by `context.py:_STEERING_CAP`, or a per-session "what was actually injected" trace.
- Steering files outside the two standard roots (arbitrary `file://` resources in an agent config are not browsable here).
- `AGENTS.md` / `CLAUDE.md` foundational files, which Kiro loads by a separate mechanism.
