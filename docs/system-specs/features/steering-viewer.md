# Steering Viewer

The Steering tab under Agent Capabilities lists the standard user and workspace steering roots and reads, creates, edits, and deletes their Markdown files; `POST` / `PUT` / `DELETE` are filesystem mutations, not a read-only viewer. `handlers/steering.py:api_steering`, `api_steering_create`, and `api_steering_detail` enforce the surface. It also lets an author set the `inclusion` mode each document declares.

**Kiro Crew reports and edits the declaration; it does not act on it.** What a mode causes is the harness's own behaviour, it moves between kiro-cli releases (see [kiro-cli steering](../../reference/kiro-cli/steering.md)), and a client that reimplemented any part of it would duplicate whatever the harness does next.

## Policy

Two locations are shown, with provenance, because two different mechanisms load them:

| Source | Location | Loaded by |
|--------|----------|-----------|
| `user` (Global) | `~/.kiro/steering/**/*.md` | kiro-cli for every session; also what the CC-backend injection in `context.py:_load_steering_resources()` reaches, since its `file://.kiro/steering/**/*.md` resource globs against `$HOME` |
| `workspace` (Workspace) | `<project>/.kiro/steering/**/*.md` | kiro-cli, because the session subprocess runs with the slot's project directory as cwd |

### Declared inclusion mode

Each listed document carries the `inclusion` mode its own front matter declares, so the tab can show what the author asked for. Three fields, from one bounded head read per document (`_head_meta()`):

- `inclusion` — canonicalized to one of `STEERING_INCLUSION_MODES` (`always`, `fileMatch`, `manual`, `auto`), matched case-insensitively so `FILEMATCH` reports as the documented `fileMatch`.
- `inclusion_declared` — the value exactly as written, `""` when the field is absent. It differs from `inclusion` only when the spelling is not a mode.
- `file_match_pattern` — `fileMatchPattern` verbatim; only meaningful beside `inclusion: fileMatch`.

An absent **or unrecognized** declaration reports `STEERING_INCLUSION_DEFAULT` (`always`). That is Kiro's documented default, and it is also what kiro-cli does with a value it does not recognize — measured against 2.19.1 over ACP, a document declaring a nonsense mode is injected like an `always` one. Reporting a typo as a mode of its own would show the author an authoritative-looking state that nothing implements; keeping the raw spelling beside the resolved mode is what lets the tab say *`manaul` is not a mode, it is being read as `always`* — the only thing that explains why a document its author declared `manual` loads into every session.

**Kiro Crew does not act on the value.** On the live ACP path the load decision belongs to kiro-cli, which reads the same front matter itself; this listing is a mirror of the declaration, never a second implementation of it. Measured on 2.19.1 over ACP (`acp --agent <name>` + `session/set_mode`, the shapes `acp/client.py` sends): `always` loads from both roots, `manual` and `fileMatch` are withheld, `fileMatch` never matches even when a file under its pattern is read in the same turn, and an `auto` document loads unconditionally. See [kiro-cli steering](../../reference/kiro-cli/steering.md).

The one-line `description` is taken from the document **body**, not from the raw head. Before this it was the first non-`---` line, so a document opening with front matter was summarized as its first declaration and the tab showed `inclusion: manual` where the author's title belongs. A front-matter block longer than the head slice has no closing fence to find inside it, so there is no body to read and the description is empty — falling back to the raw head would reinstate exactly that bug. `inclusion` needs no redaction (closed vocabulary); the two free-text fields are redacted and capped at `_STEERING_META_MAX_CHARS` like the description.

The mode **name itself is never translated** in the UI. `fileMatch` is a literal the author types into their own front matter, so a localized chip would name a mode that does not appear in the file — the same rule that keeps a token the user must type out of the catalog. Only the surrounding explanation is copy.

### Editing the declaration

`PUT /api/steering/{key}` accepts two optional fields beside `content` — `inclusion` and `file_match_pattern` (`STEERING_WRITABLE_FIELDS`). `name` and `description` are deliberately not writable: they matter (they are what the on-demand index shows the model) but an author sets them by editing the document, and accepting a field nothing writes is surface to defend at every review for no behavior. Absent means "leave alone"; an empty string **removes** that key, which is how a document goes back to declaring nothing at all. Only those two are writable: the endpoint edits a document's *declaration*, and everything else in its front matter belongs to the author.

The rewrite happens **server-side**, through `frontmatter.set_frontmatter_fields()`, and the body is preserved byte for byte. The obvious alternative — have the editor splice YAML into the textarea it is already showing — was rejected: the body is the user's document, a client that got the splice subtly wrong would corrupt the very file whose purpose is to be read by the agent, and every client would have to reimplement it. The writer also folds three cases a naive splice gets wrong: creating a block where there is none, dropping the fence when the last key is removed (rather than leaving a bare `---` the renderer draws as a rule), and consuming a YAML block scalar's continuation lines along with its key.

- **A written value is quoted unless it is provably plain.** The document is read back by kiro-cli as real YAML, where a bare scalar is retyped and re-cut by rules this module's line-wise reader never sees: `true`/`no`/`null`/`123` stop being strings, `src # old/*.ts` is truncated at the comment, and a leading `*`, `[`, `{`, `!` or `&` opens an alias, a flow collection, a tag or an anchor — `fileMatchPattern: *.ts` is the most ordinary glob a user can type and it makes the whole file unparseable. So bare output is gated on an allowlist (`_PLAIN_SAFE_RE` plus the resolver keywords) rather than on a list of known-bad spellings, which keeps the closed mode vocabulary unquoted and quotes everything else. `test/test_frontmatter.py` pins the property by feeding what is emitted to a YAML parser, not only to this module's own.
- **The editor strips a symmetric quote pair before sending** (`normalizePattern`). Kiro's documentation spells the field `fileMatchPattern: "src/**/*.ts"`, so the quoted form is exactly what an author copies; sent verbatim it would be refused for carrying a quote. No glob is delimited by quotes, so removing the wrapper cannot lose meaning.
- **An inline `# comment` belongs to the author, on both sides of the read.** `STEERING_LOADER` opts into `strip_inline_comments`, so `inclusion: manual # rationale` reads as `manual` here exactly as it does for kiro-cli — without it the tab reported an unrecognized mode the agent never saw. The writer carries the comment across a rewrite (`split_inline_comment`), so changing the mode does not delete the rationale beside it. The flag is per-dialect: shortening what the skills catalog already accepts is the silent drift those dialects exist to prevent.
- **Values are verified to round-trip.** The single-line grammar has no escape sequence — `strip_quotes` is `str.strip` over quote characters, which removes *runs* of them and understands no escape at all — so a value ending in a quote would read back shorter than it went in. `_verify_round_trip()` re-parses what was written and refuses a value that does not survive (`steering_field_unrepresentable`), rather than silently truncating the author's text.
- **`fileMatch` requires a pattern** (`steering_file_match_needs_pattern`). A patternless `fileMatch` document can never match, so it would be withheld forever with nothing to explain why. Checked against the **result**, so flipping the mode on a document that already carries a pattern is not a rejection. The UI disables Save for the same reason, stating the requirement at the moment it applies rather than after the user has committed.
- **An unknown mode is refused** (`steering_unknown_inclusion`) and a known one is canonicalized on write, so `FILEMATCH` lands as `fileMatch`.
- **Only the fields whose control actually moved are sent.** The server applies a declaration ON TOP of the submitted text, so unconditionally sending the seeded values would silently revert front matter the user had just edited by hand in the textarea — the mode control winning an argument the user never started. A switch away from `fileMatch` deliberately does not clear the pattern either: the endpoint edits a declaration, and a glob the author typed is theirs to keep.
- **A CRLF document is a document.** `STEERING_LOADER` uses a CRLF-tolerant fence, and the writer emits the newline the document already uses. The LF-only fence matched a Windows-authored file not at all, which was two silent failures at once: its declaration was invisible (the tab reported the default mode), and an edit prepended a SECOND front-matter block instead of rewriting the first.
- **The write's response seeds the cache** before the invalidation. A refetch can fail or lag, and a second Edit would then re-seed from the pre-save body and mode and write them back over what was just saved.
- **The response echoes the stored text** plus the resolved declaration. Without that, an editor still holding the pre-rewrite body would re-send it on the next save and undo the mode it had just set.

In the UI the mode is a segmented control inside the editor (`DeclarationEditor`), with the pattern field appearing only for `fileMatch`. The tab deliberately carries **no per-mode promise** about what will happen: that belongs to the harness and would go stale the next time it changes. An unrecognized mode does get a detail-pane banner as well as the chip tooltip — that one is a fact about the file, not about the harness, and a tooltip is unreachable on touch.

`handlers/steering.py:steering_roots()` offers a missing standard root as an empty root so the first file can be created, but omits a sensitive root. `list_steering_blocking()` recursively lists Markdown files whose LEAF name is not dot-prefixed — the filter tests `entry.name`, so a dot-prefixed intermediate directory is still traversed and a file inside one is listed — records their source-qualified keys, and redacts the display metadata; `TestListing` in `test/test_steering_api.py` pins those discovery rules.

The active project comes from `_ChatSlot.project` via `handlers/_shared.py:active_project_dir()`, which resolves deterministically: the slot named by the request's `X-Session-Key` if it has a project, else the single project shared by slots that have one, else nothing. That last case matters for mutations — with two chats open on different projects there is no defensible "active" project for a settings page, and picking the first-inserted slot would create, overwrite or delete files in the wrong project.

`GET /api/steering` reports `project_state` (`set` | `none` | `ambiguous`) from `handlers/_shared.py:active_project_state()` — the same resolution, with the reason for an absent project preserved instead of collapsed to `None`. "No project is set" and "your open chats are on different projects" are different problems with different remedies (bind a project, or close the chat that disagrees), and a client told only that the project is absent reports the first when it means the second. With no resolvable project only the global root is offered, and `POST /api/steering` with `source=workspace` is a 400 with `code: "steering_workspace_unavailable"` whose message names the cause, so the create dialog can state which fix applies rather than reporting an unexplained rejection.

Project precondition on workspace writes (`handlers/steering.py`):

- The listing also returns `project_key`: an opaque SHA-256-derived fingerprint of the selected project path, empty when there is no project. A digest rather than the path itself, because its only job is equality — the display path is lossy (`~` collapsed, credential-redacted) and needlessly revealing for that. `TestWorkspaceProjectPrecondition.test_listing_publishes_a_project_key` pins the representation.
- Every **workspace-scoped write** must echo the `project_key` it was listed in a required `X-Steering-Project` request header: `POST /api/steering` with `source=workspace`, and `PUT` / `DELETE /api/steering/{key}` where the key's source is `workspace`. A header rather than a body field because `DELETE` carries no body.
- The precondition exists because a chat slot's project is **mutable**, so the session key cannot close this on its own — it names a slot, and the slot is exactly what moves. List project A, let the slot be re-pointed at B, and a delete issued from the still-visible listing resolves B and unlinks B's file of the same name. A workspace write must therefore state which project it believed it was acting on.
- Mismatch **or absence** returns `steering_project_changed` with 409. Absence fails closed for the same reason the resolver refuses an ambiguous project: a caller that cannot say which project it meant has not earned a write to one. `TestWorkspaceProjectPrecondition` pins refusal of moved and headerless writes, including preservation of both files.
- The denial emits `sel().log_api_access(operation="steering.create|update|delete", outcome="denied", resources="steering_project_changed")`, audited like any other refusal to write — a stale-header burst is the shape a confused, or hostile, client produces, and a denial nobody records is one nobody can review. Enqueued rather than synchronous: the write is already refused, so the record gates nothing and reports a decision already made.
- `user/` keys are **not** gated — they anchor on `$HOME`, which no project can move under. **Reads** are not gated either: a stale read shows the wrong file but destroys nothing, and the save that would act on it comes back through the guard.

Every steering filesystem transaction — the two-root scan, the single-file read, and each create / update / delete — runs as one complete blocking function on `discovery_executor()`. A project on a slow or network filesystem must never stall the event loop, and with it every chat and the heartbeat, for the duration of a write. `handlers/steering.py:_offload()` dispatches the transactions.

Path policy (`handlers/steering.py`):

- A file handle is `"<source>/<relpath>"`. `_split_key()` rejects a missing/unknown source, absolute paths, `~`, `..` segments, backslashes, NUL, and any suffix other than `.md`.
- Containment is anchored on the **trust base** (`$HOME` for `user`, the project dir for `workspace`), not on the steering root: `_contained()` resolves the deepest *existing* ancestor and requires it to sit at or under the resolved base. This is what rejects a `~/.kiro/steering` symlink pointing at `/etc` — comparing against the root itself would follow such a link.
- `is_sensitive_path()` gates every root, listed entry and resolved target; writes additionally gate on `is_sensitive_write_path()`.
- A symlink at the **leaf** never resolves for write — not merely one that escapes the base. `.kiro/steering/rules.md -> ../../README.md` satisfies base containment, so without this a `PUT` would truncate (and `DELETE` unlink) a file that is not a steering document. It IS listed and readable, read-only, when its resolved target passes the session loader's admission gate against the **source's link trust base** — `context.py:steering_target_admissible(resolved, base)`: a regular file, not sensitive, and under `$HOME` for `user` or under the **steering root itself** for `workspace` (`_link_trust_base`). The `user` latitude exists for loader parity: `_load_steering_resources()` follows a leaf link and injects its target into every session, and before this the tab hid the entry and reported "Steering (0)" for a directory of symlinks. `workspace` has no such loader (kiro-cli reads that root itself), so a repository-committed link earns no latitude beyond the root — with the whole project as the base, `leak.md -> ../../.env` would serve the project's own credentials verbatim through the steering GET. A linked entry carries `linked: true`, `editable: false` and `target` (the resolved display path); its `description`/`inclusion` metadata is head-read from the TARGET with `within_root` bound to that same base. A link whose target escapes its base, is sensitive, dangles, or loops (`Path.resolve(strict=True)` raises `RuntimeError` on a symlink loop, caught beside `OSError`) stays hidden. `resolve_steering_file(follow_links=True)` is the read path's opt-in; update and delete resolve with the default and keep refusing the key (`TestLinkedEntries` pins both halves, both sources).
- Update replaces the file (`atomic_write()`: unique temp file in the same directory, then a publishing rename) rather than truncating in place — on a nearly full filesystem a truncate followed by a failed write would destroy the user's document. The rename swaps the leaf directory entry rather than writing through it, so a leaf symlink raced into place is replaced rather than followed. Two things the replacement does **not** reproduce, and they apply equally to `/api/file-write` and to the skills update since all three share `atomic_write`: **ownership** (the fresh inode is the gateway's own uid/gid, and an unprivileged writer cannot give a file away — bits and the POSIX ACL are carried, so a cross-owned document changes owner without the effective grant widening), and **a Windows DACL** (the carry is POSIX xattrs only, so on Windows the replacement lands on the DACL inherited from the containing directory rather than the one the replaced file carried — a file tightened below its directory's inheritance is widened back to it). Closing the second needs a `platform_compat` primitive to READ a DACL, which does not exist yet — `restrict_to_owner` only writes one — so it belongs to `atomic_write` and to all three surfaces at once, not to a per-surface revert to an in-place write.
- All three mutations address the **leaf relative to a descriptor pinning the parent chain** where the platform has the descriptor-relative syscalls (`_DIR_FD_SUPPORTED` = `pinned_fs.supports_pinned_walk()` and `os.unlink` in `os.supports_dir_fd`). The walk opens the parent component by component with `O_NOFOLLOW`, so an ancestor directory swapped for a symlink *after* the resolution above cannot redirect where the write, the create or the unlink lands — the leaf checks close the final component only, and the by-name `mkstemp`/rename/`unlink` re-resolve every component before them. Concretely: create does the `mkdir(parents=True)` by name (callers own their tree roots, as in `prompts.py`) and then opens only `target.name` with `dir_fd=`; update passes the descriptor as `atomic_write(parent_dir_fd=…)`, which stages the temp with `os.open(name, O_CREAT|O_EXCL|O_NOFOLLOW, dir_fd=)` and publishes with `renameat` (`os.rename` with `src_dir_fd`/`dst_dir_fd`) — `os.replace` is not in `os.supports_dir_fd` on every interpreter, and on POSIX `os.rename` already overwrites the destination; delete unlinks `target.name` with `dir_fd=`. Windows takes the by-name floor unchanged, so `os.replace` remains the publish there and the two branches are both live.
- **Which pinning primitive a verb uses follows from whether it already holds a canonical path, and getting that backwards silently undoes the pin.** Update and delete are handed the **resolved** leaf (`resolve_steering_file` with `for_write` False returns `target.resolve(strict=True)`), so `pinned_fs.pin_parent(str(target.parent))` walks the chain that resolution already canonicalized and a component that has since become a link fails `O_NOFOLLOW` — the swap is *refused*. `open_dir_pinned` would `realpath` the chain again at pin time and *follow* the swap: a second resolution cannot be more faithful than the first, only less. Create is the opposite case — `for_write` True returns `root / rel`, which need not exist and whose containment was checked on the deepest *existing* ancestor only — so there is no canonical chain to be faithful to, `open_dir_pinned`'s own `realpath` is the first resolution, and `pin_parent` there would refuse the symlinked ancestors `_contained()` deliberately allows above the trust base (a symlinked `$HOME`, `/tmp` on macOS) and break create outright. Create's residual is therefore the by-name `mkdir(parents=True)`, which follows a link already sitting on the chain. `test_dashboard_pinned_write_migration.py::test_a_grandparent_swapped_after_canonicalization_is_refused` pins the update and delete halves.
- Update gates on **both** capabilities — `_DIR_FD_SUPPORTED` for the walk that produces the descriptor and `atomic_write.pinned_parent_replace_supported()` for the rename that consumes it — and passes `None` when either is False. `atomic_write` *refuses* a `parent_dir_fd` it cannot publish through rather than quietly staging by name, so asking only the walk would make every save a 500 where the two probes disagree instead of degrading to the floor.
- **Once the parent is pinned, nothing downstream of it is addressed by name again — including the metadata read.** Update pins *before* opening the access-control source and passes the descriptor as `open_access_control_source(target, dir_fd=…)`, so the mode (`os.fstat`, not the by-name `lstat`) and the ACL come from the inode inside the directory that was walked. A by-name open there is a hole rather than a redundancy: a directory replaced at the parent's name between the pin and that open would supply the mode and the ACL while the rename still published into the pinned original, handing the user's document back carrying permissions chosen by whoever did the replacing. With `dir_fd` the helper returns a descriptor even where the xattr syscalls are absent (macOS has `openat` and no `listxattr`), because the *mode* carry needs one there too. `test_dashboard_pinned_write_migration.py::test_the_mode_and_acl_source_is_opened_through_the_pinned_directory` pins it by injecting the directory swap inside that exact window. The by-name `lstat` above stays as the symlink/non-regular pre-check and is the mode source only on the unpinned floor, where nothing was pinned to disagree with it.
- A parent that cannot be pinned raises `pinned_fs.PinnedPathRefusal`, and each verb maps it to the token its existing contract already carries: `writefailed` on create and update (steering has no linked-root token to report, and the write genuinely did not happen), `notfound` on delete (a leaf reachable only through a linked ancestor is not reachable through the tree the caller named, which is the same answer a by-name unlink gives when the file is gone). No new response shape reaches the client.
- Update preserves the target's existing permission bits (`mode=stat.S_IMODE(pre.st_mode)`) rather than forcing `0o600` — the old in-place write inherited them, and a project steering file checked out group-readable must not be silently tightened by a save. Create uses owner-only mode, which is correct for a file this endpoint is bringing into existence. `TestUpdateDeleteEndpoints.test_update_preserves_existing_file_mode` pins the preservation rule.
- Update also carries the target's access-control extended attributes across the replace. The replace installs a fresh inode, so `mode=` alone reproduces permission bits only; a named POSIX ACL (`system.posix_acl_access`, or `system.posix_acl_default`) would otherwise be dropped, handing back a file protected more narrowly than the one it replaced. Update opens the existing file `O_NOFOLLOW` and passes that descriptor to `atomic_write(preserve_access_control_from=…)`, which reads the source's xattrs off the descriptor and reproduces them on the replacement — refusing the write if an access-control attribute cannot be carried, treating `user.*` attributes as best-effort, and treating a filesystem with no xattrs (`ENOTSUP`/`EOPNOTSUPP`/`ENOSYS`) as nothing to carry. `TestUpdateDeleteEndpoints.test_update_routes_acl_preservation_through_atomic_write` pins the routing.
- The carry is an **allowlist** — the two `system.posix_acl_*` names plus `user.*` — and nothing else, because the replacement holds content the *caller* supplied. Replaying `security.capability` would attach the old file's capabilities to that new content, and replaying `security.ima`/`security.evm` would forge an integrity signature over bytes that were never measured. `security.selinux` is excluded too: a fresh inode already gets its type from the parent directory's transition rule, and writing that attribute needs `relabelfrom`/`relabelto` the dashboard process usually lacks on an enforcing host, which under the fail-closed rule above would refuse every save there. A denylist would close today's three names and re-open on the next privileged namespace, so the policy names what it needs instead.
- Both write paths pass `newline=""`. Text-mode writes translate `\n` to `\r\n` on Windows, so a document read back and saved again would accumulate carriage returns on every cycle (CRLF → CR CR LF → …). Content lands on disk exactly as the editor sent it. `TestUpdateDeleteEndpoints.test_crlf_content_round_trips_byte_exact` pins the behavior.
- Create uses `os.open` with `O_EXCL` and `O_NOFOLLOW` where the platform provides it — relative to the pinned parent descriptor on the pinned branch, by name on the floor; `O_EXCL` refuses a pre-planted leaf, including a symlink. The pinned branch writes the encoded body with an `os.write` loop and adds `O_BINARY` (a Windows-only flag, unreachable there since that platform takes the floor) to get the same byte-exactness the floor's `newline=""` `fdopen` gives; a partial body is removed through the same descriptor via `pinned_fs.unlink_verified` — identity-checked against the inode the create made, so a rival that replaced the name inside the failure window keeps ITS file rather than losing it to the cleanup — or an `O_EXCL` retry would answer `exists` forever. The leaf descriptor is also closed INSIDE that guarded region rather than in a `finally`, because a deferred write error is reported by `close()` (ENOSPC on the last flush, EIO on NFS) and would otherwise raise after the cleanup arm was skipped — and the identity probe itself is inside it too, since an `fstat` that fails would otherwise escape with the empty `O_EXCL` name still on disk. That identity is then asked for **once more through the descriptor the call still holds** — the close at the end of the guarded region is what takes it away, an EIO on a network filesystem is usually transient, and a re-probe of a descriptor can never answer with a different object. **No unlink runs without an identity.** With both probes failed the name STAYS, because removing it would be removing whatever answers to that name, and that is a file this code has never read. The cost is bounded: the identity probe precedes the first `os.write`, so a rollback with no identity is one where nothing was written, and what is left is an EMPTY document rather than a truncated one — listed, editable and deletable from the dashboard, so the recovery is a save rather than a shell. Update first rejects a symlink or non-regular leaf with `lstat`, then delegates replacement to `atomic_write()`; it does not use an open-then-`fstat` identity comparison. `TestUpdateDeleteEndpoints.test_update_is_atomic_and_preserves_content_on_write_failure` pins the no-truncate failure behavior.
- Create sanitizes the user-supplied name (`_safe_rel_name()`): disallowed characters become `-`, `.`/`..` segments are dropped, and a `.md` suffix is appended. A traversal attempt lands inside the steering root or is rejected — never outside it.
- Listing and document-size bounds are enforced by `STEERING_MAX_FILES` and `STEERING_FILE_MAX_BYTES`; `TestListing.test_file_cap_enforced`, `TestReadEndpoint.test_growth_past_cap_mid_read_is_413_not_500`, and `TestCreateEndpoint.test_oversize_content_is_413` pin them.
- Read responses return content **verbatim** — no credential redaction. The response populates the editor and is written straight back on save, so redacting it would overwrite the user's own file with `[REDACTED]` markers — a data-loss bug in exchange for partial confidentiality. The tradeoff is real rather than free: verbatim content is served to any authenticated dashboard session, which is not necessarily the local OS user who owns the file, because a remote browser reaches the dashboard through the ordinary token flow. `TestMetadataRedaction.test_detail_content_is_verbatim` pins this behavior. Listing **metadata** — the first-heading description, display paths, the project path — is run through `redact_credentials()` + `redact_exfiltration_urls()` via `_redact_meta()`; metadata never round-trips, so redacting it is free. Paths also collapse the real home to `~`.
- The single-file read is one offloaded transaction, `_resolve_and_read_blocking()`: it resolves (following an admissible leaf link — `follow_links=True`), then reads through `hooks.safe_read_file_bytes_nolink()` with `within_root` set to the steering root — or to the source's link trust base for a linked entry (`$HOME` for `user`; for `workspace` the link base IS the steering root), the same anchor its target was admitted against. That helper opens with `O_NOFOLLOW`, `fstat`s the descriptor (rejecting hardlinks and non-regular files), and verifies the **opened** descriptor's real path resolves inside the root and is not sensitive — `O_NOFOLLOW` alone guards only the final path component, so an ancestor directory swapped for a symlink between resolution and open would otherwise escape. Resolution and read are not split, to keep the check-to-use window minimal. The pre-read `lstat` only supplies the size for the 413 message; a file that grows past the cap before the descriptor read makes the helper raise `FileTooLargeError`, which is caught and mapped to 413 rather than a 500.
- Every filesystem touch goes through `_offload()`, including `resolve_steering_file()` — resolution is itself `is_dir`/`lstat`/`resolve` metadata work, and on a network-backed project a stat storm alone is enough to stall the loop. Nothing in these handlers stats, reads, writes or unlinks on the event loop.
- The listing's per-document head read goes through `hooks.safe_read_file_bytes_nolink()` too, not a bare `open()`. The scan above it rejects a symlinked entry and a sensitive resolved path, but a HARDLINK defeats both: the entry's own path stays innocently inside the steering root while its inode is somebody else's secret, whose first line would then be published as this document's description. The guarded reader `fstat`s the descriptor it opened and refuses `st_nlink > 1`.
- Restricted (incognito / temporary / guest) sessions may read steering but never create, update or delete it (`_is_restricted_session` → 403). Every mutation emits `sel().log_api_access(operation="steering.create|update|delete")`; reads emit `log_tool_invocation(tool_kind="steering")`.

Behavior is pinned by `test/test_steering_api.py`, `website/src/test/SteeringTab.test.tsx` and `website/src/test/ApiClient.coverage.test.tsx` (which scope of write sends the header, and that a user-scoped write does not).

## Wiring

- `src/kiro_crew/dashboard/handlers/steering.py` — `steering_roots()`, `list_steering_blocking()`, `resolve_steering_file()` (keyword-only `follow_links` for the read path), the blocking transactions `_resolve_and_read_blocking()` / `_create_file_blocking()` / `_update_file_blocking()` / `_delete_file_blocking()` (all dispatched through `_offload()` onto `discovery_executor()`, the same pool as `/api/skills`), the precondition pair `_project_key()` / `_project_precondition()` with the `STEERING_PROJECT_HEADER` constant, and the handlers `api_steering`, `api_steering_create`, `api_steering_detail`.
- `src/kiro_crew/context.py:steering_target_admissible(resolved, base=None)` — the shared admission gate for a resolved steering path (a regular file, not sensitive, under the trust base; `base` defaults to `$HOME`). `_load_steering_resources()` routes every glob hit through the default; the listing and the read path route leaf symlinks through it with the source's link trust base (`_link_trust_base`), so the tab and the loader cannot drift apart and a workspace link stays inside its steering root.
- `src/kiro_crew/dashboard/handlers/_shared.py:active_project_dir(state, session_key="")` — shared, deterministic project-dir resolution; `_resolve_skill_root()` and `api_skills` route through it too. `active_project_state()` is the same resolution returning `(project, "set" | "none" | "ambiguous")`, for callers that must explain an absent project rather than only handle one.
- `src/kiro_crew/dashboard/routes/skills.py` — registers `GET/POST /api/steering` before the catch-all `GET/PUT/DELETE /api/steering/{key:.+}`.
- `src/kiro_crew/frontmatter.py` — `STEERING_LOADER`, `set_frontmatter_fields()`, `render_frontmatter_value()`, the dialect `_head_meta()` parses steering front matter with. A separate constant from `SKILL_LOADER` rather than a second reference to it: the two document families have no reason to move together.
- `website/src/pages/overview/SteeringTab.tsx` — `InclusionChip` (rendered only when the mode departs from the default, or the declared spelling is not a mode); `LinkedChip` (rendered on `linked: true` entries, tooltip naming the resolved target; Edit/Delete are disabled — not hidden — on `editable: false`, with the same sentence as their `title`); list-detail layout (React Query keys `['steering', slotKey]`, `['steering-file', key, slotKey, projectKey]` — `project_key` is part of the file's identity, since `workspace/api.md` names a different file in a different project), `MarkdownRenderer` for view, textarea for edit, `Modal` for create with a scope selector. Workspace writes send the listed `project_key`; an in-progress edit sends the key **captured when the draft loaded**, not the live one, so a draft typed against project A fails the precondition for B (409, draft still on screen) instead of satisfying it and overwriting B's same-named file.
- `website/src/pages/CapabilitiesPage.tsx` — the `steering` tab (Compass icon) between Skills and Hooks.
- `website/src/api/client.ts` — `steeringFiles`, `steeringFile`, `createSteering`, `updateSteering`, `deleteSteering`; the three write helpers take the project key and set `X-Steering-Project` from it.

## Non-goals

- Changing WHEN a document reaches the model. Which documents kiro-cli loads, and when, is the harness's decision; this tab reads and writes the declaration and nothing else.
- Semantic matching of a description. The index hands the model the name and description and lets it decide; there is no embedding step here.
- Withholding an `always` document, or anything else kiro-cli chose to inject.
- Editing the agent config's `resources` globs — that already exists at `GET/PUT /api/agent/config`; this tab shows the files those globs reach, not the globs.
- Showing the truncation state of the context budget enforced by `context.py:_STEERING_CAP`, or a per-session "what was actually injected" trace.
- Steering files outside the two standard roots (arbitrary `file://` resources in an agent config are not browsable here).
- `AGENTS.md` / `CLAUDE.md` foundational files, which Kiro loads by a separate mechanism.
