# Jev Decision Seam

Owners: `src/kiro_crew/decisions/`, `src/kiro_crew/context.py`, `src/kiro_crew/config/sections.py`, `src/kiro_crew/dashboard/handlers/decisions.py`, the strip hand-off in `src/kiro_crew/dashboard/chat_runner.py`, and the Decisions card in `website/src/pages/settings/FeaturePreviewsSection.tsx`.

## 1. Scope

The foundation sends typed questions to Jev and validates its answers. `skills.select` is the only business integration: an enabled, sampled session can use Jev to select one eligible skill, or no skill, instead of the word-overlap result. Cron delivery and skill deduplication remain unchanged. There is no shadow mode, LLM comparison implementation, calibration report, or decisions report command: the word-overlap result IS computed on every sampled turn and recorded beside Jev's, but the arm that is injected is always Jev's, so the second arm is an observation rather than a mode.

## 2. Configuration and sampling

Consent is the KEYSTONE leaf `~/.kiro/crew/decisions_consent.json` (`config.loader.decisions_consent_path()`, module `decisions.consent`), holding `{"enabled": bool, "endpoint": str}`; it defaults to absent, which reads as not consented, and only a literal boolean true consents. Consent is bound to a destination: `provider.endpoint` is in the agent-writable `config.json` too, so an enabling PUT must echo the endpoint the owner reviewed (`endpoint` in the body, the `configured_endpoint` the GET showed) and is refused with `409 decisions_consent_endpoint_changed` when the config names a different one -- the GET-to-PUT window is operator-paced while the agent runs, so binding to a fresh server-side read would consent to an address the owner never saw; on a match the PUT records it (`decisions.consent.save_enabled(enabled, endpoint=...)`, `gate.configured_endpoint()` supplying the same default `impl_jev` uses), and the gate sends only while `consent.permits(configured_endpoint)` holds: enabled is true AND the recorded endpoint equals the configured one. A keystone with the flag but no recorded endpoint permits nothing. A later edit of `provider.endpoint` is therefore a refusal, warned once per address in the application log, until the owner turns the switch off and on again; the GET returns `endpoint`, `configured_endpoint` and `permits` so the card shows the address consent is for and says when the two disagree. Disabling clears the recorded endpoint. The `dashboard/handlers/decisions.py` module imports the `decisions` package inside its handlers, not at module top, so the optional seam stays off the gateway boot path (`no-new-work-on-gateway-boot-path`; pinned by `test_decisions_consent.py::test_the_handler_module_keeps_the_seam_off_the_boot_path`). It is deliberately not a `config.json` field: that file is writable by an auto-approved agent shell and the live config watcher applies it without a restart, so a switch there could be flipped by a prompt-injected agent to start sending its own conversation off the machine. The leaf is on `security._CREW_SECRET_LEAVES` (agent file tools refuse it), `sandbox._CREW_READONLY_LEAVES` (mounted read-only in every sandbox) and the absent-ceiling pre-create list, the same placement as `computer_use.json` and `aws_service_consent.json`; its only writer is the owner-only, browser-called `PUT /api/decisions/consent` (`dashboard/handlers/decisions.py`), which refuses app tokens and non-owner users on the read as well as the write, audits every grant and revocation to SEL, and never overwrites a corrupt file. `DecisionsConfig` carries no `enabled` field and `PATCH /api/config/kirocrew` refuses `decisions.enabled`; an `enabled` key an operator or agent writes into `config.json` under any spelling is inert. `decisions.bucket` is an integer percentage from 0 to 100; an absent key is the default of 100, an out-of-range number is clamped, and a value that does not parse as a whole number reads as 0 (nobody sampled), never as everybody. `decisions.history_budget_chars` bounds the PRIOR CONVERSATION one request may carry beside the message, and its default is **0**: consent is recorded against the text the owner reviewed, which names the message excerpt and the candidate descriptions, so shipping prior turns under a standing grant would widen egress with no new choice. Raising it is that choice, and the config alone cannot make it: the CEILING is `history_budget_chars` on the keystone (`consent.STATE_KEY_HISTORY_BUDGET`, `consent.consented_history_budget`), written only by the owner-only PUT, and `gate.history_budget_chars()` sends the SMALLER of the two. `config.json` is agent-writable, so a budget recorded only there could be raised by the very agent whose conversation would then be sent -- the same argument that put `endpoint` on the keystone. Only a whole non-negative number reads as a ceiling; absent, a bool, a string and a float all read as 0, so every consent recorded before the ceiling existed keeps meaning "no prior turns", and an unreadable keystone reads as 0 as well. A zero config value short-circuits before the keystone is read, so the shipped default costs no extra IO on the turn path. It is floored at 0 and an unparsable value reads as 0 -- the same fail-closed direction `bucket` takes, because both decide how much conversation leaves the machine. It is read through `gate.history_budget_chars()`, so a point never imports the config loader onto its own hot path, and it is not writable through `PATCH /api/config/kirocrew` (the route's editable set stays `decisions.bucket` alone). There is no per-request MENU budget: `MAX_CANDIDATES` (100) x (`MAX_KEY_CHARS` 120 + `MAX_DESCRIPTION_CHARS` 200) already caps a menu at 32,000 chars, so a budget below that could only split a request that was never too large, and one above it could never fire. Sampling uses the session key's SHA-256 digest, so a session remains in the same group rather than drawing again on each message. Zero samples none; 100 samples every otherwise eligible session.

The provider configuration contains endpoint, API-key reference, model and `timeout_ms`. A default timeout is 1000 milliseconds. The sampling percentage and provider use the existing live config snapshot; consent is one small keystone read per decision, performed off the event loop (`asyncio.to_thread` in `decide`, the caller's executor thread in `is_enabled`).

Legacy `preview`, `points`, `arm`, `shadow`, and `live` values do not enable this behavior. Enabling an observation-only configuration must never silently authorize business decisions. The keystone consent is the one explicit opt-in.

## 3. Core contract

`decide(point, state, questions, session_key=...)` returns validated answers or `None`. Disabled, unknown-point, unsampled, scrubbed, timed-out, transport-error and invalid-answer paths return `None`. Cancellation propagates so a caller can abandon a pending request. `is_enabled` provides the same cheap preflight before a caller builds its candidate menu; `decide` checks the gates again.

Jev is the sole provider implementation, and `Choice` is the only question type. Requests use its documented wire format with bounded response reads, no retry and no redirect following (`allow_redirects=False`; a 3xx is refused as a provider error, since consent is bound to the endpoint asked and a followed redirect would replay the body elsewhere). A reply is accepted only when each answer's type is `choice`, its `choice` is a string, and the probability for that choice is a finite number in 0..1 (a boolean is not a number); the gate then checks identifiers and options again before anything is consumed. Provider failures do not fabricate a selection. The response mapping is tested against a loopback server; those tests do not prove a real TypeSafe account round-trip.

Before transmission, the request -- the state, the questions and the provider model id together, rendered as the wire will render them -- is scanned with the existing credential patterns, canonical credential redactor and exfiltration-URL detector. A match or scanner failure refuses the whole request. No partially scrubbed request is sent. Every agent-writable provider field that can reach the wire is bounded: `provider.model` must match `types.MODEL_ID_RE` (letters, digits, `.`, `_`, `-`, at most 64 characters) or the request is refused as `scrubbed:provider-model`, checked in the gate before the scan and again in `impl_jev._to_wire`; `provider.endpoint` is bound by consent (above); and `provider.api_key` is never itself a credential -- only the reference `secret://TYPESAFE_API_KEY` (`impl_jev.VAULT_SECRET_NAME`) resolves, from the dashboard secrets vault the agent cannot read, so a literal key written into `config.json` is refused with a warning naming the fix and a reference to any other vault entry resolves to no key and never touches the vault. Where the vault key goes is decided by consent, not by the endpoint being the default: an owner who consented to a proxy address gets the vault key sent there and nowhere else. Configuration is not an independent authorization boundary: an actor allowed to change it can enable requests only to the consented endpoint, with the operator's own model id and key.

## 4. Skill selection

The normal word-overlap result remains the fallback. The Jev candidate menu uses skills available through the existing loader and its project-confinement rules. The explicit no-skill option is `/no skill applies`: a key's first component is a directory name, so no skill can carry that name, and a skill literally called `none` or `(no skill applies)` stays selectable. Always-loaded skills are not candidates; negative triggers and `skills.max_triggered` remain effective. A zero trigger cap means no automatic selection and no Jev request. Skill identifiers are preserved, not shortened into different names.

A validated choice replaces the triggered list before the existing body/pointer split. The explicit no-skill answer produces an empty list; `None` means retain the original list. Custom-agent and minimal-context paths do not acquire automatic skill selection.

The state carries the message (truncated to 2000 chars), the candidate menu, and -- only when the owner has raised `history_budget_chars` above its default of 0 -- the conversation so far as `history`: earlier `user` and `assistant` rows of the SAME session, walked newest-first until the budget is spent with the last entry admitted clipped to fit. The READ is bounded independently at `MAX_HISTORY_MESSAGES` (20) rows so a long conversation cannot turn one selection into a whole-file parse, which means a budget far above a few thousand characters is not the binding constraint. Prior turns are inside `state`, which is what `gate._scan_text` renders, so a credential or exfiltration URL in an earlier turn refuses the whole request exactly as one in the message does (pinned by `test_decisions_points.py::test_a_secret_in_a_prior_turn_refuses_the_whole_request`); history carried beside the state would be egress the scrub never sees. `history` is OMITTED when there is none, so at the shipped default of 0 the request carries exactly the shape it carried before prior turns existed -- a wire change for every consented owner who never opts in is not worth a distinction the log already records. "No prior turns were reachable" is told apart from "this build does not send them" by `history_chars` on the call row, not by an empty list on the wire. The budget is also read BEFORE the transcript, so at 0 the source is never called and a sampled turn pays nothing for a read it would discard. Tool output is never included -- the restriction is applied at the READ (`ConversationLog.recent(roles={"user", "assistant"})`), not filtered afterwards -- and a row whose text equals the current message is skipped, because the turn's own user message may already be flushed. The source is a CALLABLE passed from `build_message` and invoked by the point only after its own gate check, so an unsampled turn pays for no transcript read; `exclude_last_n` is forwarded as every other reader of that log receives it, and a source that raises reads as no history rather than as a failed selection.

## 5. Operational log

The basic JSONL log records call metadata: timestamp, point, hashed session, latency, scrubbed boolean, bounded answer data and an error category. Raw messages, conversation history, candidate descriptions, API keys and provider exception text do not belong in rows.

A point may add its own fields through `log.build_row(extra=...)`, merged FLAT beside those seven and bounded exactly as an answer value is (`_MAX_EXTRA_KEYS`, `_MAX_EXTRA_ITEMS`, `_MAX_VALUE_CHARS`); a key naming one of the seven is dropped, so an extra can only ever add a field and never rewrite `session`, `scrubbed` or `ts`. `decide(extra=...)` writes it onto whichever row that call produces, including a timeout, scrub or provider-error row, and it is never sent -- it takes no part in `_scan_text` because it never reaches the provider. The three cheap refusals still write nothing, extra included.

`skills.select` therefore emits, per sampled turn: one CALL row for the question asked (`turn_id`, `candidates`, `history_chars`, `truncated`), written by the gate; and, only where a usable answer arrived, one OUTCOME row written by the point, carrying `baseline` (the word-overlap keys), `jev` (the keys actually injected, cap applied), `agree` (SET equality, so an order difference is not a disagreement), `p`, `tokens_saved`, the same counts and the shared `turn_id`. `tokens_saved` is an ESTIMATE: injected-body characters of the baseline minus those of the pick, divided by `CHARS_PER_TOKEN` (4), measured only over the symmetric difference because a skill both arms chose cancels -- so agreement costs no body read at all -- and counting bodies means a pointer-only skill is overstated. A refused turn writes no outcome row: `agree` against an answer that never arrived would compare one arm with nothing, and the gate's own row already carries the error category. The baseline arm is computed from the SAME tree walk that builds the menu (`candidates_from_loader(baseline_out=...)`, the same `MIN_TRIGGER_OVERLAP`, the same score order with ties in walk order, the same `skills.max_triggered` cut), so the comparison costs no second enumeration and cannot drift from the matcher's own result.

After writing the row -- and only when `append` reported that it WROTE, since a strip whose durable row was refused describes a decision no verdict could be filed against -- the point calls `publish(session_key, row)` resolved by name from `kiro_crew.decisions.outcomes` inside `try`/`except ImportError`; a build without that module, a module without that attribute, and a publisher that raises are all no-ops that cannot cost the turn its answer. The published dict IS the row that was written, so the dashboard and the log cannot become two descriptions of one turn.

Disabled and unsampled paths do not write logs. A candidate menu that cannot be built -- the loader walk raised, or every entry it yielded was unreadable -- writes one row with error `candidates-failed`, so a loader change that breaks enumeration is visible rather than indistinguishable from an unsampled session; an empty skill tree writes nothing. The log DIRECTORY is sealed alongside the keystone: `decisions` is in `sandbox._CREW_READONLY_LEAVES`, `_CREW_PRECREATE_READONLY_DIR_LEAVES` and `_CREW_NOFOLLOW_READONLY_DIR_LEAVES` -- the last because a resolving symlink is followed by the mount, which would seal a planted target while leaving the lexical name replaceable and the seal satisfied by a link the governed party chose, because sealing the grant while leaving the record writable is half a control -- an agent that cannot enable the seam could still append a `kind="feedback"` row in the shape `build_feedback_row` produces, and that row would be read as a verdict nobody gave. That argument needs BOTH enforcement points, so `~/.kiro/crew/decisions` is also on `security._WRITE_PROTECTED_HOME_PATHS`: the sandbox mount covers a shell and is absent on a host without the OS sandbox, while the agent's file-edit tool is present on every host -- the same input-to-an-authorization-decision placement `rotation.yaml`, the OMC index and the session store take. It is WRITE-protected rather than sensitive, because reading the rows is the point of recording them, and `platform_log_append` opens the file directly without passing that gate. Read stays open and a directory bind shows live contents, so a day-file written later is visible; every legitimate writer is the gateway, outside the sandbox. Rows are appended through `platform_log_append.append_line`, a confined, locked, full-write append (see `docs/system-specs/common/platform-compat.md`) that works on POSIX and Windows alike; a link at the directory or the leaf, or a file that is not a regular single-link file, refuses the write. Each day-file is capped at `MAX_FILE_BYTES` (8 MiB): a row that would cross the ceiling is refused inside the lock before any byte is written, and the first refusal per file is logged at WARNING. Day-files older than `RETENTION_DAYS` (14) are removed by the first append of each UTC day; only regular files carrying this module's own file-name pattern are candidates, and the directory is listed and unlinked through the same pinned, no-follow descriptor the append uses (`platform_log_append.pinned_log_dir`), so a directory link swapped in under the log directory's name cannot redirect the deletion. Log failure cannot turn a valid decision into an application exception. `append` RETURNS whether the row was written, and exactly one caller reads it: the verdict route (section 6), because that row is a person's answer rather than an observation. Every other caller ignores the value by design -- a decision must not fail because its row did. JSON serialization keeps control characters encoded as data; this feature has no terminal report renderer. Logging is best effort, not proof that a selection reached the assembled context.

## 6. The decision strip on the message

A decision is made during prompt assembly, on a worker thread, before the reply it shapes exists; the strip has to ride that reply's message record. `decisions.outcomes` is the only connection between the two: `publish(session_key, outcome)` stores at most one outcome per session and `consume(session_key)` POPS it. The registry is in-process memory, not a file: producer and consumer are the same turn in the same process, and the durable record is the log in section 5. It is bounded three ways because a published outcome is not guaranteed a reader -- one entry per session (a second publish replaces the first), a 600-second TTL, and a 1000-session ceiling evicting oldest-published-first -- so a cancelled turn leaks nothing. `publish` runs on the executor thread and `consume` on the event loop, so both hold one lock over dict operations only; neither raises, because the producer is inside a turn and the consumer is inside the message finalizer.

`consume` is destructive by design. The strip describes ONE turn, so leaving the entry in place would attach the same decision to every later reply in the session and read as a decision made on that turn.

The read happens at `chat_runner._decisions_strip_meta(slot)`, passed as `meta=` to the `slot.append("assistant", ...)` call at both finalizers -- the normal `_flush_segment` and the recovery `_persist_partial_reply` a turn that dies mid-reply goes through. Passed AT append time, not written onto the row afterwards: `slot.append` broadcasts the live `chat_message` frame from inside the call, so a later write would persist but miss the frame the open tab renders. The field is `meta.decisions_strip`, carrying the published dict unchanged. `meta` is the carrier because it is the part of a row that already travels every door -- `_build_message_entry_uncached` persists it, the restore path reads it back, `chat_message_frame` puts it on the WS push, and `append`'s own `mid` minting merges into it. A session with no decision gets no `meta` key at all: absent, never null.

No shipped surface READS `meta.decisions_strip` yet: the dashboard renderer and the verdict control are a separate change, so this module's contribution is the record and the routes, and the field's absence on an ordinary turn is what keeps that inert. `PUT /api/decisions/consent` additionally accepts an optional `history_budget_chars` (a whole non-negative number, refused rather than coerced), records it on enable and clears it on disable so a re-enable cannot inherit an unreviewed budget, audits it beside the endpoint, and the GET reports it so the card can show what was consented to rather than what the config currently asks for. An OMITTED field preserves the recorded ceiling rather than defaulting to 0: the card writes `enabled` and `endpoint` alone, so a default would let an ordinary switch flip erase a ceiling recorded through this same route, and the two facts are independent -- the switch says whether the seam may send, the ceiling says how much prior conversation it may carry, and each moves only when its own field is present. The route hands `consent.KEEP_HISTORY_BUDGET` down rather than resolving the ceiling itself, and `save_enabled` resolves that sentinel inside its own read-modify-write: a caller that read the ceiling first would hold a value read before a concurrent PUT lowered it and write that number back, raising an egress limit by losing a race. Resolving it there is necessary and not sufficient, so that read-modify-write is HELD under one process-wide lock: the handler runs `save_enabled` on a thread, two owner PUTs therefore interleave, and without the lock the enable PUT still writes back the ceiling the lowering PUT had already reduced. The lock spans the read and the write together, so the lower of two concurrent ceilings survives whichever order they took, and it covers `enabled` and `endpoint` on the same terms. A distinct object is what tells "not mentioned" from a chosen `0`, since no number can mean both. An explicit `0` still clears the ceiling, which is how prior turns are taken back without turning the seam off, and the SEL row reports the ceiling actually written. `POST /api/decisions/feedback` takes `{"turn_id": str, "verdict": "right"|"wrong"|null, "side": "jev"|"baseline"}` and appends exactly one `kind="feedback"` row through `log.append`, off the event loop. It answers `503 decisions_feedback_not_recorded` when the append did not land: the day-file ceiling is shared with the turn's own rows, so on a busy sampled day a `200` would report a verdict that was never written, and the SEL row says `denied` for it rather than `allowed`. A null verdict is a real value meaning a verdict taken back. Nothing is coerced: a missing or blank `turn_id`, an ABSENT `verdict` key, a verdict outside the pair, or a side outside the pair is `400 decisions_feedback_invalid_body` and writes nothing, because such a row makes the fold wrong rather than incomplete. Presence is tested apart from value because `null` is itself a verdict here -- the one that takes an earlier one back -- so a body that dropped the field would otherwise append a retract nobody sent. It is the line `KEEP_HISTORY_BUDGET` draws one route over: no in-band value can also mean "not asked". A verdict is never merged into the decision row it judges -- the append is constant-cost by construction, and an edit would lose both when the verdict was given and the fact that someone changed their mind.

A decision row carries no `kind`, so readers tell the two apart by `kind` being absent; that is the only test that also holds for files already written. There is NO aggregate ROUTE: the rows already carry `agree`, `p` and `tokens_saved` beside the verdict rows, so a window is a `jq` pass over `~/.kiro/crew/decisions/*.jsonl` and a served endpoint would be a second reader of the same bytes with its own failure modes -- every crash the review lanes found in this module was in that fold (a non-finite number, an unhashable verdict, a record cap taken from a shared default), and none of them could exist in a file the gateway only appends to. When a surface needs the numbers it can fold them where it renders them. The turn count is `agree + disagree`, the rows carrying a boolean `agree`, and never the row count: one sampled `skills.select` turn writes a call row plus an outcome row (section 5). The feedback route is dashboard-owner only, like the consent pair in the same module, because it writes the log an operator reads.

There is no `GET /api/decisions/strip`. The message carries the record, so a second fetch could only disagree with it.

## 7. Settings and validation

The Decisions card reads and writes the keystone through `GET`/`PUT /api/decisions/consent`, not localStorage and not the config route, and reads the sampling share from the config GET. It prints the configured endpoint ("Sent to") beside the switch so consent is to an address, and a body-weight notice when consent stands for a different address than the config now names. It carries no `configKey`, because it writes no config path; `test_settingref_schema_fixture.py` pins that `decisions.enabled` is absent from the schema and the card. The backend editable-field validation accepts the bounded integer bucket only; sensitive provider credentials remain masked in GET output. The card prints the sampling share in both switch states, phrased as a fact about the on state, because the shipped default of 100 means every session and consent must see that before the switch is flipped. A backend exposing only legacy `preview` is unsupported, not an enabled gateway; that state fades the card, including the egress note, and names Settings › Releases as the fix. A literal `configKey` is required so the settings extractor connects the control to the schema.

Tests cover strict opt-in and legacy non-migration; sampling; the history budget, its 0 default, its fail-closed coercion, and the keystone ceiling that caps it (including an agent-raised config reaching 0); the omitted `history` key and the transcript read the default budget skips; the sealed log directory, its directory-not-file pre-creation and its no-follow membership; the outcome that is not published when its row was refused; Jev success, malformed replies and failure; credential refusal; log shape, the bounded flat `extra` merge and its core-field protection; real PATCH/GET behavior; actual skill-selection consumption and fallback from an executor thread; the prior-turn walk (order, clipping, role restriction, current-message skip, unsampled turns paying nothing) against a real `ConversationLog`; the single question at a full menu, the retired split vocabulary and the deadline; the refused verdict (503, audited as denied) and the writer's return value; both arms with `agree`, `tokens_saved` and the outcome row; the publish hook present, absent and raising; negative triggers and cap limits; frontend field support, writes, refused writes and generated key parity. These are local/loopback tests. Live provider verification requires a real key and separate consent to send test data.
