# Jev Decision Seam

Owners: `src/kiro_crew/decisions/`, `src/kiro_crew/context.py`, `src/kiro_crew/config/sections.py`, `src/kiro_crew/dashboard/handlers/decisions.py`, the strip hand-off, the tool-card annotation hook and the model-routing hook in `src/kiro_crew/dashboard/chat_runner.py`, the `message.steer` call site in `src/kiro_crew/dashboard/chat_handlers.py` with the two stamps in `src/kiro_crew/dashboard/chat_delivery.py`, the `Auto (Jev)` picker entry in `website/src/lib/jevRoute.ts`, and the Decisions card in `website/src/pages/settings/FeaturePreviewsSection.tsx`.

## 1. Scope

The foundation sends typed questions to Jev and validates its answers. Five business integrations ship and only three of them decide anything. `skills.select`: an enabled, sampled session can use Jev to select one eligible skill, or no skill, instead of the word-overlap result. `message.steer` (section 10): a message the dashboard owner sends into a RUNNING turn is routed to the steer path or the queue path by Jev instead of by the sender. `model.route` (section 11): an enabled, sampled session whose owner picked `Auto (Jev)` in the chat model picker can use Jev to put one chat turn in a difficulty tier and run that turn on the model the tier maps to. `tool.risk` (section 9) decides nothing -- it only ANNOTATES a tool call the permission policy has already answered. `compaction.keep` (section 12) decides nothing either, and not in the same way: it MEASURES, at every automatic compaction, which of the session's tool calls would have been worth keeping, and the compaction runs byte-identically whatever the answer is, so there is no arming choice for it anywhere -- only its own consent scope. Each integration's refusal is the shipped behaviour and never a third outcome. No deciding point is reached by consent alone -- each needs a second, owner-made choice (a non-zero `skills.max_triggered`, the send button's `Auto (Jev)` entry, the picker entry), so consenting to the seam arms nothing by itself. The two non-deciding points need no such choice, because there is no behaviour for one to arm. Cron delivery and skill deduplication remain unchanged. There is no shadow mode, LLM comparison implementation, calibration report, or decisions report command: the word-overlap result IS computed on every sampled turn and recorded beside Jev's, but the arm that is injected is always Jev's, so the second arm is an observation rather than a mode.

## 2. Configuration and sampling

Consent is the KEYSTONE leaf `~/.kiro/crew/decisions_consent.json` (`config.loader.decisions_consent_path()`, module `decisions.consent`), holding `{"enabled": bool, "endpoint": str}`; it defaults to absent, which reads as not consented, and only a literal boolean true consents. Consent is bound to a destination: `provider.endpoint` is in the agent-writable `config.json` too, so an enabling PUT must echo the endpoint the owner reviewed (`endpoint` in the body, the `configured_endpoint` the GET showed) and is refused with `409 decisions_consent_endpoint_changed` when the config names a different one -- the GET-to-PUT window is operator-paced while the agent runs, so binding to a fresh server-side read would consent to an address the owner never saw; on a match the PUT records it (`decisions.consent.save_enabled(enabled, endpoint=...)`, `gate.configured_endpoint()` supplying the same default `impl_jev` uses), and the gate sends only while `consent.permits(configured_endpoint)` holds: enabled is true AND the recorded endpoint equals the configured one. A keystone with the flag but no recorded endpoint permits nothing. A later edit of `provider.endpoint` is therefore a refusal, warned once per address in the application log, until the owner turns the switch off and on again; the GET returns `endpoint`, `configured_endpoint` and `permits` so the card shows the address consent is for and says when the two disagree. Disabling clears the recorded endpoint. The `dashboard/handlers/decisions.py` module imports the `decisions` package inside its handlers, not at module top, so the optional seam stays off the gateway boot path (`no-new-work-on-gateway-boot-path`; pinned by `test_decisions_consent.py::test_the_handler_module_keeps_the_seam_off_the_boot_path`). It is deliberately not a `config.json` field: that file is writable by an auto-approved agent shell and the live config watcher applies it without a restart, so a switch there could be flipped by a prompt-injected agent to start sending its own conversation off the machine. The leaf is on `security._CREW_SECRET_LEAVES` (agent file tools refuse it), `sandbox._CREW_READONLY_LEAVES` (mounted read-only in every sandbox) and the absent-ceiling pre-create list, the same placement as `computer_use.json` and `aws_service_consent.json`; its only writer is the owner-only, browser-called `PUT /api/decisions/consent` (`dashboard/handlers/decisions.py`), which refuses app tokens and non-owner users on the read as well as the write, audits every grant and revocation to SEL, and never overwrites a corrupt file. `DecisionsConfig` carries no `enabled` field and `PATCH /api/config/kirocrew` refuses `decisions.enabled`; an `enabled` key an operator or agent writes into `config.json` under any spelling is inert. `decisions.model_route` is the `{tier: model_id}` map `model.route` reads (section 11). All three tiers are present and **every one defaults to `""` -- inherit**, meaning the turn keeps the model its session is already on. No model id is named in code, and none may be: a hardcoded id fails at runtime -- silently, until the first prompt -- for every account not entitled to it, so `docs/system-specs/common/model-selection.md` keeps code defaults at `""`/`"auto"` and admits pins only in an operator-written map, and `code-review.yml` gates on it. Each value goes through `normalize_agent_model`, exactly as `coerce_role_models` does, so `"auto"` and a non-string both collapse to `""` and "inherit" has ONE spelling. A tier outside the three is dropped -- the question never offers it, so it could never be answered. The three keys stay PRESENT rather than being omitted, because "this tier is unpinned" is a state the log and the strip report (section 11), so it needs a spelling of its own instead of being inferred from a missing key. Unreadable reads as every tier unpinned, which applies nothing: the fail-closed direction for a value that decides what a turn costs. It is read through `gate.model_route_map()` so the point never imports the config loader, and it is NOT writable through `PATCH /api/config/kirocrew` (the route's editable set stays `decisions.bucket` alone); an owner edits `config.json`. `decisions.bucket` is an integer percentage from 0 to 100; an absent key is the default of 100, an out-of-range number is clamped, and a value that does not parse as a whole number reads as 0 (nobody sampled), never as everybody. `decisions.history_budget_chars` bounds the PRIOR CONVERSATION one request may carry beside the message, and its default is **0**: consent is recorded against the text the owner reviewed, which names the message excerpt and the candidate descriptions, so shipping prior turns under a standing grant would widen egress with no new choice. Raising it is that choice, and the config alone cannot make it: the CEILING is `history_budget_chars` on the keystone (`consent.STATE_KEY_HISTORY_BUDGET`, `consent.consented_history_budget`), written only by the owner-only PUT, and `gate.history_budget_chars()` sends the SMALLER of the two. `config.json` is agent-writable, so a budget recorded only there could be raised by the very agent whose conversation would then be sent -- the same argument that put `endpoint` on the keystone. Only a whole non-negative number reads as a ceiling; absent, a bool, a string and a float all read as 0, so every consent recorded before the ceiling existed keeps meaning "no prior turns", and an unreadable keystone reads as 0 as well. A zero config value short-circuits before the keystone is read, so the shipped default costs no extra IO on the turn path. It is floored at 0 and an unparsable value reads as 0 -- the same fail-closed direction `bucket` takes, because both decide how much conversation leaves the machine. It is read through `gate.history_budget_chars()`, so a point never imports the config loader onto its own hot path, and it is not writable through `PATCH /api/config/kirocrew` (the route's editable set stays `decisions.bucket` alone). There is no per-request MENU budget: `MAX_CANDIDATES` (100) x (`MAX_KEY_CHARS` 120 + `MAX_DESCRIPTION_CHARS` 200) already caps a menu at 32,000 chars, so a budget below that could only split a request that was never too large, and one above it could never fire. Sampling uses the session key's SHA-256 digest, so a session remains in the same group rather than drawing again on each message. Zero samples none; 100 samples every otherwise eligible session.

The provider configuration contains endpoint, API-key reference, model and `timeout_ms`. A default timeout is 1000 milliseconds. The sampling percentage and provider use the existing live config snapshot; consent is one small keystone read per decision, performed off the event loop (`asyncio.to_thread` in `decide`, the caller's executor thread in `is_enabled`).

Legacy `preview`, `points`, `arm`, `shadow`, and `live` values do not enable this behavior. Enabling an observation-only configuration must never silently authorize business decisions. The keystone consent is the one explicit opt-in.

## 3. Core contract

`DECISION_POINT_NAMES` is the CLOSED tuple `("skills.select", "tool.risk", "message.steer", "model.route")`: a name outside it is refused, so a point added without being listed there refuses every call rather than borrowing the section's switch. `decide(point, state, questions, session_key=...)` returns validated answers or `None`. Disabled, unknown-point, unsampled, scrubbed, timed-out, transport-error and invalid-answer paths return `None`. Cancellation propagates so a caller can abandon a pending request. `is_enabled` provides the same cheap preflight before a caller builds its candidate menu; `decide` checks the gates again.

Jev is the sole provider implementation, and `Choice` is the only question type. Requests use its documented wire format with bounded response reads, no retry and no redirect following (`allow_redirects=False`; a 3xx is refused as a provider error, since consent is bound to the endpoint asked and a followed redirect would replay the body elsewhere). A reply is accepted only when each answer's type is `choice`, its `choice` is a string, and the probability for that choice is a finite number in 0..1 (a boolean is not a number); the gate then checks identifiers and options again before anything is consumed. Provider failures do not fabricate a selection. The response mapping is tested against a loopback server; those tests do not prove a real TypeSafe account round-trip.

Before transmission, the request -- the state, the questions and the provider model id together, rendered as the wire will render them -- is scanned with the existing credential patterns, canonical credential redactor and exfiltration-URL detector. A match or scanner failure refuses the whole request. No partially scrubbed request is sent. Every agent-writable provider field that can reach the wire is bounded: `provider.model` must match `types.MODEL_ID_RE` (letters, digits, `.`, `_`, `-`, at most 64 characters) or the request is refused as `scrubbed:provider-model`, checked in the gate before the scan and again in `impl_jev._to_wire`; `provider.endpoint` is bound by consent (above); and `provider.api_key` is never itself a credential -- only the reference `secret://TYPESAFE_API_KEY` (`impl_jev.VAULT_SECRET_NAME`) resolves, from the dashboard secrets vault the agent cannot read, so a literal key written into `config.json` is refused with a warning naming the fix and a reference to any other vault entry resolves to no key and never touches the vault. Where the vault key goes is decided by consent, not by the endpoint being the default: an owner who consented to a proxy address gets the vault key sent there and nowhere else. Configuration is not an independent authorization boundary: an actor allowed to change it can enable requests only to the consented endpoint, with the operator's own model id and key.

## 4. Skill selection

The normal word-overlap result remains the fallback. The Jev candidate menu uses skills available through the existing loader and its project-confinement rules. The explicit no-skill option is `/no skill applies`: a key's first component is a directory name, so no skill can carry that name, and a skill literally called `none` or `(no skill applies)` stays selectable. Always-loaded skills are not candidates; negative triggers and `skills.max_triggered` remain effective. A zero trigger cap means no automatic selection and no Jev request. Skill identifiers are preserved, not shortened into different names.

A validated choice replaces the triggered list before the existing body/pointer split. The explicit no-skill answer produces an empty list; `None` means retain the original list. Custom-agent and minimal-context paths do not acquire automatic skill selection.

The state carries the message (truncated to 2000 chars), the candidate menu, and -- only when the owner has raised `history_budget_chars` above its default of 0 -- the conversation so far as `history`: earlier `user` and `assistant` rows of the SAME session, walked newest-first until the budget is spent with the last entry admitted clipped to fit. The READ is bounded independently at `MAX_HISTORY_MESSAGES` (20) rows so a long conversation cannot turn one selection into a whole-file parse, which means a budget far above a few thousand characters is not the binding constraint. Prior turns are inside `state`, which is what `gate._scan_text` renders, so a credential or exfiltration URL in an earlier turn refuses the whole request exactly as one in the message does (pinned by `test_decisions_points.py::test_a_secret_in_a_prior_turn_refuses_the_whole_request`); history carried beside the state would be egress the scrub never sees. `history` is OMITTED when there is none, so at the shipped default of 0 the request carries exactly the shape it carried before prior turns existed -- a wire change for every consented owner who never opts in is not worth a distinction the log already records. "No prior turns were reachable" is told apart from "this build does not send them" by `history_chars` on the call row, not by an empty list on the wire. The budget is also read BEFORE the transcript, so at 0 the source is never called and a sampled turn pays nothing for a read it would discard. Tool output is never included -- the restriction is applied at the READ (`ConversationLog.recent(roles={"user", "assistant"})`), not filtered afterwards -- and a row whose text equals the current message is skipped, because the turn's own user message may already be flushed. The source is a CALLABLE passed from `build_message` and invoked by the point only after its own gate check, so an unsampled turn pays for no transcript read; `exclude_last_n` is forwarded as every other reader of that log receives it, and a source that raises reads as no history rather than as a failed selection.

## 5. Operational log

The basic JSONL log records call metadata: timestamp, point, hashed session, latency, scrubbed boolean, bounded answer data and an error category. Raw messages, conversation history, candidate descriptions, API keys and provider exception text do not belong in rows.

A point may add its own fields through `log.build_row(extra=...)`, merged FLAT beside those seven and bounded exactly as an answer value is (`_MAX_EXTRA_KEYS`, `_MAX_EXTRA_ITEMS`, `_MAX_VALUE_CHARS`); a key naming one of the seven is dropped, so an extra can only ever add a field and never rewrite `session`, `scrubbed` or `ts`. `decide(extra=...)` writes it onto whichever row that call produces, including a timeout, scrub or provider-error row, and it is never sent -- it takes no part in `_scan_text` because it never reaches the provider. The three cheap refusals still write nothing, extra included.

`skills.select` therefore emits, per sampled turn: one CALL row for the question asked (`turn_id`, `candidates`, `history_chars`, `truncated`), written by the gate; and, only where a usable answer arrived, one OUTCOME row written by the point, carrying `baseline` (the word-overlap keys), `jev` (the keys actually injected, cap applied), `agree` (SET equality, so an order difference is not a disagreement), `p`, `tokens_saved`, the same counts and the shared `turn_id`. `tokens_saved` is an ESTIMATE: injected-body characters of the baseline minus those of the pick, divided by `CHARS_PER_TOKEN` (4), measured only over the symmetric difference because a skill both arms chose cancels -- so agreement costs no body read at all -- and counting bodies means a pointer-only skill is overstated. A refused turn writes no outcome row: `agree` against an answer that never arrived would compare one arm with nothing, and the gate's own row already carries the error category. The baseline arm is computed from the SAME tree walk that builds the menu (`candidates_from_loader(baseline_out=...)`, the same `MIN_TRIGGER_OVERLAP`, the same score order with ties in walk order, the same `skills.max_triggered` cut), so the comparison costs no second enumeration and cannot drift from the matcher's own result.

After writing the row -- and only when `append` reported that it WROTE, since a strip whose durable row was refused describes a decision no verdict could be filed against -- the point calls `publish(session_key, row)` resolved by name from `kiro_crew.decisions.outcomes` inside `try`/`except ImportError`; a build without that module, a module without that attribute, and a publisher that raises are all no-ops that cannot cost the turn its answer. The published dict IS the row that was written, so the dashboard and the log cannot become two descriptions of one turn.

`model.route` emits, per routed turn: one CALL row written by the gate (`turn_id`, `history_chars`, `truncated`); and one OUTCOME row written by the point where a tier arrived AND its model could be applied, carrying `tier`, `p`, `model_chosen`, `baseline_model` (the model the turn would otherwise have used) and the shared `turn_id`, with the elapsed time in the core `latency_ms` field rather than in `extra`. A tier that arrived and could NOT be applied writes a row with an `error` category instead and publishes nothing: `model-not-advertised` (the tier maps to an id this account cannot run), `no-switch-seam` (the provider cannot express a per-turn model at all) or `switch-failed` (the provider refused it). Each is written rather than dropped because the gate's own call row already says the decision succeeded, so without one the log would report a healthy seam while every turn kept the old model. Disabled and unsampled paths do not write logs. A candidate menu that cannot be built -- the loader walk raised, or every entry it yielded was unreadable -- writes one row with error `candidates-failed`, so a loader change that breaks enumeration is visible rather than indistinguishable from an unsampled session; an empty skill tree writes nothing. The log DIRECTORY is sealed alongside the keystone: `decisions` is in `sandbox._CREW_READONLY_LEAVES`, `_CREW_PRECREATE_READONLY_DIR_LEAVES` and `_CREW_NOFOLLOW_READONLY_DIR_LEAVES` -- the last because a resolving symlink is followed by the mount, which would seal a planted target while leaving the lexical name replaceable and the seal satisfied by a link the governed party chose, because sealing the grant while leaving the record writable is half a control -- an agent that cannot enable the seam could still append a `kind="feedback"` row in the shape `build_feedback_row` produces, and that row would be read as a verdict nobody gave. That argument needs BOTH enforcement points, so `~/.kiro/crew/decisions` is also on `security._WRITE_PROTECTED_HOME_PATHS`: the sandbox mount covers a shell and is absent on a host without the OS sandbox, while the agent's file-edit tool is present on every host -- the same input-to-an-authorization-decision placement `rotation.yaml`, the OMC index and the session store take. It is WRITE-protected rather than sensitive, because reading the rows is the point of recording them, and `platform_log_append` opens the file directly without passing that gate. Read stays open and a directory bind shows live contents, so a day-file written later is visible; every legitimate writer is the gateway, outside the sandbox. Rows are appended through `platform_log_append.append_line`, a confined, locked, full-write append (see `docs/system-specs/common/platform-compat.md`) that works on POSIX and Windows alike; a link at the directory or the leaf, or a file that is not a regular single-link file, refuses the write. Each day-file is capped at `MAX_FILE_BYTES` (8 MiB): a row that would cross the ceiling is refused inside the lock before any byte is written, and the first refusal per file is logged at WARNING. Day-files older than `RETENTION_DAYS` (14) are removed by the first append of each UTC day; only regular files carrying this module's own file-name pattern are candidates, and the directory is listed and unlinked through the same pinned, no-follow descriptor the append uses (`platform_log_append.pinned_log_dir`), so a directory link swapped in under the log directory's name cannot redirect the deletion. Log failure cannot turn a valid decision into an application exception. `append` RETURNS whether the row was written, and exactly one caller reads it: the verdict route (section 6), because that row is a person's answer rather than an observation. Every other caller ignores the value by design -- a decision must not fail because its row did. JSON serialization keeps control characters encoded as data; this feature has no terminal report renderer. Logging is best effort, not proof that a selection reached the assembled context.

## 6. The decision strip on the message

A decision is made during prompt assembly, on a worker thread, before the reply it shapes exists; the strip has to ride that reply's message record. `decisions.outcomes` is the only connection between the two: `publish(session_key, outcome)` stores at most one outcome per POINT per session and `consume(session_key)` POPS the list. Per point, because two points decide the same turn -- `skills.select` during prompt assembly and `model.route` before the prompt is sent -- and both describe the SAME reply, so one slot per session would make the second publish erase the first. A second publish for the same point still replaces, since there is one such decision per turn. The registry is in-process memory, not a file: producer and consumer are the same turn in the same process, and the durable record is the log in section 5. It is bounded four ways because a published outcome is not guaranteed a reader -- one entry per (session, point), at most `MAX_POINTS_PER_SESSION` (8) points per session evicting oldest-published-first, a 600-second TTL, and a 1000-session ceiling evicting oldest-published-first -- so a cancelled turn leaks nothing and a caller publishing under an invented point name bounds itself. The TTL ages the whole session entry from its newest publish, because the reply the list rides on is one event. `publish` runs on the executor thread and `consume` on the event loop, so both hold one lock over dict operations only; neither raises, because the producer is inside a turn and the consumer is inside the message finalizer.

`consume` is destructive by design. The strip describes ONE turn, so leaving the entry in place would attach the same decision to every later reply in the session and read as a decision made on that turn.

The read happens at `chat_runner._decisions_strip_meta(slot)`, passed as `meta=` to the `slot.append("assistant", ...)` call at both finalizers -- the normal `_flush_segment` and the recovery `_persist_partial_reply` a turn that dies mid-reply goes through. Passed AT append time, not written onto the row afterwards: `slot.append` broadcasts the live `chat_message` frame from inside the call, so a later write would persist but miss the frame the open tab renders. The field is `meta.decisions_strip`, carrying the published dicts unchanged as a LIST -- always a list, even for the one-decision turn that is the common case, because a shape that held one would have to drop the second or change shape between turns, and a reader that must branch on "object or array" is a reader two producers can disagree about. The frontend reader still accepts a bare object, so a row written by an earlier release reads unchanged. `meta` is the carrier because it is the part of a row that already travels every door -- `_build_message_entry_uncached` persists it, the restore path reads it back, `chat_message_frame` puts it on the WS push, and `append`'s own `mid` minting merges into it. A session with no decision gets no `meta` key at all: absent, never null.

The dashboard reads that field and only that field: the strip renderer and the verdict control are section 8, the model row is section 11, and the field's absence on an ordinary turn is what keeps them drawing nothing. One strip is drawn per record, keyed by the record's own `point`. `PUT /api/decisions/consent` additionally accepts an optional `history_budget_chars` (a whole non-negative number, refused rather than coerced), records it on enable and clears it on disable so a re-enable cannot inherit an unreviewed budget, audits it beside the endpoint, and the GET reports it so the card can show what was consented to rather than what the config currently asks for. An OMITTED field preserves the recorded ceiling rather than defaulting to 0: the card writes `enabled` and `endpoint` alone, so a default would let an ordinary switch flip erase a ceiling recorded through this same route, and the two facts are independent -- the switch says whether the seam may send, the ceiling says how much prior conversation it may carry, and each moves only when its own field is present. The route hands `consent.KEEP_HISTORY_BUDGET` down rather than resolving the ceiling itself, and `save_enabled` resolves that sentinel inside its own read-modify-write: a caller that read the ceiling first would hold a value read before a concurrent PUT lowered it and write that number back, raising an egress limit by losing a race. Resolving it there is necessary and not sufficient, so that read-modify-write is HELD under one process-wide lock: the handler runs `save_enabled` on a thread, two owner PUTs therefore interleave, and without the lock the enable PUT still writes back the ceiling the lowering PUT had already reduced. The lock spans the read and the write together, so the lower of two concurrent ceilings survives whichever order they took, and it covers `enabled` and `endpoint` on the same terms. A distinct object is what tells "not mentioned" from a chosen `0`, since no number can mean both. An explicit `0` still clears the ceiling, which is how prior turns are taken back without turning the seam off, and the SEL row reports the ceiling actually written. `POST /api/decisions/feedback` takes `{"turn_id": str, "verdict": "right"|"wrong"|null, "side": "jev"|"baseline"}` and appends exactly one `kind="feedback"` row through `log.append`, off the event loop. It answers `503 decisions_feedback_not_recorded` when the append did not land: the day-file ceiling is shared with the turn's own rows, so on a busy sampled day a `200` would report a verdict that was never written, and the SEL row says `denied` for it rather than `allowed`. A null verdict is a real value meaning a verdict taken back. Nothing is coerced: a missing or blank `turn_id`, an ABSENT `verdict` key, a verdict outside the pair, or a side outside the pair is `400 decisions_feedback_invalid_body` and writes nothing, because such a row makes the fold wrong rather than incomplete. Presence is tested apart from value because `null` is itself a verdict here -- the one that takes an earlier one back -- so a body that dropped the field would otherwise append a retract nobody sent. It is the line `KEEP_HISTORY_BUDGET` draws one route over: no in-band value can also mean "not asked". A verdict is never merged into the decision row it judges -- the append is constant-cost by construction, and an edit would lose both when the verdict was given and the fact that someone changed their mind.

A decision row carries no `kind`, so readers tell the two apart by `kind` being absent; that is the only test that also holds for files already written. There is NO aggregate ROUTE: the rows already carry `agree`, `p` and `tokens_saved` beside the verdict rows, so a window is a `jq` pass over `~/.kiro/crew/decisions/*.jsonl` and a served endpoint would be a second reader of the same bytes with its own failure modes -- every crash the review lanes found in this module was in that fold (a non-finite number, an unhashable verdict, a record cap taken from a shared default), and none of them could exist in a file the gateway only appends to. When a surface needs the numbers it can fold them where it renders them. The turn count is `agree + disagree`, the rows carrying a boolean `agree`, and never the row count: one sampled `skills.select` turn writes a call row plus an outcome row (section 5). The feedback route is dashboard-owner only, like the consent pair in the same module, because it writes the log an operator reads.

There is no `GET /api/decisions/strip`. The message carries the record, so a second fetch could only disagree with it.

## 7. Governance

The keystone is the OWNER's consent; `capabilities.decisions` is the FLEET's, and the two answer different questions -- may my messages be sent, versus may this machine run the seam at all. An owner on a managed laptop can consent in good faith to a paid external endpoint their fleet never approved, so the ceiling stands above the keystone rather than beside it. The row is a `SCOPE_CATALOG` capability with `capability_default=True` (data only -- no `CONTRACT_VERSION` or evaluator change, mirroring `capabilities.social_share`), so naming no row leaves the standalone user exactly where they were. `decisions/capability.py::is_decisions_denied(surface_key)` resolves it through `vet_and_audit`, and every layer's denial is honoured, because this is a per-request question rather than a process-wide startup one. The surface key is what a profile binds on, and the two kinds of caller supply it differently. The dashboard callers -- the config route and the consent PUT -- leave it at the `dashboard:ui` default, because on an HTTP request the equivalent `X-Session-Key` header is caller-controlled and honouring it would let a request carrying `slack:x` dodge a profile bound to the dashboard surface. The gate passes the turn's own session key, which is runtime state rather than caller input: it is the same value `in_bucket` hashes and the decision log records, and without it a profile bound to a non-dashboard surface would never be consulted on the one path that actually sends. A caller with no session names no surface, so the default applies and every layer above the surface still binds. It fails CLOSED: a wrong-DENY falls back to the shipped word-overlap rule that every unconsented install already runs, a wrong-PERMIT sends message excerpts to a paid third party on a fleet that forbade it. Every evaluation leaves a `governance_decision` SEL row (tool `dashboard_config_decisions`), grant and denial alike.

Two chokepoints, because either alone is a half-control. `PUT /api/decisions/consent` refuses an ENABLING write with `403 decisions_capability_denied` and writes nothing, so a denial is visible where an owner would flip the switch; a DISABLING write still succeeds, because the gate already reads the seam as off and refusing it would trap an owner with a stale `"enabled": true` keystone they cannot clear. And `gate._consented_for` -- the one keystone read every `decide` and `is_enabled` path funnels through -- reports NOT consented under a denial, so a keystone written before the pin is inert rather than carried over; without that half a fleet could pin the row and still send from every machine consented earlier. The ceiling is consulted AFTER the keystone read and inside the same off-loop hop: an install without consent costs nothing (no governance evaluation, no SEL row, no second `await`), and past that line consent is on, which is exactly when a fleet denial is a fact an auditor needs recorded. The warning is said once per process, not once per message.

`GET /api/decisions/consent` folds a denial into `permits`, so no caller reads "a decision would be sent" under a pin; the denial is not reported as a field of its own, because nothing read one and the surface a caller acts on is the 403 on an enabling write. And `GET /api/dashboard/config` reports `decisions_enabled` beside `social_share_enabled` -- read-only, dropped from the `PUT` body like the other governance-derived fields, since governance and not config owns the answer. Both are presentation: the Feature Previews card is not drawn at all unless `decisions_enabled === true` (absent fails closed), which is a card withheld rather than a disabled one, because a ceiling is not a state the user can act on. The Security panel's ceiling viewer needs no i18n key for the row: the humanising fallback renders the `decisions` leaf as "Decisions".

A policy pins it off MACHINE-WIDE with one object -- every surface, every path. A profile bound to a surface withdraws only turns on that surface, so stopping the seam everywhere means the policy, or a profile per sending surface:

```json
{"version": 1, "capabilities": {"decisions": {"enabled": false}}}
```

## 8. Settings and validation

The Decisions card reads and writes the keystone through `GET`/`PUT /api/decisions/consent`, not localStorage and not the config route, and reads the sampling share from the config GET. It prints the configured endpoint ("Sent to") beside the switch so consent is to an address, and a body-weight notice when consent stands for a different address than the config now names. It carries no `configKey`, because it writes no config path; `test_settingref_schema_fixture.py` pins that `decisions.enabled` is absent from the schema and the card. The backend editable-field validation accepts the bounded integer bucket only; sensitive provider credentials remain masked in GET output. The card prints the sampling share in both switch states, phrased as a fact about the on state, because the shipped default of 100 means every session and consent must see that before the switch is flipped. A backend exposing only legacy `preview` is unsupported, not an enabled gateway; that state fades the card, including the egress note, and names Settings › Releases as the fix. A literal `configKey` is required so the settings extractor connects the control to the schema.

## 8. The decision strip's record and feedback

The transcript's receipts for a turn's decisions travel as `decisions_strip` on the assistant row that ends it: a LIST of records, told apart by each record's own `point` (`readDecisionRecords` / `readDecisionRecord`). A bare object is read as a list of one, so a row written before the second point existed still renders. The `skills.select` record is below; the `model.route` one is section 11. The receipt for one `skills.select` decision is the shape this section pins. `meta` is the carrier on both doors -- the live websocket frame and a row reloaded from history (section 6) -- and the reader also accepts a top-level `decisions_strip`, so a producer that stamps it there is read too. Absent means the turn was not decided by this seam, and the strip draws nothing.

This block IS the contract between the gateway that stamps the record and `website/src/pages/chat/decisionRecord.ts`, which reads it. The reader's fail-safe is to draw nothing, which is byte-identical to a healthy release that stamps no record at all -- so a field renamed on one side would make the strip silently vanish rather than fail. `website/src/test/decisionStripContract.test.ts` parses the fenced record below out of this file and asserts the reader accepts it, so a change here without the matching reader change is a red test on the frontend side.

```json
{
  "turn_id": "turn-4f2a9c",
  "point": "skills.select",
  "baseline": ["brazil", "crux-code-reviews"],
  "jev": ["brazil"],
  "p": 0.81,
  "tokens_saved": 3240,
  "candidates": 42,
  "message_chars": 96,
  "history_chars": 1840,
  "latency_ms": 197,
  "dropped": [{ "key": "tst", "p": 0.12 }],
  "error": null
}
```

`baseline` is what the word-overlap rule would have loaded and `jev` is the validated choice, both as skill keys. Agreement is NOT a field: the strip derives it from the two lists, because a flag that disagreed with the names beside it could only put a check mark over a real divergence, so promising one would invite a producer to stamp a value whose only use is to be wrong. A timestamp is not a field either -- the assistant row the record rides on carries its own. `p` is the probability for the chosen option, a finite number in 0..1 or `null`; anything else prints no number. `tokens_saved`, `candidates`, `history_chars` and `latency_ms` are whole counts, and a negative or unparsable one reads as 0. `message_chars` and `history_chars` are the two halves of the question's egress, each measured on the string that was actually sent -- `message_chars` after the excerpt cap, so it is what left and not what the owner typed.

`message_chars` is the ONE count whose absence is not 0. A turn that reached the selector had text, so zero characters is not a credible measurement of it, and a record that does not state the field is a record whose producer did not measure the excerpt -- not one reporting that nothing left. The reader therefore reads an absent or unparsable `message_chars` as "not stated" and the strip DRAWS NO egress row at all, the same way it draws no latency row without a `latency_ms`. `history_chars` keeps the floor-to-zero rule in full, because 0 there is a real observation: it is how "no history was reachable" is distinguished from a field that was never sent (section 4). `latency_ms` is one of the six core log fields rather than a field of the point's own, and it rides to the strip because the record IS the log row. The strip prints it as `Jev latency` on the expanded card and inside the collapsed parenthetical beside the score. `dropped` names answers the gate refused with the score each arrived with. `error` is the failure category when the decision failed, `null` otherwise. Nothing here carries message text, candidate descriptions or a provider key -- the same bound section 5 puts on the log; `message_chars` is a length, and a length is not the text.

A count that is the same on every turn is not on the record. There is no batch count -- the menu is asked in ONE question (section 4) -- and no history-clip count: clipping is a fact about the transcript READ, which the call row carries, and a strip row for it printed 0 on every turn at the shipped history budget of 0 while saying nothing a reader could act on.

A key the reader does not know is IGNORED, not refused: a producer may stamp extra fields (a later addition, or an internal one) and the strip renders from the keys above regardless. So the contract is a floor on what must be present, not a ceiling on what may be sent. A `point` the reader does not know is the one exception and draws NOTHING rather than being read through the shape above -- rendering an unknown record through a known reader is how a row comes to print a claim nobody made.

The strip is drawn whenever the row carries this record, and the consent switch is not consulted. A stamped record is history that already happened and already sits on the machine, so drawing it sends nothing; consent governs whether a FUTURE turn may ask Jev. Gating the receipt on the current switch would mean an owner who tried the preview and turned it off loses the record of which past replies were Jev-picked.

The verdict control sends `POST /api/decisions/feedback` (section 6) as `{"turn_id": str, "side": "jev" | "baseline", "verdict": "right" | "wrong" | null}`. `side` says which of the two lists is being rated, so the word-overlap rule can be called the better pick. `verdict` is nullable because pressing a lit thumb again retracts an earlier answer, and a retraction is a recorded event rather than an absent one.

## 9. The `tool.risk` annotation on the tool card

`tool.risk` asks one question about one tool call and puts the answer on that call's card. It decides NOTHING. The permission decision is taken without consulting it and is not altered by it: a call the policy allows still runs with `risky` on it, and a call the policy refuses is still refused with `safe` on it. Two things it does NOT claim, because neither is true. It is not free of TIMING -- the caller awaits it in the `tool_call` branch, which the harness sends BEFORE it asks for permission, so a sampled call's approval is answered up to the wait budget later than it otherwise would be; the cost is bounded, sampled, and paid only where the seam is on. And a badge is not a verdict on whether the call RAN: a host gate, a `PreToolUse` hook or a batch cascade can refuse a call that already carries one, which is the same asymmetry the `policy` field's own paragraph below describes. That property is the reason the point may exist at all -- an oracle answer is an observation, and an observation that could gate a tool would be a gate nobody reviewed -- and it is pinned as a mutation rather than asserted as a claim (`test_decisions_tool_risk_card.py::TestPermissionBehaviourIsUnchanged` runs one scripted turn twice, with the point answering and with it silent, and holds the `approve_tool`/`reject_tool` calls and the SEL audit rows equal).

The hook is `chat_runner._tool_risk_meta`, called from the `tool_call` event branch -- the one funnel that appends the tool card row -- and that branch contains no approval code at all. It is deliberately NOT placed in the permission branch: placing an `await` beside `approve_tool` would make "nothing about approval changed" a claim about the ordering of two adjacent statements rather than a claim about two disjoint regions of the file. The await sits AFTER the live `tool_call` broadcast and BEFORE `slot.append`, so the pill an open tab draws is not delayed and the record reaches both doors -- the `chat_message` frame `append` broadcasts from inside the call, and the persisted transcript line -- from one write.

It runs only where the owner consented to TOOL-ARGUMENT egress, and that is a second consent rather than a wider reading of the first. `skills.select` sends a message excerpt and candidate descriptions; this point adds the tool's name and its arguments, so the keystone records the two separately: `tool_args` (`consent.STATE_KEY_TOOL_ARGS`, read through `consent.consented_tool_args`), where only a literal `true` consents and ABSENT reads as not consented. `gate._tool_args_scoped` refuses any point in `POINTS_NEEDING_TOOL_ARGS` without it, checked inside `_consented_for` -- the documented chokepoint every `decide` and `is_enabled` path funnels its one keystone read through -- so the scope costs no second read and cannot be enforced in the preflight alone. The consequence is the point of it: an install that consented before this scope existed is INERT for `tool.risk` rather than retroactively signed up for it, which is the argument `history_budget_chars` already settled one field over. The refusal is warned once per point, because an owner whose feature does nothing must be able to tell that from a broken build. `PUT /api/decisions/consent` records it on the same terms as the history ceiling: written on enable, cleared on disable so a re-enable cannot inherit a scope nobody re-reviewed, an OMITTED field PRESERVING the recorded value through `consent.KEEP_TOOL_ARGS` resolved inside the writer's own lock, and a non-boolean refused with `400` rather than coerced -- `"true"` and `1` are not deliberate yeses about a new egress category. The GET reports it so the card draws the recorded state rather than inferring it. There is no new route.

It runs only for a session that AUTO-APPROVES its tool calls (`_session_auto_approves`, which is `_slot_is_trusted(slot) or state.is_yolo_active()` -- the same two helpers the permission branch decides by, so the annotation cannot claim a mode the approval path is not in). A session that prompts puts the call in front of the person, who is the annotation; a badge beside a control they are already operating is noise. A trusting session describes nothing to anybody, which is where a badge is the only signal there is.

The state is the tool name, its arguments and an excerpt of the message that led to the call, each bounded (`MAX_TOOL_CHARS` 120, `MAX_ARGUMENT_CHARS` 2000, `MAX_MESSAGE_CHARS` 2000) and each passed through the canonical redactors FIRST, clipped after -- clipping first can halve a secret into a fragment neither redactor matches. Redaction rather than the gate's refusal is the one place this point differs from `skills.select`, and it is a deliberate difference: the gate REFUSES a state carrying a credential, which is right for a message excerpt, where a secret is a finding; a credential in a tool argument is ORDINARY (an `aws` command, a curl header), so refusing on it would mean the seam never annotates the calls most worth annotating. The placeholder is what the gate then scans, so nothing unredacted is cleared for the wire -- pinned in both directions, with the redacted state passing `gate.scrub_reason` and the raw one refused as `scrubbed:credential`. A redactor that itself fails drops the field rather than sending it. The message is OMITTED when empty, so the wire shape says something by its absence.

One question, one `Choice`, three options: `safe`, `caution`, `risky`, in that severity order, with a one-sentence rubric per tier in the prompt (`safe` only reads or reports; `caution` changes something inside the workspace that is easy to put back; `risky` destroys data, touches credentials, sends local data out over the network, or acts outside the workspace). An answer outside those three is unusable and annotates nothing.

Rows: the gate writes the CALL row (`turn_id`, `tool`, `arg_chars`, `policy`, `call_index`), and the point writes one OUTCOME row for every ANSWERED call -- `safe` included -- carrying `turn_id`, `tool`, `tier`, `p`, `policy` and `flagged`. `policy` is the grant that answers the call (`yolo`, `trust` or `trust_scope`, the caller's own descriptive spelling from `_auto_approve_reason`), NOT a per-call verdict, and it cannot be one: the harness sends the `tool_call` notification BEFORE it asks for permission, so the card this record rides exists before any verdict about it does. A later refusal -- a host gate, a `PreToolUse` hook, a batch cascade -- is recorded by the SEL tool-invocation audit, which is where a per-call outcome already lives; guessing at it here would give the log two descriptions of one call and make the weaker one look authoritative.

`safe` is recorded and NOT badged, and that asymmetry is the design: the log is the observation, so a log that only kept the alarming answers could not say how often the seam is wrong, while a badge on every card of a sampled session would cost the flag its meaning. So the point returns the row it wrote only for `caution` and `risky`, and returns nothing at all for `safe`, for a refusal, for a timeout, and for a row `append` reported it did not write -- a badge whose durable row was refused names a `turn_id` no verdict could be filed against, the rule section 5 states for the strip. There is no publish hook and no `decisions.outcomes` entry: that registry holds one outcome per SESSION and `consume` pops it, which is right for a strip describing one turn and wrong for an annotation describing one of several calls inside one turn. Producer and consumer here are the same line of code, so the record is handed straight to the `slot.append` that carries it.

Two budgets. The wait is `timeout_secs` plus `WAIT_MARGIN_SECS`, clamped into `MIN_WAIT_SECS` .. `MAX_WAIT_SECS` -- the same shape and the same three values `skills.select` waits by, held equal by test so a point cannot invent its own ceiling. And at most `MAX_CALLS_PER_TURN` (20) oracle calls per turn, counted by the caller's own per-turn tool counter: the call that CROSSES the cap writes one row with error `turn-cap` carrying `calls`, so "this turn stopped being annotated" is visible instead of indistinguishable from an unsampled one, and the calls after it write nothing. That cap row is the one row here not produced by a `decide` call, so it does not inherit the gate's refusals and asks for them itself -- an unsampled session writes nothing at all, cap included.

The record on the row is `meta.decisions_tool_risk`, on the TOOL message rather than the assistant reply, because the annotation is about one call:

```json
{
  "turn_id": "tr-9d41c7",
  "point": "tool.risk",
  "tool": "bash",
  "tier": "risky",
  "p": 0.88,
  "policy": "trust",
  "flagged": true,
  "latency_ms": 420,
  "error": null
}
```

This block IS the contract between the gateway that stamps the record and `website/src/pages/chat/toolRiskRecord.ts`, which reads it, on the same terms section 8 states for the strip: the reader's fail-safe is to draw nothing, which is byte-identical to a healthy release that stamps no record, so a rename on either side would hide the badge with no exception and no red test. `website/src/test/ToolRiskBadgeContract.test.ts` parses the fixture out of this section and asserts the reader accepts it field for field.

`safe` is not a readable tier on the frontend either: the reader refuses it, so "a record exists" and "this call was flagged" are one fact, and a producer that started stamping `safe` records could not quietly badge every card. An unknown tier, a missing `turn_id` and a probability outside 0..1 each draw nothing rather than a best-effort reading -- the badge's whole claim is that a flag means something, and a `turn_id` the thumbs could not name would be a control that lies about being one. A key the reader does not know is IGNORED, so the whole row can be stamped as the log wrote it and a later field is additive.

The badge renders under the tool pill: the tier word, the score, and one thumbs pair. Its tooltip says in words that the call ran anyway and that flagging it changed nothing, because a coloured word on a tool card otherwise reads as "this was blocked" -- and for the same reason `risky` is drawn in the WARNING colour, never the danger colour this transcript uses for a call that was actually refused. The thumbs are `DecisionVerdictThumbs`, shared with the strip, posting `POST /api/decisions/feedback` (section 6) as `{"turn_id": str, "side": "jev", "verdict": "right" | "wrong" | null}`. `side` is always `jev`: there is no second arm to rate -- the shipped permission policy is not an answer to this question, it is what happened regardless of it. No new route and no new config knob: the point is governed by the same consent keystone, the same `decisions.bucket` sample and the same `capabilities.decisions` ceiling as everything else in this package.

## 10. Mid-turn handling (`message.steer`)

A message typed while a turn is RUNNING takes one of two shipped paths, and the sender picks: the composer's split send button defaults to STEER (`chat_delivery.steer_into_running_turn`, injecting into the live turn) and offers QUEUE (`chat_delivery.queue_for_next_turn`, holding it for the next one). `message.steer` asks Jev which one this message wants. Both paths are unchanged; the point only decides which is taken, so every refusal -- the seam off, the session unsampled, a timeout, an answer outside the two options -- is the steer path the composer has always defaulted to, and there is no third outcome.

The point runs only when the sender SELECTED it. The split button carries a third mode, `Auto (Jev)`, drawn only while `GET /api/dashboard/config` reports `decisions_enabled === true` AND `GET /api/decisions/consent` reports `permits` (`website/src/pages/chat/useJevAutoSend.ts`, fail-closed on `=== true` for both) AND a turn is actually RUNNING on the slot. The last conjunct is not the same as the composer being busy: `selectComposerBusy` is also true for a slot whose background sub-agents are still working, and there is no turn to decide ABOUT in that state -- the send starts a fresh turn and this point never runs -- so offering the mode there would promise a decision nothing makes. Choosing it sends `steer: "auto"` instead of `steer: true`. A manual Steer or Queue never reaches the point -- that pick IS the answer to this question -- and `chat_handlers.steer_is_auto` accepts only the exact string, so the boolean every existing client sends stays a manual steer. There is no settings page and no config field for the mode: it is the per-slot composer preference `mc-busy-send-mode` already holds, and a stored `auto` resolves back to Steer while the seam is unavailable, so a withdrawn consent cannot leave a mode on screen whose send would not be decided.

The other preconditions are the call site's, and they are the branch's own: `api_chat`'s busy branch, which runs only when a turn is on the slot (`slot.running or slot._in_stage_execution`) and only for a send that is NOT app-authenticated. The turn is also FENCED across the decision: `slot.task` is captured before the await and compared after, and a change discards the answer and the receipt so the send takes the branch's own default. A decision is a provider round-trip, so the turn it describes can end inside it -- and "interrupt what it is doing" is not an answer about a turn that finished, nor about the successor that replaced it. The row stays in the log; only the receipt is dropped, because a receipt is what would misattribute it. An app token, an integration or a cron is never decided -- each already falls through to the fail-closed queue, and none has an owner watching the reply. The decision is resolved ABOVE the steer branch rather than inside it, so that branch keeps its exact shape and the only things `auto` changes about it are one conjunct on its condition and the receipt it stamps.

The state carries the new message (truncated to 2000 chars, the same bound `skills.select` applies) and, inside the consented ceiling, the RUNNING turn: its own request (at most 1000 chars) and the newest assistant text and tool activity (at most 1500 chars, `assistant`/`chunk`/`tool` rows only, walked newest-first back to that request). Those two halves are conversation the sender did not type into this send, so they are spent out of the SAME `gate.history_budget_chars` ceiling prior turns are -- the smaller of `config.json`'s ask and what the keystone recorded the owner reviewing -- which means the shipped default of 0 sends the new message alone and the decision is made on it. The request is served before the activity because the activity only makes sense against it. `thinking` rows are never sent. Both halves are passed through `redact_credentials` and `redact_exfiltration_urls` before the gate sees them, and that is a CLEAN rather than a refusal on purpose: this text is whatever the agent printed, so refusing on it would turn "the reply quoted an env file" into "the seam stopped deciding", while the gate's own scan still refuses a spelling the clean missed. There is no `history` key: prior turns have ended, the turn in progress is what the question is about, and one ceiling spent on both would make the context worse the further back it reached.

The point emits, per decided send: one CALL row from the gate (`turn_id`, `turn_chars`) and, only where a usable answer arrived, one OUTCOME row carrying `turn_id`, `choice`, `baseline` (always `steer`, the arm the product would have taken) and `p`. A refused decision writes no outcome row and stamps no receipt, so a receipt exists only for a decision that was actually made.

The receipt rides the USER row, not the assistant one, and `decisions.outcomes` is deliberately not used for it: that registry holds one outcome per session for whatever finalizes the next ASSISTANT message and `consume` POPS, so claiming it here would take a `skills.select` turn's strip and attach it to the wrong reply. `message_steer.record_outcome` therefore RETURNS the row it wrote and the handler passes it to whichever delivery path runs, as `decision_strip=`: `steer_into_running_turn` stamps it into the `meta` of the row it appends, and `queue_for_next_turn` stamps it onto the queue ENTRY's meta, which the drain unions onto the row it writes -- the same mechanism `sendId` and the attachment lists already ride. The field is `meta.decisions_strip`, the same one section 8 describes, read by the same reader. A send that was not decided carries no such key, which is what keeps every other row byte-identical. The key is RESERVED to the gateway: `api_chat` drops it from request-supplied `meta` (`RESERVED_ROW_META_KEYS`) at the point that value enters, because `meta` rides verbatim onto the persisted row and onto the queue entry (`_redact_meta` redacts string values; it is not an allowlist), so a caller -- an app token included -- could otherwise stamp a decision nobody made and have the strip's verdict control file feedback against its turn id.

One case has the two disagreeing: `auto` answered `steer` and the steer was UNAVAILABLE (no live client, an unsupported backend, an RPC failure), so the send falls through to the queue carrying a record that says `steer`. The record describes the DECISION and the row's own `steerState` describes how the delivery ended; withholding it there would lose the only record that a decision was made.

`website/src/pages/chat/SteerDecisionLine.tsx` renders it as ONE line on the user row -- what Jev CHOSE, its probability and the latency, with the same `jev` thumbs pair `DecisionStrip` uses (shared, not copied). The line is phrased as the CHOICE rather than the delivery, because the two can differ: a chosen steer whose live client is gone falls through to the queue, and a line reading "steered the running turn" over a queued message would report the opposite of what happened. The delivery is what the row's own steer badge and queue card describe. The probability carries its own word rather than standing as a bare number, since the hover title is unreachable on touch and silent to a screen reader, and the thumbs' visible label names the CHOICE rather than repeating Jev's name, which the line already opens with. One line rather than a disclosure card because everything the decision produced fits on it: there is no second arm to compare and no menu to expand. Side `jev` only: the record names one decision by one party, and rating the `baseline` would rate a path this send did not take. The record on the row is the only condition, the same rule section 8 states -- a stamped record is history that already sits on the machine, so drawing it sends nothing.

The reader is `readSteerRecord` in `website/src/pages/chat/decisionRecord.ts`, and this block is its contract:

```json
{
  "turn_id": "turn-91c3ab",
  "point": "message.steer",
  "choice": "queue",
  "baseline": "steer",
  "p": 0.83,
  "latency_ms": 190
}
```

`choice` IS the claim and is held against the two shipped paths: unlike a skill key or a difficulty tier, a third value would name a code path that does not exist, so the line draws nothing rather than printing it. An absent or unknown `point` is not read as this record either -- an absent one is the older producer's shape and belongs to `readDecisionStrip`. `baseline` is on the record because the record IS the log row and the day-file fold reads it, and the READER ignores it: it is `steer` on every row -- the one arm a refusal keeps -- so a line printing it would print one word forever, which this document's own rule about a count that never changes excludes. There is no `error` field, and its absence is the producer's contract: a failed decision takes the steer path and stamps nothing. `latency_ms` floors to 0, which prints no latency, and a `p` outside 0..1 prints no score.

Tests: the two arms, the fallback on every refusal, the transcript walk (its stop at the running turn's request, the excluded `thinking` rows, the shared budget's split, the bounded read, the redaction of both halves) and the row's shape (`test_decisions_message_steer.py`); which path a `steer: "auto"` send takes, that a MANUAL steer or queue is never decided, that an app send is never decided, that a refused row stamps no receipt, that a request cannot supply a receipt through either door, and that a turn ending inside the decision discards the answer (`test_decisions_message_steer_apply.py`); the reader, the line, the user row's absent-field path and the third mode's availability (`website/src/test/SteerDecisionLine.test.tsx`), with the fenced record above held against the reader in `website/src/test/decisionStripContract.test.ts`.
## 11. Model routing (`model.route`)

An enabled, sampled session whose owner selected `Auto (Jev)` in the chat model picker asks Jev to put each chat turn in one of three difficulty tiers and runs that turn on the model `decisions.model_route` maps the tier to. A refusal leaves the session on the model it was already on, which is exactly what every unconsented install does.

Only the owner arms it, and the arming is not a config key. The picker draws an `Auto (Jev)` entry only while `GET /api/dashboard/config` reports `decisions_enabled === true` (the fleet's `capabilities.decisions` answer, section 7) AND `GET /api/decisions/consent` reports `enabled === true` (the owner's keystone); both are read as an exact `true`, and either alone withholds the row (`website/src/lib/jevRoute.ts`, drawn by `ChatPage` and each split `ChatPane`). Neither read is an enforcement point -- the gate re-checks both, so a request carrying the sentinel against an unconsented keystone routes nothing -- so the two reads are presentation.

Selecting the entry sends `POST /api/chat/slots/{slot}/model` with the sentinel `auto:jev` (`chat_handlers.JEV_ROUTE_MODEL`). The sentinel is resolved at the TOP of that handler and nowhere else: every reader below it -- the model guard, the live `session/set_model`, the reset path, the session allocation, the composer chip -- takes the plain `auto` it produces, and the choice survives only as the slot's `jev_route` flag. It is deliberately NOT stored in `slot.model`: that field is a provider model id, it reaches `session/set_model` and the session allocation, and a value no provider advertises would have to be filtered at each of those readers -- one filter per reader, and a real breakage the first time one is missed. The prefix is `auto` so a client too old to know the entry reads it as the Auto it behaves like, and the colon keeps it outside the model namespace, since no advertised id carries one. Matching is exact on a stripped string: a near-miss spelling is not this entry and falls through to the ordinary model path, where the guard refuses it.

`jev_route` is committed on each SUCCESS path of the handler and nowhere else: once in the same-value shortcut -- which is the commonest case for this flag, since an unpinned slot picking `Auto (Jev)` resolves to the `auto` it already holds -- and once inside the transaction, where `_rollback_pick` restores `prior_jev_route` with the model. Nothing is written above the busy check, so the `409 turn_in_flight` refusal cannot change what the next turn runs on. It is written on EVERY pick, not only the routed one: picking a concrete model is the owner answering the very question this point asks, so it clears the flag. The bulk switcher clears it too, on both its switched and its unchanged paths, and broadcasts when the only change was that. It is projected on every slot as `jev_route`, so an absent key and "pinned by hand" are not the same reading, and it is inherited by a fork (in-process, gateway-authored).

The flag is **in-memory only and deliberately not persisted**. It records an OWNER's pick that spends money -- a routed turn can run on a dearer model -- and transcript metadata is editable by the agent's own file tools, so a value read back from there would let a prompt-injected agent write `"jev_route": true`, wait for a restart, and be granted routing the owner never selected. A strict `is True` read does not close that: a genuine JSON `true` deserializes to `True`. This is the same rule, for the same reason, as the crew log refusing to promote a restored `_created_by` to gateway-authored lineage. The cost is that a gateway restart leaves the slot on its persisted model -- which is the documented refusal, not a new failure mode -- and the owner re-picks `Auto (Jev)` to route again. `test_the_flag_never_touches_agent_writable_transcript_metadata` asserts the absence against the source of every module that handles that file, because a re-added key would reopen the hole silently.

The point runs for a NORMAL dashboard chat turn and nothing else. `chat_runner._run_chat` calls it after the model-fallback restore probe and before the prompt is sent, gated on `slot.jev_route` AND the turn's structural actor being `user` (`_crew_log_actor`) AND the turn being neither a synthetic payload, a harness slash command, nor a recovery continuation. Cron deliveries, sub-agent turns, crew-relayed turns, app injections and autonudge wakes are therefore excluded: each already resolves its model through its own tier (`agent.role_models`, a crew binding, a cron's own slot), and none has an owner watching what a dearer model costs.

The state is the message excerpt (`MAX_MESSAGE_CHARS` 2000, the same bound `skills.select` applies, because it is the same text answering a question about the same turn) plus `history` under the same shared budget -- `gate.history_budget_chars()`, the smaller of `decisions.history_budget_chars` and the keystone ceiling, over the same `MAX_HISTORY_MESSAGES` (20) read bound and the same `user`/`assistant` roles. Both points read prior turns through one implementation (`decisions/points/__init__.py`: `history_budget`, `prior_turns`, `build_history`), because a second copy of that walk would be a second place for the consented budget to be spent differently. `history` is omitted when there is none, so at the shipped default of 0 the request carries the message alone. The budget is read off the event loop and BEFORE the transcript, so at 0 the transcript source is never called.

The question is ONE `Choice` over `("simple", "medium", "complex")`, each carried in the prompt with a one-sentence description of the WORK. No description names a model or a price: the tier-to-model mapping is the owner's, and naming a model would ask the oracle to price the turn rather than to judge it. The tier domain is closed, so a provider inventing a fourth tier is refused by the gate as an invalid result; the point checks the value against the domain again, because it is about to index a map the owner writes where a near-miss spelling would read as an absent key.

An UNPINNED tier is answered, recorded and shown, and applies nothing. That is the shipped state for all three tiers, and it is deliberately not a refusal: the answer is what tells an owner which tier their turns land in, which is how they decide what to pin. The outcome row and the strip carry `model_chosen: ""` (`model_route.UNPINNED`), the strip reads `complex -> (unpinned)`, and no `set_model` is attempted. `model_route.is_unpinned(tier, mapping)` is what tells that apart from a pin the account cannot run: both keep the model, only the second is a finding, and conflating them would hide the second.

`resolve_model(tier, mapping, advertised)` answers the model id or `""` (keep the current model). `""` covers an unpinned tier, a tier absent from the map, and a pin the provider does not advertise. The advertised list is the one the picker is built from (`llm_helpers.provider_advertised_ids`), so "the owner could have picked this by hand" and "the tier may route to it" are one test. An EMPTY advertised list is "not known", not "nothing is runnable", and reads as permitted -- the list comes from a live provider read that can be cold, and refusing on a cold read would make the feature silently inert on the first turn after a restart. Comparison goes through the canonical registry first and falls back to the frontend's own lossless fold (trim, lowercase, `.`->`-`) for an id the registry does not list; the registry's dotted and dashed entries stay DISTINCT (`claude-opus-4.8` is not `claude-opus-4-8`: two entries, two context windows), so routing never silently lands on a smaller window. Those two are named as the registry PAIR under test, which is the one thing a placeholder cannot stand in for -- a fake id has no registry entry and would exercise the string fold instead.

The switch itself goes through `llm_helpers.resolve_substitute_set_model(client)`, under the SAME two locks the fallback swap and the restore probe hold (the session-scoped switch lock, then the slot's pick lock, in that order), because it is the same kind of model transaction: without them a pick arriving through another alias of this session could land inside the `set_model` await and then be silently overwritten. The `decide` call is deliberately OUTSIDE those locks -- it is a network round trip, and holding a session-scoped lock across it would stall every sibling alias for the provider budget. `served_model` is re-read after the switch so the composer chip names the model the turn runs on.

A routed turn is NOT reverted afterwards: the point runs again next turn and answers again. So `baseline_model` is the model the turn would have used, i.e. whatever the session was on as the turn started -- on an already-routed session that is the previous turn's tier rather than the pin. That is the honest reading of the field, and it is what a refusal keeps.

The outcome row is written and published only once the switch has landed, so the strip and the log describe the model the turn actually ran on; the append is pushed to a thread, since the caller is the event loop. The strip's record is:

```json
{
  "turn_id": "turn-7b1c40",
  "point": "model.route",
  "tier": "complex",
  "model_chosen": "model-c",
  "baseline_model": "model-b",
  "p": 0.91,
  "latency_ms": 180,
  "history_chars": 0,
  "truncated": 0,
  "applied": true,
  "model_used": "model-c",
  "error": null
}
```

`tier` is REQUIRED and non-empty: it IS the answer, and a record that cannot name it has no claim left to print, so the reader draws nothing. It is deliberately not held against a fixed list of three -- the tiers are the backend's own question domain, and a reader that refused a fourth would hide a shipped tier instead of showing it. `model_chosen` MAY be `""`, which is the shipped state rather than a broken producer: the answered tier is unpinned and the turn kept its session's model, which the row prints as `(unpinned)`. The id above is illustrative; the one worked example of an owner's real pins is in `src/kiro_crew/docs/decisions.md`. `baseline_model` may be `""`, which is a real value and the common one: it is what the gateway records for a session running the backend's own default, and the row prints a named default rather than an empty gap. `p` is a finite number in 0..1 or `null`. `latency_ms`, `history_chars` and `truncated` are whole counts, and a negative or unparsable one reads as 0. `applied` and `model_used` appear on a row that ATTEMPTED a switch and say whether it took: a returning `set_model` is not proof, because a backend that judges the model value can exhaust its candidate ladder and stay on the backend default without raising. So the model the session reports afterwards is read and recorded as `model_used`, and `applied` is `false` when the turn neither reached the chosen id nor moved off `baseline_model` at all -- a ladder's fallback spelling is a move, and a session already on the chosen model counts as applied. The reader treats only an exact `false` as a failed switch, so an unpinned row (which attempts nothing and carries neither field) and a row written before the fields existed both read as applied. The row is what an owner reads when deciding what to pin, and it is never rewritten, so it states what happened rather than what was asked for. Nothing here carries message text or a provider key -- the same bound section 5 puts on the log.

The row renders as one collapsed line: the point, the tier, the model it routed to, the score, the elapsed time, and the model the turn would otherwise have used. The last one is what makes the line actionable -- "complex" alone is not a claim a reader can disagree with, while "complex, so opus-5 instead of opus-4.8" is one about this reply. Expanding adds the tier, both models, the conversation the question carried and what was clipped, plus the failure category when there is one. There is ONE thumbs pair, side `jev`, through the existing `POST /api/decisions/feedback` route (section 6) -- no new route and no new side: the alternative to a routed model is not another judgement but the absence of one, so a `baseline` pair would ask the reader to rate "whatever the session was on", which is not a decision anybody made about this turn.

Routing a turn to a dearer model spends more. That is why the point is reachable only through the picker entry: the owner opted in by selecting it, a manual model choice is never overridden, and clearing the entry is one pick.

## 12. Compaction scoring (`compaction.keep`)

`compaction.keep` asks, at every AUTOMATIC compaction, which of that session's tool calls would have been worth keeping. It is a SHADOW point: there is no apply path, `score_compaction` returns a record for tests and for the card and nothing in the product branches on it, and the compaction runs byte-identically whatever the answer is. That is the reason the point may exist at all -- the alternative is a live keep-list, and whether that trade is worth making is a question about data this point produces.

Why shadow and not live. Nothing in Kiro Crew can replace a harness's message list: `LLMProvider` (`providers/base.py`) offers `start / shutdown / stream / stream_command / compact / wait_for_compaction / cancel / steer` and no set-messages call, and `/compact` summarizes inside the harness process. The one place a keep-list COULD land is the transcript Crew re-injects after a recycle (`context.build_session_replay`), and that replay admits `user` / `assistant` / `inject` rows only (`context.RECALL_ROLES`) -- so every tool call and every tool result is already dropped today, and a live keep-list could only DISPLACE text inside the same 80 000-character budget.

The hook is `session_compaction.CompactionCoordinator._shadow_score_compaction`, called at the top of `_compact_session`. That method is the ONE funnel both AUTOMATIC entry points reach -- the per-turn threshold trigger (`check_context_usage` -> `_trigger_compaction`, a background task) and the awaited between-turn one (`compact_if_needed`) -- and it is reached BEFORE the Claude arm, before `_recycle_unmanaged` and before `_compact_in_place`, so every arm Crew itself takes is covered and the transcript observed is the one that stood when the compaction was decided.

What that population IS, and is not, stated exactly -- because "every backend" would be false. The hook sits inside the funnel, so it covers exactly the compactions Crew DISPATCHES; a harness that compacts on its own initiative is declined by `_compaction_gate_decision` before the funnel and is therefore never scored:

| Compaction shape | Scored? | Why |
|---|---|---|
| Threshold auto-compaction Crew dispatches — the in-place `/compact` on kiro-cli, codex, opencode | **yes** | `check_context_usage` → `_trigger_compaction` → `_compact_session` |
| The awaited between-turn check | **yes** | `compact_if_needed` → `_compact_session`, the same funnel |
| A recycle, because the in-place `/compact` failed or the backend has none (deepseek) | **yes** | reached from inside `_compact_session` |
| **Claude-Code-managed sessions** | no | `_compaction_gate_decision` returns `cc_managed` and declines before `_compact_session`; Claude compacts natively in-prompt, and Crew never dispatches it |
| **A harness that summarizes on its own initiative** (KAS, `ACP_BACKENDS_HARNESS_MANAGED_COMPACTION`) | no | the same gate returns `compact_unsupported`; KAS compacts and reports it, so there is no Crew-side dispatch to hang the measurement on |
| A backend in no compaction set at all | no | declined on the same rung, with the warning that names the missing classification |
| Manual `/compact` | no | dispatched as an ordinary turn through `provider.stream_command`; the person typed the command |
| Any other gate decline — below threshold, unconfirmed reading, already compacting, cooldown | no | `_compact_session` is never scheduled |

The two declines in bold are not gaps to close from here: there is no Crew-side dispatch to hang a measurement on, because Crew is not the one compacting. KAS reports its own summarization through `summarization_completed` and Claude compacts in-prompt, so measuring either would mean a different hook on a different event -- and the live design (#12516) targets the recycle path, which is exactly the population this hook already covers.

MANUAL `/compact` is excluded by CONSTRUCTION, not by a flag: the dashboard dispatches that command as an ordinary turn through `provider.stream_command("/compact")` and never calls `_compact_session`, which `test_decisions_compaction_hook.py::TestManualCompactIsExcluded` pins by asserting no caller of that method exists outside the session layer.

It cannot delay or alter the compaction, and that is structural rather than asserted. The task is created and NEVER awaited, tracked on `owner._background_tasks` so it cannot be collected mid-await; the compaction proceeds on its own coroutine; the only thing the deadline decides is whether the task gives up. `test_decisions_compaction_hook.py` runs one scripted compaction with a scoring that hangs for an hour and holds the compaction's own outcome and arm equal to a run with the hook stubbed out.

It runs only where the owner consented to WHOLE-TRANSCRIPT egress, and that is a THIRD consent rather than a wider reading of either of the first two. `tool_args` was reviewed as the arguments of the one call about to run; this sends the conversation and every tool input the session has accumulated, in a request one to two orders of magnitude larger. So the keystone records `compaction` (`consent.STATE_KEY_COMPACTION`, read through `consent.consented_compaction`), where only a literal `true` consents and ABSENT reads as not consented. `gate._scope_consented` refuses any point in `POINTS_NEEDING_COMPACTION` without it, from inside `_consented_for` -- the same chokepoint, so the scope costs no second keystone read. `_scope_consented` replaces the earlier `_tool_args_scoped` and drives BOTH scopes off one table (`gate._POINT_SCOPES`), because a predicate per scope is a second place to forget one. `PUT /api/decisions/consent` records it on exactly the terms `tool_args` is recorded on: written on enable, cleared on disable, an OMITTED field PRESERVING the recorded value through `consent.KEEP_COMPACTION` resolved inside the writer's own lock, and a non-boolean refused with `400`. The GET reports it. There is no new route.

A write that moves only a SCOPE omits `enabled` entirely, and that is a property of the route rather than a convention its callers follow. A body carrying the switch can only carry what its sender last READ, so a view read before a revoke hands `true` back and re-grants egress the owner just withdrew -- and no client-side guard can make such a body safe, because the staleness is in the value. So an omitted `enabled` on a body that names at least one scope is a scope-only write: the route hands `consent.KEEP_ENABLED` down, and `save_enabled` resolves the switch AND the endpoint from the keystone inside the same lock the other three sentinels resolve in, writing both back unchanged. Such a write can neither grant nor revoke consent, and cannot rebind the endpoint -- the recorded binding is the one the owner reviewed. Against a REVOKED keystone it leaves the record revoked and stores no scope, which is the same rule that clears the scopes on a disabling write: a scope is only meaningful while the seam is on. A body naming neither the switch nor a scope is a `400`, so an empty or misspelled body is refused rather than silently rewriting the record as itself, and a non-boolean `enabled` is still a `400` -- accepting the omission did not widen what counts as consent. The fleet ceiling still gates only the ENABLING direction, because a scope-only write cannot turn the seam on and so acquires no authority a withdrawn ceiling would have to refuse. Both scope switches on the card write this shape; `client.ts` takes `enabled` as optional and sends the key only when the switch is what moved.

The state is read from `ConversationLog.read_messages(session_key)` -- the same JSONL the dashboard reads, and the only corpus carrying `meta.input` and `meta.output`; `recent` and the replay builder both project a row down to `role` and `content`. The SINGLE file rather than a chained or archive-inclusive read, and that is the subject rather than an oversight: the measurement is about THIS compaction, so its universe is the session as the compaction finds it. `read_messages_chained` would pull in a forked parent's rows and `read_messages_chained_full` the size-rotated archive -- rows this compaction is not discarding, which would sit in the denominator and shrink a share that is about what it throws away. Bounded three ways, and the third is a SIZE rather than a count: the newest `MAX_ROWS` (4000), the newest `MAX_CALLS` (1000), and `MAX_FIELD_CHARS` (4096) on each retained string. Counts alone left one pathological row -- a file read, a base64 blob -- held whole and re-redacted once per rung of the ladder, so the bytes a single transcript costs were unbounded; rows times this cap is what makes them finite. 4 KB is a SMALL multiple of what any rung sends rather than a large one: every rung clips a tool input to 1000 characters or less, so nothing is lost there, and a message longer than this reaches the wire as its first 4 KB -- which a measurement of which TOOL CALLS to keep does not turn on (conversation text is 6% of a measured transcript's characters). A bound generous enough to keep every message whole is a bound that does not close the crash it exists for. The admission bound is itself REDACT-then-clip, through the same `redacted` every other clip here goes through: a slice would cut a credential spanning the bound into a fragment neither redactor matches, and the fragment is what would travel, because a stage's own clip only ever sees what admission kept. Every LENGTH is taken from the RAW value, before both the redaction and the clip, so no tally and neither character arm moves; a tool RESULT is never sent at any stage, so only its length is retained at all. `user` / `assistant` text travels verbatim, each tool input is redacted then clipped, and EVERY tool result is replaced by `ok, N chars (omitted)` -- no result byte is on the wire at any stage, which is the widest single omission in the seam and keeps the largest half of a transcript local (results are 53% of a measured transcript's characters, inputs 33%, conversation text 6%). The first row and the newest `PINNED_TAIL_ROWS` (6) are PINNED: kept whatever an answer would say, marked `pinned: true` in the state, and never asked about.

Redaction is `platform.context.redact_via_context`, the canonical egress shim, and NOT the bare `security.redact_credentials` baseline. The baseline knows only the patterns this repository ships; a host that loaded a companion has its own credential and cookie spellings, and a baseline-only pass over a WHOLE TRANSCRIPT would send those verbatim to a third party. The shim deliberately re-raises `PlatformCompositionError` so a host that could not compose its companion cannot silently downgrade, and the point catches that and DROPS the field -- the same direction every other arm of `redacted` fails in, because a scan that did not complete cannot clear text for the wire. The shipped exfiltration-URL pass runs on top, since the shim covers credentials. Registered in `security_posture._REDACTION_SINKS`.

Tool ROWS are folded by `tool_call_id` before anything is counted. One logical call reaches the transcript as up to THREE `role="tool"` rows sharing one id -- the dispatch row `chat_runner` appends, plus the approval path's own approved/rejected row -- so a per-row count is not a count of calls: it inflated `total_calls`, sent the same input twice in the state, asked two questions about one call, and counted its characters twice in the denominator. Each field of the fold takes the first NON-EMPTY value (the dispatch row carries the input; the result handler writes the output onto whichever row it matched) and `pinned` is the OR across the rows, because a call whose approval landed inside the newest rows is one the agent is still working through. A row carrying NO `tool_call_id` -- a hook-blocked row -- gets a key of its own, because two rows that name no call cannot be shown to be the same call and merging them would undercount. The fold finishes before the cap is applied, so the cap measures CALLS rather than rows.

A walk that reaches `MAX_CALLS` keeps the NEWEST `MAX_CALLS` calls, in chronological order, and COUNTS the ones it dropped as `calls_truncated`; the count travels to the row, to the reader and onto the line. The newest end is chosen rather than fallen into: a forward walk that simply stops admitting keeps the OLDEST calls, which are the least likely to still matter, are not what the pinned tail is chosen for, and are not what this document promises. Past the cap the totals describe a PREFIX of the session, so a bare "N of M" would be a wrong sentence -- M is the cap, not the session's call count -- and the line says `(+K not scored)` instead, only when `K > 0`. A count rather than a flag, and published rather than withheld, because both other answers are worse: a wrong number, or hiding a measurement that is accurate about everything it covers. The overflow rows' characters are left out of BOTH arms, which keeps the two on one universe; the count is what says that universe is smaller than the session.

`chars_today_eligible <= chars_jev_eligible <= chars_all` is an INVARIANT, not a coincidence, and it is what makes the card's percentage a percentage. The arms count different ROLES -- the replay admits `inject` rows, which carry no tool call and are not part of the state -- so `chars_all` counts every row EITHER arm counts, not only `STATE_ROLES`. Without that, an ordinary `inject` row (a cron notification, a subagent-completion event) put bytes in the numerator that the denominator skipped, and the card rendered a share above 100%. The reader holds the same invariant from its own side: a share above 1 prints NO percentage rather than being clamped, because clamping would print a plausible number over a broken measurement.

Fitting is a five-rung ladder (`STAGES`), and the FIRST rung whose state is under `STATE_TOKEN_CEILING` (25 000 estimated tokens at `CHARS_PER_TOKEN` 4) is the one sent: inputs at 1000, then 200, then 60 characters, then the conversation text cut to head+tail halves, then to a quarter with each call's whitespace collapsed onto one line. The order is part of the contract -- inputs are clipped before text is touched at all, because clipping the 6% first would buy almost nothing and lose the part the question is answered against. Measured over 206 real transcripts the rungs admit 25% / 67% / 80% / 88% / 92% of sessions; the remaining ~8% fit nowhere and write one `state-too-large` row and send nothing, so the population that cannot be measured is visible rather than silently absent.

One `Choice` per NON-PINNED call, id `call_<index>`, options `drop` / `call` / `both` -- the reference design's three outcomes: drop it entirely, keep the call without its result, keep both. Questions are split into requests of `QUESTIONS_PER_REQUEST` (25) carrying the SAME state, at most `MAX_CONCURRENT_REQUESTS` (4) in flight, each an ordinary `decide` so each is scrubbed, bounded by `timeout_secs` and logged on its own. A batch is ALL-OR-NOTHING (`read_decisions`): a mapping missing one of the calls it was asked about cannot be folded into a fraction over all of them. The whole run is bounded by `wait_budget()` -- `timeout_secs` plus `WAIT_MARGIN_SECS`, clamped into `MIN_WAIT_SECS` .. `MAX_WAIT_SECS`, the same three values every point in this package waits by -- and a run that outlives it writes one `run-timeout` row.

Rows: the gate writes one CALL row per request (`turn_id`, `request`, `requests`, `questions`, `fitting_stage`), and the point writes one OUTCOME row per compaction carrying `total_calls`, `pinned_calls`, `kept_both`, `kept_call`, `dropped`, `calls_truncated`, `chars_all`, `chars_today_eligible`, `chars_jev_eligible`, `requests` and `fitting_stage`. The gate's own row records at most `log._MAX_ANSWERS` (8) answers whatever the batch size, which is why the tallies live on the outcome row rather than being recounted from the request rows.

Both character arms are named ELIGIBLE, and the names are the contract rather than a caveat. `chars_today_eligible` counts the rows today's recycle replay ADMITS BY ROLE, using `context.RECALL_ROLES` read from the replay's own definition rather than restated. That is the role filter only: `build_session_replay` additionally applies per-role row quotas (`_REPLAY_CONVERSATION_MAX_ROWS`, `_REPLAY_INJECT_MAX_ROWS`) and an 80 000-character budget scaled by the model window, so a long session is replayed with LESS than this arm reports. The true figure is deliberately not derived here: the quota walk takes a `ConversationLog` rather than a row list and the budget is applied inline while formatting, so the only thing available to measure is a rendered string whose length carries `Role:` prefixes and separators — formatting overhead inside a content measurement, and large enough to break the invariant below. Re-deriving the selection in this module would be a second implementation of it, free to disagree with the one that runs. So the arm is named for what it is and the card's copy says `up to`. `chars_jev_eligible` inherits the bound, because it seeds from that arm and then adds the kept calls' inputs and results, measured on the TRANSCRIPT's own lengths rather than the clipped state's (a live keep-list would re-inject the transcript's bytes). `chars_all` is everything the compaction is discarding and is the denominator the card's percentage is taken over.

A PARTIAL answer writes the row with error `partial-answers` and publishes NOTHING, because "23 of 61" over a denominator including calls nobody was asked about is a wrong number rather than an incomplete one.

Each compaction mints an ATTEMPT token (`begin_attempt`), synchronously, before the scoring task exists. `publish_record` refuses a run whose token is not the session's newest -- and an ABSENT counter is a mismatch, never a match, because the cap evicts the oldest counters and reading an absent one as equal would let the token AUTHORIZE a publish rather than only refuse one. Minting retires whatever the previous attempt left pending -- the rule `outcomes.discard` applies at the start of a turn, for the same reason. Without it, a scoring that straggled past its own compaction's notice had its record popped by the NEXT compaction on that key and shown as that one's measurement. The rows are written either way: the observation happened, and the log is where it lives.

The record reaches the compaction card through a store of the point's own (`publish_record` / `take_record`, one entry per session, `RECORD_TTL_SECONDS` 60, `MAX_PENDING_RECORDS` 200 bounding both the records and the tokens, the read destructive). The token itself comes from ONE process-wide `itertools.count`, so no value is ever handed out twice: numbering kept per session restarts at 1 once the cap evicts that session's entry, and a re-minted 1 equals the 1 a straggler minted before the eviction still carries -- the one way an equality comparison that may otherwise only REFUSE could ADMIT a record belonging to a notice already drawn. Losing a session's entry to the cap reads as a MISMATCH, which is the safe direction. `decisions.outcomes` is deliberately NOT used: that registry holds one outcome per session for the next ASSISTANT reply and `consume` pops, so claiming it here would take a `skills.select` turn's strip and attach it to a compaction notice. `dashboard/state.py::_compaction_keep_record` takes it and stamps `meta.decisions_strip` on the notice row `_on_compacted` already appends. A compaction that finishes before the scoring does takes no record, which is the documented "no card line" and is the same outcome as the seam being off.

The reader is `readCompactionKeepRecord` in `website/src/pages/chat/decisionRecord.ts`, and this block is its contract:

```json
{
  "turn_id": "cmp-7ab419",
  "point": "compaction.keep",
  "total_calls": 61,
  "pinned_calls": 7,
  "kept_both": 14,
  "kept_call": 9,
  "dropped": 38,
  "chars_all": 1482300,
  "chars_today_eligible": 74110,
  "chars_jev_eligible": 607743,
  "requests": 3,
  "fitting_stage": "inputs_200",
  "calls_truncated": 0,
  "latency_ms": 2140,
  "error": null
}
```

`keptCalls` is DERIVED by the reader from `kept_both + kept_call` rather than read as a field, the rule section 8 applies to `agree`: the line prints "N of M", and a count disagreeing with the tallies beside it would be a number nobody could reconcile with the log. A record whose three tallies do not SUM to `total_calls` draws nothing, and so does one with `total_calls: 0` -- "0 of 0" is furniture, not a measurement.
