# Jev Decision Seam

Owners: `src/kiro_crew/decisions/`, `src/kiro_crew/context.py`, `src/kiro_crew/config/sections.py`, and the Decisions card in `website/src/pages/settings/FeaturePreviewsSection.tsx`.

## 1. Scope

The foundation sends typed questions to Jev and validates its answers. `skills.select` is the only business integration: an enabled, sampled session can use Jev to select one eligible skill, or no skill, instead of the word-overlap result. Cron delivery and skill deduplication remain unchanged. There is no shadow mode, LLM comparison implementation, calibration report, or decisions report command.

## 2. Configuration and sampling

Consent is the KEYSTONE leaf `~/.kiro/crew/decisions_consent.json` (`config.loader.decisions_consent_path()`, module `decisions.consent`), holding `{"enabled": bool, "endpoint": str}`; it defaults to absent, which reads as not consented, and only a literal boolean true consents. Consent is bound to a destination: `provider.endpoint` is in the agent-writable `config.json` too, so an enabling PUT must echo the endpoint the owner reviewed (`endpoint` in the body, the `configured_endpoint` the GET showed) and is refused with `409 decisions_consent_endpoint_changed` when the config names a different one -- the GET-to-PUT window is operator-paced while the agent runs, so binding to a fresh server-side read would consent to an address the owner never saw; on a match the PUT records it (`decisions.consent.save_enabled(enabled, endpoint=...)`, `gate.configured_endpoint()` supplying the same default `impl_jev` uses), and the gate sends only while `consent.permits(configured_endpoint)` holds: enabled is true AND the recorded endpoint equals the configured one. A keystone with the flag but no recorded endpoint permits nothing. A later edit of `provider.endpoint` is therefore a refusal, warned once per address in the application log, until the owner turns the switch off and on again; the GET returns `endpoint`, `configured_endpoint` and `permits` so the card shows the address consent is for and says when the two disagree. Disabling clears the recorded endpoint. The `dashboard/handlers/decisions.py` module imports the `decisions` package inside its handlers, not at module top, so the optional seam stays off the gateway boot path (`no-new-work-on-gateway-boot-path`; pinned by `test_decisions_consent.py::test_the_handler_module_keeps_the_seam_off_the_boot_path`). It is deliberately not a `config.json` field: that file is writable by an auto-approved agent shell and the live config watcher applies it without a restart, so a switch there could be flipped by a prompt-injected agent to start sending its own conversation off the machine. The leaf is on `security._CREW_SECRET_LEAVES` (agent file tools refuse it), `sandbox._CREW_READONLY_LEAVES` (mounted read-only in every sandbox) and the absent-ceiling pre-create list, the same placement as `computer_use.json` and `aws_service_consent.json`; its only writer is the owner-only, browser-called `PUT /api/decisions/consent` (`dashboard/handlers/decisions.py`), which refuses app tokens and non-owner users on the read as well as the write, audits every grant and revocation to SEL, and never overwrites a corrupt file. `DecisionsConfig` carries no `enabled` field and `PATCH /api/config/kirocrew` refuses `decisions.enabled`; an `enabled` key an operator or agent writes into `config.json` under any spelling is inert. `decisions.bucket` is an integer percentage from 0 to 100; an absent key is the default of 100, an out-of-range number is clamped, and a value that does not parse as a whole number reads as 0 (nobody sampled), never as everybody. Sampling uses the session key's SHA-256 digest, so a session remains in the same group rather than drawing again on each message. Zero samples none; 100 samples every otherwise eligible session.

The provider configuration contains endpoint, API-key reference, model and `timeout_ms`. A default timeout is 1000 milliseconds. The sampling percentage and provider use the existing live config snapshot; consent is one small keystone read per decision, performed off the event loop (`asyncio.to_thread` in `decide`, the caller's executor thread in `is_enabled`).

Legacy `preview`, `points`, `arm`, `shadow`, and `live` values do not enable this behavior. Enabling an observation-only configuration must never silently authorize business decisions. The keystone consent is the one explicit opt-in.

## 3. Core contract

`decide(point, state, questions, session_key=...)` returns validated answers or `None`. Disabled, unknown-point, unsampled, scrubbed, timed-out, transport-error and invalid-answer paths return `None`. Cancellation propagates so a caller can abandon a pending request. `is_enabled` provides the same cheap preflight before a caller builds its candidate menu; `decide` checks the gates again.

Jev is the sole provider implementation, and `Choice` is the only question type. Requests use its documented wire format with bounded response reads, no retry and no redirect following (`allow_redirects=False`; a 3xx is refused as a provider error, since consent is bound to the endpoint asked and a followed redirect would replay the body elsewhere). A reply is accepted only when each answer's type is `choice`, its `choice` is a string, and the probability for that choice is a finite number in 0..1 (a boolean is not a number); the gate then checks identifiers and options again before anything is consumed. Provider failures do not fabricate a selection. The response mapping is tested against a loopback server; those tests do not prove a real TypeSafe account round-trip.

Before transmission, the request -- the state, the questions and the provider model id together, rendered as the wire will render them -- is scanned with the existing credential patterns, canonical credential redactor and exfiltration-URL detector. A match or scanner failure refuses the whole request. No partially scrubbed request is sent. Every agent-writable provider field that can reach the wire is bounded: `provider.model` must match `types.MODEL_ID_RE` (letters, digits, `.`, `_`, `-`, at most 64 characters) or the request is refused as `scrubbed:provider-model`, checked in the gate before the scan and again in `impl_jev._to_wire`; `provider.endpoint` is bound by consent (above); and `provider.api_key` is never itself a credential -- only the reference `secret://TYPESAFE_API_KEY` (`impl_jev.VAULT_SECRET_NAME`) resolves, from the dashboard secrets vault the agent cannot read, so a literal key written into `config.json` is refused with a warning naming the fix and a reference to any other vault entry resolves to no key and never touches the vault. Where the vault key goes is decided by consent, not by the endpoint being the default: an owner who consented to a proxy address gets the vault key sent there and nowhere else. Configuration is not an independent authorization boundary: an actor allowed to change it can enable requests only to the consented endpoint, with the operator's own model id and key.

## 4. Skill selection

The normal word-overlap result remains the fallback. The Jev candidate menu uses skills available through the existing loader and its project-confinement rules. The explicit no-skill option is `/no skill applies`: a key's first component is a directory name, so no skill can carry that name, and a skill literally called `none` or `(no skill applies)` stays selectable. Always-loaded skills are not candidates; negative triggers and `skills.max_triggered` remain effective. A zero trigger cap means no automatic selection and no Jev request. Skill identifiers are preserved, not shortened into different names.

A validated choice replaces the triggered list before the existing body/pointer split. The explicit no-skill answer produces an empty list; `None` means retain the original list. Custom-agent and minimal-context paths do not acquire automatic skill selection.

The selection runs inside `SkillsLoader.get_triggered_skills`, ahead of its single `skill_trigger` security-event row, so that row names the set actually injected and marks it as selected. A superseded word-overlap match is never recorded as injected, and an empty selection still produces a row.

`ContextBuilder.build_message` is synchronous. On its worker thread, it submits the decision to the captured running event loop and waits with a finite budget. It must not block the event-loop thread itself. Missing or closed loops, same-loop calls, invalid answers and expired budgets fall back. An abandoned future is cancelled; its eventual answer cannot change a context already assembled.

## 5. Operational log

The basic JSONL log records call metadata rather than an A/B score: timestamp, point, hashed session, latency, scrubbed boolean, bounded answer data and an error category. Raw messages, candidate descriptions, API keys and provider exception text do not belong in rows. No claimed price, baseline or agreement curve is emitted.

Disabled and unsampled paths do not write logs. A candidate menu that cannot be built -- the loader walk raised, or every entry it yielded was unreadable -- writes one row with error `candidates-failed`, so a loader change that breaks enumeration is visible rather than indistinguishable from an unsampled session; an empty skill tree writes nothing. Rows are appended through `platform_log_append.append_line`, a confined, locked, full-write append (see `docs/system-specs/common/platform-compat.md`) that works on POSIX and Windows alike; a link at the directory or the leaf, or a file that is not a regular single-link file, refuses the write. Each day-file is capped at `MAX_FILE_BYTES` (8 MiB): a row that would cross the ceiling is refused inside the lock before any byte is written, and the first refusal per file is logged at WARNING. Day-files older than `RETENTION_DAYS` (14) are removed by the first append of each UTC day; only regular files carrying this module's own file-name pattern are candidates, and the directory is listed and unlinked through the same pinned, no-follow descriptor the append uses (`platform_log_append.pinned_log_dir`), so a directory link swapped in under the log directory's name cannot redirect the deletion. Log failure cannot turn a valid decision into an application exception. JSON serialization keeps control characters encoded as data; this feature has no terminal report renderer. Logging is best effort, not proof that a selection reached the assembled context.

## 6. Settings and validation

The Decisions card reads and writes the keystone through `GET`/`PUT /api/decisions/consent`, not localStorage and not the config route, and reads the sampling share from the config GET. It prints the configured endpoint ("Sent to") beside the switch so consent is to an address, and a body-weight notice when consent stands for a different address than the config now names. It carries no `configKey`, because it writes no config path; `test_settingref_schema_fixture.py` pins that `decisions.enabled` is absent from the schema and the card. The backend editable-field validation accepts the bounded integer bucket only; sensitive provider credentials remain masked in GET output. The card prints the sampling share in both switch states, phrased as a fact about the on state, because the shipped default of 100 means every session and consent must see that before the switch is flipped. A backend exposing only legacy `preview` is unsupported, not an enabled gateway; that state fades the card, including the egress note, and names Settings › Releases as the fix. A literal `configKey` is required so the settings extractor connects the control to the schema.

Tests cover strict opt-in and legacy non-migration; sampling; Jev success, malformed replies and failure; credential refusal; log shape; real PATCH/GET behavior; actual skill-selection consumption and fallback from an executor thread; negative triggers and cap limits; frontend field support, writes, refused writes and generated key parity. These are local/loopback tests. Live provider verification requires a real key and separate consent to send test data.
