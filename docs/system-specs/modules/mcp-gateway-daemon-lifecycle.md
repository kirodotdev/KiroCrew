# MCP gateway daemon lifecycle (one owner, one code revision)

The MCP gateway daemon (`mcp_gateway/gatewayd.py`) pools MCP backends across sessions. It is a separate process from the gateway, spawned by `mcp_gateway/manager.py::GatewayManager` with `start_new_session=True` so a gateway crash cannot take live sessions' brokers down with it. That independence is also a hazard: the daemon can outlive the gateway that spawned it, and a later gateway that finds a healthy daemon on the socket adopts it rather than spawning its own. Adoption compared what the daemon could serve (its baked target-stem map) and nothing about which code it was running. A daemon from one checkout therefore kept serving a gateway restarted from a newer one, and the pooled `kirocrew mcp-core` it handed out spoke a control-frame shape (`/api/session-directive`, `{kind, args}`) the gateway had stopped reading (`{tool, raw_args}`). Every `monitor_start` on the affected sessions was refused `not_derivable` while the tool reported success, for a day.

This module states the contract that closes it. Two gateways deliberately sharing one data home are not a supported configuration (they contend for the dashboard port, `.local_secret` and `config.json` before the daemon is ever reached), so the design is **one daemon, one owner**: the daemon belongs to the gateway process that spawned it, dies with it, and is never adopted across a code revision.

## Code fingerprint

`code_fingerprint.code_fingerprint()` is one opaque token naming WHICH Kiro Crew code a process imported, computed once per process. Git is resolved through `platform_compat.trusted_git_bin` (fixed system directories, never `PATH`) and run with global and system config disabled, inherited `GIT_*` variables dropped and `--no-ext-diff --no-textconv`, because this runs in the gateway process on a tree an agent can write to; no trusted git means the mtime rule. Inside a git worktree it is the HEAD commit plus `+<sha256 of the tracked diff>` when tracked files differ — the diff TEXT, not a dirty bit, because two uncommitted edits to one HEAD are different code, and a bare `+dirty` would let a daemon from the first edit be adopted by a gateway on the second. Otherwise it is `mtime:<digest>` over the installed distribution version and the newest `*.py` mtime under the package, since a wheel is immutable until replaced and replacing it moves the mtimes. The only contract is *equal iff the same code*. The first computation runs `git` or walks the package tree, so the two async owners — `run_gatewayd` before it binds, `GatewayManager._start_locked` before its election loop — await `warm_code_fingerprint()` (`asyncio.to_thread`) once; every later synchronous read on their event loops (the pong, the stand-down handler, `_code_drift`) is a cache hit. The stub computes it inside `build_register_payload`, which already runs on the subprocess executor.

This exists because nothing else could answer the question. The MCP stub's `binary_version` (`mcp_gateway/stub.py::_binary_version`) hashes the target binary, and for Kiro Crew's own servers that binary is the `.venv/bin/kirocrew` console-script shim — byte-identical across every commit of an editable install. The distribution version changes only at a release.

## Owner liveness

`GatewayManager._spawn_once` passes `--owner-pid <gateway pid>` on the daemon's argv. `run_gatewayd` publishes it (`_OWNER_PID`) and, after a successful bind, arms `_owner_liveness_sweeper`: every `_OWNER_LIVENESS_INTERVAL_SECS` (15 s) it checks that the owner PID exists AND that its `platform_compat.process_start_time` equals the value read at arm time, so a recycled PID number is not mistaken for the owner. `_OWNER_LIVENESS_MISSES` (2) consecutive conclusive misses set `stop_event`, which is the same graceful path SIGTERM takes: accepts stop, attached stubs drain, `pool.shutdown_all()` takes every pooled backend down, the endpoint and the singleton lock are released. An unreadable start time at arm time disables the check with a warning (nothing to compare against); an unreadable probe later is inconclusive and neither counts nor resets. No `--owner-pid` (an operator running the module by hand) arms nothing.

The same rule reaches the CLI. `cli_server._stop` — and therefore `kirocrew restart`, which reuses it — calls `_stop_mcp_gateway_daemon` after signalling the gateway, on both the service and the listener path. That goes through `mcp_gateway/daemon_control.py::stop_daemon`: ping the configured socket (`configured_socket_path`: `mcp_gateway.socket_path` when set, the data-home default otherwise — the same resolution the gateway uses to spawn), read the daemon's `pid` from the pong, verify that process's command line names `kiro_crew.mcp_gateway.gatewayd` (a forged pong cannot aim a signal), SIGTERM it through `platform_compat.kill_pid_pinned` on the `start_time` the daemon reported about itself in the pong — computed once at daemon startup off the loop (`_OWN_START_TIME`), since on macOS it is a `ps` subprocess and the pong is answered from the connection handler — re-confirmed against `process_start_time(pid)` immediately before the signal on POSIX, where `kill_pid_pinned` has no handle to hold (a daemon that reports no token is refused), so a PID recycled between the ping and the signal is not signalled — never SIGKILL, because the drain is what reaps the pool — and wait up to the daemon's published shutdown budget for the singleton lock to free. The synchronous stop matters even though the daemon would exit on its own: a restart spawns the replacement gateway inside the owner-probe interval, and that gateway would otherwise meet a healthy daemon and adopt it. Every outcome (`stopped`, `draining`, `denied`, `unverified`, `absent`) is reported and none fails the command.

## The adoption gate

The daemon's ping reply (`gatewayd._pong_payload`) carries `targets`, `fingerprint`, `owner_pid` and `pid`.

A fast ping is bounded at `_PING_TIMEOUT_SECS`, which under load measures how loaded the daemon is rather than whether it is alive -- and because `_ping_raw` gives up at that bound, a late pong is never seen at all. So every decision that would DISPLACE a running daemon escalates first (`_ping_with_escalation`): the fast probe, then one further probe at `_LIVENESS_ESCALATED_TIMEOUT_SECS` if it missed. A daemon that answers either is alive, and the owned path's `_LIVENESS_MAX_CONSECUTIVE_FAILURES` grace counts only cycles where neither answered. The adopted path escalates too, and then acts on ONE miss rather than carrying the owned path's `_LIVENESS_MAX_CONSECUTIVE_FAILURES` grace. That asymmetry is deliberate: on the adopted path the verdict's latency IS the outage. An adopted daemon that really is gone leaves nothing listening on its address, so no attached stub can serve a call until a replacement binds. One escalated miss displaces at 26s worst case -- 2+2+2 for the fast probe's three steps, then 20 for the escalated one -- while three cycles would take 26 + 30 + 26 + 30 + 26 = 138s, five times the outage in exchange for evidence the escalation already provides. The load misverdict the escalation exists for is already handled by the escalation itself: a daemon that answers either probe is alive and is never displaced, and no case has been observed of a live daemon silent past the escalated bound. The owned path can afford its grace because its own socket stays bound while it waits. The one-shot assessment gates (the start-time election, the post-respawn incumbent check) and the public `GatewayManager.ping()` status probe keep the fast bound. For the status probe that is right: a readout must answer a UI poll promptly, and a wrong readout displaces nothing. For the assessment gates it is a SCOPE boundary, not a safety argument. Their miss path reaches `_clear_stale_socket` -> `transport.remove_stale`, which asks `transport.probe_live` whether the endpoint is live before unlinking it -- and on POSIX that probe reads a full accept backlog as not-live, because a unix `connect()` against a saturated listener blocks until the probe's own 1s timeout and the resulting `socket.timeout` is an `OSError`, which the probe reports as False. So under the very load this escalation exists for, an assessment gate can unlink a LIVE daemon's socket and block every new and reconnecting stub. The root of that is `probe_live` treating a timeout as a negative answer while its own contract says an inconclusive probe must err toward leaving the endpoint alone; fixing it belongs with the endpoint lifecycle, not with the supervisor's verdict, and is not attempted here.

A stub whose live connection dies mid-session retries the Register handshake within `stub._RECONNECT_TOTAL_BUDGET_SECS`, and that budget has to outlast the recovery it is waiting for. The owned liveness path cannot be faster than 91s -- three `_LIVENESS_PING_INTERVAL_SECS` cycles must elapse before the third failure can be counted at all -- and runs to about 191s once the probes and the SIGTERM wait are added, so a budget below that is not patience but a guarantee that an ORDINARY slow recovery costs every attached session its MCP tools for good. The budget therefore clears the derived worst case several times over rather than being tuned to a typical restart, and a test asserts it against the manager's own constants so raising the detection cost fails there instead of silently re-breaking this. It is deliberately not a cover for every conceivable recovery: a respawn that keeps failing backs off to 60s per retry with no attempt cap, and past five minutes the honest signal to a waiting session is that its tools are gone rather than more silence. Requests already in flight when the connection drops are failed fast with `-32603` before any retry begins. A request kiro-cli issues DURING the window is not: the bridge pumps are down, so it waits in the stub's stdin queue until the reattach or the budget ends, which is why the budget is sized to cover the recovery and no more rather than generously. That gap is tracked separately. A refusal -- an older daemon that cannot honour `poolable`, or a generation that answers the handshake differently -- stays terminal rather than being retried.

`GatewayManager` reads the incumbent's pong at every point it might adopt — the start-time election, the lost-the-lock branch, the watchdog's periodic re-check of an adopted daemon (`_reconcile_adopted`), and the watchdog's re-election after a daemon dies — and adopts only when `_adoption_drift` (target stems), `_code_drift` (fingerprint) AND `_owned_by_a_live_other` are all clear. The last one reads the pong's `owner_pid`: an owner that is alive and is not this process means another gateway still owns that daemon. That is either the unsupported two-gateways-one-home layout or a restart racing the old gateway's exit, and in both cases adopting would take a daemon whose owner sweeper is about to shut it down mid-traffic. The start refuses the broker (`ERROR`, returns False; stubs fall back to per-session exec) and the watchdog backs off and looks again, rather than asking that daemon to stand down — it is not ours to cycle. An owner that is absent (0) or this process is not a rival, and the other two gates decide. An owner that is DEAD makes the daemon an orphan (`_orphaned`), and an orphan is not adopted either, even on matching stems and code: its own sweeper ends it within two probes, so adopting it hands every session a broker that exits under them mid-call. It is treated as draining — asked to stand down on the `orphaned` ground, which the daemon honours only after confirming from its own `_OWNER_PID` that the owner really is gone (a caller's claim ends no daemon whose gateway is alive) — and replaced by a daemon this process owns. `_code_drift` is true when the fingerprint differs from this process's own OR is absent: a daemon that omits it predates this code by construction and is stale, not unverifiable.

Either drift asks the incumbent to stand down through `_request_stand_down`, whose frame now also carries `caller_fingerprint` when code drift is the ground. `gatewayd._apply_stand_down` honours a request on two independent grounds — a needed stem it cannot resolve, or a caller fingerprint that differs from its own — and still refuses one it has no reason to honour: a daemon that resolves every requested stem AND matches the caller's code has nothing to gain from cycling. The reply names both grounds (`missing`, `stale_code`) and the SEL audit row records them. An old-shape frame (stems only) is handled exactly as before.

The fail-open branch is unchanged in kind and louder in degree: a stale daemon that REFUSES is still serving, so it is adopted rather than left unsupervised, but for code drift the log line is an ERROR naming the consequence (pooled backends may speak a stale protocol) and the fix (`kirocrew restart`).

## The pool key

`stub.pool_binary_version` folds `code_fingerprint()` into the registered `binary_version` when the target args name one of Kiro Crew's own servers (`_KIROCREW_MCP_SUBCOMMANDS`: `mcp-core`, `mcp-cron`, `mcp-work`, `mcp-computer`, `mcp-dashboard`) and leaves third-party servers on the binary hash alone. So even a daemon that survives — an operator-run one with no owner, or one whose stand-down was refused — hands a stub from new code a NEW pool partition rather than the old checkout's backend; a `git pull` cold-starts Kiro Crew's own servers and nothing else.

## Diagnosis

`dashboard/handlers/sessions.py::api_session_directive` recognises the pre-call-input body (`kind` present, `tool` absent) and refuses it as `stale_mcp_backend`, with a warning that names the cause (an MCP server running older code than the gateway) and the fix, instead of the generic `not_derivable` that pointed operators at the directive tools. `kirocrew doctor` (`cli_doctor._doctor_mcp_gateway_daemon`) prints the daemon's pid, owner and fingerprint beside this install's, and records an issue when they differ; the same read is `daemon_control.describe_daemon`.
