# MCP gateway daemon lifecycle (one owner, one code revision)

The MCP gateway daemon (`mcp_gateway/gatewayd.py`) pools MCP backends across sessions. It is a separate process from the gateway, spawned by `mcp_gateway/manager.py::GatewayManager` with `start_new_session=True` so a gateway crash cannot take live sessions' brokers down with it. That independence is also a hazard: the daemon can outlive the gateway that spawned it, and a later gateway that finds a healthy daemon on the socket adopts it rather than spawning its own. An adoption that compared only what the daemon could serve (its baked target-stem map) and nothing about which code it runs would let a daemon from one checkout keep serving a gateway restarted from a newer one, handing out a pooled `kirocrew mcp-core` that speaks a control-frame shape the gateway no longer reads, so directive tools would be refused while reporting success.

This module states the contract that closes it. Two gateways deliberately sharing one data home are not a supported configuration (they contend for the dashboard port, `.local_secret` and `config.json` before the daemon is ever reached), so the design is **one daemon, one owner**: the daemon belongs to the gateway process that spawned it, dies with it, and is never adopted across a code revision.

## Code fingerprint

`code_fingerprint.code_fingerprint()` is one opaque token naming WHICH Kiro Crew code a process imported, computed once per process. Git is resolved through `platform_compat.trusted_git_bin` (fixed system directories, never `PATH`) and run with global and system config disabled, inherited `GIT_*` variables dropped and `--no-ext-diff --no-textconv`, because this runs in the gateway process on a tree an agent can write to; no trusted git means the mtime rule. Inside a git worktree it is the HEAD commit plus `+<sha256 of the tracked diff>` when tracked files differ — the diff TEXT, not a dirty bit, because two uncommitted edits to one HEAD are different code, and a bare `+dirty` would let a daemon from the first edit be adopted by a gateway on the second. Otherwise it is `mtime:<digest>` over the installed distribution version and the newest `*.py` mtime under the package, since a wheel is immutable until replaced and replacing it moves the mtimes. The only contract is *equal iff the same code*. The first computation runs `git` or walks the package tree, so the two async owners — `run_gatewayd` before it binds, `GatewayManager._start_locked` before its election loop — await `warm_code_fingerprint()` (`asyncio.to_thread`) once; every later synchronous read on their event loops (the pong, the stand-down handler, `_code_drift`) is a cache hit. The stub computes it inside `build_register_payload`, which already runs on the subprocess executor.

This exists because nothing else could answer the question. The MCP stub's `binary_version` (`mcp_gateway/stub_register.py::_binary_version`) hashes the target binary, and for Kiro Crew's own servers that binary is the `.venv/bin/kirocrew` console-script shim — byte-identical across every commit of an editable install. The distribution version changes only at a release.

## Owner liveness

`GatewayManager._spawn_once` passes `--owner-pid <gateway pid>` on the daemon's argv. `run_gatewayd` publishes it (`_OWNER_PID`) and, after a successful bind, arms `_owner_liveness_sweeper`: every `_OWNER_LIVENESS_INTERVAL_SECS` (15 s) it checks that the owner PID exists AND that its `platform_compat.process_start_time` equals the value read at arm time, so a recycled PID number is not mistaken for the owner. `_OWNER_LIVENESS_MISSES` (2) consecutive conclusive misses set `stop_event`, which is the same graceful path SIGTERM takes: accepts stop, attached stubs drain, `pool.shutdown_all()` takes every pooled backend down, the endpoint and the singleton lock are released. An unreadable start time at arm time disables the check with a warning (nothing to compare against); an unreadable probe later is inconclusive and neither counts nor resets. No `--owner-pid` (an operator running the module by hand) arms nothing.

The same rule reaches the CLI. `cli_server._stop` — and therefore `kirocrew restart`, which reuses it — calls `_stop_mcp_gateway_daemon` after signalling the gateway, on both the service and the listener path. That goes through `mcp_gateway/daemon_control.py::stop_daemon`: ping the configured socket (`configured_socket_path`: `mcp_gateway.socket_path` when set, the data-home default otherwise — the same resolution the gateway uses to spawn), read the daemon's `pid` from the pong, verify that process's command line names `kiro_crew.mcp_gateway.gatewayd` (a forged pong cannot aim a signal), SIGTERM it through `platform_compat.kill_pid_pinned` on the `start_time` the daemon reported about itself in the pong — computed once at daemon startup off the loop (`_OWN_START_TIME`), since on macOS it is a `ps` subprocess and the pong is answered from the connection handler — re-confirmed against `process_start_time(pid)` immediately before the signal on POSIX, where `kill_pid_pinned` has no handle to hold (a daemon that reports no token is refused), so a PID recycled between the ping and the signal is not signalled — never SIGKILL, because the drain is what reaps the pool — and wait up to the daemon's published shutdown budget for the singleton lock to free. The synchronous stop matters even though the daemon would exit on its own: a restart spawns the replacement gateway inside the owner-probe interval, and that gateway would otherwise meet a healthy daemon and adopt it. Every outcome (`stopped`, `draining`, `denied`, `unverified`, `absent`) is reported and none fails the command.

The in-app restarts reach the same rule from inside the gateway. The dashboard restart (`dashboard/handlers/updates_apply.py::_restart_gateway`) replaces the process with `os.execv` and never runs `_shutdown`, so it stops the broker it owns, `_stop_mcp_broker`, the call the clean shutdown makes, reached by the dashboard handler through `DashboardState._mcp_gateway_stop` (wired by `_wire_mcp_gateway_dashboard`), after `close_all()`, when nothing is mid-call, and before the exec. Without that stop the outcome depends on what the exec does to the pid. A POSIX `execv` into the Python module keeps it: the successor's election finds `owner_pid == os.getpid()`, adopts a same-code daemon or stands a stale-code one down, and the restart costs a stand-down round trip. A launcher that runs the selected gateway as a supervised child does not: the old pid lives on as the supervisor with an unchanged start time, the owner-liveness sweeper keeps passing, and the successor meets a daemon "owned by another LIVE gateway" and refuses the broker for its whole lifetime, every stubbed server on per-session exec, a daemon on the previous code keeping its pooled backends. A refused or deferred restart (the interpreter guard, a lost fence, a drain that did not finish) returns before the stop, so the broker keeps serving the sessions that stay open; a stop that raises is caught by the dashboard handler and the exec still runs, because a broker that will not stop must not strand a gateway whose sessions are already closed.

The stop reaches only the daemon this gateway spawned. `GatewayManager.shutdown` leaves an adopted daemon alone on both the clean exit and the restart — it belongs to its own owner, and the adoption gate is what handles it at the next start: an owner recorded as `0` (an operator-run daemon) is adopted again, and an owner that has exited is an orphan the successor stands down and replaces. The case those two rules do not cover — an adopted daemon whose `--owner-pid` is this gateway's own pid, which a supervising launcher would carry across the exec as a live owner — is not one this code produces: the two in-app restarts above retire the daemon they spawned before the exec, and a same-pid survivor left by a different build carries a different `code_fingerprint`, so `_code_drift` stands it down rather than adopting it. What remains is a daemon that outlived the pre-exec SIGTERM→SIGKILL escalation in `_terminate_process`, which no exit request from `shutdown` would end either.

The pre-exec stop is prophylactic, so the adoption gate also reads the supervisor as this gateway. The restart that installs the stop runs the previous release's restart code, and a host already in the state never reaches one: the refused successor holds no broker to stop, and the daemon's owner, the supervisor, lives as long as the service. So `_owned_by_a_live_other` treats the supervisor as this process, not as a rival: `platform_compat.is_exec_supervisor_of_this_process` accepts a live ancestor (a bounded parent walk that never counts pid 1) whose current executable is known and is not a Python interpreter. Ancestry alone would not do: a gateway started from a shell a live gateway spawned has that gateway as an ancestor too, and adopting or standing down its daemon would take the broker from a gateway that is serving. What the exec changes is the image — the supervisor runs the launcher, while every gateway runs Python — so an ancestor still running Python stays a rival. Every process between the two must pass the same test: a live Python process in between may be the very gateway the supervisor runs, which started this one, so the walk refuses as soon as it passes one. An executable the host will not report (Windows, an unreadable process), on the owner or in between, keeps the refusal. The supervisor's daemon then meets the ordinary gates: a stale-code one is stood down with `stale_code=True` and replaced by a daemon this gateway owns, and a same-code one is adopted. The run-marker boot fence (`instances/run_marker.py::_record_names_another_live_gateway`) applies the same rule to `gateway-<port>.pid`, which after such an exec still names the supervisor with a matching start token: the supervisor's record is overwritten with this gateway's pid, so CLI identity checks that read it see the process that serves the port.

## The adoption gate

The daemon's ping reply (`daemon/control.py::_pong_payload`) carries `targets`, `fingerprint`, `owner_pid`, `pid` and `start_time`.

A fast ping is bounded at `_PING_TIMEOUT_SECS`, which under load measures how loaded the daemon is rather than whether it is alive -- and because `_ping_raw` gives up at that bound, a late pong is never seen at all. So every decision that would DISPLACE a running daemon escalates first (`_ping_with_escalation`): the fast probe, then one further probe at `_LIVENESS_ESCALATED_TIMEOUT_SECS` if it missed. A daemon that answers either is alive, and the owned path's `_LIVENESS_MAX_CONSECUTIVE_FAILURES` grace counts only cycles where neither answered. The adopted path escalates too, and then acts on ONE miss rather than carrying the owned path's `_LIVENESS_MAX_CONSECUTIVE_FAILURES` grace. That asymmetry is deliberate: on the adopted path the verdict's latency IS the outage. An adopted daemon that really is gone leaves nothing listening on its address, so no attached stub can serve a call until a replacement binds. One escalated miss displaces at 26s worst case -- 2+2+2 for the fast probe's three steps, then 20 for the escalated one -- while three cycles would take 26 + 30 + 26 + 30 + 26 = 138s, five times the outage in exchange for evidence the escalation already provides. The load misverdict the escalation exists for is already handled by the escalation itself: a daemon that answers either probe is alive and is never displaced, and no case has been observed of a live daemon silent past the escalated bound. The owned path can afford its grace because its own socket stays bound while it waits. The one-shot assessment gates (the start-time election, the post-respawn incumbent check) and the public `GatewayManager.ping()` status probe keep the fast bound. For the status probe that is right: a readout must answer a UI poll promptly, and a wrong readout displaces nothing. For the assessment gates it is a SCOPE boundary, not a safety argument. Their miss path reaches `_clear_stale_socket` -> `transport.remove_stale`, which asks `transport.probe_live` whether the endpoint is live before unlinking it. On POSIX that probe reports only `ConnectionRefusedError` and `FileNotFoundError` as dead; any other `OSError` (a timeout against a saturated accept backlog, `EAGAIN`, `EINTR`) reports live, so an assessment gate leaves a loaded daemon's socket in place rather than unlinking it.

A daemon the manager just spawned gets the same allowance before its endpoint appears. `_spawn_and_confirm` waits `_SOCKET_READY_TIMEOUT_SECS` (5 s) for the endpoint; if it is still missing but the spawned process is still running, it keeps waiting up to `_SOCKET_READY_SLOW_START_SECS` (30 s) in total before it terminates the daemon and reports the start as failed. A cold start on a slow host (on-access antivirus scanning every imported file is common on Windows) can need more than 5 s to bind, and killing that daemon drops every session to per-session MCP, which starts many more cold processes on the same host. A daemon that has already exited (for example one that lost the singleton lock) is not waited on.

A stub whose live connection dies mid-session retries the Register handshake within `stub._RECONNECT_TOTAL_BUDGET_SECS`, and that budget has to outlast the recovery it is waiting for. The owned liveness path cannot be faster than 90 s -- three `_LIVENESS_PING_INTERVAL_SECS` cycles must elapse before the third failure can be counted at all -- and runs to at worst 168 s plus the 20 s `_SHUTDOWN_GRACE_SECS` (derived in the liveness section below), so a budget below that is not patience but a guarantee that an ORDINARY slow recovery costs every attached session its MCP tools for good. The budget therefore clears the derived worst case several times over rather than being tuned to a typical restart, and a test asserts it against the manager's own constants so raising the detection cost fails there instead of silently re-breaking this. It is deliberately not a cover for every conceivable recovery: a respawn that keeps failing backs off to 60s per retry with no attempt cap, and past ten minutes the honest signal to a waiting session is that its tools are gone rather than more silence. Requests already in flight when the connection drops are failed fast with `-32603` before any retry begins. A request kiro-cli issues DURING the window is answered too, but on a delay: `stub._reconnect_while_draining` pairs the retry loop with `_drain_while_disconnected`, which is the only reader of the session's stdin queue while no bridge pump exists. It holds each frame for `stub._QUEUED_GRACE_SECS` -- the same figure a live bridge already allows a silent gateway, `_BRIDGE_PING_INTERVAL_SECS` x `_BRIDGE_PING_MAX_MISSES`, so a queued call is never held longer than a forwarded one -- and past that answers it with the same retryable `-32603`. The two clocks are separate on purpose: the SESSION keeps waiting for the whole budget because giving up is irreversible, while no one CALL waits more than the grace because failing it retryably costs one retry. Which of the two a call gets follows from how the bridge ended, and the grace is sized so the split falls in the right place. A `socket_eof` ending is observed at once, so a daemon that respawns promptly is re-attached within seconds and the call is served for real. A `peer_dead` ending has already spent `_BRIDGE_PING_INTERVAL_SECS` x `_BRIDGE_PING_MAX_MISSES` detecting the silence, and the supervisor's own path cannot beat 90 s, so a call arriving in that window is failed retryably rather than held for the minutes the reattach will actually take -- which is the whole point of bounding it. Three kinds of frame are held rather than failed -- a notification (no id to answer), a line that does not parse (forwarded verbatim, as the pump would), and `initialize` (the handshake replay answers it for real, the same exception `_split_abandoned_ids` makes) -- and held frames go back to the head of kiro-cli's stream so the next bridge forwards them in order, while a failed one is dropped because its id has been answered. Anything still held when the reconnect gives up is answered by the terminal path instead. What the drain retains is bounded in BOTH dimensions -- `stub._STDIN_QUEUE_MAXSIZE` frames and `_HELD_TOTAL_BYTES` of them, with `_HELD_FRAME_BYTES` per frame -- the same pair and the same reasoning as `gatewayd._MAX_PENDING_FRAMES` / `_MAX_PENDING_BYTES`, since a count bound alone admits that many maximum-size lines and a byte bound alone leaves the per-object overhead of very many tiny frames unaccounted; the aggregate follows the per-frame ceiling upward so one frame the reader was willing to return cannot trip it alone, and is floored at the shipped read limit so tuning `read_buffer_limit_bytes` down cannot tighten the hold. At a bound the HOLD yields rather than the answer: a request is failed immediately instead of being kept, and a frame with no id to answer -- a notification, or a line that does not parse -- is dropped and logged, the same choice `_serve_capacity_refusal` makes for the same reason. A refusal -- an older daemon that cannot honour `poolable`, or a generation that answers the handshake differently -- stays terminal rather than being retried.

`GatewayManager` reads the incumbent's pong at every point it might adopt — the start-time election, the lost-the-lock branch, the watchdog's periodic re-check of an adopted daemon (`_reconcile_adopted`), and the watchdog's re-election after a daemon dies — and adopts only when `_adoption_drift` (target stems), `_code_drift` (fingerprint) AND `_owned_by_a_live_other` are all clear. The last one reads the pong's `owner_pid`: an owner that is alive and is not this process means another gateway still owns that daemon. That is either the unsupported two-gateways-one-home layout or a restart racing the old gateway's exit, and in both cases adopting would take a daemon whose owner sweeper is about to shut it down mid-traffic. The start refuses the broker (`ERROR`, returns False; stubs fall back to per-session exec) and the gateway starts the same manager again on the L4 schedule ([§A failed start is retried by the gateway](#a-failed-start-is-retried-by-the-gateway)); the watchdog's re-election after a daemon it supervised dies meets the same gate and backs off and looks again. Neither asks that daemon to stand down: it is not ours to cycle. An owner that is absent (0) or this process is not a rival, and the other two gates decide. An owner that is DEAD makes the daemon an orphan (`_orphaned`), and an orphan is not adopted either, even on matching stems and code: its own sweeper ends it within two probes, so adopting it hands every session a broker that exits under them mid-call. It is treated as draining — asked to stand down on the `orphaned` ground, which the daemon honours only after confirming from its own `_OWNER_PID` that the owner really is gone (a caller's claim ends no daemon whose gateway is alive) — and replaced by a daemon this process owns. `_code_drift` is true when the fingerprint differs from this process's own OR is absent: a daemon that omits it predates this code by construction and is stale, not unverifiable.

Either drift asks the incumbent to stand down through `_request_stand_down`, whose frame also carries `caller_fingerprint` when code drift is the ground. `daemon/control.py::_apply_stand_down` honours a request on two independent grounds — a needed stem it cannot resolve, or a caller fingerprint that differs from its own — and still refuses one it has no reason to honour: a daemon that resolves every requested stem AND matches the caller's code has nothing to gain from cycling. The reply names both grounds (`missing`, `stale_code`) and the SEL audit row records them. An old-shape frame (stems only) is handled exactly as before.

The fail-open branch is unchanged in kind and louder in degree: a stale daemon that REFUSES is still serving, so it is adopted rather than left unsupervised, but for code drift the log line is an ERROR naming the consequence (pooled backends may speak a stale protocol) and the fix (`kirocrew restart`).

The adoption gate does not compare the daemon's env, so the boot-time `SSH_AUTH_SOCK` a gateway hands its daemon (`agent_socket.DAEMON_ENV`, only while `ssh_auth_sock_consent.json` names a shared backend; see `security.md`) is fixed for that daemon's life. A daemon spawned while the grant named no backend has no socket, so a backend named later gets it only from the next daemon (`kirocrew restart`). A daemon spawned with the socket re-reads the grant before every launch, so adding or removing a name takes effect at that backend's next launch.

## The pool key

`stub.pool_binary_version` folds `code_fingerprint()` into the registered `binary_version` when the target args name one of Kiro Crew's own servers (`_KIROCREW_MCP_SUBCOMMANDS`, every name in `mcp_discovery._MANAGED_SERVER_SUBCOMMANDS`; the daemon-generation check in `handshake` runs only when the stub has a code fingerprint and `--server` names one of `mcp_cleanup.KIROCREW_BIN_MCP_SERVERS`) or when the launch runs this install's own code (`hashing.runs_install_code` -- the gateway interpreter `apps/bridges_mcp.py` pins, whose `command_args_hash` is an alias and so cannot see a release on its own, with `-m kiro_crew...` or the `deps_boot` shim in argv), and leaves third-party servers -- including one that merely runs on that interpreter -- on the binary hash alone. So even a daemon that survives — an operator-run one with no owner, or one whose stand-down was refused — hands a stub from new code a NEW pool partition rather than the old checkout's backend; a `git pull` cold-starts Kiro Crew's own servers and nothing else.

## Diagnosis

`dashboard/handlers/sessions_parts/live_turn.py::api_session_directive` recognises the pre-call-input body (`kind` present, `tool` absent) and refuses it as `stale_mcp_backend`, with a warning that names the cause (an MCP server running older code than the gateway) and the fix, instead of the generic `not_derivable` that pointed operators at the directive tools. `kirocrew doctor` (`doctor_checks.mcp._doctor_mcp_gateway_daemon`) prints the daemon's pid, owner and fingerprint beside this install's, and records an issue when they differ. The exception is a daemon whose fingerprint comes from the other rule (`code_fingerprint.same_scheme`: a git revision against an `mtime:` stamp) while a live gateway owns it: that daemon belongs to another install on the machine, so doctor prints it as information and records no issue. One with no live owner still records the issue. The same read is `daemon_control.describe_daemon`. Doctor calls `daemon_control.describe_daemon_detailed`, which keeps the probe's outcome (one of `PROBE_OUTCOMES`) so it prints "not running" only for `absent` (nothing listening) and names every other failed probe as unreachable or unverified with its reason; `describe_daemon` and `stop_daemon` read the same probe and are unchanged.

The backend lifecycle log lines end in join keys from `mcp_gateway/lifecycle_log.py`, so the lines of one backend can be joined without parsing their text. `backend_generation_id` is minted once per backend process in `spawn_backend` and lives on `Backend`; a respawn is a new process and a new generation. `attempt_id` is minted with it and again when `_retry_after_rehandshake` re-sends `initialize` to the same process. `event` and `reason` come from the bounded `EVENTS` and `REASONS` sets (a name outside them is logged as `unknown`), and a line that only starts something carries no `reason`. The lines: spawn (`initialize_started`; a respawn is a new spawn), both initialize successes (`initialize_succeeded`), `_fail_init` (`initialize_timed_out` from the deadline, `initialize_failed` otherwise, and for a refused re-sent `initialize`), the rehandshake (`initialize_started` again, under its new `attempt_id`), the transparent-respawn rebind in `daemon/replacement.py` (`reconnect_succeeded`, the new backend's keys plus `previous_backend_generation_id`, the dead one's, so a chain joins across the respawn), the shutdown SIGKILL escalation (`forced_exit`), the heartbeat's wedge lines, `daemon/sweepers.py`'s recycle line and the line naming a backend's own exit (all `backend_gone`; `heartbeat_recycle_reason` names a wedge `deadline`, and a `gone` backend `process_exit` when it was reaped or `transport_closed` when only its ping write broke; the own-exit line says `process_exit` once the process is reaped and `transport_closed` while only its stdout has closed). The ids are random hex, carry no user data, server name, path or command, and no decision reads them.

A backend that dies without the gateway ending it is named once at WARNING with the last lines it wrote to its stderr (`Backend._report_backend_exit`), because the daemon runs at INFO and `_pump_stderr` logs each stderr line only at DEBUG: without it a server that printed its reason and exited leaves only `exit rc=N` behind, and a connection-private one leaves no line at all. The pump keeps the last `_STDERR_TAIL_LINES` (20) lines in `Backend._stderr_tail` as the server wrote them (`backend_wire._keep_stderr_line`), not redacted one by one, because a line redacted on its own loses the context, such as a PEM header, that the joined tail needs to recognise a secret spread over several lines; only the DEBUG line is redacted per line, and the field is left out of `Backend`'s repr. A PEM block, from the line carrying `pem_scan.HEADER_PREFIX` (`-----BEGIN `) through the line carrying `-----END `, is kept as one `_STDERR_PEM_WITHHELD` line, so no body line enters the ring, even once a key longer than the ring would have pushed its header out; a block that never closes withholds the rest of the stream. Every other line is judged whole and only then made one printable line and capped at `_STDERR_TAIL_LINE_MAX` (500) characters, blank lines dropped, so the ring holds at most 20 lines of 500 characters however long a line on the pipe is (`READ_BUFFER_LIMIT_BYTES`). A line whose secret the cap or the collapse would cut out of the kept text is kept in its redacted spelling, so no fragment of it is left at the cut. One residual: a secret wrapped from the cut-off end of an overlong line onto the next line is judged without the part the cap removed. Five places see the process go with no `_dead_reason` recorded first, and each names it: the stdout pump's end; the heartbeat's reaped check; `shutdown` finding the process already reaped; and the first-`initialize` deadline (`_init_deadline`) and the respawn prime's timeout (`prime_initialize`) finding it reaped. `shutdown` is how an eviction (`pool.get_or_create` replacing a dead entry for a new attach or a co-tenant's respawn, the idle and LRU sweeps) meets a backend whose stdout a helper it spawned keeps open, so the pump never ends, and it drops the backend before the heartbeat could name it. The two handshake timers meet the same backend when the server dies inside the handshake, and name it in place of their timeout: the deadline's queued stubs get `backend gone: exit rc=N` and the prime raises `BackendGone` with `exit rc=N`, as when the pump sees that death. None of them names a death the gateway caused: that death records its reason before the process goes, or comes after `Backend._gateway_ending` is set. `shutdown` sets it before it closes stdin and `recycle_if_idle` before its kill, and it stays set when that act is cancelled (an eviction's unshielded `shutdown`, the daemon's teardown cancelling a bridge) or yields before it records its reason (the Windows kill runs `taskkill` in an executor). A death the gateway decides on (a wedge, an initialize timeout of a live backend, a recycle) is logged with the gateway's reason and no tail. Every waiter is answered with the `backend gone` error first, in the tick the reason is recorded, as for any other death; only then does the stderr drain get `_STDERR_DRAIN_WAIT_SECS` (0.5 s) to finish, since the pipe closes with the process but not in step with stdout and the last lines carry the verdict, and the line is written even when `shutdown` cancels that wait. One residual: a death a write meets first is not named. A forward, a handshake write or the heartbeat's ping that hits the dead process's stdin before anything sees the process go records `stdin closed: ...` or `heartbeat ping write failed: ...`, so the five places then find a reason recorded and the server's stderr reaches only the DEBUG log. That takes a write between the process's exit and the first of the five to look: one loop tick when the pump sees EOF with the exit, up to a heartbeat interval when a helper keeps stdout open but not stdin. The line's tail is `agent_sdk.published_stderr_tail(Backend._stderr_tail, " | ", _STDERR_TAIL_LINES)`, the SDK's rule for a child's stderr tail, judged by `acp.stderr_tail.safe_stderr_tail`, the rule a harness's stderr gets: the kept lines are judged joined and with the breaks removed, the tail is withheld whole as `STDERR_WITHHELD` when the redactor rewrites either spelling, and otherwise every kept line is logged joined with ` | `, so the ring bounds the line. The gateway reaches it through `agent_sdk`, never `acp` directly (`scripts/check_agent_sdk_boundary.py`). The tail stays in the daemon's log: `_dead_reason`, and so the `backend gone: ...` error every attached stub is sent, keeps the gateway's own `exit rc=N`, `stdout EOF` or `process exited rc=N`, because a pooled backend's stubs belong to several sessions and what the server printed can hold one session's request. The line's `backend_generation_id` joins it to the heartbeat's recycle line.

## Overload is not death

The watchdog (`GatewayManager._run_watchdog`) supervises the daemon it owns by two signals: process exit, and a periodic ping. `_liveness_probe_loop` pings every `_LIVENESS_PING_INTERVAL_SECS` (30 s) and, after `_LIVENESS_MAX_CONSECUTIVE_FAILURES` (3) consecutive misses, returns a zombie verdict that the race turns into SIGTERM→SIGKILL and a respawn. The ping catches the silent zombie (accept loop dead, Python process alive) that `proc.wait()` cannot. It cannot, on its own, tell that zombie from a daemon whose event loop is merely saturated: under a ~1000-session fan-out the daemon has carried 100-185 connections in flight, a short ping queued behind them times out three times running, and the watchdog killed a daemon that was serving the whole time — ten times in thirty-five minutes, each kill severing every attached session's kirocrew-core transport and cold-starting every pooled backend. The two conditions call for opposite actions, so a cycle counts as a miss only when the daemon answered NEITHER probe.

**One escalated probe is what separates them.** Each cycle asks twice: the fast ping, bounded per step at `_PING_TIMEOUT_SECS` (2 s) — the bound the ordinary call sites keep, and the bound `_ping_raw` gives up at, so a late pong is otherwise never even seen — and then, only if that missed, ONE further probe at `_LIVENESS_ESCALATED_TIMEOUT_SECS` (20 s) as a SHARED whole-round-trip bound rather than 20 s per step. A daemon that answers either probe is alive and the run of misses resets; only a cycle in which neither answered counts toward `_LIVENESS_MAX_CONSECUTIVE_FAILURES`, and there is no further reprieve past the third. So a verdict costs at worst 3 × (30 s interval + 6 s fast probe + 20 s escalated probe) = 168 s, cannot arrive faster than the three intervals (90 s), and `_SHUTDOWN_GRACE_SECS` (20 s) more elapses before the SIGKILL. The full argument for the escalation — why it must reach every step but not multiply per step, the deliberate one-miss asymmetry on the adopted path, and which call sites keep the fast bound and why — is [§The adoption gate](#the-adoption-gate).

## Respawn backoff is the ladder's L4 rung

The watchdog's respawn delay is read from the shared recovery ladder, not held
here: `_RESPAWN_BACKOFF_START_SECS` / `_RESPAWN_BACKOFF_MAX_SECS` are
`recovery.ladder.LADDER.layer(L4_GATEWAYD).base_secs / max_secs` (1s / 60s), and
every doubling goes through `GatewayManager._next_respawn_backoff`, which doubles,
caps and applies equal jitter (`[raw/2, raw]`) so two supervisors that lost their
daemons together do not respawn in lock-step. The two names survive because the
stub mirrors the cap by name (`_SUPERVISOR_RESPAWN_BACKOFF_MAX_SECS`) and
`test_stub_reconnect_budget.py` pins the mirror; L4 is `pinned` in the ladder
for the same reason -- the stub's 600s reconnect budget is three kill->respawn
cycles that each include this cap, so the `agent.recovery_backoff_*` knobs
never move it. After each successful respawn the watchdog records
`kirocrew.recovery.restarts{layer=L4_gatewayd}` and one L4 failure on the
ladder; a SECOND respawn inside the 600s window escalates to L5, which is one
notification -- the loop keeps supervising, and an automatic gateway restart is
out of scope. Thirty seconds alive resets both the local backoff and the
ladder's count. See [session.md § Recovery ladder](session.md#recovery-ladder-recoverypolicypy-recoveryladderpy).

## A failed start is retried by the gateway

`GatewayManager.start` arms the watchdog only when it spawned a daemon or adopted one, so a start that returns False (a daemon owned by another live gateway, a draining incumbent, a spawn whose endpoint or ping never answered, the election rounds spent) leaves nothing inside the manager that will ever start again. The gateway owns that retry: `slack/gateway_runtime/mcp_broker.py::_init_mcp_gateway` keeps the failed manager in `_mcp_gateway_pending` and starts `_retry_mcp_gateway_start` (task `mcp-gateway-start-retry`). It logs one WARNING, then awaits `start()` on that SAME manager after each `_mcp_gateway_start_retry_delay(attempt)`, which is `LADDER.layer(L4_GATEWAYD).backoff_secs(attempt)`: 1s doubling to the 60s cap with equal jitter and no attempt cap, the rung the watchdog respawns on. Reusing the manager keeps its lifetime `_MAX_STAND_DOWN_REQUESTS` budget and its election gates across attempts, so two gateways cannot trade the socket by retrying. The first start that returns True goes through `_mark_mcp_broker_ready`, the same publish a boot start makes: `_mcp_gateway_manager`, `DashboardState._mcp_gateway_manager` (wired at boot with no broker), the overlay refresher, the approval persist and the `broker ready` line. Until then `_mcp_gateway_manager` stays None, which is what every reader takes as "no broker", and each stub uses per-session exec. `_stop_mcp_broker` cancels the retry before anything else and shuts the pending manager down as well as the live one, so a daemon an attempt spawned before the cancel is terminated with the gateway; the sharing toggle stops a pending retry before it builds a new manager, so two managers never contend for one socket.

## Overload is admitted, not forked

A daemon that stays alive under a fan-out still has to decide what to do with a thousand `ensure_backend` frames arriving together. Forking on demand would turn a burst into hundreds of concurrent `create_subprocess_exec` calls on one loop, each reading the interpreter tree off one saturated disk, with every refusal spawning a per-session exec that makes the disk busier still. The contract is **admission before allocation**: `mcp_gateway/host_budget.py::HostBudget` (every backend the daemon is answerable for -- pooled, private, and the fallback exec a rejection causes -- is charged before its fork and released when it is reaped, never when `shutdown` returns), `mcp_gateway/admission.py::SpawnGate` (one daemon-wide count of spawn+initialize windows in flight, in start order past it (`kiro_crew.start_priority.StartOrder`, the order the gateway's own start queues follow: a spawn a person's session start is waiting on first, FIFO within a priority, a background spawn passed at most four times), fixed capacity behind a `set_capacity` seam, permits whose exactly-once `settle` is separate from their idempotent `release`, a detached initialize watcher so `ready` is never delayed and an unused prewarm is never read as congestion) and `BackendPool.reserve_resident_slot` (the `max_backends` check moved in front of the fork). The order inside `_acquire_backend`'s spawn closure is permit → budget → slot → fork, released in reverse; the only step that waits is the gate, and a gate waiter holds nothing another waiter needs, so the wait-for graph is acyclic. The gate is FIRST for that clause: a charge taken before the wait prices a process that does not exist for as long as the wait lasts (up to `spawn_queue_wait_secs`, 600 s), so a deep enough queue exhausts the ceiling with nothing running and refuses the next stub `capacity` -- which authorises no fallback -- on an idle host. The daemon's drain closes admission first. A connection that keeps writing while its acquire waits is bounded too: `_await_answering_pings` parks every non-ping frame in one per-connection deque that ONLY the main loop drains, and the main loop cannot run until the wait returns, so it counts both frames and bytes against `_MAX_PENDING_FRAMES` / `_MAX_PENDING_BYTES` and past either bound cancels the pending acquire and drops that ONE connection, leaving co-pooled sessions untouched. Same guard class as `backend._STUB_INBOX_MAXSIZE` in the reverse direction. Both dimensions are load-bearing (a count bound alone admits that many maximum-size frames; a byte bound alone leaves the per-object overhead of millions of tiny frames unaccounted), the byte bound follows `read_buffer_limit_bytes` upward so one frame the reader was willing to return can never trip it alone and is floored at that key's shipped default so tuning it DOWN cannot tighten the park, and the overflowing frame is parked before the bound is read so no frame is ever dropped while the peer is told nothing. The protocol half -- `spawn_queue` in `REGISTERED_CAPABILITIES`, `wait_budget_secs` on `ensure_backend`, `queued` keepalives, classed `rejected` frames (`capacity` / `compat` / `isolation`), pings answered while an acquire waits, the stub's silence timer and its typed `-32001` capacity error -- is specified in [`docs/architecture/mcp.md`](../../architecture/mcp.md#admission-before-allocation), and the config keys (`spawn_concurrency_initial/min/max`, `spawn_queue_wait_secs`, `initialize_timeout_secs`, `host_budget_max_procs/rss_mb/fds`, all `restart=True`, all on the daemon's argv from `GatewayManager._spawn_once`, which also samples available memory for the `0 = auto` ceilings) in [`config.md`](config.md).

A stub that disconnects while its backend still owes it a reply has every such request cancelled, and when it was the last consumer `_teardown_connection` kills the backend (`recycle_if_idle`), because the cancel is best-effort and abandoned tool work must not run on. Only work a cancel might fail to stop counts: `backend.has_recyclable_in_flight` ignores a ping and the read-only listings (`_RECYCLE_EXEMPT_METHODS`: `ping`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`). The upstream `initialize` never counts, because it is pending under the `__init__` sentinel rather than the stub's uuid. Killing a backend for a listing threw away a backend that had just finished starting, and the client's retry then paid a fresh spawn at the back of the gate queue -- a client that gives up on a slow start once would give up every time. The backend stays pooled instead and the retry reattaches to it. `test_gatewayd_more_coverage.py::TestDisconnectTeardown` pins both halves: tool work still recycles, an abandoned ping or listing does not, and the exempt set equals the one listed here.

## The gate's capacity is moved, not configured

`spawn_concurrency_initial` is where the gate STARTS; the live capacity is owned by the gateway's adaptive concurrency controller ([`adaptive-concurrency.md`](adaptive-concurrency.md)). It moves it through one more one-shot control frame on the uid-gated socket, beside `claim` / `abort` / `stand-down`: `{"type": "set-spawn-capacity", "capacity": n}` (sent by `GatewayManager.set_spawn_capacity`, over `_control_roundtrip`) is answered by `daemon/control.py::_apply_set_spawn_capacity` with `{"type": "spawn-capacity", "capacity": <what took effect>, ...gate snapshot}` after `admission.gate.set_capacity(n)`, or `spawn-capacity-rejected` for a frame with no usable integer (a non-number, a boolean, `NaN`, and `±inf` -- which `json.loads` produces from `1e400` and `int()` refuses) or a daemon with no admission. Every value earns one of those two answers, because an exception raised here escapes to the connection handler, which drops the control connection with no reply at all: the controller would then keep retrying a value against a daemon that never answers. The gate clamps to `[spawn_concurrency_min, spawn_concurrency_max]` and never revokes an in-flight spawn, so the reply reports the clamped value and the controller keeps a value the daemon did not confirm PENDING and retries it on its next tick. The verdict that moves it is the gate's own track, which never reads the dashboard gateway's loop lag: critical memory, gate init failures or slow inits (each sufficient alone) halve the capacity (to no lower than the floor); a clean window earns `+1` when the gate's own `success` outcomes and its queue say there is demand, and a cut gate below its fresh-start value also climbs `+1` per clean window once none of its signals has fired for the idle-recovery window, demand or not; memory at the critical line for two samples pauses the gate at its floor (the execution cap is never paused). A daemon that never receives the frame runs at its configured initial forever -- the fixed-capacity contract above is the floor the controller builds on, not something it replaces. The evidence it moves on comes from the gate too: besides its outcome counters, `SpawnGate.snapshot()` reports `slow_inits`, the successful spawn+initialize windows (grant to `success` settle) in the last `SLOW_INIT_WINDOW_SECS` (60 s) that took at least `SLOW_INIT_FRACTION` (80 %) of their own initialize deadline, which the controller reads as `gate_slow_inits`; `test_mcp_gateway_spawn_gate.py::test_a_success_near_its_own_deadline_counts_as_slow` pins that slowness is relative to each init's own timeout and the window ages out.

## A dead generation's pooled backends are reaped by whoever finds its record

Pooled backends are session leaders, so a daemon that dies without running `pool.shutdown_all` leaves them alive. The heartbeat therefore publishes them in `<socket>.backends` (`mcp_gateway/backend_record.py`), one `<pid> <start-id>` line each, the start id read by `platform_compat.get_process_start_id` once right after spawn, before the first await (`Backend.start_id`), and published from there by the heartbeat (`BackendPool.live_backend_identities`) rather than re-read: a read at heartbeat time could meet a backend that has already exited and had its pid recycled, and would publish the stranger's identity. Three readers reap it. The manager does when it is the one that SIGKILLed a wedged daemon (`_terminate_process`), and on Windows after every terminate: there SIGTERM is `TerminateProcess`, so no drain ran. `kirocrew stop` / `restart` (`daemon_control.stop_daemon`) does the same on Windows once the daemon is gone. The next daemon does at boot, right after it wins the singleton lock: the lock proves no daemon serves that socket, so a record still on disk was left by a generation that crashed, was OOM-killed or was SIGKILLed from outside, and the replacement's first heartbeat would otherwise overwrite the only list of what it leaked. Before binding it only renames the record aside to `<socket>.backends.reaping.<pid>.<ns>` with `os.replace` (`backend_record.detach`). No bytes are rewritten, so a failure (a full disk) leaves the record exactly where it was, never truncated, and the daemon then refuses to start (it releases the lock and raises) rather than serve over a record its first heartbeat would overwrite; the manager's respawn retries, and stubs use per-session exec meanwhile. The kills run as a tracked background task, so the manager's socket-ready budget does not depend on how much leaked (one `taskkill` per entry on Windows). A reap interrupted by shutdown leaves its `.reaping.*` file, and the next boot reaps every such file it finds. A daemon that loses the lock returns before any of this, so it never touches the record of the daemon that is serving.

A reap SIGKILLs the process group of an entry only while the live process under that pid still has the recorded start id, through the repository's identity-pinned kills rather than a compare followed by a pid-addressed kill: on POSIX `process_identity.isolated_group_of` reads the start id on both sides of the group lookup and the group is then signalled by id (`platform_compat.kill_process_group`); on Windows `platform_compat.kill_process_tree_pinned` holds the verified handle across the terminate, off the event loop. It removes the record afterwards. A pid that is gone, recycled onto another process, or written bare (by a daemon from before the start id was recorded, or when the id could not be read) is unknown identity and is left alone; each reap logs how many groups it killed and which pids it left. SIGKILL rather than SIGTERM, because a wrapper that ignores stdin EOF commonly ignores SIGTERM too. What a reap does not reach: a group whose leader has already exited (no live process left to confirm the identity against), and a descendant that moved to a session of its own. `runtime_reconcile._mcp_backend_pids` reads only the pid field.

## A private backend is reaped by the pool, never inline

A connection-private backend (a stub that could not pool) outlives nothing: when its stub disconnects, `_handle_connection`'s `finally` (`daemon/connection.py::_teardown_connection`) hands it to `pool.spawn_shutdown(orphan)` -- the pool's tracked reap task, the same one `shutdown_all` joins -- and returns. An inline `await orphan.shutdown()` would be a backend nobody owns: daemon teardown cancels the connection handlers, so the cancel could land AFTER `release_exclusive` had dropped the backend from the exclusive map, leaving it outside `shutdown_all`, never meeting the SIGKILL escalation, with its pipe transports finalizing after the daemon returned. A reap the pool tracks completes before `shutdown_all` does, and `process.wait()` -- which asyncio resolves only once every pipe is closed -- is part of it. `test_mcp_gateway_pool_integ.py::test_real_stubs_without_poolable_get_their_own_backend` pins it from the outside: after `run_gatewayd` returns, none of the three private backends' pids exists any more (the inline form leaves all three alive).

## The daemon names the backend's cwd itself

Every stub the rewriter writes registers the same `--work-dir`: the gateway's default work dir `workspace_root()/_default` (`config.loader_locations._session_work_dir(None)`, baked into `launch_resolve.rewrite_kwargs`). The register frame carries it as `PoolKey.work_dir`, but the frame is not where the cwd comes from: any same-user process on the socket can send a frame, and the launch approval covers the command, the arguments and the env, not the cwd. So the gateway hands the daemon the exact directory its rewrite wrote into every stub: `mcp_broker` puts the rewrite's `work_dir` on `GatewaySpec.backend_work_dir`, and `manager._spawn_once` sets it in gatewayd's env as `KIROCREW_MCP_BACKEND_WORK_DIR` (`manager.BACKEND_WORK_DIR_ENV`), dropping any value the gateway's own env inherited. It rides the env, not argv, like the target map. `env_target_resolver` (`daemon/launch.py`) takes it through `_backend_work_dir` (one resolution, `backend._default_work_dir`, shared with the restore below) and returns it as the spawn's cwd, whatever directory the frame named, and the variable itself is not passed on to the backend. The daemon does not resolve the workspace root a second time, because a non-creating resolution does not reproduce every fallback of the rewrite's creating one (a saved root behind a file, or under a mount point the gateway cannot write, falls back to the default base only when creating). Only a daemon started without that variable resolves `workspace_root(create=False)/_default` itself. Like the agent socket above, the adoption gate does not compare it, so an adopted daemon keeps the work dir it was spawned with; a workspace moved since then reaches pooled backends at the next daemon (`kirocrew restart`). A frame naming a different one (compared after `os.path.normcase`) still gets its approved backend, in the gateway's directory, with one warning naming the server, the frame's directory and the one used. When the work dir cannot be resolved at all, the resolver falls back to the frame's `PoolKey.work_dir`, as before this change, so the stub keeps its pooled backend. The pre-fork re-check in `_acquire_backend` compares only the re-resolved command and arguments, as before this change, and the backend starts in the freshly resolved cwd. Under the pin both resolutions name the same directory, because the daemon's env does not change for its whole life, so the control-plane verdict judged that same cwd.

## A vanished default work dir is put back before the spawn

That default work dir is the cwd `spawn_backend` runs every pooled, private and prewarmed backend in, and only the rewrite pass creates it. Once it is removed, every cold spawn fails with `ENOENT` on its cwd and every stub falls back to per-session exec until a restart re-runs the rewrite. So `spawn_backend` runs `_restore_default_work_dir` off the loop before the per-process temp allocation and the fork (a spawn cancelled while it waits then holds no temp dir, which only the spawn-failure branch would reclaim): a missing cwd equal to that default (compared after `os.path.normcase`) is created again, last directory only, with one warning naming the server and the path. Any other missing cwd (one an injected `target_resolver` returned) is left to fail the spawn, because the unsandboxed daemon must not create a directory anywhere but its own default. A workspace root that is gone itself (an unmounted volume) is not rebuilt either, so the spawn fails and the stub falls back, which is the right result while the volume is away.

## A control-plane backend is pooled only for the gateway that owns the daemon

The Kiro Crew control-plane servers (`CONTROL_PLANE_BACKENDS`) dial a gateway with this data home's credential, so a pooled one must dial the gateway that owns the daemon and no other. The daemon's own environment cannot name that gateway. The gateway starts the daemon during boot, before its listener binds and exports `KIROCREW_BOUND_PORT`, and an inherited `KIROCREW_PORT` or `KIROCREW_BOUND_PORT` can be another gateway's. With no port variable the client chain still picks a port (a lone live marker, else the default), and that port can be a sibling gateway on this data home. So the owner tells the daemon its port.

The gateway that owns the daemon sends it. `GatewayManager.announce_owner_port(port)` sends `{"type": "owner-port", "port": N}` over `_control_roundtrip` and returns True only for the reply `{"type": "owner-port-set", "port": N}`. The port comes from the listener's own record of its bind, `DashboardState._listener_bound_port`, which `start_dashboard` and `start_api_server` write after the TCP site listens (the OS-assigned port under `--port auto`). `_wire_mcp_gateway_dashboard` announces it once the listener is up, as a tracked background task. A broker started after that (the sharing toggle) reads the same record in `_init_mcp_gateway` and calls `set_owner_port` before `start()`. Neither path reads `os.environ`, which may carry another gateway's port. When the manager knows the port, `_spawn_once` passes `--owner-port N` on the daemon's argv, so a respawn after the bind starts with it, and `start()` sends it again after the spawn or adoption. The pong carries `owner_port`, and on each liveness reconcile the watchdog sends the stored port again when that field differs. A miss logs at WARNING once per run of misses and never fails the boot. The WARNING names the remedy: stop a daemon that keeps refusing, and the gateway starts its own. The reconcile sends nothing to a pong without the field, which is from a daemon that predates the frame, or to a pong with `owner_pid` 0, from an unowned daemon that refuses every announce. The pong also carries `owner_port_unverifiable`. The reconcile sends nothing to a pong with `owner_port` 0 and `owner_port_unverifiable` True, because that daemon binds from its environment and refuses every announce. A pong without `owner_port_unverifiable` is from an older daemon and is reconciled as before.

A boot start can fail while the dashboard does not exist yet. `_init_mcp_gateway` then keeps the manager in `_mcp_gateway_pending` for `_retry_mcp_gateway_start`, and `_wire_mcp_gateway_dashboard` finds no published manager to announce to. So the wire also stores the port on the pending manager (`set_owner_port`), and the retry's successful `start()` sends it. The retry can also come up first, after the bind and before the wire. Then `_mark_mcp_broker_ready` finds a bound port and a manager with no `owner_port`, stores the port and announces it as a tracked background task. Either order reaches the daemon, and the watchdog reconcile is the backstop once the manager has the port.

`daemon/control.py::_apply_owner_port` accepts the frame only when all of these hold:

1. The daemon is owned (`_OWNER_PID > 0`). A daemon started without `--owner-pid` has no owner to check a sender against, and any same-uid process can reach its control socket. A sandboxed agent could open a loopback listener and announce its port. New control-plane backends would then send this data home's credential and session tokens to that listener and take its answer as the session's tool policy. So an unowned daemon refuses every announce.
2. `socketsec.get_peer_pid` reports the sender's pid. The connection has already passed the same-uid peer gate. With no pid, the frame's port is not taken, and on every platform the owned daemon binds from its environment instead of refusing pooled control-plane backends. It sets `gatewayd._OWNER_PORT_UNVERIFIABLE` through `_set_owner_port_unverifiable`, which wakes every waiting acquisition. The flag is set in two ways. On a platform with no peer-pid mechanism, where `socketsec.PEER_IDENTITY_SUPPORTED` is False, `run_gatewayd` sets it for an owned daemon before anything can connect, so no acquisition waits even before the first announce. On any platform, the first frame whose pid cannot be read sets it. On Linux, macOS and Windows the read can still fail on every frame: a macOS `LOCAL_PEERPID` getsockopt failure returns None, and so does a Windows pipe handle that does not resolve. That failure must cost lost pooling, not a broken session. The frame gets `owner-port-rejected` with a reason that says the daemon binds from its environment. Each such frame logs at WARNING and writes one `denied` audit row, as every other refusal does. The watchdog sends no port to that daemon again (see the pong field above), so these frames come only from a gateway start or an adoption. A verified port always wins. The flag matters only while `_OWNER_PORT` is 0, because `bind_control_plane_to_owner` reads a known port first, and the first verified announce drains the backends bound from the environment. So one transient failed read costs main's binding at most until the next verified announce, at the next gateway start or adoption.
3. That pid is `_OWNER_PID`, or `_OWNER_PID` is an exec supervisor of it (`platform_compat.is_exec_supervisor_of`, run off the loop: every process from the sender's parent up to the owner is a readable non-Python image). This is the rule `GatewayManager._owned_by_a_live_other` uses to adopt the daemon. It admits the successor that an in-app restart through a supervising launcher leaves running, whose adopted daemon still names the launcher as its owner.
4. The port is an `int` in 1..65535. A `bool` is not one.

Any other frame gets `{"type": "owner-port-rejected", "reason": ...}` and a WARNING. On that reply the manager logs one WARNING per run of misses and does not respawn or escalate. A later accepted announce replaces the earlier one, and a change logs at INFO. Both outcomes are audited as `mcp-gateway.owner_port`. The accepted port is `gatewayd._OWNER_PORT`, written only by `_set_owner_port`, which also sets the event that waiting acquisitions watch. `--owner-port` on argv is taken only with `--owner-pid`.

`env_target_resolver` passes each control-plane spawn environment through `daemon/launch.py::bind_control_plane_to_owner`. It sets `KIROCREW_BOUND_PORT` to `_OWNER_PORT` and drops an inherited `KIROCREW_PORT` that names another port (`port_resolution.drop_foreign_inherited_port`). On an owned daemon with no port it raises `OwnerPortUnproven`, unless the daemon has switched to environment binding (see the next paragraph). The resolver never answers `None` for that case: `None` becomes `_TargetUnknown`, a `compat` refusal with `fallback: true`, and the stub's `fallback_exec` would start the server inside the session's sandbox, where the Codex masks hide `run/` and `trust/` and every gateway tool of that session fails. Before the resolver runs, `_acquire_backend` waits on the loop for the port (`launch._await_owner_port`), so no resolver thread is held. The wait uses the acquisition's own `wait_deadline` (the stub's negotiated budget less the refusal margin), sends `queued` keepalives with `position` 0 to a queue-aware stub, and its pings are answered through `_await_answering_pings`. When the port arrives, resolution binds the target environment, and the cold-spawn path binds it again after the declared-env merge and secret resolution so a spec-declared port cannot replace the proven owner port. When the deadline passes first, the refusal is `OwnerPortUnproven`, a member of `_CAPACITY_FAILURES`: class `capacity`, `retry_after_secs` set, and no `fallback` on either wire shape. After a capacity refusal `stub_link` answers every request with a typed error for the rest of that stub's life, so the wait, not the refusal, is what a normal boot meets. The first wait per server logs at WARNING and later ones at DEBUG. The prewarm pass skips a control-plane key while the port is unknown and logs that at INFO, because no stub waits on a warm backend; the top-up sweeper's next pass warms it.

An owned daemon whose host reports the sender's pid takes the port only from a verified announce. Two daemons cannot verify one, and they bind pooled control-plane backends as they did before the announce existed. An unowned daemon has no owner, so no sender can prove that a port is its own, and the daemon trusts no announce. An owned daemon that cannot read a sender's pid cannot check the sender. `run_gatewayd` sets `_OWNER_PORT_UNVERIFIABLE` at start on a platform with no peer-pid mechanism, and the first frame whose pid cannot be read sets it on any platform. On both, while `_OWNER_PORT` is 0, `_owner_port_pending` is False, so `_await_owner_port` returns at once and the prewarm pass warms control-plane keys. `bind_control_plane_to_owner` leaves the environment exactly as the resolver built it, which is main's binding, and drops nothing. This branch runs only while no owner port is known, so an inherited `KIROCREW_BOUND_PORT` is never known to be this gateway's export. For example, gateway A's agent shell exports `KIROCREW_BOUND_PORT=5476`, and the operator runs `KIROCREW_PORT=5477 kirocrew gateway` in it. Both values stay, and the backend dials 5477, as on main. The bind returns 0, so the backend records `owner_port` 0. The first such bind per server logs at WARNING and names the cause. The gateway still verifies the per-port credential that each call sends, so a wrong port fails closed. On an owned daemon that set the flag, a later verified announce wins: `_apply_owner_port` drains on every change of port, the first one included, so the backends bound from the environment fail `bound_to_owner_port` and move to the draining list. An unowned daemon still refuses every announce and ignores `--owner-port`, after a gateway adopts it too. Third-party servers are not affected. Adoption does not change, because owner pid 0 is no rival. When `GatewayManager` adopts a daemon whose pong has `owner_pid` 0 and the `owner_port` field, it logs one WARNING. The WARNING says that the daemon refuses this gateway's port and binds pooled Kiro Crew control-plane servers from its own environment, which can name another gateway's port. It names the remedy, which is to stop the hand-started daemon so that the gateway starts its own.

The port can change while the daemon runs: an in-app restart through a supervising launcher keeps the daemon and its pool, and under `--port auto` the new listener announces a different port. Each control-plane spawn is bound again after the spawn gate's wait, from the port current then, and records it as `Backend.owner_port`. When an accepted announce changes the port, `_apply_owner_port` moves every pooled control-plane backend whose `owner_port` differs to the draining list (`BackendPool.drain_matching_to_bluegreen`), the blue-green path a credential rotation uses: calls in flight finish, and the heartbeat reaps the backend at refcount 0 or after `DRAIN_DEADLINE_SECS` (60 s). `reap_draining` starts a pool-tracked reap for every backend it removes from the draining list, even when teardown cancels the heartbeat during an earlier reap, so `shutdown_all` joins each one. Unlike that rotation it does not bump the drain epoch, so no other key's spawn in flight is discarded. `_acquire_backend` passes `launch.bound_to_owner_port` to `get_or_create` as `reusable`. A pooled entry that fails it is retired the same way and a fresh backend is spawned, and a spawn that was bound before the change and lands after it fails the same check inside `add`, under the pool lock the drain takes, so it is discarded and spawned again on the new port. Third-party backends are not retired. A connection-private backend is not in the pool, so the drain does not reach it. `_acquire_backend` applies the same check to a private spawn. A private spawn that fails it is reaped as a pool-tracked task that daemon shutdown joins and then spawned again, with the bound `get_or_create` uses (`_MAX_SPAWN_DRAIN_RETRIES`), and then refused with `OwnerPortUnproven`, class `capacity`. The respawn comes first because a stub that gets `capacity` on `ensure_backend` keeps that answer for its life.

A connection that is already attached holds its own reference to its backend, pooled or private, and the drain does not change it. So `_handle_connection` checks that backend with `bound_to_owner_port` before it forwards each frame. If the check fails, the handler raises `BackendGone` and takes the transparent respawn that a dead backend gets. The frame and its caller block, with the session token, never reach the old-port backend. The request gets the retryable `backend restarted mid-call` error. The respawn replaces a private backend through `acquire_exclusive`, which shuts the old one down. It detaches from a pooled one, which the heartbeat then reaps from the draining list.
