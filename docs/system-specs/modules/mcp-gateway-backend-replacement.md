# MCP gateway backend replacement (validating a process swapped under a live session)

A client freezes its MCP tool set when the session is created and never re-reads it. The gateway, meanwhile, can swap the PROCESS behind that session: when a shared backend dies mid-call, `gatewayd._respawn_backend_for_stub` spawns a fresh one, replays the captured `initialize`, and re-binds the stub so the transport never breaks and the session keeps its server.

That recovery is worth keeping. What it must not do is adopt a replacement that publishes something else. A server upgraded in place — or an `npx`/`uvx`-style launcher resolving to a different build — can answer with the same `protocolVersion`, `capabilities` and `serverInfo` while renaming a tool, changing an argument's type, or making a field required. `initialize` metadata does not describe a tool set, so a handshake that replays identically is not evidence that a pending call is still a valid call.

## The invariant

**A replacement is adopted only when what it publishes still supports every call the recovering session could already be holding, or when that session was told nothing.**

**What that buys, stated exactly.** The invariant governs ADOPTION, and adoption is the only lever this layer has. It does not make the session safe afterwards. A refusal answers the in-flight request with a terminal error and the stub reconnects — and a reconnect re-registers, replays `initialize` (which cannot see a tool set), and attaches to the same replacement, which was deliberately left in the pool. That new attachment has no anchor of its own, so the session's next stale-schema call is forwarded exactly as it would have been without this guard, one reconnect later.

So the durable effect of the guard is a stated, audited failure at a call boundary plus a reason the session is told, rather than a silent wrong call — not a session that can no longer make one. Closing that requires the client's frozen tool set to be refreshable, which is the stub-reconnect increment under Scope. This paragraph exists so the invariant above is not read as more than it is.

Three states, and the difference between the last two is the load-bearing part:

| The stub's dying backend | The replacement | Outcome |
|---|---|---|
| told this stub no listing this host could project | not asked | adopted — there is no claim to contradict, and the extra round-trip is not paid |
| told this stub a listing | publishes the same tool surface, or only adds to it | adopted — the recovery is transparent, as before |
| told this stub a listing | dropped or changed the schema of a tool in it, or cannot be asked | **refused**, logged, and SEL-audited |
| told this stub a listing | agrees, but the stub's owner was retargeted mid-respawn | **refused** — the comparison was about a principal that no longer owns the stub |

## What counts as the same tool set

`mcp_gateway.tool_surface` owns the projection, so every adoption point compares through one definition rather than inventing its own. It maps each tool's NAME to a canonical form of its `inputSchema` — exactly the part of a listing a call is built from.

A tool the replacement ADDS is agreement, not a change. The inclusion criterion throughout is "can this invalidate arguments a client already built?", and a name the client does not know cannot: no held call names it, and the frozen tool set could not call it either way. Reporting an addition would turn the commonest upgrade shape — a server that grew a tool — into a refused recovery for nothing. A tool that is GONE or whose schema MOVED is the opposite: a held call names it.

Excluded on purpose: `description`, `annotations`, `outputSchema`. None of them can invalidate arguments a client has already built, so comparing them would only cost recoveries at servers that reword a sentence between builds. Tool ORDER is out of the comparison by construction (the projection is a mapping); ordering INSIDE a schema is not normalised, so a reordered `required` array reads as a change — telling a reorder from a rewrite needs a JSON-Schema semantic model, and the conservative reading costs one reconnect while the permissive one costs a call against a schema that no longer exists.

Model visibility IS in scope, as a filter. Only tools whose `_meta.ui.visibility` admits the model are projected, read through the same `apps.visibility_allows` the agent-facing listing filter uses so the two cannot drift. It has to be in scope because visibility is enforced at LIST time only — `AUDIENCE_MODEL` is consulted in exactly one place, `strip_model_hidden_tools`, and nothing re-checks it when a model-originated `tools/call` arrives. A replacement that withdraws a tool from the model therefore leaves a frozen client still listing it, and its call would be forwarded and executed with the same name and the same schema.

Filtering rather than comparing a per-tool flag is what makes both directions come out right: a tool the client HELD and the replacement withdraws leaves the projected set and reads as `gone`, the refusal that case needs, while a tool that was app-only and becomes model-visible ENTERS the set and reads as an addition, which is agreement for the same reason any addition is.

An unreadable listing projects to `None`, not to an empty surface, so "we could not read what it named" stays distinguishable from "it named nothing". `None` on the OLD side is agreement (no anchor); `None` on the NEW side, when an anchor exists, IS the change. An EMPTY surface is a claim like any other — a replacement that cannot be read contradicts "the server named no tools".

Retention is bounded by construction, not by the server. A surface is held per stub for that stub's lifetime and one `tools/list` frame may be as large as the transport allows (64 MiB by default), so schema VALUES are stored as fixed-width SHA-256 digests rather than as canonical text — the comparison only ever asks whether two schemas are equal. A listing over the tool-count or name-length budget is refused as unmeasurable rather than truncated to fit: dropping tools to make it fit would make a dropped tool's schema change read as agreement, which is the silent adoption this whole module exists to prevent. The budget sits well above any real server, so it is a ceiling on a pathological or hostile listing rather than a limit a genuine one meets — and a server that does exceed it simply never gets validated, never spuriously refused, because an unmeasurable OLD side is agreement.

The visibility filter runs FIRST, ahead of every other per-entry rule, and that ordering is load-bearing rather than incidental. Every other rule answers "unmeasurable", which clears the anchor and leaves the next respawn unvalidated — so judged before the filter, a tool the model cannot even see (one absurd name, one entry past the budget, one unserialisable schema) would switch the guard off for every tool it CAN see. A hidden tool must not be able to do that, so each rule is scoped to the model-visible set and the budget counts only what is retained. There is deliberately no cap on the RAW entry count for the same reason; the per-entry work is bounded by the transport's own frame limit, the same bound `apps.strip_model_hidden_tools` already lives with while iterating this identical listing.

## Pagination

`tools/list` is paginated, and a page is not a tool set. Both sides refuse to conclude from one:

* **Recording.** An anchor is kept only from a listing that is the complete set — the request carried no `cursor` AND the result carries no `nextCursor`. Either mark clears the stub's entry instead. The request side is load-bearing and cannot be derived from the response: a FINAL page carries no `nextCursor`, so on the response alone it is indistinguishable from a complete listing, which is why `_PendingRequest.list_paginated` is captured at forward time.
* **Probing.** `Backend.probe_tool_surface` asks without a cursor and treats a `nextCursor` in the reply as unmeasurable rather than following the chain — a recovery path must not issue an unbounded request sequence.

The consequence is deliberate: a paginating server keeps no anchor, so its respawns are never validated and never falsely refused, which is exactly the pre-existing behaviour. Recording a page instead would compare the last page against the probe's first page and terminate a stub whose replacement had not changed at all — a guard that fires on servers doing nothing wrong is worse than no guard. Validating a paginated server needs the anchor to accumulate pages and the probe to walk them under a bounded page budget; that is a separate change.

Tool names in the change description are the SERVER's strings and the description is written to a log line and to an SEL audit field, so each name has its line-breaking characters escaped and its length bounded before it goes in. Without that, a name carrying a newline would end the record early and open a second one the server controls — a forged entry in an append-only trail. "Line-breaking" is defined by CONSEQUENCE rather than by Unicode category: C0 controls, DEL and C1 controls, plus U+2028 and U+2029, which sit far outside those ranges and which Python's own `str.splitlines` breaks on. A ratchet test holds the predicate to whatever `splitlines` splits on, so a future gap fails in CI rather than in a forged record.

## Where the two sides come from

The **anchor** is recorded, never fetched: `Backend._maybe_intercept_ui_result` projects every model-facing `tools/list` result into `Backend._served_tool_surfaces[stub_uuid]`. It projects BEFORE the app-visibility strip mutates the listing, but the outcome does not depend on that ordering: the projection applies the same model-visibility predicate itself, so it records the set the client ends up holding either way. Recording before the strip simply keeps this call site independent of whether the strip ran.

The map is keyed **per stub**. A `PoolKey` carries no caller identity, so one backend legitimately serves several sessions; a single scalar would let the last listing served to ANY of them stand in for what a particular session was told. For a server that answers every caller alike the two are the same value, but the comparison must be about the session being recovered. The map is bounded by the attached-stub set — `detach_stub` prunes an entry with the rest of that stub's per-stub state, which is why the respawn path reads the anchor BEFORE it detaches, alongside the subscription URIs it already captures for the same reason. An unprojectable listing CLEARS the entry rather than leaving the previous one: the client just received a listing this host cannot read, so an earlier readable claim no longer describes what the session holds.

The claim **follows the session, not the process**. Once a replacement is validated and the stub rebound to it, `Backend.carry_served_tool_surface` copies the anchor onto the replacement. Without that the anchor dies with the backend it was recorded on, the replacement starts anchor-less, and the SECOND respawn of the same stub has nothing to compare — so the guard would cover only the first process swap in a session's life while the client's frozen tool set is still the one from its original listing. What carries is what the session was TOLD, not what the replacement published: the two agree on the tools the client holds, but a replacement may legitimately offer more (an addition is not drift), and recording those would let a later respawn refuse over a tool no call could name. The copy happens after the final ownership re-check, so a refused adoption never seeds a surface onto a backend the stub will not use.

The **replacement's side** is fetched fresh: `Backend.probe_tool_surface` asks the primed backend for `tools/list` on an internal stub (`INTERNAL_STUB_PREFIXES`), which keeps the reply routed to the gateway rather than to a session and keeps the strip's SEL audit from firing for a synthetic listing nobody asked for. Both sides therefore reach the projection as the server sent them, and the projection is the one place model visibility is applied. It never raises — it is called from a recovery path — and every failure mode (timeout, JSON-RPC error, unprojectable listing) reduces to `None`, which a caller cannot confuse with agreement.

Both sides belong to the caller captured when the failing request arrived: the anchor is the listing that principal was served, and the probe asks as that principal. A `claim` frame can retarget the connection's identity on any await, so ownership is re-checked against that captured caller (`_rekey_refusal_reason`) and a mismatch refuses — across a rekey the comparison describes somebody who no longer owns the stub, and on a caller-scoped server it says nothing about what the live owner would be served. Re-probing would race the same way, which is why the answer is refusal on the same terms the subscription replay already uses. A connection that cannot answer the question at all (`None`) is not read as agreement; it simply cannot be checked.

The check runs at TWO points, and only the second is the guarantee. Beside the comparison it is an optimisation, avoiding the attach and the replay when the owner has already moved. `attach_stub` and `replay_resource_subscriptions` both await, so the authoritative re-check is the one immediately before the return — everything from there to the return is synchronous, so it leaves no gap. That late refusal detaches the stub it had just attached, or the backend's refcount would hold a stub about to be told the adoption failed. Both points share one refusal helper so the log line, the audit event and the client's message cannot drift apart.

This is **not a cache**. `app_call` re-fetches `tools/list` on every call precisely because a server may revoke a tool's visibility at any moment, and nothing here weakens that: the recorded surface authorizes nothing and is never served to anybody. It answers only "does the replacement still match what we already said?".

## Why refusal is the remedy

The frozen tool set lives in the client, and no gateway-side write can refresh it. `notifications/tools/list_changed` is already fanned out to every stub (`backend._GLOBAL_BROADCAST_NOTIFICATIONS`), but a freshly spawned process has no reason to emit one and the client is not documented to re-list on it — so propagation is a no-op here, not a missing mechanism. That leaves adopting a process whose divergence the session cannot see, or refusing and saying why.

Refusal lands on the give-up path this function already has: the caller answers the one in-flight request with a terminal error and the stub reconnects. A stated failure at a call boundary, instead of a wrong result.

The reason reaches the SESSION, not only the log. A refusal raises `_ReplacementRefused` rather than returning the plain `None` the other give-ups use, and the caller puts its message into the terminal JSON-RPC error — so the client sees "the MCP server was replaced and its tool set changed (`gone=...`)" instead of a "backend gone" indistinguishable from an unrecoverable spawn. The client is the only party that could act on knowing this, and it can read neither the log nor the SEL trail. That message carries server-chosen tool names, which is safe for the same reason the log line is: they are escaped and bounded before they get there.

The fresh backend is deliberately **left in the pool**. Its tool set is wrong only for a session holding the old declaration; a session that starts afterwards reads the new one correctly, so tearing it down would punish every future session for this one's frozen view.

Both outcomes are SEL-audited as `mcp-gateway.respawn-toolset`, `denied` on a refusal and `allowed` on an adoption, through one `_audit_replacement_validated`. Two-sided because both are access decisions about which process may answer a live session — the same shape as the peer-identity and app-call trails — and because recording only refusals would leave the event this guard exists to make visible, a process gaining authority over a session that did not ask for it, as a rotating log line and nothing more. The `allowed` event is emitted at the point authority actually transfers (stub attached, subscriptions replayed), not at the comparison, so it never records authority a later give-up revokes. An adoption with no anchor is recorded too and says so: that is precisely the case where nothing checked. The `detail` field carries which tools moved on a refusal and whether the tool set was verified on an adoption — the one thing that separates a server upgrade from a server answering differently per caller. The names in it are bounded; a listing is not put in a log line.

## Scope

This covers the daemon's transparent respawn, the path that previously compared nothing. The stub's reconnect after a broker restart (`stub.StubSession`) refuses a daemon generation whose replayed `initialize` result differs, but that check cannot see a tool set: the stub holds no listing, and acquiring one would need a synthetic `tools/list` from the stub process. Extending the reconnect to compare through `tool_surface` is the remaining increment.

## Tests

`test_mcp_tool_surface.py` pins the projection (order-insensitivity, description-only changes, an addition alone, the concrete regressions, every unmeasurable shape, the fixed-width schema digest and the tool-count / name-length budget, a tool withdrawn from or newly offered to the model, control-character and length bounding of the reported names) plus the per-stub recording (the anchor is the model-visible set, one stub cannot overwrite another's anchor, detach prunes it, an unreadable listing supersedes a readable one, a page leaves no anchor on either the first-page or the final-page spelling, an internal probe records nothing) and the probe (including a paginated reply establishing nothing). `test_mcp_gatewayd_coverage.TestRespawnBackendForStub` pins the decision: drift is refused before `attach_stub` with the reservation still released, an unaskable replacement is refused, an unchanged tool set is adopted, no anchor skips the probe entirely, a co-pooled sibling's listing is not this stub's anchor, the anchor is read before the real `detach_stub` prunes it, a validated surface survives into the NEXT respawn of the same stub, and an owner retargeted mid-respawn is refused even when the tool set agrees (with an unchanged owner as the control, and a case where the claim lands inside the adoption await so only the late re-check can catch it).
