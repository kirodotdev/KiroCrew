# Session Work Ledger

Owners: `kiro_crew.session_ledger`, `kiro_crew.mcp_tools.ledger`, and the dashboard ledger routes. Cleanup for both on-disk ledgers — this one and the conductor work ledger in `kiro_crew.work_ledger` — is owned by `kiro_crew.ledger_sweep`; see [Cleanup](#cleanup).

## 1. Purpose

`kiro_crew.session_ledger` provides durable, per-session work state for long-running work. The state record holds a goal, phase, resumable next step, rejected approaches, artifact pointers, and a bounded event history. This separates resumable state from transcript context; `mcp_tools.ledger.schemas()` describes the record as authoritative over prior-cycle memory.

## 2. Storage, identity, and lifecycle

Each recorded ledger lives below `<data_home>/ledger/` in a directory containing:

```
slot_key   # original ledger key breadcrumb
state.json # complete state record
.lock      # dedicated cross-process lock inode
```

`session_ledger.record()` creates the directory and writes `state.json` atomically. `session_ledger._locked()` keeps the lock file separate from the replaced state file, so replacing state cannot let concurrent writers lock different inodes.

`session_ledger.ledger_key()` removes only dashboard namespace and prefix spellings before storage. `session_ledger._store_name()` combines a readable fold with a digest of that exact key; `test_distinct_channel_keys_never_share_a_ledger` guards against the lossy-fold collision that would otherwise let one channel session overwrite another. `session_ledger.ledger_dir()` rejects hostile raw keys and requires the resolved directory to remain below the ledger root, preventing traversal through a folded name.

Closing a dashboard tab preserves the ledger. Permanent history deletion also
preserves it. A transcript can be created or restored by another process after
any in-process owner check, and no request-local fence can make ledger deletion
atomic with that claim. A stale ledger is reversible; deleting a successor's
resumable state is not. `purge_matching()` is the one explicit synchronous
maintenance primitive, not part of the history-delete request path, and its one
caller is the operator sweep in [Cleanup](#cleanup).

The same history-delete funnel separately releases cron ownership. The single
delete performs a strict cron-owner scan before unlink and another after it; bulk
clear batches both scans. `_delete_history_session()` binds the exact owner keys
from that scan and a readable `linked_session_key` into the immutable
`_HistoryDeleteClaim` while holding the canonical-plus-legacy transcript lock
set. `_remove_slot_for_history_key()` first revalidates the captured slot,
transcript, task and session generation, then cancels the old turn and conditionally
destroys only that manager generation. After those awaits it rechecks both live
slots and SessionManager's live/reserved keys, and hands only the proven retired
owner keys to `CronService.release_jobs_owned_by()`. Pins, ledgers and autocompact overrides are
preserved; cron release is allowed because its exact ownership was established
before unlink rather than inferred from a lossy filename fold. Known cron-store
failures (`cron_store_unreadable`, `cron_store_busy`, and for an unreadable
transcript `cron_ownership_unknown`) leave the row intact with a 409; bulk clear
reports per-row unreadable claims in `undeletable`. Other post-unlink errors log
the by-id recovery command (`kirocrew cron adopt <id> --release`). See
[learn-cron-dashboard](learn-cron-dashboard.md).

### Cleanup

Nothing in the product reclaims either ledger, so the only cleanup is an explicit operator command: `kirocrew ledger-sweep`, owned end to end by `kiro_crew.ledger_sweep` (`run_command()` is what `cli.py` dispatches to). It is its OWN top-level command and not a `doctor` mode, for two reasons that are not symmetry: `doctor` is read-only by its own contract — a diagnostic run because something broke must not unlink files — and `--purge` is irreversible, so the two do not belong under one name; and a separate command removes a whole class of hazard, because inside `doctor`'s flat flag namespace a modifier could be parsed without its mode, so bare `doctor --purge` ran the health pass and exited 0 and read exactly like a purge that found nothing. Here every flag belongs to this command and argparse refuses it anywhere else (`test_the_sweep_is_its_own_command_and_doctor_stays_read_only`). The dry run's closing hint repeats the window the report was built with — `kirocrew ledger-sweep --purge --older-than-days N` — never a bare `--purge`, which would re-scan at the default and delete the ledgers between a larger preview window and 30 days, ones the report never listed (`test_the_printed_purge_hint_carries_the_windows_the_preview_used`). The `kirocrew-commands` skill, which is injected into model context, lists the dry run only: the purge spelling is printed by the dry run to the operator who ran it, and no model-reachable surface names it. An earlier revision hosted the sweep as `doctor --ledger-sweep` and carried a stray-flag guard to patch that namespace; both went with the move, and `cli_doctor.py` is untouched by this change. It takes `--purge`, `--older-than-days N` (default `ledger_sweep.DEFAULT_OLDER_THAN_DAYS`, 30) and `--purge-unreadable`.

**It stays off every automatic path.** It is not a gateway-start hook, not part of the history-delete funnel described above, and deliberately not an MCP tool: the deletion is irreversible, so no model-reachable surface reaches it. `ledger_sweep.scan()` changes nothing at all, and a purge is a second, separate invocation over the report the first one printed. `scan()` never raises for an absent store or for any damaged record inside one, but it does raise `OSError` when a ledger root exists and cannot be read — that is the whole store the sweep cannot see, and a clean empty report over it would be a false "nothing to clean"; the CLI exits non-zero with the error. `test_an_unreadable_ledger_root_raises_instead_of_reporting_nothing_to_clean` and `test_an_absent_ledger_root_is_an_empty_report` pin both halves.

`scan()` answers "leave it alone" unless the record itself proves otherwise:

| Record | Candidate when | Never a candidate |
|---|---|---|
| session ledger | `phase` in `session_ledger.TERMINAL_PHASES` and age ≥ threshold | any in-flight phase, at any age, with no exception |
| work ledger | every item in `work_ledger.TERMINAL_ITEM_STATES`, at least one of them closed, and age ≥ threshold | one open item, at any age |
| work ledger | — | no items at all and a header present, at any age, torn header or not: finished-looking is not finished |
| work ledger | listed `unreadable` when it has neither header nor items and age ≥ threshold — the residue a purge leaves when a lock file could not be unlinked | — |
| either | listed `unreadable` when the record cannot be parsed AND age ≥ threshold | a record younger than the threshold, or a conductor with an open item — damage is classified last |

**The sweep infers nothing about sessions.** It reads the two ledger stores and nothing else — no transcript directory, no session map — so every verdict is one the record itself supports. "The session is gone" would be a disk inference, and an inference is the wrong thing to act on against an irreplaceable record: an in-flight session ledger is kept at any age with no exception, and a conductor holding no items is kept at any age too, because that shape is finished-LOOKING rather than finished — a ledger opened seconds ago and one whose creator died before dispatching look identical, and no lock can hold "its session is gone" still through a delete. Requiring a closed item is what keeps the empty conductor out of the purgeable set; an operator who wants to see such stores lists the work-ledger root, since this command reports only what it can act on. An earlier revision carried an opt-in `--include-orphans` that listed (never purged) empty conductors whose key named no session; it was removed because a list-only flag was carrying a session-existence oracle the stores are designed not to have. `test_an_in_flight_session_ledger_is_kept_at_any_age` and `test_a_conductor_with_no_items_is_kept_at_any_age` pin both halves.

A conductor record is validated, not merely counted as present: an absent, torn, oversized or non-object `conductor.json` all read as `unreadable`, because presence is not readability and treating only absence as damage let a malformed header pass as a finished ledger. The check is the store's own, `work_ledger.header_damage()`, and `purge_conductor()` re-applies it under its lock — a header that tears between the report and the purge is refused by a plain purge exactly as the scanner would have refused to list it as finished, and goes only with `allow_unreadable` (`test_a_header_that_tore_after_the_scan_is_refused_by_a_plain_purge`, `test_purge_conductor_refuses_a_torn_header_unless_the_caller_asks`).

Age is a ledger's LAST WRITE, not its terminal stamp alone. For a session ledger it is the newer of `finished_at` and `state.json`'s own mtime (`_session_age_days`): `session_ledger.record()` re-stamps `finished_at` only on a terminal PHASE write, so a goal, artifact or event-only update to an already-terminal ledger leaves the stamp alone while rewriting the file, and a record touched a minute ago would otherwise read as thirty days idle — `test_a_terminal_session_ledger_written_to_recently_is_not_old` pins the scanner and `test_the_session_guard_refuses_a_terminal_ledger_touched_after_the_scan` the guard, which applies the same reading under the lock. For a work ledger it is the NEWEST of three readings — the newest item `closed_at`, the header's own mtime, and the newest write under `items/` by mtime (`ItemCensus.newest_write_at`, every non-lock file: records, event logs, and a torn or misnamed file the census could not read). The third exists because an unreadable item carries no stamp the census can read and `_create_item` writes it without touching the header, so a crash-torn write into an old conductor would otherwise be invisible to the window and deletable under `--purge-unreadable` the moment it landed; lock files are excluded because the purge itself touches them and a reading that moved under the reader would refuse forever. `test_a_recent_unreadable_item_keeps_an_old_conductor_inside_the_window` pins the scanner and the store's recheck together. The header reading — the conductor's `goal` action rewrites `conductor.json` with no item involved, and a conductor that just bumped its round on old closed items is a live conductor about to create; newest close as an instant through `_parse_iso`, never as the lexically largest string, because the stamps carry the local offset at write time and two of them can sort in the wrong order across a DST change — falling back to `state.json` / `conductor.json` mtime when the stamp is empty — without that fallback a record whose stamp never landed would be permanently uncollectable.

`_item_census()` reads the item files directly instead of through `work_ledger.list_work_items()`, which skips an unreadable item — the right answer for a listing and the wrong one here, because "no open items" would otherwise be provable by damaging one. A conductor with any unparseable item is reported `unreadable` and kept.

**Damage is classified LAST**, after the open-item, age and no-items gates, in both scanners. An unreadable record is deletable with `--purge-unreadable`, so classifying damage first would let one torn item file carry a live open item — and the work its worker is still reporting against — into that deletion. The no-items keep sits ahead of it for the same reason: `--purge-unreadable` authorises deleting a record that cannot be READ, not one that was never shown to be finished, and an empty conductor with a torn header is both — so it is kept, not listed as damage, and `purge_conductor()` refuses the same shape under its lock so a caller-built report cannot reach it (`test_an_empty_conductor_with_a_torn_header_is_kept_not_offered_as_unreadable`, `test_purge_conductor_refuses_a_conductor_with_no_items_at_all`). An items directory that cannot be enumerated is not that case: it is damage with an unknown item count, and is listed. Nor is a directory with NEITHER header nor items: that is the residue a purge leaves when a lock file could not be unlinked — on Windows a writer queued on the conductor lock holds its handle through the post-release unlink, so the identity files go and the lock file stays — and it holds nothing a conductor wrote, so both the scanner and `purge_conductor` classify it as damage (`no conductor record`), listed and removable with `--purge-unreadable` (`test_a_lock_only_residue_is_listed_as_damage_and_removable_with_the_flag`, `test_purge_conductor_removes_a_headerless_itemless_residue_with_allow_unreadable`). The age gate runs ahead of it for the same reason in a different form: a file being replaced right now can itself read as damaged (a Windows read of a file another handle holds open raises), and for a damaged record age is the NEWER of the directory mtime, which `atomic_write` refreshes on every replace, and the record file's own mtime, which an in-place write (a truncation, a hand edit) freshens without the directory (`_damaged_session_age`, applied by the scanner and by `_still_finished`'s damaged branch alike; `test_a_recently_truncated_session_record_in_an_old_directory_is_kept`, `test_the_unreadable_session_guard_reads_the_file_mtime_not_only_the_directory`). So a live ledger reads as young and is left alone rather than reported as damage. `test_a_torn_item_beside_an_open_one_keeps_the_conductor` and `test_a_freshly_written_ledger_that_reads_as_damaged_is_left_alone` pin both halves. The census also answers the worker-binding question, which is why there is no separate binding scan: a binding names one conductor and one of its items, so a binding into a ledger whose every item is terminal is a binding onto a terminal item — the stale half-state `work_ledger._refuse_if_worker_holds_open_item()` documents as replaceable by the next bind. The sweep therefore leaves `bindings/` alone rather than deleting a worker's only report channel on a guess.

**Every string the report prints is read off disk, so every one is sanitised first.** `ledger_sweep._safe()` replaces every C0 and C1 control character — ESC and DEL included — with `U+FFFD` and elides past 120 characters; only the ledger kind and the age, which this module computes itself, print as they are. A ledger key is a session key and a channel puts arbitrary text in one, a phase and a goal are model-written, and a store directory name can be hand-created, so an unescaped line lets stored bytes move the cursor, repaint the summary count the operator is about to act on, or retitle the window. A stripped control leaves a visible mark rather than closing up into a different-looking string. `test_control_characters_in_stored_text_never_reach_the_terminal` and `test_a_very_long_stored_field_is_elided_rather_than_printed_whole` pin it.

An unreadable record is listed and NOT purged unless `--purge-unreadable` is given, and a store whose `slot_key` breadcrumb is gone is never purged at all: the directory name is a fold plus a digest and is not decodable, so neither delete primitive can be aimed at it, and the sweep names the path for a human instead. The breadcrumb is the ONLY source of a store's key for both kinds — the work header carries a `slot_key` field too, but recovering the key from it would let a store whose breadcrumb write failed be purged, against this rule. `test_a_work_store_without_a_breadcrumb_is_reported_and_never_purged` pins the work half alongside the session one.

**Neither primitive ever follows a link.** A store directory, or an `items/` inside one, that is a symbolic link or a Windows junction names files that are not this ledger's, and a removal through it would land on them — nothing in the store's own records could tell. `session_ledger.is_link()` is the one predicate: both scanners list a linked store directory as `report` (never aimed at), `census_items()` reports a linked `items/` as damage, `purge_matching()` skips a linked store and `purge_conductor()` refuses one before taking any lock — whatever flags are given, since this is not damage an operator can ask to clear but a delete aimed somewhere else — and both content walkers unlink a linked entry as a name rather than descending into it. `test_a_linked_items_directory_is_damage_and_the_purge_never_follows_it`, `test_a_linked_store_directory_is_reported_and_never_aimed_at`, `test_purge_matching_never_follows_a_linked_store_or_a_linked_entry` and `test_the_content_walker_unlinks_a_linked_items_directory_as_a_name` pin every site.

**Both primitives are aimed by key, not by path**, and each resolves the directory itself. A store is therefore purgeable only when the directory the scan looked at is the one its own breadcrumb key resolves to — `Candidate.addressable`, checked by `_path_matches_key()` in both scanners and re-asserted in `purge()` immediately before either primitive is called. A copied store, or a hand-made directory carrying another ledger's breadcrumb, would otherwise send the delete at the CANONICAL ledger: one the scan never listed and the operator never saw on the report they approved. Such a store is reported so it can be removed by hand and is never purged, `--purge-unreadable` included — and when its record reads, it is reported as `report` and counted report-only, not as `unreadable`: that word is a statement about the record, and a store whose only fault is its name is not corrupt. A damaged store whose name is also wrong is both, and stays `unreadable`. `test_a_copied_work_store_never_sends_the_purge_at_the_canonical_ledger`, `test_a_copied_session_store_is_reported_and_never_purged` and `test_purge_re_asserts_the_path_identity_on_a_hand_built_report` pin all three sites.

**A failure to enumerate an items directory is damage, never "zero items"**, in `work_ledger.census_items()`, and therefore in both the scanner and the locked recheck that share it. It is the one case where the count and the truth are unrelated: read as empty it selects the ORDINARY purge, which removes `conductor.json` and leaves the item data it could not see standing — a ledger destroyed down to the records that made it a ledger. An absent items directory is not damage, because a conductor that never created an item has none. `test_an_unreadable_items_directory_is_damage_not_a_finished_ledger` and `test_the_store_refuses_an_unreadable_items_directory_under_its_own_lock` chmod the directory on POSIX; `test_an_enumeration_error_is_damage_in_the_census` covers every platform by making the enumeration raise.

The scanner has no census of its own: it calls `work_ledger.census_items()`, which reads each item through `_read_json_record` — the store's own reader, which already applies the size ceiling and answers `None` for absent, torn, oversized and non-UTF-8 alike.

**A purge's lock never creates the store it is about to delete.** `_locked(create=False)` and `conductor_lock(create=False)` skip the `mkdir` and the `O_CREAT`/`touch` a writer's lock performs and raise `FileNotFoundError` for a store that is gone, and both purges skip such a store. Otherwise two sweeps racing over one store would have the second rebuild the directory the first just removed — holding nothing but a lock file, with no breadcrumb, which no later purge could name — and only then find nothing to guard. `test_a_purge_racing_a_finished_purge_recreates_nothing` pins it on both halves; `test_a_writer_lock_still_creates_the_store` pins that a writer's lock is unchanged.

**The delete decision is re-taken under the store's own lock, by the store that owns it.** `ledger_sweep` selects; `session_ledger.purge_matching(guard=...)` and `work_ledger.purge_conductor()` decide. The guard is called inside that ledger's own `_locked()` hold and the removal happens in the same hold, so a session resumed after the scan is refused rather than erased — selecting under the lock would not be enough, which is why the guard is a callback and not a filter the caller applies first. The guard applies the WHOLE rule the scanner applied — terminal phase and age, or for a damaged record still-damaged and the DIRECTORY age the scanner used — not the phase or the damage alone (`test_the_unreadable_session_guard_refuses_a_store_written_to_after_the_scan`: a torn store written to between the report and the purge is fresh by its directory and is stood down on): `session_ledger.record()` re-stamps `finished_at` on every terminal write, so a session that resumed and finished again inside the purge window is terminal but young, and young means it was just in use. `purge_conductor(slot_key, *, allow_unreadable, idle_for)` takes both keywords with NO defaults — an irreversible delete with one production caller must not let a future caller skip the retention window or the unreadable-record refusal by omission; "no window" is spelled `idle_for=timedelta(0)`, visibly. It takes `conductor_lock`, then every item lock non-blocking in sorted order (`_hold_every_item_lock`, the documented conductor → item order), and holds all of them through the removal. An item lock that cannot be taken is a worker mid-write and the purge refuses: a file being replaced reads as unreadable to the census — a Windows read of a held file raises, a POSIX half-rename is torn — so a census alone cannot tell "damaged" from "being written", and without the item locks `--purge-unreadable` would let an operator remove an item its worker is writing this instant. `test_purge_conductor_refuses_while_a_worker_holds_an_item_lock` and `test_purge_conductor_holds_every_item_lock_through_the_removal` pin it. Inside those holds it re-runs the item census and raises `CODE_LEDGER_NOT_FINISHED` on any open item, on an items directory it cannot enumerate, on any unreadable item unless the caller passes `allow_unreadable`, and — against the `idle_for` window every caller must pass, as the sweep does with its own — on any activity by either writer (`_newest_activity`: newest close or header mtime, falling back to the directory mtime when the header cannot be statted — a store whose header is gone was written to when it went, and dropping that reading would leave the newest close as the only age; `test_newest_activity_falls_back_to_the_directory_when_the_header_is_gone`) younger than that window. The census is `work_ledger.census_items()`, the one classification both the sweep's scanner and this recheck use, so the two cannot disagree — and it applies `read_work_item`'s own identity rule: a record whose stored `item_id` names a different item than the file it sits in is a misnamed or hand-moved file the store will not read, so for a delete decision it is `unreadable`, never `closed`, whatever its `state` says — and so is any `.json` under `items/` whose stem is not an id the store minted, which a census that skipped it would let a plain purge remove with the rest of the contents (`test_census_reads_an_item_shaped_file_with_a_foreign_stem_as_unreadable`) (`test_census_reads_a_misnamed_item_as_unreadable_not_closed`). `_create_item` holds that same lock across its whole transaction, so a conductor cannot mint an item between the census and the removal — and it re-reads the header under that lock and refuses with `CODE_NO_LEDGER` when the header is gone, so a create that was waiting behind a purge cannot write an item into a store that no longer has one. The sweep records such a refusal as `stale`, not as a failure: the guard working is the expected outcome, not an error.

That census reads the item files directly and classifies an unrecognised `state` as damage rather than closure — so `--purge-unreadable` still clears it, while counting it as an open item would leave the ledger permanently uncollectable. `test_purge_conductor_refuses_a_ledger_that_still_has_an_open_item`, `test_purge_conductor_refuses_a_torn_item_unless_the_caller_asks`, `test_purge_conductor_reads_an_unknown_item_state_as_damage_not_as_closure` and `test_a_session_ledger_resumed_after_the_scan_is_refused_under_its_lock` pin the store half.

`ledger_sweep.purge()` does not re-scan to "confirm" the report before entering a store — the store's own locked refusal is the confirmation, and it is recorded as `stale`. A report is a snapshot and the gateway keeps running while an operator reads it, so a ledger can be reopened, an item created, or a header touched in between — each of which makes the ledger live again, and each of which the store's own locked check catches. `test_a_ledger_reopened_after_the_scan_is_not_purged`, `test_a_conductor_that_opened_an_item_after_the_scan_is_not_purged` and `test_the_session_guard_refuses_a_terminal_ledger_touched_after_the_scan` pin that a stale report cannot delete.

Deletion goes through the two primitives that already existed for it. Session ledgers use `session_ledger.purge_matching(exact_keys, *, guard)`, which matches EXACT keys only, so the only thing that can match is a breadcrumb holding exactly one of the keys the report named — the earlier fold half (`folded_keys`, `fold`) had no caller that passed anything but the identity, and a lossy fold is the one way a caller could remove a ledger it never listed, so it is gone rather than kept as a default (`test_purge_matching_is_exact_and_a_folded_spelling_matches_nothing`). Work ledgers use `work_ledger.purge_conductor()`, added for this: it takes `conductor_lock` — first in the store's lock order — removes the directory contents under that hold, and unlinks the lock file only after releasing it, because Windows refuses to unlink a file an open handle still holds and doing it inside the critical section would leave the directory behind on exactly the platform the lock covers.

**Removal is ordered and the identity files go last.** `purge_conductor()` removes items and any other content first, counts every failure instead of ignoring it (`_remove_contents_locked`), and only once everything else is gone unlinks `conductor.json` and then the `slot_key` breadcrumb — header first, breadcrumb after, so a header unlink that fails leaves a store that still names itself and can be purged again rather than one no key can reach. So the store is never left as a header-less pile of items nor as a nameless one: on any failure it keeps whatever identity it still has and reads as `unreadable` to the next sweep. `test_purge_conductor_keeps_the_breadcrumb_until_the_header_is_gone` pins the order. Every lock file — the conductor's and each `items/<stem>.lock` — is left standing by that content pass and removed by `_remove_lock_shell` only after every hold is released, because the purge holds all of them open and a Windows `os.open` handle has no `FILE_SHARE_DELETE`: unlinking a held lock raises, so removing them inside the hold would count a failure per item that ever existed and the work half could never succeed on Windows. `items/` is therefore walked file by file rather than `rmtree`'d. `test_purge_never_unlinks_a_lock_file_while_its_handle_is_held` pins it under simulated Windows unlink rules. `test_purge_conductor_keeps_the_header_when_any_content_survives` and `test_purge_conductor_removal_failures_are_counted_not_ignored` pin it. The session half has the same shape, and only that shape — `purge_matching()` has one spelling of deletion, locked, ordered and identity-last, and its `guard` is a required parameter, so no caller can skip the re-decision by omission: `session_ledger._remove_store_contents()` removes other entries first, counts failures, and unlinks `state.json` and `slot_key` only once the count is zero, so a failed removal leaves a store that still has its record and still names itself; a store that could not be fully removed is not counted as removed. `test_purge_matching_with_an_accept_all_guard_is_still_locked_and_ordered` pins that even an accept-all guard runs under the lock and the ordering. `test_guarded_purge_keeps_the_record_and_breadcrumb_when_any_content_survives` and `test_guarded_purge_counts_rmtree_failures_instead_of_ignoring_them` pin it.

**The lock inode.** Removing a store removes the inode its lock is taken on, and the kernel still grants a queued writer the lock on that detached inode — so without a check, a writer that was waiting behind the purge would proceed, its `mkdir` would recreate the directory, and it would publish a torn store into a purged key: state without a breadcrumb, or a header-less item. Two things close it together. `session_ledger.require_lock_inode()`, run by both `_locked()` and `work_ledger._open_lock()` immediately after the acquire, inside the hold, compares the identity of the file the writer holds (`fstat`) against the file now at the lock's path (`stat`) and refuses with the same `OSError` a held lock produces when the path is gone or the inode differs. And the purge unlinks every lock file **inside the hold** (`unlink_lock_in_hold`), so the path is already gone by the time a queued writer acquires — unlinked after release there is a window where the writer acquires, validates against a path that still exists, proceeds, and the late unlink detaches the very inode it holds, handing the next writer a second one. On Windows the in-hold unlink is refused and happens after release instead, which is safe there precisely because it fails whenever a writer still holds a handle: the OS keeps lock identity stable, a successful late unlink proves nobody was queued, and `require_lock_inode` is therefore inert on Windows by construction. The post-release step unlinks **only** the lock paths the hold could not (`lock_gone` / `item_locks_left`): a path already unlinked inside the hold is never touched again, because a writer that refused on the detached inode may by then have retried, rebuilt the store and taken a fresh lock at that path, and a second unlink would detach that fresh inode under its holder. `test_the_post_release_shell_never_touches_a_lock_the_hold_already_removed` pins it on both halves. That post-release step runs after EVERY hold is released, the conductor's included: on Windows the conductor lock's own file is one of the paths the hold could not unlink, so a shell that ran inside that hold raised on it, left the directory non-empty and reported `False` over a store it had already emptied. `test_purge_never_unlinks_a_lock_file_while_its_handle_is_held` and `test_purge_matching_succeeds_under_windows_unlink_rules` simulate the Windows rule on every platform — tracking both the `os.open` and the module-`open` lock handles, since a version that tracked only the first was blind to the conductor lock and passed over exactly that regression. `test_the_lock_inode_is_unlinked_inside_the_hold` and `test_every_lock_inode_is_unlinked_inside_the_holds` pin the POSIX order. `_create_item` and `_write_goal` additionally refuse with `CODE_NO_LEDGER` when the header FILE IS ABSENT under the lock (`_header_under_lock`) — a `goal` that waited behind a purge must not rewrite its stale pre-lock snapshot into the removed store, which would resurrect a header with no breadcrumb. That is the one case the purge needs refused and the only one refused: a header that is present but does not parse under the lock is a damaged live ledger, not a purged one — the caller holds the lock, so no other writer is mid-replace — and the pre-lock snapshot stands in for it as it always did, so a `goal` rewrites and repairs the header and a create takes its default round from it. File presence is what separates "purged" from "damaged" under a lock the purge also takes. `test_goal_refuses_when_the_header_is_gone`, `test_create_item_refuses_when_the_header_is_gone` and `test_a_torn_but_present_header_is_repaired_from_the_snapshot_not_refused` pin the two sides. And every writer to an EXISTING store takes its lock non-creating: `conductor_lock` and `item_lock` create the lock file and `mkdir` the store around it, which is right for `ensure_conductor` and `_create_item`'s new item and wrong everywhere else, because a `goal`, an item-create or a worker report that arrives after the purge would rebuild `<store>/.lock` or `<store>/items/<id>.lock` on its way to refusing — a lock-only store with no header and no items, which the no-items keep hides forever. So `_write_goal` and `_create_item` take `_existing_conductor_lock` (a missing lock file is `CODE_NO_LEDGER`) and the three item writers take `item_lock(create=False)` (a missing lock file is `CODE_UNKNOWN_ITEM`, unless the item record is still there and only its lock file was hand-removed, in which case the store exists and the lock is recreated — under the conductor lock, taken non-creating, with the record re-checked inside that hold, because the purge removes records and lock files under the same lock and a plain creating open in the gap would lose the race and rebuild the very lock-only store the parameter exists to prevent). `test_a_late_report_on_a_purged_ledger_refuses_and_rebuilds_nothing`, `test_a_goal_on_a_purged_ledger_refuses_and_rebuilds_nothing`, `test_an_item_that_lost_only_its_lock_file_is_still_writable` and `test_the_lost_lock_recreate_loses_a_purge_race_without_rebuilding_the_store` pin the four behaviours. `test_goal_refuses_when_the_header_is_gone` pins the goal half. `test_a_writer_queued_behind_a_purge_refuses_instead_of_publishing`, `test_every_store_lock_runs_the_inode_check_after_acquiring`, `test_a_record_queued_behind_a_purge_refuses_instead_of_publishing` and `test_create_item_refuses_when_the_header_is_gone` pin it.

`--older-than-days` must be a **finite** count of days. `math.isfinite` runs before the sign check, because every comparison against NaN is false: a NaN window passes `window < 0` and then makes every `age < window` false too, which admits every ledger in both stores at once. Infinity is refused with it — it is not a window, and reading it as "collect nothing" would make a typo look like a working command.

`test_ledger_sweep.py` pins the rules: `test_dry_run_lists_both_kinds_and_deletes_nothing`, `test_purge_removes_only_the_candidates`, `test_an_in_flight_session_ledger_is_never_a_candidate`, `test_a_conductor_with_an_open_item_is_never_a_candidate`, `test_threshold_is_a_boundary_not_a_hint`, `test_unreadable_session_state_is_listed_but_survives_a_plain_purge`, `test_a_torn_item_record_makes_the_whole_conductor_unreadable`, `test_a_store_without_a_breadcrumb_is_reported_and_never_purged`, `test_a_conductor_with_no_items_is_kept_at_any_age`, and `test_a_window_that_is_not_a_finite_count_of_days_refuses` (a clamped negative window would make every ledger a candidate). `test_work_ledger.py::test_purge_conductor_removes_the_ledger_under_the_conductor_lock` pins the lock, asserting what was gone while the hold was still open rather than the return value, which a purge running entirely outside the lock would also produce.

## 3. State record and bounded writes

`session_ledger._empty_state()` defines the state fields:

| Field | Meaning |
|---|---|
| `schema` | stored schema marker |
| `goal` | binding objective |
| `phase` | current free-form work phase |
| `next` | concrete resumable intent |
| `tried` | rejected approaches with their reason and timestamp |
| `artifacts` | string pointers to work artifacts |
| `events` | recent classified progress entries |
| timestamps | creation, latest progress, and terminal-completion time |

`session_ledger._coerce_state()` supplies defaults for malformed known fields and preserves unknown fields for forward compatibility. `session_ledger._read_state_unlocked()` treats unreadable, malformed, undecodable, or oversized state as empty rather than failing a turn. `test_read_state_malformed_oversized_or_undecodable_reads_empty` pins that behavior.

`session_ledger.record()` applies partial updates. Omitted fields retain their stored value; artifact updates merge with the stored map; a supplied rejected approach appends to `tried`; and a nonblank event appends to `events`. `test_record_roundtrip_and_partial_update`, `test_artifacts_merge_and_clamp`, `test_tried_appends_and_caps`, and `test_events_tail_bounded` pin the retention and aging rules. The bounds keep a resumed session from accumulating unbounded durable context.

Every accepted record advances `last_progress_at`. Changing `phase` requires a nonblank event and a recognized event kind. `session_ledger.record()` writes the phase and its event in one atomic state document, so a crash cannot expose a phase move without its classified reason; `test_phase_and_event_land_in_one_document` enforces this load-bearing audit trail. A phase in `session_ledger.TERMINAL_PHASES` stamps `finished_at`; a later non-terminal phase clears it, as guarded by `test_terminal_phase_sets_finished_at_and_reopening_clears_it`.

`session_ledger._serialize_bounded()` evicts oldest history before an accepted state file can exceed the reader ceiling. `test_writer_guarantees_the_read_ceiling_for_legitimate_records` ensures a valid record remains readable, and `test_oversized_unknown_fields_are_dropped_not_self_corrupting` ensures oversized forward-compatible fields do not destroy known state.

Each eviction discards data that never reaches disk, so it cannot be recovered from the stored file the way a read-side clamp can. `_serialize_bounded()` therefore logs one warning per over-budget serialization naming the ledger, the evicted `events`/`tried` counts, and any unknown fields dropped - including on the refusal path, which raises with the in-memory record already stripped. The line describes the document the call built rather than a durable write, because `atomic_write` runs afterwards and may still fail. A document that fits logs nothing. `TestBoundedWriteIsLoudAboutLoss` pins the counts, the named ledger, the refusal report, the failed-write case leaving the stored file intact, and the silence.

`record()` returns the same dict `_serialize_bounded()` evicts from, so a caller's post-write view is the document on disk rather than the pre-eviction one. `test_record_returns_exactly_what_landed_on_disk` pins that equality across an eviction; serializing a copy instead would report entries the write dropped.

Writes use the bounded exclusive lock in `session_ledger._locked()`. Contention raises `OSError` rather than allowing an unserialized write or indefinitely blocking a worker; `test_record_fails_closed_on_held_lock` enforces this. Reads are lock-free because `atomic_write` exposes either the previous or complete replacement document, so the state and event tail come from one transaction.

## 4. MCP surface and authorization

`mcp_tools.__init__.DOMAIN_MODULES` registers `mcp_tools.ledger`. `session_ledger_read` has no arguments and returns the calling session's state and recent event tail. `session_ledger_record` accepts only optional state fields; `validation.SESSION_LEDGER_RECORD_SCHEMA` validates their types and lengths, while `session_ledger.record()` enforces the conditional phase/event rule.

`mcp_tools.ledger._strict_session_key()` obtains a gateway-authored session identity before either tool calls the loopback routes. This is load-bearing because the lenient resolver can walk a subagent process tree to its parent; rejecting an unverified identity prevents a subagent from reading or overwriting the parent's ledger. `test_mcp_tools_refuse_without_strict_identity` and `test_mcp_tools_pass_the_verified_key_to_transport` enforce that boundary.

`dashboard.handlers.session_ledger._resolve_ledger_key()` derives storage identity from the recognized `X-Session-Key`, never the request body. The routes reject missing or unrecognized identities and restricted session modes, so a request can read or write only its own durable ledger. `api_session_ledger_record()` sends bounded-lock failures back as retryable service errors and validates that artifact maps contain only strings. `test_route_refuses_unrecognized_session`, `test_route_refuses_restricted_session`, and `test_route_rejects_non_string_artifacts` cover those boundaries.

## 5. Auto-nudge injection

`dashboard.handlers.autonudge.compose_nudge_body()` renders the normal nudge body, then reads `render_snapshot()` in a worker thread. A nonempty, non-terminal ledger snapshot prefixes the nudge; an absent ledger, terminal phase, or snapshot exception leaves the nudge body unchanged. `test_compose_nudge_body_prefixes_snapshot`, `test_compose_nudge_body_unchanged_without_ledger`, and `test_compose_nudge_body_survives_snapshot_failure` enforce those outcomes.

`session_ledger.render_snapshot()` includes current goal, phase, next step, recent rejected approaches, and artifact pointers, and applies its own rendering bounds. It omits terminal records because completed work provides no next-cycle steering; `test_snapshot_empty_without_ledger_or_when_terminal` and `test_snapshot_contains_state_and_is_capped` guard this behavior.

Every `_fire_*_nudge` adapter in `slack.gateway` calls `compose_nudge_body()`, including the messaging and dashboard transports. `test_gateway_fire_callbacks_use_the_composer` enumerates adapters rather than pinning their count, so a new transport cannot silently bypass the ledger snapshot.

## 6. Failure behavior and scope

A read failure yields an empty ledger. A write lock failure is retryable. Both
closing a tab and permanently deleting its history preserve matching ledger
directories; the explicit sweep in [Cleanup](#cleanup) is what removes stale
ledger state later, and it reports rather than deletes any record it cannot
parse. Snapshot failures are best-effort and never prevent the nudge from
firing.

The ledger does not journal individual tool operations, arbitrate execution ownership with leases, or add a dashboard UI. It records state between wakes; the MCP tools and nudge composer are its public surfaces.
