# Session Work Ledger

Owners: `kiro_crew.session_ledger`, `kiro_crew.mcp_tools.ledger`, and the dashboard ledger routes. The live record is a projection of the session's crew log (`crew-log-core.md`); its entries are removed with that log through the permanent-delete funnel. Cleanup for the two on-disk ledger stores that the sweep still reaches — the retired session ledger-store residue and the conductor work ledger in `kiro_crew.work_ledger` — is owned by `kiro_crew.ledger_sweep`; see [Cleanup](#cleanup).

## 1. Purpose

`kiro_crew.session_ledger` provides durable, per-session work state for long-running work. The state record holds a goal, phase, resumable next step, rejected approaches, artifact pointers, and a bounded event history. This separates resumable state from transcript context; `mcp_tools.ledger.schemas()` describes the record as authoritative over prior-cycle memory.

The record is a projection, not a document. `session_ledger.record()` appends exactly one `ledger/recorded` crew-log entry per call, and every reader folds those entries back into the record with the `ledger` fold registered in `crew_log.projection`. One append-only authority means the record and its audit event cannot diverge: the fields a call sets and the event that explains them ride on the same appended line, so there is no ordering in which a reader sees a phase that moved without its reason.

The ledger DEPENDS on the session crew log: the record is a fold of that log's entries, so a gateway started without `KIROCREW_CREW_LOG=1` cannot record one and `session_ledger_record` refuses with `crew_log_unavailable` (HTTP 409) naming that setting, rather than falling back to a document of its own -- a fallback would recreate the second writer this design removes. The env var is the only setting; there is no config key.

## 2. Storage, identity, and lifecycle

A slot owns one ACP session id at a time, not for its whole life. A reset, an agent change, a model change, or a provider change can cold-start another session id for the same slot, so a slot's updates are spread over the crew log of each id it ran under. `crew_log.store.session_units_for_slot()` returns the header-proved units for a slot, oldest first, and the `ledger` fold joins them in that order, so later updates replace earlier state. A read joins every unit; a write only ever needs the unit it is in.

`session_ledger.record()` requires its keyword-only `session_id` argument, the ACP session the slot is serving right now. It appends one entry through `crew_log.emit.on_ledger_recorded()` and returns the record produced by advancing the same fold over that pending entry, so the answer does not depend on the writer having already drained and is not a second implementation of the update rules. `read_state()`, `has_ledger()`, and `render_snapshot()` all read the same slot-keyed projection.

Recording requires `KIROCREW_CREW_LOG=1`, a nonempty session id, and an existing crew log for that session. Otherwise `record()` raises `LedgerUnavailable`, and `api_session_ledger_record()` returns HTTP 409 with `crew_log_unavailable`. A silent write that went nowhere is the one outcome a durable record must never produce, so the absence of a log is established at the call rather than discovered as silence. A read is best-effort by contract: a slot with no entries and a fold that cannot be made both read as the empty record, and the two are distinguished in the log rather than in the answer — an absent ledger is silent, a refused fold is a warning, because that one means a reader older than the writer. Reads are lock-free and safe because the crew log is append-only: a reader sees a prefix of the truth, never a torn record.

### Durable acknowledgement

`session_ledger.record()` waits for the crew log's writer to drain before it answers, so a queued entry is not what a caller is handed as taken. The caller is about to act on the record, and an unclean death inside the queue-to-flush window would otherwise lose an update already reported as taken. The wait runs on a worker thread, so it costs no event-loop time.

A drained queue is not the same claim as "this entry landed": `flush` answers false only when the writer is still busy past the budget, in which case the entry is queued rather than lost, and a permanently refused append drains the job and is counted instead.

One refusal is decided BEFORE the append instead of being reported through durability. An entry over the crew log's `MAX_ENTRY_BYTES` ceiling is refused by the writer, which counts it and drops it — and that reaches the caller as the same `durable=false` a writer that is merely still busy gives, though that update is recorded and does land. The two need opposite answers: a busy writer's update is taken and the caller may proceed, while an entry over the ceiling can never land however often it is retried, so a success would promise a record that never exists and is absent from the slot at the next read. The clamps permit it: `_MAX_ARTIFACTS` artifacts at `_MAX_ARTIFACT_KEY` and `_MAX_TEXT` each exceed the ceiling on their own, so this is reachable through clamped input rather than through a runaway writer. The size is the one part knowable in advance, so `record_update()` asks `crew_log.emit.ledger_entry_fits()` — the same serializer, entry type and src the append uses, so the two cannot disagree — and raises `LedgerEntryTooLarge` before enqueueing anything. Everything else stays as below. Two readings decide it, both bracketing the append. The refusal counter is sampled BEFORE and compared after, because a second gateway owning the unit appends inline rather than queueing and an inline refusal moves the counter during the call, which a sample taken afterwards would fold into its own baseline. And THIS UNIT's own newest seq must have moved, which is the part a process-wide counter cannot say: a counter that did not move proves only that no append anywhere was refused, while a file whose seq did not move proves nothing was written here. Requiring both leaves a false positive only for a concurrent append into the SAME unit — one conversation writing twice at once — rather than for any session in the process. On expiry the entry is still owed and counted by the writer, and the call logs that the update is not yet durable instead of raising. Raising would invite a retry that appends the same update twice, or would attribute a concurrent session's process-wide refusal here and reject a good write; the loss is logged, surfaced by `dropped_writes()`, and superseded by the next update, which re-reads its base from disk.

`record_update()` RETURNS that answer beside the record, and `record()` is the wrapper for a caller that cannot act on it. Returning it is what makes it about this append: a module-level flag keyed by slot would be read under the caller's spelling while the write stored the canonical one, a missing key would have to mean something, and a concurrent update on the same slot would land between the write and the read. The route answers `durable`, and `session_ledger_record` tells the caller when it is false: the agent is usually recording precisely so the state survives a restart, so being told the write is not yet on disk is the difference between retrying and assuming. The flag rides BESIDE the record rather than inside it, because every reader of the record expects its ten fields and durability is a fact about one call rather than about the workstream.

### Fold checkpoint

Folding is O(the log), not O(the record): the fold interprets only `ledger/recorded` entries but the reader walks every line of every unit to find them, and a session's log carries its message bodies. So the checkpoint is kept in memory per slot and advanced incrementally over the entries that arrived since, using the same seq-anchored machinery a cold fold uses — the resumed answer and the from-scratch answer come out of one implementation, which is the property `crew_log.projection` pins. An older unit CAN still grow: a forced reset tears a session down while a turn is running, and that turn keeps appending through the handle it holds. So the checkpoint key carries every unit's seq, not just the newest, and it is continued only when the newest unit grew forward with every earlier seq identical — otherwise the fold is taken cold. The per-unit seqs are re-sampled after the fold and cached only when they agree with the sample taken before it, because an append landing during the fold is in the checkpoint but not in the earlier sample, and caching that pair would advance the next read from a seq already folded. That guard is applied by the CONTINUED path as well as the cold one, and it is load-bearing there rather than a precaution: an active session appending while its own record is read is the ordinary case, the advance streams to the end of the file and folds an entry the pre-read sample missed, and the next read would then hand `advance` an entry at or below its checkpoint — which is refused, so the read degrades to the empty record. The key also carries the DATA HOME: one process serves more than one home — a pod, a test, a gateway restarted in place — and a slot key is not unique across them.

The checkpoint is keyed by data home plus slot, because one process serves more than one home — a pod, a test, a gateway restarted in place — and a slot key is not unique across them, so keying on the slot alone would let one home's checkpoint answer another home's read. Three things force a cold rebuild, each a wrong answer rather than a slow one otherwise: a different unit list, a newest unit whose seq went backwards, and nothing cached at all. The cache is in memory rather than on disk on purpose: the reader that pays this cost is the gateway's own loop, one process, and a durable checkpoint is a store of its own with its own invalidation rules; a second process simply folds cold. A failed advance evicts the cached checkpoint, because a half-advanced state must not become the next read's answer.

### Exact-key identity

`session_ledger.ledger_key()` strips only the dashboard namespace and prefix spellings, losslessly. One dashboard session is legitimately spelled both `dashboard_chat-X` and `chat-X`, and both must reach one ledger, while a charset fold here would map two distinct channel session keys onto one — one session reading and overwriting another's state. `session_ledger._store_name()` combines a readable fold with a digest of that exact key, so `Foo`/`foo` and long shared prefixes all get distinct directories on every filesystem, and the name is not decodable back to the key — the key is persisted inside the store instead. `session_ledger.ledger_dir()` rejects hostile raw keys and requires the resolved directory to stay below the ledger root through `resolved_within`, preventing traversal through a folded name.

`session_ledger.canonical_slot()` then resolves which of a session's spellings the record is keyed by, because the fold has to agree with the append. A unit's header records the LIVE slot key, while a caller reaches the ledger under its own session key, and those are the same string only for a dashboard session, whose prefix the fold strips. A cron-injected, hook, task-runner or ACP subagent session is keyed `cron:<id>`, `hook:<id>`, `taskrunner:...` or `acp:...` — names `ledger_key` deliberately leaves alone — so without this the append lands in a unit headed by the slot key while every later read looks up the caller's key, finds no unit, and answers with an empty record. The header's slot becomes the key for the fold, the checkpoint and every control file; the caller's own spelling is joined BESIDE it as an alias, so a record already written under that spelling keeps reading. Both entry points take the caller's live ACP session id to resolve it, and every fallback — no unit yet, a crew log that is off, an unreadable header — keeps the caller's key.

### Legacy store and permanent deletion
The former per-slot ledger-store directory below `<data_home>/ledger/` is residue that nothing writes. `state.json` is read only to be RETIRED, by the upgrade carry-forward below and by that carry's read-side preview, and no other reader consults it. The one written place under that root is the sibling `control/` directory described further down, which is not a store and which no purge or sweep treats as one. Permanent deletion of a live record removes the session crew-log unit through the crew log's own deletion funnel, so the record goes with the log that holds it.

Closing a dashboard tab preserves the ledger. Permanent history deletion of a session removes it. The two are deliberately different. A transcript can be created or restored by another process after any in-process owner check, and no request-local fence can make a store deletion atomic with that claim; a stale ledger is reversible, and deleting a successor's resumable state is not. That reasoning about the ledger-store residue does not carry to the append-only crew log, which the same funnel does remove: the hazard the residue guards against is key reuse, because a store keyed by the slot key lets a successor tab in the same slot inherit and resume the record, while the crew log is keyed by the ACP session id, which never names a different conversation, and it holds a kernel-arbitrated write lease that refuses a removal while any writer still owns the unit. Neither property holds for the slot-keyed residue, which is why the crew-log record and the residue are collected differently rather than inconsistently.

The same history-delete funnel separately releases cron ownership. The single delete performs a strict cron-owner scan before unlink and another after it; bulk clear batches both scans. `_delete_history_session()` binds the exact owner keys from that scan and a readable `linked_session_key` into the immutable `_HistoryDeleteClaim` while holding the canonical-plus-legacy transcript lock set. `_remove_slot_for_history_key()` first revalidates the captured slot, transcript, task and session generation, then cancels the old turn and conditionally destroys only that manager generation. After those awaits it rechecks both live slots and SessionManager's live/reserved keys, and hands only the proven retired owner keys to `CronService.release_jobs_owned_by()`. Pins, ledgers and autocompact overrides are preserved; cron release is allowed because its exact ownership was established before unlink rather than inferred from a lossy filename fold. Known cron-store failures (`cron_store_unreadable`, `cron_store_busy`, and for an unreadable transcript `cron_ownership_unknown`) leave the row intact with a 409; bulk clear reports per-row unreadable claims in `undeletable`. Other post-unlink errors log the by-id recovery command (`kirocrew cron adopt <id> --release`). See [learn-cron-dashboard](learn-cron-dashboard.md).

### Fold control files

Three files govern what a slot's fold reads, one directory per slot under `<data_home>/ledger/control/` (`session_ledger.control_dir()`). They sit BESIDE the per-slot stores rather than inside one because those stores are collectable: `purge_matching()` removes a whole store by breadcrumb and the sweep proposes a finished one for purge by age, so a control file inside a store is removable by documented maintenance — and losing the exclusion list is exactly what lets a recycled slot key fold a deleted conversation's units. Both scans skip the directory by name (`_scan_session_ledgers`, `purge_matching`), the way the work-ledger scan skips its bindings directory. It stays under the ledger root so it inherits that root's fence: these files decide what a fold reads, so a copy outside the fence would let an agent tool hide a live slot's units.

`deleted-units` holds the unit ids a permanent delete removed from the slot, one per line, and `crew_log_units()` drops them from every read. A list that cannot be READ fails closed to no units, which reads as the empty record: answering "nothing is excluded" would serve a deleted conversation's goal and phase to whoever holds the slot key now and nothing later takes that back, while an empty record tells the person nothing and is recovered by the next read that can see the list. An exclusion is also taken back when the deleted key was not the only one running that ACP session: two keys imported onto one session share its unit, the delete preserves that unit for the survivor, and leaving it excluded would strand the survivor's record empty for good. That lookup EXCLUDES the key the delete retired, whose own mapping can still be present at that point -- a lookup able to answer with it reads as "nobody else has this session", which is the answer that strands the real survivor. Because this runs AFTER the unlink, a failure there is reported as what it is: the row is gone, so neither delete path calls it a refusal, and a bulk row still counts as cleared. The funnel removes the conversation's own unit, but a slot accumulates one unit per reset and the earlier ones survive it, so a fresh session on a recycled slot key would otherwise fold them and read a deleted conversation's goal and phase. Ids are recorded rather than a timestamp because the ids present at delete time are exactly the ones that delete is entitled to exclude, and a successor's unit carries an id that is not among them, so no clock decides it. They are recorded rather than deleted because a unit may still be open to a writer and a slot key is recycled, so removing everything under the slot would take a live successor's log. `exclude_units()` runs as one transaction under the slot's own lock, reads the current set, adds only ids that are not already in it, and rewrites the file as one deduplicated set — so two concurrent deletes of the same slot cannot lose each other's ids and a file written by hand or by an older build is compacted rather than carried forward. The set is BOUNDED by `_MAX_EXCLUDED_UNITS` and overflow FAILS CLOSED: the exclusion is refused and so is the delete, because dropping an id to stay under a bound is precisely the resurrection the file exists to prevent. The READ bound is derived from that count bound (`_MAX_EXCLUDED_BYTES`) rather than shared with the order file's smaller one, and a file past it is REJECTED rather than truncated -- a truncated read rewritten as the whole set would permanently drop the most recently deleted units, which is the silent version of the loss the count bound is there to refuse loudly. It returns the ids it ADDED and whether it TOMBSTONED the slot's legacy document, and those two are exactly what the rollback may take back: a rollback that dropped every id it was asked about would take away a concurrent delete's exclusions too, and a marker already committed when the transaction ran is another call's proof that a carry landed rather than this delete's tombstone. It reads back inside the hold, and RAISES `LedgerExclusionError` when the record cannot be made — the carry tombstone included, because a slot whose marker is absent or still `pending` is a CLAIMABLE one, so a delete proceeding on a failed tombstone leaves exactly the resurrection this file exists to prevent. That refusal LEAVES THE SLOT AS IT FOUND IT, and does it INSIDE the hold. The exclusion write, the tombstone settle (`_settle_carry_locked`, the lock-free half of `_finish_carry`, split out because the slot lock is not re-entrant) and the take-back are ONE transaction on the slot's own lock, and being inside it is what makes the take-back safe rather than merely present. Settling the tombstone after the release would publish the exclusion first, and a concurrent delete of the same slot would then read those ids as already present, add none of its own, settle the marker, and UNLINK its transcript on the strength of an exclusion the first call is about to withdraw — resurrecting exactly the state that second delete removed, which is unbounded and unrecoverable. From inside the hold no other delete can read the file until the take-back has already put it back, so the second delete adds the id itself and rests on its own record. The take-back writes back the set the transaction READ rather than subtracting the ids it added; inside the hold those are the same thing, and writing back what was read cannot express anything else. The caller's 409 answers on the strength of "a refusal wrote nothing", which has to be true in `exclude_units` rather than remembered in the handler. A rollback that itself fails is logged with the units left behind and swallowed, so the original failure is what the caller sees; the delete is refused either way. Both halves run off the event loop through one thread hop, because listing a slot's units walks the crew-log root and reads a header per unit while the write fsyncs, and either would stall every other session while one delete runs.

The exclusion is written BEFORE the transcript is unlinked, on BOTH delete paths — the single delete and each row of bulk clear — and a failure refuses that delete with `ledger_exclusion_unwritable` and the row intact. Only that side of the unlink can refuse anything: the crew-log removal runs after the transcript is already gone, so a failure there leaves this slot's surviving units foldable by the next session on the same recycled slot key with nothing left to stop the delete. An undeleted conversation is visible and can be deleted again, while state resurrected into a stranger's session is neither. The listing is by SLOT KEY and a slot key is recycled, so two things keep a successor's units out of the exclusion: the captured session GENERATION must still be current, and the unit the slot is serving on now is never excluded. BOTH are re-read AFTER the listing and before the ids are persisted, because a read taken before it cannot describe what the listing then returned. What makes the second generation read sufficient rather than merely narrower is the order the system's own writers work in: a successor's unit is written by a session that published its reservation on the slot key first, and that publication advances the generation, so a unit new enough to be a successor's cannot appear in the listing without the generation having already moved by the time it is re-read. The first read is kept so a stale claim is refused before the walk is done at all. A reset in the window before the delete otherwise gives the slot a live successor whose unit lands under the same key, and excluding it empties a live conversation's record with no rollback that would fire -- the successor carries a new session id, so the shared-unit rollback does not cover it. The crew-log REMOVAL is fenced by ACP session id and needs none of this; the exclusion does, because its key is the recyclable one. The removal stage that runs AFTER the unlink excludes only the conversation's OWN unit, never a rescan by slot key: the slot's other units are already excluded under the delete's lock, and a rescan at that point could pick up a successor's unit and hide a live conversation's record with nothing left to refuse. The exclusion runs INSIDE that locked transaction and only once the claim is RESOLVED, because that is the first point where the slot owning this transcript is proved: a provisional claim can name a stacked duplicate's slot, and excluding on it empties an unrelated LIVE session's record. The transaction reports the ids it added on the claim, so the caller can take back exactly those. `unexclude_units()` rolls the exclusion back when the delete does not proceed, because those units then belong to a session that still exists; a rollback that cannot be written is PROPAGATED and answered as retryable rather than as a clean refusal, because a request that reports success while a live record reads empty has told the person something untrue. The rewrite and the tombstone withdrawal share ONE acquisition of the slot's lock (`_withdraw_tombstone_locked`, the lock-free half split out for the same reason `_settle_carry_locked` is). Two acquisitions leave a gap in which a concurrent delete commits its OWN tombstone, and the withdrawal cannot tell that marker from the one it is undoing -- `_carry_committed` answers what a marker SAYS, never whose it is -- so removing it would carry that delete's legacy state into a recycled slot with nothing left to put it back. A withdrawal that does not persist is raised rather than logged and dropped, for the same reason the exclusion rewrite is read back: only this path ever removes a committed marker, so a swallowed failure makes the spared session's lost state permanent and silent, while a raise becomes a retryable answer that can succeed. The residue is a process that dies between the two, which is recoverable by hand where the other ordering is not.

`unit-order` holds the slot's units in the order they LAST recorded, one per line, written by the call that records into each. The append is FSYNCED before the update is acknowledged, because the fallback for a missing line is header order and a backward clock step is exactly what that fallback gets wrong -- a crash that keeps the ledger entry and loses the order line would restore a retired session's state over a later one's. RECORD order is what makes it causal, and the fold reads units in it: unit headers carry a wall clock, and a clock that steps backward — an NTP correction, a manual set — sorts a newer unit before an older one, which applies a retired session's goal and phase over a later one's. Ordering by FIRST record is not enough, and the gap is not the clock: a request from a session the slot has since replaced can reach the recorder AFTER its successor has already recorded, and a presence check that never revisits a known id would leave that retired unit last for good, so its phase and next step would win every later fold. The recording unit is therefore MOVED to the end when it is not already there, which makes the file order units by their newest record — the question the fold actually asks — and makes the answer an observation rather than a claim, because among units that have recorded, the one recording right now holds the newest entry whatever any clock says. While a late-arriving retired unit is last its entry genuinely IS the newest one recorded, and the successor's next record corrects the order, so no inversion is frozen. The move is a read-modify-write and runs under the slot's lock, which an unlocked one would use to drop a concurrent first record's append; the ordinary case — one live unit recording repeatedly — is already last and stays a bare read, so no rewrite is paid per update. The log keeps the newest `_MAX_ORDERED_UNITS` distinct ids, so anything absent from it is older than everything in it — a unit predating the log, one whose append failed, or one evicted when the log filled — and all of them therefore apply BEFORE the kept tail, in header order among themselves. Reads deduplicate: the is-it-known check before the append is not atomic, and a repeated id would fold one unit twice, replaying entries the fold has already consumed. The FILE is bounded too, not only the window a read returns: the dedup check sees the window alone, so a slot past the cap re-appends ids that fell out of it, and the file is compacted through an atomic replace once it crosses `_MAX_ORDER_BYTES`. Compacting on a threshold rather than on every record keeps the ordinary path a bare append, and a single read consumes at most `_MAX_ORDER_READ_BYTES` whatever the file's size. Both of those bounds are DERIVED from `_MAX_UNIT_ID_BYTES`, which is ENFORCED at every site that retains an id rather than assumed of the input. Hardcoded, a file bound says nothing about the ids in it: it holds only while every id is far under the per-id bound, and the two drift apart with nothing to catch it. The consequence is not a bounded read, because this read does not reject an oversized file — it comes back SHORT, taking the oldest bytes, while its caller rewrites what it read, so the newest ids would be lost permanently and older units would fold afterward over the current record. Derived, a full window of maximum-size ids is read whole by construction. Refusing is the safe direction at both retain sites: an exclusion becomes a refused delete, which is what that file's count bound already does, and the order log becomes a missing line, which falls back to header order — the same state a crash between the entry and the line leaves.

`carried` is the claim on the slot's legacy document, described next.

### Upgrade carry-forward

A slot whose state was written while the record was a document of its own has state no entry describes, and a loop resuming into the folded record would otherwise find its goal, phase and next step gone. So the first update that finds a slot's folded record empty carries that document into the log as one entry through `_carry_legacy_forward()`, then appends its own. The trigger is the empty folded record rather than an absent unit, because a session's crew log is created on its first turn: a slot that has recorded nothing still has a unit, and keying on the unit would carry nothing at all.

The carry can only run from a WRITE — it needs a crew log to append into, it takes an exclusive claim, and it refuses its caller when another holder is mid-carry — but the first thing a resuming loop does is READ, on its way into the turn. A write-only carry-forward would therefore answer that first turn with the empty record, and no later carry undoes a turn already taken. So `read_state()` folds the same pending entry in WITHOUT appending it, through `_legacy_preview()`: the same payload builder (`_legacy_carry_payload()`), the same projection, the same base checkpoint, so the previewed record is the post-carry record by construction rather than by agreement, and the carry stays the only thing that makes it permanent. Three things keep it from becoming a second authority. It answers only when the folded record has no CONTENT, the same trigger the write path uses, so it can never override anything the log recorded. It stops entirely once the `carried` marker reads `committed` — which is both what a finished carry leaves and what a permanent delete leaves when it tombstones the slot, so a successor on a recycled slot key cannot see a deleted conversation's document through the read any more than through the carry. And it folds ONTO the base rather than replacing it, so a slot that recorded a reason and no state keeps that event. Every failure answers the empty record the caller already had: an unreadable document correctly REFUSES a write, because that write can still carry later, but a read has nothing to offer and must not raise into a nudge cycle. Because the preview has to be reachable for a slot with no crew log at all — the case a pre-crew-log slot is in — the read folds a zero-unit checkpoint rather than returning early on an absent unit. A REFUSED fold is not previewed: that means a reader older than the writer, so the log may hold entries newer than the document, and answering with the document would assert something about a log this build could not read.

The carry is a consumption, not a fallback. `_legacy_document()` is read by that carry and by its read-side preview and by nothing else, and both exist to retire the file rather than to consult it, so the log remains the single authority; once the carried entry lands the record has content and the carry is never taken again for that slot. An entry holds one rejected approach, so the carry brings the goal, phase, next step, artifacts and the newest approach, and its event names how many earlier approaches and event lines it could not bring — counting them keeps the loss visible, while carrying them all would mean an append per row, which is unbounded work inside a turn. The phase rides with that event, so the carried entry keeps the invariant the record rests on. An UNREADABLE document is not an empty one: reading it as empty would land the update, make the folded record non-empty, and retire the only trigger the carry has, so one transient error would orphan the legacy state permanently. It refuses the update instead and releases the claim so the retry carries. Content no retry can parse is a different case and is treated as empty, so the claim is consumed rather than retried forever. A document past the `_MAX_STATE_BYTES` ceiling is not parsed, and a carry whose own append does not drain refuses the update with `LedgerUnavailable` rather than ordering an update ahead of the state it is meant to extend. That refusal releases the claim only when the append is PROVED unable to land — the queue drained and this unit's own seq did not move, so nothing of the carry is in flight. When the flush ran out of budget instead, the append may still be queued, and the process-wide refusal counter cannot say whose write it dropped: releasing there lets the retry, which reads the same empty fold, carry a SECOND time, and the fold then applies both carried entries with nothing that dedups them. So the claim stays `pending` and the retry is answered `busy` until either the queued append lands — after which the fold is not empty and no carry is attempted at all — or the claim goes stale and a take-over carries, which is safe for that same reason. A refusal bounded by the staleness window is the cheaper side of that trade against history no later write repairs.

The claim is TWO-PHASE and answers THREE ways, and `carried` says which phase it is in. `_claim_carry()` creates the marker with `O_EXCL` holding `pending`, and creating it is the claim rather than a flag set afterwards: checking a marker and then carrying is a race two first records on one slot pass together — a resumed loop and its own dashboard tab produce exactly that — and both would append the legacy goal and phase. The read, the decision and the replacement all happen under the slot's own lock: an exclusive create alone picks one winner among callers arriving together, but the take-over path unlinks first, so two callers that both saw one stale marker would each unlink and each create and both would carry. A claim that cannot be made at all is PROPAGATED rather than answered `done`, because `done` lets the update be appended, and an appended update makes the folded record non-empty -- after which the carry is never attempted again and a transient filesystem error has lost the legacy state for good. A caller that finds ANOTHER caller's live claim is answered `busy` and refuses its update with `LedgerUnavailable` rather than recording past a carry that has not landed: its own entry would be appended first and the carry's legacy fields would then apply over it. `_finish_carry()` rewrites the marker to `committed` only once the append is proved, and RELEASES it by unlinking when the carry did not land or when the document read back empty. The commit is FSYNCED and renamed into place like every other control write, and it is READ BACK inside the hold, because a marker that is only in the page cache is not a tombstone: the crash it guards against is the one that would lose it, and a short write on a full filesystem would otherwise leave the slot claimable while the call reported it tombstoned. A commit that does not land RAISES rather than answering `False`, because that answer already means "already committed by another call", which is a slot that IS tombstoned — a caller unable to tell those apart proceeds on the wrong one. The two callers then diverge deliberately: a DELETE turns the raise into a refused delete through `LedgerExclusionError`, mirroring the exclusion write, while the CARRY path logs it and goes on, because there its append is already proved landed, so the folded record is non-empty and the take-over rule refuses a second carry on its own evidence — refusing the update there would fail a carry that worked. A failed RELEASE is still swallowed: it leaves the claim `pending`, which goes stale and is taken over. A release only ever removes a marker that still reads `pending`, and both branches run under the slot's own lock so that check cannot be raced: a committed marker is another call's proof that the carry landed, an ABSENT marker is a claimable one, and a release that withdrew a committed marker would hand the next session on a recycled slot key a fresh claim on a deleted conversation's document. Committing first would make a crash permanent: the claim it left behind would refuse every later attempt at state that was never carried. A `pending` marker older than `_CARRY_STALE_SECS` is abandoned rather than in flight, because a holder's window is bounded by its own append wait, and another call takes it over through the same exclusive create. Taking over cannot duplicate a carry: a carry runs only when the folded record is empty, and a carry that landed makes it non-empty. A `committed` marker is never taken over, which is what stops a permanent delete's preserved document coming back on a recycled slot key. A DELETE settles the marker itself, whatever state it was in: take-over rests on "a landed carry leaves the folded record non-empty", and a delete removes the unit holding that entry, so the record reads empty again -- a marker left `pending` by a crash between the carry append and its commit would then let the next session on that slot key carry the preserved document back in. It settles it even when the exclusion added NOTHING, which is the retry of a delete that already recorded its ids and then failed further on: an early return on "nothing added" would skip the consumption in exactly the case a crash produced, leaving the `pending` marker standing over a record the delete has since emptied. It settles it even when the delete had NO UNITS AT ALL, for the same reason at one remove: the document is the SLOT's rather than any one unit's, a conversation that never recorded has nothing to exclude, and the sweep above is the only thing that ever removes that document — so returning early there leaves it claimable by the next session on the recycled slot key, which is the resurrection this whole mechanism exists to prevent. A delete that does NOT proceed gives the tombstone back through `_withdraw_tombstone_locked()`, the one place that removes a committed marker, because the session it would silence still exists and its pre-projection state is still owed to it; the rollback therefore runs when EITHER the ids or the tombstone need taking back, since gating it on the ids alone would skip it entirely for the no-units delete. The tombstone is lifted only when the rollback leaves the slot with no exclusions at all — an id still recorded is another delete's evidence that it proceeded, and the document is the slot's — and NOT on the path where the transcript did go and only a shared unit comes back out. The residue, named rather than implied: two concurrent deletes of one recycled slot key that both record no ids cannot be told apart this way, so one of them rolling back lifts the other's tombstone.

### Cleanup

Nothing in the product reclaims either on-disk ledger store, so the only cleanup is an explicit operator command: `kirocrew ledger-sweep`, owned end to end by `kiro_crew.ledger_sweep` (`run_command()` is what `cli.py` dispatches to). It is its own top-level command and not a `doctor` mode, for two reasons that are not symmetry: `doctor` is read-only by its own contract — a diagnostic run because something broke must not unlink files — and `--purge` is irreversible, so the two do not belong under one name; and a separate command removes a whole class of hazard, because inside `doctor`'s flat flag namespace a modifier could be parsed without its mode, so bare `doctor --purge` ran the health pass and exited 0 and read exactly like a purge that found nothing. Here every flag belongs to this command and argparse refuses it anywhere else (`test_the_sweep_is_its_own_command_and_doctor_stays_read_only`). The dry run's closing hint repeats the window the report was built with — `kirocrew ledger-sweep --purge --older-than-days N` — never a bare `--purge`, which would re-scan at the default and delete the ledgers between a larger preview window and 30 days, ones the report never listed (`test_the_printed_purge_hint_carries_the_windows_the_preview_used`). The `kirocrew-commands` skill, which is injected into model context, lists the dry run only: the purge spelling is printed by the dry run to the operator who ran it, and no model-reachable surface names it. It takes `--purge`, `--older-than-days N` (default `ledger_sweep.DEFAULT_OLDER_THAN_DAYS`, 30) and `--purge-unreadable`.

**It stays off every automatic path.** It is not a gateway-start hook, not part of the history-delete funnel described above, and deliberately not an MCP tool: the deletion is irreversible, so no model-reachable surface reaches it. `ledger_sweep.scan()` changes nothing at all, and a purge is a second, separate invocation over the report the first one printed. `scan()` never raises for an absent store or for any damaged record inside one, but it does raise `OSError` when a ledger root exists and cannot be read — that is the whole store the sweep cannot see, and a clean empty report over it would be a false "nothing to clean"; the CLI exits non-zero with the error. `test_an_unreadable_ledger_root_raises_instead_of_reporting_nothing_to_clean` and `test_an_absent_ledger_root_is_an_empty_report` pin both halves.

`scan()` answers "leave it alone" unless the record itself proves otherwise:

| Record | Candidate when | Never a candidate |
|---|---|---|
| session ledger | `phase` in `session_ledger.TERMINAL_PHASES` and age ≥ threshold | any in-flight phase, at any age, with no exception |
| work ledger | every item in `work_ledger.TERMINAL_ITEM_STATES`, at least one of them closed, and age ≥ threshold | one open item, at any age |
| work ledger | — | no items at all and a header present, at any age, torn header or not: finished-looking is not finished |
| work ledger | listed `unreadable` when it has neither header nor items and age ≥ threshold — the residue a purge leaves when a lock file could not be unlinked | — |
| either | listed `unreadable` when the record cannot be parsed AND age ≥ threshold | a record younger than the threshold, or a conductor with an open item — damage is classified last |

**The sweep infers nothing about sessions.** It reads the two ledger stores and nothing else — no transcript directory, no session map — so every verdict is one the record itself supports. "The session is gone" would be a disk inference, and an inference is the wrong thing to act on against an irreplaceable record: an in-flight session ledger is kept at any age with no exception, and a conductor holding no items is kept at any age too, because that shape is finished-LOOKING rather than finished — a ledger opened seconds ago and one whose creator died before dispatching look identical, and no lock can hold "its session is gone" still through a delete. Requiring a closed item is what keeps the empty conductor out of the purgeable set; an operator who wants to see such stores lists the work-ledger root, since this command reports only what it can act on. `test_an_in_flight_session_ledger_is_kept_at_any_age` and `test_a_conductor_with_no_items_is_kept_at_any_age` pin both halves.

A conductor record is validated, not merely counted as present: an absent, torn, oversized or non-object `conductor.json` all read as `unreadable`, because presence is not readability and treating only absence as damage let a malformed header pass as a finished ledger. The check is the store's own, `work_ledger.header_damage()`, and `work_ledger.purge_conductor()` re-applies it under its lock — a header that tears between the report and the purge is refused by a plain purge exactly as the scanner would have refused to list it as finished, and goes only with `allow_unreadable` (`test_a_header_that_tore_after_the_scan_is_refused_by_a_plain_purge`, `test_purge_conductor_refuses_a_torn_header_unless_the_caller_asks`).

Age is a ledger's LAST WRITE, not its terminal stamp alone. For a session ledger it is the newer of `finished_at` and `state.json`'s own mtime (`session_ledger._session_age_days` via the sweep's reading): `session_ledger.record()` re-stamps `finished_at` only on a terminal PHASE write, so a goal, artifact or event-only update to an already-terminal ledger leaves the stamp alone while rewriting the file, and a record touched a minute ago would otherwise read as thirty days idle — `test_a_terminal_session_ledger_written_to_recently_is_not_old` pins the scanner and `test_the_session_guard_refuses_a_terminal_ledger_touched_after_the_scan` the guard, which applies the same reading under the lock. For a work ledger it is the NEWEST of three readings — the newest item `closed_at`, the header's own mtime, and the newest write under `items/` by mtime (`ItemCensus.newest_write_at`, every non-lock file: records, event logs, and a torn or misnamed file the census could not read). The third exists because an unreadable item carries no stamp the census can read and `_create_item` writes it without touching the header, so a crash-torn write into an old conductor would otherwise be invisible to the window and deletable under `--purge-unreadable` the moment it landed; lock files are excluded because the purge itself touches them and a reading that moved under the reader would refuse forever. `test_a_recent_unreadable_item_keeps_an_old_conductor_inside_the_window` pins the scanner and the store's recheck together. The header reading — the conductor's `goal` action rewrites `conductor.json` with no item involved, and a conductor that just bumped its round on old closed items is a live conductor about to create; newest close as an instant through `_parse_iso`, never as the lexically largest string, because the stamps carry the local offset at write time and two of them can sort in the wrong order across a DST change — falling back to `state.json` / `conductor.json` mtime when the stamp is empty — without that fallback a record whose stamp never landed would be permanently uncollectable.

`work_ledger.census_items()` reads the item files directly instead of through `work_ledger.list_work_items()`, which skips an unreadable item — the right answer for a listing and the wrong one here, because "no open items" would otherwise be provable by damaging one. A conductor with any unparseable item is reported `unreadable` and kept.

**Damage is classified LAST**, after the open-item, age and no-items gates, in both scanners. An unreadable record is deletable with `--purge-unreadable`, so classifying damage first would let one torn item file carry a live open item — and the work its worker is still reporting against — into that deletion. The no-items keep sits ahead of it for the same reason: `--purge-unreadable` authorises deleting a record that cannot be READ, not one that was never shown to be finished, and an empty conductor with a torn header is both — so it is kept, not listed as damage, and `work_ledger.purge_conductor()` refuses the same shape under its lock so a caller-built report cannot reach it (`test_an_empty_conductor_with_a_torn_header_is_kept_not_offered_as_unreadable`, `test_purge_conductor_refuses_a_conductor_with_no_items_at_all`). An items directory that cannot be enumerated is not that case: it is damage with an unknown item count, and is listed. Nor is a directory with NEITHER header nor items: that is the residue a purge leaves when a lock file could not be unlinked — on Windows a writer queued on the conductor lock holds its handle through the post-release unlink, so the identity files go and the lock file stays — and it holds nothing a conductor wrote, so both the scanner and `purge_conductor` classify it as damage (`no conductor record`), listed and removable with `--purge-unreadable` (`test_a_lock_only_residue_is_listed_as_damage_and_removable_with_the_flag`, `test_purge_conductor_removes_a_headerless_itemless_residue_with_allow_unreadable`). The age gate runs ahead of it for the same reason in a different form: a file being replaced right now can itself read as damaged (a Windows read of a file another handle holds open raises), and for a damaged record age is the NEWER of the directory mtime, which `atomic_write` refreshes on every replace, and the record file's own mtime, which an in-place write (a truncation, a hand edit) freshens without the directory (`session_ledger` residue via `_damaged_session_age`, applied by the scanner and by `_still_finished`'s damaged branch alike; `test_a_recently_truncated_session_record_in_an_old_directory_is_kept`, `test_the_unreadable_session_guard_reads_the_file_mtime_not_only_the_directory`). So a live ledger reads as young and is left alone rather than reported as damage. `test_a_torn_item_beside_an_open_one_keeps_the_conductor` and `test_a_freshly_written_ledger_that_reads_as_damaged_is_left_alone` pin both halves. The census also answers the worker-binding question, which is why there is no separate binding scan: a binding names one conductor and one of its items, so a binding into a ledger whose every item is terminal is a binding onto a terminal item — the stale half-state `work_ledger._refuse_if_worker_holds_open_item()` documents as replaceable by the next bind. The sweep therefore leaves `bindings/` alone rather than deleting a worker's only report channel on a guess.

**Every string the report prints is read off disk, so every one is sanitised first.** `ledger_sweep._safe()` replaces every C0 and C1 control character — ESC and DEL included — with `U+FFFD` and elides past 120 characters; only the ledger kind and the age, which this module computes itself, print as they are. A ledger key is a session key and a channel puts arbitrary text in one, a phase and a goal are model-written, and a store directory name can be hand-created, so an unescaped line lets stored bytes move the cursor, repaint the summary count the operator is about to act on, or retitle the window. A stripped control leaves a visible mark rather than closing up into a different-looking string. `test_control_characters_in_stored_text_never_reach_the_terminal` and `test_a_very_long_stored_field_is_elided_rather_than_printed_whole` pin it.

An unreadable record is listed and NOT purged unless `--purge-unreadable` is given, and a store whose `slot_key` breadcrumb is gone is never purged at all: the directory name is a fold plus a digest and is not decodable, so neither delete primitive can be aimed at it, and the sweep names the path for a human instead. The breadcrumb is the ONLY source of a store's key for both kinds — the work header carries a `slot_key` field too, but recovering the key from it would let a store whose breadcrumb write failed be purged, against this rule. `test_a_work_store_without_a_breadcrumb_is_reported_and_never_purged` pins the work half alongside the session one.

**Neither primitive ever follows a link.** A store directory, or an `items/` inside one, that is a symbolic link or a Windows junction names files that are not this ledger's, and a removal through it would land on them — nothing in the store's own records could tell. `session_ledger.is_link()` is the one predicate: both scanners list a linked store directory as `report` (never aimed at), `census_items()` reports a linked `items/` as damage, `session_ledger.purge_matching()` skips a linked store and `work_ledger.purge_conductor()` refuses one before taking any lock — whatever flags are given, since this is not damage an operator can ask to clear but a delete aimed somewhere else — and both content walkers unlink a linked entry as a name rather than descending into it. `test_a_linked_items_directory_is_damage_and_the_purge_never_follows_it`, `test_a_linked_store_directory_is_reported_and_never_aimed_at`, `test_purge_matching_never_follows_a_linked_store_or_a_linked_entry` and `test_the_content_walker_unlinks_a_linked_items_directory_as_a_name` pin every site.

**Both primitives are aimed by key, not by path**, and each resolves the directory itself. A store is therefore purgeable only when the directory the scan looked at is the one its own breadcrumb key resolves to — `Candidate.addressable`, checked by `_path_matches_key()` in both scanners and re-asserted in `purge()` immediately before either primitive is called. A copied store, or a hand-made directory carrying another ledger's breadcrumb, would otherwise send the delete at the CANONICAL ledger: one the scan never listed and the operator never saw on the report they approved. Such a store is reported so it can be removed by hand and is never purged, `--purge-unreadable` included — and when its record reads, it is reported as `report` and counted report-only, not as `unreadable`: that word is a statement about the record, and a store whose only fault is its name is not corrupt. A damaged store whose name is also wrong is both, and stays `unreadable`. `test_a_copied_work_store_never_sends_the_purge_at_the_canonical_ledger`, `test_a_copied_session_store_is_reported_and_never_purged` and `test_purge_re_asserts_the_path_identity_on_a_hand_built_report` pin all three sites.

**A failure to enumerate an items directory is damage, never "zero items"**, in `work_ledger.census_items()`, and therefore in both the scanner and the locked recheck that share it. It is the one case where the count and the truth are unrelated: read as empty it selects the ORDINARY purge, which removes `conductor.json` and leaves the item data it could not see standing — a ledger destroyed down to the records that made it a ledger. An absent items directory is not damage, because a conductor that never created an item has none. `test_an_unreadable_items_directory_is_damage_not_a_finished_ledger` and `test_the_store_refuses_an_unreadable_items_directory_under_its_own_lock` chmod the directory on POSIX; `test_an_enumeration_error_is_damage_in_the_census` covers every platform by making the enumeration raise.

The scanner has no census of its own: it calls `work_ledger.census_items()`, which reads each item through `_read_json_record` — the store's own reader, which already applies the size ceiling and answers `None` for absent, torn, oversized and non-UTF-8 alike.

**A purge's lock never creates the store it is about to delete.** `session_ledger._locked(create=False)` and `conductor_lock(create=False)` skip the `mkdir` and the `O_CREAT`/`touch` a writer's lock performs and raise `FileNotFoundError` for a store that is gone, and both purges skip such a store. Otherwise two sweeps racing over one store would have the second rebuild the directory the first just removed — holding nothing but a lock file, with no breadcrumb, which no later purge could name — and only then find nothing to guard. `test_a_purge_racing_a_finished_purge_recreates_nothing` pins it on both halves; `test_a_writer_lock_still_creates_the_store` pins that a writer's lock is unchanged.

**The delete decision is re-taken under the store's own lock, by the store that owns it.** `ledger_sweep` selects; `session_ledger.purge_matching(guard=...)` and `work_ledger.purge_conductor()` decide. The guard is called inside that ledger's own `_locked()` hold and the removal happens in the same hold, so a session resumed after the scan is refused rather than erased — selecting under the lock would not be enough, which is why the guard is a callback and not a filter the caller applies first. The guard applies the WHOLE rule the scanner applied — terminal phase and age, or for a damaged record still-damaged and the DIRECTORY age the scanner used — not the phase or the damage alone (`test_the_unreadable_session_guard_refuses_a_store_written_to_after_the_scan`: a torn store written to between the report and the purge is fresh by its directory and is stood down on): `session_ledger.record()` re-stamps `finished_at` on every terminal write, so a session that resumed and finished again inside the purge window is terminal but young, and young means it was just in use. `purge_conductor(slot_key, *, allow_unreadable, idle_for)` takes both keywords with NO defaults — an irreversible delete with one production caller must not let a future caller skip the retention window or the unreadable-record refusal by omission; "no window" is spelled `idle_for=timedelta(0)`, visibly. It takes `conductor_lock`, then every item lock non-blocking in sorted order (`_hold_every_item_lock`, the documented conductor → item order), and holds all of them through the removal. An item lock that cannot be taken is a worker mid-write and the purge refuses: a file being replaced reads as unreadable to the census — a Windows read of a held file raises, a POSIX half-rename is torn — so a census alone cannot tell "damaged" from "being written", and without the item locks `--purge-unreadable` would let an operator remove an item its worker is writing this instant. `test_purge_conductor_refuses_while_a_worker_holds_an_item_lock` and `test_purge_conductor_holds_every_item_lock_through_the_removal` pin it. Inside those holds it re-runs the item census and raises `CODE_LEDGER_NOT_FINISHED` on any open item, on an items directory it cannot enumerate, on any unreadable item unless the caller passes `allow_unreadable`, and — against the `idle_for` window every caller must pass, as the sweep does with its own — on any activity by either writer (`_newest_activity`: newest close or header mtime, falling back to the directory mtime when the header cannot be statted — a store whose header is gone was written to when it went, and dropping that reading would leave the newest close as the only age; `test_newest_activity_falls_back_to_the_directory_when_the_header_is_gone`) younger than that window. The census is `work_ledger.census_items()`, the one classification both the sweep's scanner and this recheck use, so the two cannot disagree — and it applies `read_work_item`'s own identity rule: a record whose stored `item_id` names a different item than the file it sits in is a misnamed or hand-moved file the store will not read, so for a delete decision it is `unreadable`, never `closed`, whatever its `state` says — and so is any `.json` under `items/` whose stem is not an id the store minted, which a census that skipped it would let a plain purge remove with the rest of the contents (`test_census_reads_an_item_shaped_file_with_a_foreign_stem_as_unreadable`) (`test_census_reads_a_misnamed_item_as_unreadable_not_closed`). `_create_item` holds that same lock across its whole transaction, so a conductor cannot mint an item between the census and the removal — and it re-reads the header under that lock and refuses with `CODE_NO_LEDGER` when the header is gone, so a create that was waiting behind a purge cannot write an item into a store that no longer has one. The sweep records such a refusal as `stale`, not as a failure: the guard working is the expected outcome, not an error.

That census reads the item files directly and classifies an unrecognised `state` as damage rather than closure — so `--purge-unreadable` still clears it, while counting it as an open item would leave the ledger permanently uncollectable. `test_purge_conductor_refuses_a_ledger_that_still_has_an_open_item`, `test_purge_conductor_refuses_a_torn_item_unless_the_caller_asks`, `test_purge_conductor_reads_an_unknown_item_state_as_damage_not_as_closure` and `test_a_session_ledger_resumed_after_the_scan_is_refused_under_its_lock` pin the store half.

`ledger_sweep.purge()` does not re-scan to "confirm" the report before entering a store — the store's own locked refusal is the confirmation, and it is recorded as `stale`. A report is a snapshot and the gateway keeps running while an operator reads it, so a ledger can be reopened, an item created, or a header touched in between — each of which makes the ledger live again, and each of which the store's own locked check catches. `test_a_ledger_reopened_after_the_scan_is_not_purged`, `test_a_conductor_that_opened_an_item_after_the_scan_is_not_purged` and `test_the_session_guard_refuses_a_terminal_ledger_touched_after_the_scan` pin that a stale report cannot delete.

Deletion goes through the two primitives that exist for it. Session ledgers use `session_ledger.purge_matching(exact_keys, *, guard)`, which matches EXACT keys only, so the only thing that can match is a breadcrumb holding exactly one of the keys the report named — a lossy fold is the one way a caller could remove a ledger it never listed, so it is refused rather than kept as a default (`test_purge_matching_is_exact_and_a_folded_spelling_matches_nothing`). Work ledgers use `work_ledger.purge_conductor()`: it takes `conductor_lock` — first in the store's lock order — removes the directory contents under that hold, and unlinks the lock file only after releasing it, because Windows refuses to unlink a file an open handle still holds and doing it inside the critical section would leave the directory behind on exactly the platform the lock covers.

**Removal is ordered and the identity files go last.** `purge_conductor()` removes items and any other content first, counts every failure instead of ignoring it (`_remove_contents_locked`), and only once everything else is gone unlinks `conductor.json` and then the `slot_key` breadcrumb — header first, breadcrumb after, so a header unlink that fails leaves a store that still names itself and can be purged again rather than one no key can reach. So the store is never left as a header-less pile of items nor as a nameless one: on any failure it keeps whatever identity it still has and reads as `unreadable` to the next sweep. `test_purge_conductor_keeps_the_breadcrumb_until_the_header_is_gone` pins the order. Every lock file — the conductor's and each `items/<stem>.lock` — is left standing by that content pass and removed by `_remove_lock_shell` only after every hold is released, because the purge holds all of them open and a Windows `os.open` handle has no `FILE_SHARE_DELETE`: unlinking a held lock raises, so removing them inside the hold would count a failure per item that ever existed and the work half could never succeed on Windows. `items/` is therefore walked file by file rather than `rmtree`'d. `test_purge_never_unlinks_a_lock_file_while_its_handle_is_held` pins it under simulated Windows unlink rules. `test_purge_conductor_keeps_the_header_when_any_content_survives` and `test_purge_conductor_removal_failures_are_counted_not_ignored` pin it. The session half has the same shape, and only that shape — `session_ledger.purge_matching()` has one spelling of deletion, locked, ordered and identity-last, and its `guard` is a required parameter, so no caller can skip the re-decision by omission: `session_ledger._remove_store_contents()` removes other entries first, counts failures, and unlinks `state.json` and `slot_key` only once the count is zero, so a failed removal leaves a store that still has its record and still names itself; a store that could not be fully removed is not counted as removed. `test_purge_matching_with_an_accept_all_guard_is_still_locked_and_ordered` pins that even an accept-all guard runs under the lock and the ordering. `test_guarded_purge_keeps_the_record_and_breadcrumb_when_any_content_survives` and `test_guarded_purge_counts_rmtree_failures_instead_of_ignoring_them` pin it.

**The lock inode.** Removing a store removes the inode its lock is taken on, and the kernel still grants a queued writer the lock on that detached inode — so without a check, a writer that was waiting behind the purge would proceed, its `mkdir` would recreate the directory, and it would publish a torn store into a purged key: state without a breadcrumb, or a header-less item. Two things close it together. `session_ledger.require_lock_inode()`, run by both `_locked()` and `work_ledger._open_lock()` immediately after the acquire, inside the hold, compares the identity of the file the writer holds (`fstat`) against the file now at the lock's path (`stat`) and refuses with the same `OSError` a held lock produces when the path is gone or the inode differs. And the purge unlinks every lock file **inside the hold** (`session_ledger.unlink_lock_in_hold`), so the path is already gone by the time a queued writer acquires — unlinked after release there is a window where the writer acquires, validates against a path that still exists, proceeds, and the late unlink detaches the very inode it holds, handing the next writer a second one. On Windows the in-hold unlink is refused and happens after release instead, which is safe there precisely because it fails whenever a writer still holds a handle: the OS keeps lock identity stable, a successful late unlink proves nobody was queued, and `require_lock_inode` is therefore inert on Windows by construction. The post-release step unlinks **only** the lock paths the hold could not (`lock_gone` / `item_locks_left`): a path already unlinked inside the hold is never touched again, because a writer that refused on the detached inode may by then have retried, rebuilt the store and taken a fresh lock at that path, and a second unlink would detach that fresh inode under its holder. `test_the_post_release_shell_never_touches_a_lock_the_hold_already_removed` pins it on both halves. That post-release step runs after EVERY hold is released, the conductor's included: on Windows the conductor lock's own file is one of the paths the hold could not unlink, so a shell that ran inside that hold raised on it, left the directory non-empty and reported `False` over a store it had already emptied. `test_purge_never_unlinks_a_lock_file_while_its_handle_is_held` and `test_purge_matching_succeeds_under_windows_unlink_rules` simulate the Windows rule on every platform — tracking both the `os.open` and the module-`open` lock handles, since a version that tracked only the first was blind to the conductor lock and passed over exactly that regression. `test_the_lock_inode_is_unlinked_inside_the_hold` and `test_every_lock_inode_is_unlinked_inside_the_holds` pin the POSIX order. `_create_item` and `_write_goal` additionally refuse with `CODE_NO_LEDGER` when the header FILE IS ABSENT under the lock (`_header_under_lock`) — a `goal` that waited behind a purge must not rewrite its stale pre-lock snapshot into the removed store, which would resurrect a header with no breadcrumb. That is the one case the purge needs refused and the only one refused: a header that is present but does not parse under the lock is a damaged live ledger, not a purged one — the caller holds the lock, so no other writer is mid-replace — and the pre-lock snapshot stands in for it, so a `goal` rewrites and repairs the header and a create takes its default round from it. File presence is what separates "purged" from "damaged" under a lock the purge also takes. `test_goal_refuses_when_the_header_is_gone`, `test_create_item_refuses_when_the_header_is_gone` and `test_a_torn_but_present_header_is_repaired_from_the_snapshot_not_refused` pin the two sides. And every writer to an EXISTING store takes its lock non-creating: `conductor_lock` and `item_lock` create the lock file and `mkdir` the store around it, which is right for `ensure_conductor` and `_create_item`'s new item and wrong everywhere else, because a `goal`, an item-create or a worker report that arrives after the purge would rebuild `<store>/.lock` or `<store>/items/<id>.lock` on its way to refusing — a lock-only store with no header and no items, which the no-items keep hides forever. So `_write_goal` and `_create_item` take `_existing_conductor_lock` (a missing lock file is `CODE_NO_LEDGER`) and the three item writers take `item_lock(create=False)` (a missing lock file is `CODE_UNKNOWN_ITEM`, unless the item record is still there and only its lock file was hand-removed, in which case the store exists and the lock is recreated — under the conductor lock, taken non-creating, with the record re-checked inside that hold, because the purge removes records and lock files under the same lock and a plain creating open in the gap would lose the race and rebuild the very lock-only store the parameter exists to prevent). `test_a_late_report_on_a_purged_ledger_refuses_and_rebuilds_nothing`, `test_a_goal_on_a_purged_ledger_refuses_and_rebuilds_nothing`, `test_an_item_that_lost_only_its_lock_file_is_still_writable` and `test_the_lost_lock_recreate_loses_a_purge_race_without_rebuilding_the_store` pin the four behaviours. `test_goal_refuses_when_the_header_is_gone` pins the goal half. `test_a_writer_queued_behind_a_purge_refuses_instead_of_publishing`, `test_every_store_lock_runs_the_inode_check_after_acquiring`, `test_a_record_queued_behind_a_purge_refuses_instead_of_publishing` and `test_create_item_refuses_when_the_header_is_gone` pin it.

`--older-than-days` must be a **finite** count of days. `math.isfinite` runs before the sign check, because every comparison against NaN is false: a NaN window passes `window < 0` and then makes every `age < window` false too, which admits every ledger in both stores at once. Infinity is refused with it — it is not a window, and reading it as "collect nothing" would make a typo look like a working command.

`test_ledger_sweep.py` pins the rules: `test_dry_run_lists_both_kinds_and_deletes_nothing`, `test_purge_removes_only_the_candidates`, `test_an_in_flight_session_ledger_is_never_a_candidate`, `test_a_conductor_with_an_open_item_is_never_a_candidate`, `test_threshold_is_a_boundary_not_a_hint`, `test_unreadable_session_state_is_listed_but_survives_a_plain_purge`, `test_a_torn_item_record_makes_the_whole_conductor_unreadable`, `test_a_store_without_a_breadcrumb_is_reported_and_never_purged`, `test_a_conductor_with_no_items_is_kept_at_any_age`, and `test_a_window_that_is_not_a_finite_count_of_days_refuses` (a clamped negative window would make every ledger a candidate). `test_work_ledger.py::test_purge_conductor_removes_the_ledger_under_the_conductor_lock` pins the lock, asserting what was gone while the hold was still open rather than the return value, which a purge running entirely outside the lock would also produce.

## 3. State record and bounded writes

The `ledger` fold renders these fields, the same shape every reader already expected of the stored document, so the MCP tool, the route and the injected snapshot do not have to learn a new one (see `crew_log.projection`'s ledger render):

| Field | Meaning |
|---|---|
| `schema` | stored schema marker |
| `goal` | binding objective |
| `phase` | current free-form work phase |
| `next` | concrete resumable intent |
| `tried` | rejected approaches with their reason and timestamp |
| `artifacts` | string pointers to work artifacts |
| `events` | recent classified progress entries |
| timestamps | creation, latest progress, and terminal-completion time |

`session_ledger._entry_data()` writes only the fields a call supplies, because the fold reads presence as "changed": writing every field on every entry would make a call that set only `next` also assert an empty goal, and the record would lose the goal it never touched. Omitted fields retain their prior folded value; an artifact update merges with the retained map; a supplied rejected approach appends to `tried`; a nonblank event appends to `events`. The fold derives every timestamp from the entry envelope, so the record has one clock, and `read_state()` treats an unreadable, malformed, undecodable, or oversized log as the empty record rather than failing a turn.

Every accepted record advances `last_progress_at`. Changing `phase` requires a nonblank event and a recognized event kind from `session_ledger.EVENT_KINDS`. The phase and its event are fields of the same `ledger/recorded` entry, so a crash cannot expose a phase move without its classified reason; this is the load-bearing audit trail, now a property of one entry rather than of two writes a crash can separate. A phase in `session_ledger.TERMINAL_PHASES` stamps `finished_at`; a later non-terminal phase clears it. An unrecognized `event_kind` on an event that does not change phase is coerced to `note` at the writer, so the declared vocabulary is a closed enum the append path enforces and no call site can widen it.

Bounds are applied twice, and the reason is that a file's bytes are not the writer's to promise: each entry is clamped when it is built AND when the fold reads it, so a runaway writer degrades to a clamped record while a damaged or planted line is exactly the input that ignores the writer's clamp. Text, phase, artifact key, rejected-approach count, artifact count, event count, event tail, and snapshot sizes stay bounded, and the fold evicts the oldest rejected approaches, artifact pointers, and events when their retained limits are reached, keeping a resumed session from accumulating unbounded durable context. The `session_ledger._MAX_STATE_BYTES` ceiling is the size gate on the legacy `state.json` residue that the carry-forward and the sweep read, not part of the live record path.

`session_ledger.record()` returns the record the appended entry produces, folded by the same fold every reader uses — the state on disk, advanced over this one entry — so a caller's post-write view is the record it just wrote rather than a second implementation of the update rules. The append is bounded against a live cross-process holder by `_locked()`, which fails closed with `OSError` rather than entering the critical section unserialized.

## 4. MCP surface and authorization

`mcp_tools.__init__.DOMAIN_MODULES` registers `mcp_tools.ledger`. `session_ledger_read` has no arguments and returns the calling session's folded state and recent event tail. `session_ledger_record` accepts only optional state fields; `validation.SESSION_LEDGER_RECORD_SCHEMA` validates their types and lengths, while `session_ledger.record()` enforces the conditional phase/event rule.

`mcp_tools.ledger._strict_session_key()` obtains a gateway-authored session identity before either tool calls the loopback routes. This is load-bearing because the lenient resolver can walk a subagent process tree to its parent; rejecting an unverified identity prevents a subagent from reading or overwriting the parent's ledger. `test_mcp_tools_refuse_without_strict_identity` and `test_mcp_tools_pass_the_verified_key_to_transport` enforce that boundary.

`dashboard.handlers.session_ledger._resolve_ledger_key()` derives storage identity from the recognized `X-Session-Key`, never the request body. The routes reject missing or unrecognized identities and restricted session modes, so a request can read or write only its own durable ledger; incognito, temporary, and guest sessions cannot create durable ledger state and receive the restricted-session refusal. The record route resolves the ACP session unit currently serving the slot, returns the folded record on success, 400 for invalid input or a phase without its required event, 413 when the update cannot fit one crew log entry, 409 when the crew log is unavailable, and a retryable 503 for a storage failure, and it validates that artifact maps contain only strings. `test_route_refuses_unrecognized_session`, `test_route_refuses_restricted_session`, and `test_route_rejects_non_string_artifacts` cover those boundaries.

## 5. Auto-nudge injection

`dashboard.handlers.autonudge.compose_nudge_body()` renders the normal nudge body, then reads `session_ledger.render_snapshot()` in a worker thread. A nonempty, non-terminal ledger snapshot prefixes the nudge; an absent ledger, terminal phase, or snapshot exception leaves the nudge body unchanged. `test_compose_nudge_body_prefixes_snapshot`, `test_compose_nudge_body_unchanged_without_ledger`, and `test_compose_nudge_body_survives_snapshot_failure` enforce those outcomes.

`session_ledger.render_snapshot()` reads one fold — the record has no file to stat, so asking whether it exists and asking what it says are the same question — and includes the current goal, phase, next step, recent rejected approaches, and artifact pointers, applying its own rendering bounds so every injected snapshot stays small against a clamped-but-full record. It omits terminal records because completed work provides no next-cycle steering; `test_snapshot_empty_without_ledger_or_when_terminal` and `test_snapshot_contains_state_and_is_capped` guard this behavior.

Every `_fire_*_nudge` adapter in `slack.gateway` calls `compose_nudge_body()`, including the messaging and dashboard transports. `test_gateway_fire_callbacks_use_the_composer` enumerates adapters rather than pinning their count, so a new transport cannot silently bypass the ledger snapshot.

## 6. Failure behavior and scope

A read failure yields the empty record. A ledger write fails explicitly when the live session lacks a crew log, when the crew log is disabled, or when the session id is absent; the route maps those cases to `crew_log_unavailable`, and a storage failure remains retryable. Both closing a tab and permanently deleting a session's history are deliberately different acts: the crew-log record goes with the unit the delete funnel removes, while the legacy ledger-store residue is left for the explicit sweep in [Cleanup](#cleanup), which reports rather than deletes any record it cannot parse. Snapshot failures are best-effort and never prevent the nudge from firing.

The ledger does not journal individual tool operations, arbitrate crew-log write ownership with leases, or add a dashboard UI. It records state between wakes; the session crew log owns persistence and deletion, the MCP tools and nudge composer are its public surfaces, and the legacy ledger-store helpers exist only for explicit residue cleanup.
