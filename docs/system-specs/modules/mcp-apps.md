# MCP Apps (SEP-1865 interactive app rendering via gatewayd)

Interactive MCP Apps: a pooled MCP server declares a `ui://` resource on a tool; when that tool's result flows through gatewayd, the gateway fetches the app's HTML document, spools it to disk, and injects an opaque marker into the result text. The dashboard intercepts the marker, renders the app inline at the tool-call transcript row inside a sandboxed null-origin iframe, and relays the app's `tools/call` requests back through the gateway under a deny-by-default visibility gate.

Producer side is gated by the `KIROCREW_MCP_APPS` env flag (default OFF — flag off is byte-identical legacy behavior). The dashboard consumer side is flag-independent: a marker that appears is handled.

## The four durable contracts

These are persisted-data / wire contracts (one-way doors). Any breaking change MUST bump the relevant version and update this spec in the same commit.

### 1. Render marker grammar (persisted in transcripts)

`[kirocrew-mcp-app:<id>]` where `<id>` is exactly 32 lowercase hex chars (`uuid4().hex`). Producer: `mcp_gateway/apps.py` (`MARKER_PREFIX`/`MARKER_SUFFIX`, appended to the first text content item of the intercepted result). Consumer: `mcp_apps_render.MARKER_RE` (anchored to exactly 32 hex; malformed markers are ignored, never treated as ids). The marker is stripped from displayed/persisted transcript text after interception.

### 2. On-disk spool record (schema v1)

Path: `$KIROCREW_HOME/mcp-apps/<id>.json` (override: `KIROCREW_MCP_APPS_SPOOL`), mode `0600` in a `0700` dir. Writer: `mcp_gateway/apps.py::write_spool` — persists ONLY the schema keys (extras dropped): `schema`, `server`, `tool`, `session_key`, `callback_secret`, `pool_digest`, `html`, `csp`, `permissions`, `structured_content`, `tool_input`, `result_content`, `created_at`. `tool_input` (the originating tools/call `arguments`) and `result_content` (the result `content` array) are ADDITIVE optional v1 fields — readers `.get()` them; they feed the SEP-1865 `ui/notifications/tool-input`/`tool-result` notifications so an app initializes from its real state. On Windows the record and directory get an owner-only DACL via `platform_compat.restrict_to_owner` (POSIX mode bits are not enforced there); a record whose lockdown fails is unlinked and the write raises (fail-closed — the interception failure-safe path delivers the original result). The record is refused if it would exceed the shared read cap (below).

- `schema` — `SPOOL_SCHEMA_VERSION = 1`, single source of truth in `mcp_apps_render.py` (the writer imports it). **Enforced fail-closed by every reader**: `load_spool` rejects any record whose `schema != 1`, so a stale reader refuses rather than silently mis-reads a future shape.
- `callback_secret` — **the app's callback capability (#418)**. A high-entropy `secrets.token_urlsafe(32)` minted per render. Delivered ONLY over the owner-only WS render frame and REQUIRED (constant-time compared) by the `app-call` handler. This is what splits the render id from the capability: the model-visible marker carries only `spool_id`, which authorizes NOTHING on its own, so a model that reads the marker from its own context cannot invoke app-visible tools against the uid socket.
- `pool_digest` — exact PoolKey digest of the producing backend; the app-call path resolves its backend exclusively through this (never by server name), so a callback can't cross tenant partitions. Records without it are denied.
- `session_key` — the producing session; binds the render (below).
- Read cap: 8 MiB (`MAX_SPOOL_BYTES`); oversized records are refused at write time and ignored on read.
- Sidecar `<id>.rendered` — single-consume render claim (below).

Lifecycle / TTL: `sweep_spool(max_age_hours=24)` reaps records (and their sidecars) past 24h. It runs at gatewayd startup and opportunistically on every `write_spool`; additionally, `load_spool` enforces the same 24h TTL on READ (`SPOOL_TTL_SECS`) — refusing and reaping a stale record + sidecar even if no sweep has run since, so a `callback_secret` cannot outlive the window. Expiry is a deliberate capability-lifetime decision: sweeping a record also expires its `callback_secret`, so the embedded app's ability to call tools ends with it — 24h outlives any dashboard session while bounding disk growth (a real PDF-viewer record is 4.4MB per render).

### 3. gatewayd `app-call` control frame (unix socket)

`{"type": "app-call", "spool_id": <32hex>, "callback_secret": <str>, "tool": <name>, "arguments": {…}}` on the uid-gated gateway socket (same trust basis as `claim`/`abort`). Handler: `mcp_gateway/app_call.py::handle_app_call`. Reply shapes: `app-result` (backend result), `app-error` (backend JSON-RPC error relayed verbatim), `app-call-rejected` (gateway policy/infrastructure denial with `reason`).

Authorization ladder (every allow/deny SEL-audited as `mcp-gateway.app-call`):
1. **Capability** — the frame carries the opaque `spool_id` (which names a record) AND the `callback_secret` (which authorizes). The gateway re-reads its OWN spool record to recover `{server, session_key, pool_digest, callback_secret}`. Unknown/expired/schema-mismatched id → deny; a record with no secret, or a frame whose `callback_secret` does not `hmac.compare_digest`-match the record's → deny. Per #418 the `spool_id` alone (which the model can read from the marker) authorizes nothing.
2. **Backend binding** — backend resolved by exact `pool_digest` and re-checked against the record's server name; missing digest or dead backend → deny.
3. **Visibility** — target tool must declare `_meta.ui.visibility` including `"app"` in the backend's own `tools/list`, fetched FRESH per call (an authorization input is never cached, so a server-side revocation via `tools/list_changed` takes effect on the very next call). No declared visibility = model-only = deny (SEP-1865 default).
4. **Argument validation** — iframe-controlled `arguments` are validated fail-closed against the tool's declared `inputSchema` via `validation.validate_mcp_tool_arguments` (no schema → only `{}`; declared `properties` reject unknown keys unless `additionalProperties` opts in; unknown type names reject; a schema using validation keywords the subset does not enforce — `oneOf`, `$ref`, `multipleOf`, … — rejects outright so constraints are never silently dropped; annotation-only keywords like `title`/`format` are ignored; depth/string caps). Violations → deny before the payload reaches any backend.
5. **Governance** — the canonical `@server/tool` reference is resolved against the governance ceiling ∩ active profile (`mcp` scope), the same decision Plane A applies to model-originated MCP calls — one un-disableable ceiling across both invocation authorities. Evaluation errors DENY (fail-closed; this path has no always-on deny floor to backstop a fail-open). Ungoverned standalone hosts (no policy, no profile) permit, as on Plane A.
6. **Forward** — through the normal `forward_from_stub` seam on an ephemeral stub with `CallerContext(session_type="mcp-app")`, timeouts 10s (`tools/list`) / 20s (`tools/call`).

### 4. Dashboard endpoint `POST /api/mcp-apps/call`

Body `{"spool_id", "callback_secret", "tool", "arguments"}`. Three dashboard-side gates run before the relay, denies SEL-audited: (1) the AUTHENTICATED caller identity (token-auth middleware's `request["user"]`/`request["app"]`, never a client header) must be the dashboard owner — app-scoped tokens and non-owner subjects are refused; (2) restricted (incognito/guest) sessions are refused (the same ephemeral gate memory operations use); (3) the caller's `X-Session-Key` must match the spool record's `session_key` when the record carries one — the bare slot key is canonicalized (`_history_key_for`) before comparison so a legitimate owner call is not refused as a bare-vs-prefixed mismatch (defense-in-depth against a leaked spool id relayed from another session's context). The `callback_secret` (delivered to the iframe over the owner-WS render frame) is relayed in the owner-authenticated, non-model-visible POST body and forwarded to the gateway, which authorizes on it. The unix-socket reader is sized to the gateway's 64 MiB frame cap (+ wrapper margin) so a large structured/non-text result is not a false 503; the outer relay timeout (45s) exceeds the gateway's combined inner budgets. Handler `dashboard/handlers/mcp_apps.py` relays to the gateway `app-call` frame, credential/exfil-URL-redacts the returned result before handing it to the iframe, and maps rejections: 403 (policy denial), 404 (unknown spool id without gateway), 503 (gateway down), 504 (timeout). Consumed by the SPA AppBridge (`McpAppFrame.tsx`), which relays `tools/call` postMessages from the iframe.

## Render path & security model

- **Interception** (`mcp_gateway/backend.py`): a `tools/call` result triggers spooling when it carries `_meta.ui.resourceUri` OR its tool declared a `ui://` uri in `tools/list` (`extract_declared_ui_uris` — the form real servers use). `isError` results never spawn a render. Failure-safe: any interception error delivers the original result unchanged.
- **Marker handling** (`mcp_apps_render.handle_tool_result`, async — the spool read is `asyncio.to_thread`-offloaded because records are multi-MB and the seam runs on the dashboard event loop): validates the id, loads the record, then:
  - **Binding before claim** (order matters): the record's `session_key` must match the receiving slot FIRST — a marker echoed into the wrong session is refused *without* consuming the render, so a replay racing ahead cannot burn the legitimate slot's render. Empty binding is allowed with a log line.
  - **Single-consume**: only a binding-passing caller takes the atomic `O_CREAT|O_EXCL` sidecar claim (`<id>.rendered`) — a marker echoed into a later turn (LLM echo, transcript replay) is inert. The record itself stays until the TTL sweep so the already-rendered app's callback capability keeps working.
  - Broadcasts `mcp_app_render` to OWNER-authorized WebSockets only (`broadcast_ws_owners`) — the frame carries the `callback_secret` (the live capability, #418), so guest/non-owner sockets never receive it. It also carries `tool_input`/`result_content`/`structured_content`, each **credential/exfil-URL-redacted** (`security.redact` over string leaves) before it crosses into the server-authored iframe; the marker is stripped from the transcript text in all paths. Binding uses the CANONICAL producing session key (`dashboard:<slot>`) passed separately from the bare routing slot key, so a real render is not silently refused as a mismatch. Frontend: `chatSlice.mcpApps` is keyed by `(session_key, tool_call_id)` — cross-slot ACP-id reuse can never cross-render — with a bounded per-slot cap (oldest evicted) and full eviction when the slot is deleted or its conversation cleared (payloads are multi-MB).
- **Iframe isolation** (`website/src/lib/mcpAppSrcdoc.ts`, `McpAppFrame.tsx`): null-origin sandbox (`allow-scripts allow-forms`, NO `allow-same-origin`). The per-app CSP `<meta>` is emitted **before every untrusted byte** of the app document (only a strictly-anchored leading doctype is hoisted, preserving standards mode) — no author markup can parse ahead of the policy. Policy defaults: `default-src 'none'`, `form-action 'none'` (locked; `form-action` does not fall back to `default-src`), `connect-src`/`frame-src` `'none'` unless the app's sanitized domain lists open them (`sanitizeCspDomain`: https-origin grammar, rejects CSP-structural characters). Camera/microphone are NOT advertised in the iframe `allow` (unusable on a null/opaque origin), and the AppBridge bounds concurrent app→gateway callbacks per frame. **Navigation confinement**: the AppBridge only accepts messages whose `source` is the iframe's `contentWindow`, and it retires the callback bridge the moment the app navigates its document away from our srcdoc. A trusted bridge-guard `<script>` (injected right after the CSP meta, before any app byte) signals navigation-start on the original document's `pagehide`/`beforeunload` — which fire *before* a navigated-to page's `<head>` scripts run — so a replacement document cannot post a `tools/call` in the pre-`load` window and have the host relay it with the callback capability (the iframe `load` handler is the backstop). Forging that signal only makes the bridge more restrictive (self-DoS), so it needs no nonce.
- **Governance**: app-originated calls traverse the governance ceiling (`mcp` scope on `@server/tool`) inside `handle_app_call` — step 5 of the authorization ladder above, resolved with the producing backend's `agent` name so an agent-bound deny profile is honored; see `governance.md`. Issue #418 (the render-id vs callback-capability split) is IMPLEMENTED here (see `callback_secret` above); the follow-up issue tracks only optional Plane A parity refinements (arg-classification scopes, shared audit plumbing).
- **Token confidentiality**: the `callback_secret` — not the marker — is the capability, and it never enters model-visible text (owner-WS only). As defense-in-depth the default spool directory (`mcp-apps` under the crew home) is on `security._SENSITIVE_HOME_DIRS`, so the agent's own file tools cannot read spool records; legitimate readers (gatewayd, dashboard) open the files in-process. (A `KIROCREW_MCP_APPS_SPOOL` override to a non-default location is an operator config choice, outside the single-user agent-attacker model.)
