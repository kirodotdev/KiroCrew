# MCP Apps (SEP-1865 interactive app rendering via gatewayd)

MCP Apps render server-provided `ui://` HTML inline for a successful model-originated `tools/call`. The gateway fetches the resource out of band, spools the render payload, appends an opaque marker to the ordinary result, and the dashboard replaces that marker with an isolated iframe. `mcp_gateway.backend.Backend._maybe_intercept_ui_result` only reaches this path for stdio servers behind a gateway stub. Raw HTTP/SSE and streamable-HTTP server entries have no stub, remain unmodified by `mcp_gateway.rewriter`, and do not provide this Apps host path.

The producer advertises the MCP UI extension only while `mcp_gateway.backend._mcp_apps_enabled` permits it. An explicit `KIROCREW_MCP_APPS` disable or stored `mcp_gateway.apps_enabled = false` disables rendering even for a stubbed server; `mcp_gateway.enabled` only changes backend sharing, not Apps eligibility. The dashboard consumer still handles a valid marker independently of the producer gate. `test_mcp_apps_e2e.test_flag_off_is_a_noop` pins that the disabled producer path neither injects the extension nor creates a spool record.

`Backend._maybe_intercept_ui_result` still filters model-facing `tools/list` responses while the Apps producer gate is off; the server's app-only visibility declaration remains an authorization boundary rather than a rendering preference. Its exemption for a gateway-internal stub runs first, so an app authorization listing still sees app-only tools. That exemption is keyed on `backend.INTERNAL_STUB_PREFIXES` rather than on `__app_call__` alone: a tool-surface probe (`__tool_surface__`, see `mcp-gateway-backend-replacement.md`) asks the server for its own declaration and must not receive a narrowed one. `test_mcp_gateway_apps_spool.test_listing_filtered_even_when_feature_disabled` and `test_app_call_listing_unfiltered_when_feature_disabled` pin the ordering.

## Render handoff

### Marker and spool record

`mcp_gateway.apps.append_marker` appends `[kirocrew-mcp-app:<id>]` to the first text item of the result, or adds a text item when none exists. `mcp_apps_render.MARKER_RE` accepts only a lowercase hexadecimal UUID-shaped id, so marker text cannot select an arbitrary path. `mcp_apps_render.handle_tool_result` strips every recognized marker from transcript text whether or not its record can render, keeping the control token out of the transcript and model-visible result.

`mcp_gateway.apps.write_spool` writes the schema owned by `mcp_apps_render.SPOOL_SCHEMA_VERSION` to the configured spool directory. `mcp_apps_render.load_spool` rejects malformed ids, path escapes, non-files, oversized or expired records, non-object JSON, and an unknown schema before returning data. This makes the spool record an unambiguous capability-bearing wire contract rather than best-effort JSON that a stale reader could misinterpret. `test_mcp_apps_render.test_load_spool_rejects_wrong_or_missing_schema` and `test_mcp_apps_render.test_load_spool_rejects_and_reaps_expired` pin the fail-closed reader behavior.

A record carries the producing server, canonical session key, exact producing backend pool digest, app HTML, resource CSP and permissions, callback capability, structured result, original tool arguments, and original result content. `write_spool` drops input keys outside that schema, so render-only or future caller fields cannot become silently persisted authority.

`write_spool` creates the directory and record with owner-only protection before content is published. The record filename and callback capability authorize a live app path, so publishing bytes before protection would expose both during the write window. `test_mcp_gateway_apps_spool.TestWriteSpool.test_lockdown_precedes_content` and `test_failed_lockdown_publishes_no_record` pin that no unprotected final record is observable.

The writer sweeps stale records opportunistically and `load_spool` enforces expiry on every read. The reader also removes the rendered sidecar with an expired record, so an app callback cannot survive merely because the background sweep has not run.

### Rendering and delivery

`mcp_gateway.backend.Backend._maybe_intercept_ui_result` accepts a `ui://` URI from result metadata or a prior `tools/list` declaration. It rejects every other scheme, ignores failed tool results, and falls back to the original unmodified result when resource reading, MIME validation, decoding, or spooling fails. `test_mcp_gateway_apps_spool.test_resources_read_timeout_delivers_original`, `test_wrong_mimetype_delivers_original`, and `test_is_error_result_never_intercepts_either_form` pin the failure-safe path.

`Backend._read_ui_resource` asks the same producing backend for `resources/read`; `Backend._parse_ui_contents` accepts only the MCP Apps HTML MIME profile and either UTF-8 text or validated base64 data. The gateway never dereferences an arbitrary network or filesystem URI supplied by the tool result.

`mcp_apps_render._load_bound` checks the canonical producing-session key, and `_take_claim` atomically creates the rendered sidecar. The order is load-bearing: a marker replayed into another session cannot consume the legitimate session's one render. The record remains until expiry after a successful claim because the already-rendered iframe still needs its callback capability. `test_mcp_apps_render.test_wrong_slot_replay_does_not_burn_the_render_claim` and `test_handle_tool_result_replayed_marker_is_inert` pin those replay properties.

The two are separate functions so that every CANCELLABLE step finishes before the claim is taken. `handle_tool_result` loads the record, redacts the app-bound payload, and only then claims, with no `await` left between the claim and its own return. Claiming is irreversible and makes every later replay inert, and `CancelledError` is a `BaseException` that the seam's `except Exception` does not catch, so a turn cancelled inside the redaction offload would otherwise return nothing to the caller and leave an app that no replay can render and no row records. Ordering the claim last means such a cancellation leaves the record claimable instead. The cost is one wasted redaction pass when a concurrent replay wins the claim. `test_mcp_apps_render.test_a_cancelled_redaction_leaves_the_record_claimable` pins it.

`_take_claim` is OFFLOADED via `asyncio.to_thread`, because `os.close()` on a file descriptor is named by the `blocking: true` `no-blocking-call-on-event-loop` rule in `AUTOSDE.yaml`: the gateway runs every task on one loop, so a claim stalling on network or FUSE spool storage freezes the user's turn and the liveness heartbeat together until the watchdog kills the process. That the syscalls are cheap on a local path does not exempt them; the rule's own guidance is to offload when in doubt. The offload reintroduces a loss window, because an executor thread runs to completion whatever happens to the awaiting coroutine, so a cancellation delivered mid-`os.open` would create the sidecar while the caller raises and records nothing. `handle_tool_result` closes it by SHIELDING the call, which keeps the worker's outcome knowable through the cancellation, and by calling `_release_claim` to unlink a sidecar it can no longer record: a claim nobody can record is worse than no claim, since it makes every later replay inert. A shield alone is NOT enough to reach that release, and the spec previously claimed it was: `asyncio.shield` protects the inner future, not the awaiting coroutine, so a SECOND `.cancel()` on the task raises `CancelledError` out of the cleanup's own `await` and past the `except Exception` beside it, stranding the claim with nothing recorded. A turn deadline and a slot deletion firing on one task is ordinary operation, so both cleanup awaits go through `_drain_shielded`, which absorbs repeated cancellation until the worker's outcome is in hand; the original `CancelledError` is then re-raised by the caller, never swallowed. That drain cannot spin: an iteration either suspends on a pending future or returns once it is done, so iterations are driven only by further `.cancel()` calls. Inside `_take_claim` the DIRECTORY ENTRY is the claim, and it CARRIES the rows that own it: `{slot_key, rows, row_ids}` is written into a `.tmp` and `os.link`ed into place, so `link` is the only syscall whose outcome decides whether the claim was taken, and it fails with `FileExistsError` exactly as `O_CREAT|O_EXCL` did. Creating the sidecar empty and writing the identity afterwards is NOT equivalent, because a claim could then exist that is neither attributable nor recoverable.

`link` is therefore the PREFERRED publisher, not the only one, corrected after review: a data home on a filesystem with no hard links -- exFAT, a number of FUSE and network mounts, which is the same storage this offload plans for -- refuses every `link`, and reporting `"error"` for it turned a standing configuration property into silent loss of EVERY app render, because the caller strips the marker on that branch and records nothing. `_take_claim_without_link` publishes the sentinel directly under `O_CREAT|O_EXCL`, which keeps both properties the link path exists for: the create is atomic, and an existing claim still raises `FileExistsError` so a spent claim is attributed rather than overwritten. `os.replace` is not the alternative despite needing no links, because it replaces silently and a second caller would take a claim another row owns. The fallback runs on ANY `link` failure rather than an errno allowlist, since it can answer nothing the link path would not -- an existing claim reaches the same spent branch and a home that can create no sentinel still reaches `"error"` -- while an errno list can only be incomplete, EPERM, EOPNOTSUPP and ENOSYS all being in use for this by real drivers. What the fallback gives up is a window in which the sentinel exists with no identity in it. A death there leaves a ZERO-BYTE sentinel, and `_attribute_spent_claim` reads that as `"inert"` rather than as an unowned claim it may take -- an adoption was written first and then removed, because the shipped code takes its claim as `os.open(sentinel, O_CREAT|O_EXCL)` followed by a bare `os.close`, writing nothing, so on every deployed gateway each SUCCESSFULLY rendered app already leaves an empty sentinel for the record's TTL. Emptiness therefore cannot distinguish an interrupted claim from a legacy rendered one, and adopting it would re-render every legacy app on whichever row replayed its marker after an upgrade. Inert is also what the shipped code answers a replay, so the legacy case is unchanged rather than merely safe. The write-FAILURE branch is recovered instead, since the caller that created the sentinel observes it and unlinks what it could not fill; only a hard kill between the two syscalls is unrecoverable, costing one app once on a link-less host.

A SECOND window sits one layer out and is now closed. The claim is durable the moment it is published, while the row's `mcp_app` flag rides the slot's next save, so a gateway death between those two writes leaves a spent claim on an unflagged row -- the app gone and nothing saying it existed, which is the silence this module exists to remove, reached through a crash rather than a reload. Nothing recovered it: the in-turn recovery is the `"spent"` branch of `handle_tool_result`, and that function has exactly ONE caller, the live turn path, so a restart never re-runs it; the marker a replay would need was stripped before the row was written, and in this crash it never reached disk either. BOTH of those recoveries need the OWNING ROW to exist, which is a THIRD window one layer further out. The claim is durable the moment it is taken, while the rows it names ride the slot's next save, so a hard exit between them leaves a sidecar naming rows the transcript never received -- and with the rows gone neither recovery can reach them, the `"spent"` branch having no row to replay and the restore pass no row to match. `handle_tool_result` therefore awaits the caller's `persist_rows` immediately before the claim, and only when the claim will name a row, so the durable claim is strictly NEWER than the durable rows and every crash after the claim leaves a row for the restore to flag. `chat_runner` passes `save_slot_off_loop(..., rows_only=True)`, which writes the transcript window off-loop and leaves the metadata line alone; it never clears `_dirty` -- only the flush passes do -- so the `mcp_app` flag written afterwards is still owed to the periodic flush exactly as before. It is BEST-EFFORT by contract: a persist that fails logs and leaves the rows owed to that flush, which leaves the pre-existing window rather than widening it, and refusing the claim instead would trade a rare crash for a common silent no-render under benign lock contention, which is the silence this module exists to remove. A raise is fail-closed for the same reason it is safe: the seam's own error path strips the marker with no flag and the claim was never created, so the record stays claimable. `test_mcp_apps_render.test_the_owner_rows_are_persisted_before_the_claim_is_taken` pins the order, `test_a_claim_that_names_no_row_persists_nothing` the gate, and `test_a_persist_that_raises_takes_no_claim` that the persist is a precondition rather than a call beside it. Three mutations are verified against a green baseline and named rather than counted: dropping the persist fails 2, moving it after the claim fails 2, and dropping the names-a-row gate fails 1, with the pre-existing claim-path tests green under every one. Recovery therefore reads the claim back at restore, which is what its `{slot_key, rows, row_ids}` body is for, and it is split in two because the halves belong in different places. `load_claimed_row_groups` does the filesystem work -- a spool scan plus a read per sidecar -- and returns ONE ROW GROUP PER CLAIM rather than a flat set, while `apply_claimed_rows` only touches memory, so each restore path uses the half it may: the two bulk drivers whose reads are inline by construction call `_recover_mcp_app_claims`, and the loop-affine ones call `_recover_mcp_app_claims_async`, which awaits the read on a worker thread exactly as those drivers already do for their transcript reads. Fusing the two would put a directory walk on the event loop and stall the gateway, which is what AUTOSDE's `no-blocking-call-on-event-loop` forbids outright. Every field the body carries is bounded, and the bound on the whole body is derived from the field bounds rather than chosen, so a body this code writes can always be read back -- a field left outside that sum let a long value push a legitimate claim past the limit, where the reader then refused a claim the writer had produced. The row identities are trimmed to fit. The slot key is not: a restore matches on it, and a trimmed key is a REAL key owned by whichever slot's own key is that prefix, so trimming would attribute the claim to the wrong slot. An over-long key is therefore OMITTED from the body, which matches no slot and so recovers nothing, and the claim is still taken -- failing the write instead would reach the caller's blanket handler, which strips the marker and records nothing, losing the render as well as the recovery.

The app flag and its lead marker are written in ONE update, at both sites that write them, because a half-written row renders NOTHING. The periodic flush takes `slot.messages` as a shallow copy of REFERENCES and serializes those same live `meta` dicts on a worker thread, so two separate assignments are visible half-done: a snapshot landing between them stores `mcp_app` with no `mcp_app_lead`, and the client draws the notice on the lead alone. Nothing repairs that state, which is what makes the write shape load-bearing rather than tidy -- `apply_claimed_rows` reads a surviving `mcp_app` as proof the lead survived, so it marks the claim's lead taken and skips the row, and the claim is then swept at its TTL and the notice is lost for good. `dict.update` applies both keys in one step, so a reader holding the interpreter sees both or neither. `test_mcp_app_absence_marked.TestTheFlagAndItsLeadReachTheRowTogether` pins the write SHAPE rather than only the result: it records how the row's `meta` was written and refuses either key arriving on its own. The live-turn site carries the same single-update shape and is not pinned by a test -- its `meta` dicts are built inside the turn, where a recording dict cannot be injected -- so that half rests on the code.

What that recovery reads is BOUNDED, which review required: retaining one group per claim made a restore's retention grow with the spool's age rather than with the work in front of it, since the spool is swept at 24h and a slot that renders apps steadily leaves far more sidecars than a restored transcript could ever match. `mcp_apps_render._MAX_RESTORE_CLAIMS` bounds it, and WHERE the bound sits is the whole point: capping the groups while still building a list of every sidecar and sorting it retained the spool regardless of the cap, which is what a second review pass said in so many words. The scan therefore STREAMS the directory and keeps a bounded min-heap of the newest matching claims, each claim past the cap displacing the oldest one held, so the pass retains the cap and nothing more. Streaming leaves an open directory handle, which this pass closes itself. The ORDER is what makes the bound safe: the newest claims are kept, because the loss this pass exists to repair is the one that just happened, so the newest claims are the ones a restored row can still match and the oldest are the ones worth dropping. Past the cap an old claim goes unrecovered, costing one notice on a row that old -- the same silence this module chooses wherever a row cannot be identified. What the cap does NOT bound is the scan's reach: a slot whose claims are outnumbered by other slots' sidecars still examines them to find its own, and bounding that needs the slot in the sidecar NAME, which the gateway pairs and sweeps by. Reads are what the advisory lanes priced; RETENTION is what the blocking finding was about, and only the second is bounded here. The bound reaches the NESTED field too, because capping the claims while one claim's own set grows with the rows that shared a `tool_call_id` leaves the retention unbounded through the nesting: `_MAX_CLAIM_ROWS` caps the identities one claim carries and `_MAX_ROW_ID_LEN` drops one longer than a `meta.mid` or an ISO stamp can be. Both sides apply it -- the payload a claim is written with, and the set a restore builds from a sidecar it did not author -- so a corrupt or oversized body costs a bounded amount of memory. `test_mcp_apps_render.TestOneClaimCarriesABoundedNumberOfRowIdentities` pins the write cap, the load cap, the dropped over-long identity, and that a claim of ordinary size is untouched. `test_mcp_apps_render.TestTheRestoreKeepsABoundedNumberOfClaims` pins the count, the newest-win ordering against a directory that reports the oldest first, that a slot under the cap is untouched, and that the directory handle is closed. No test observes retention directly, which is why the first attempt's tests passed over a scan that still held the whole listing.

The fifth site is the one that matters for reach, and it is inside a function rather than beside a driver. `rehydrate_slot_from_history_async` is the only way anything outside `chat_persistence` rebuilds a single slot from disk, and eight callers use it -- members, messaging, files, two in the Slack gateway, Issue Radar, Spec Builder -- so recovery runs there, on the slot it is about to hand back, and every caller has it without asking. Wiring those callers one at a time is precisely how the bulk drivers were first done, and two of the four were missed that way in one pass; a caller added later would restore a row whose flag the crash lost and nothing would say so. `test_source_corpus.TestNoGateEnumeratesTheCheckoutByWalking` records the same shape for a different convention: a rule nothing pins does not propagate. The live-slot early return is deliberately NOT covered -- nothing was read from disk there, the flags are already in memory, and `messaging` documents that lookup as an O(1) dict hit, so a spool scan would be charged to every cache hit. The `is not None` guard on the build's result is load-bearing rather than defensive: `_recover_mcp_app_claims_async` is typed for a slot, so removing it fails `mypy`, which is the gate that keeps a `None` return -- an ordinary closed session -- out of the recovery.

Its recovery does NOT sit where the bulk drivers' does, and review caught why. That function closes two races by re-checking them synchronously and immediately before the build -- a tab-close and a session deletion landing during its transcript read -- so an `await` after the build reopens the deletion one a step later: the slot is published by then, so a deletion arriving during that await leaves the caller holding a slot that is no longer the session's, and the delete-won save discards what it accepts. The remedy is the split this module already uses everywhere else -- `load_claimed_row_groups` runs in the PREFETCH phase alongside the transcript read, and the apply after the build is synchronous, so nothing separates the deletion re-check from the hand-off. `TestNoAwaitSeparatesTheDeletionCheckFromTheBuild` pins the order, the consequence -- a deletion landing during the spool read refuses the rebuild rather than handing back a slot a caller will write into -- and that the apply still lands a real claim through the synchronous path.

The grouping is carried that far because the lead marker cannot key on a `tool_call_id`, and review caught the recovery doing exactly that. A claim IS an occurrence, and a transcript-preserving reset can hand a genuinely new call an id an older row already used -- so with a call-id key an older flagged row claimed the id and the newer occurrence recovered beside it took no lead, its absence notice never rendered, and two lost apps read as one. That is the same defect the client's superseded rules had, reached through the restore rather than through the live turn, which is the second time this one call id has been mistaken for an identity. The lead is now keyed on the claim's own index, so occurrences are independent by construction and a shared id cannot make one suppress another. Within a claim the earliest row in transcript order takes it, matching what the live path would have written, and a claim whose flag survived reserves its own lead so no recovered sibling draws a second notice -- reachable from a sidecar naming a mix of flagged and unflagged rows, which is disk content this pass does not author. `TestEachClaimGetsItsOwnLead` pins all four cases; reverting BOTH halves to a call-id key fails 2 tests, flattening the groups on the way in fails 2, dropping the survivor's reservation fails 1, and leading on every row fails 3, against a baseline of 0. A partial revert that re-keyed only the assignment killed a different pair and left the headline case green, so the full revert is the mutation that establishes it.

The read is asked for the CANONICAL producing-session key, via `effective_session_key`. This is the one trap worth naming twice: the claim body records whatever `_take_claim` was handed, and that is `binding_key`, not the bare slot key every other chat event routes on. A bare key here matches no claim and recovers nothing, in silence -- the same bare-vs-canonical mismatch the render call already guards against, one layer down on the read side. Three call sites choose that key, and the reader takes a KEY rather than a slot because one of them has none yet: the prefetch read happens before the slot is built. `session_key_for` is that rule for a name plus its persisted `linked_session_key`, and `effective_session_key` delegates to it so a second spelling cannot drift -- a restore asking with a key the live path never writes matches nothing and fails in silence. Its fallback must be `_history_key_for`, NOT `slot_transcript_key`: the two disagree for a channel-born slot, whose name is already a channel session key, and `surface_channel_session` deliberately surfaces such a slot UNBOUND when its key cannot be resolved, which leaves `linked_session_key` empty and the fallback in charge. The write side settles which is right, since `chat_runner` claims with `producing_session_key=effective_session_key(slot)`: the `dashboard:`-prefixed answer is the key the claim is filed under, so the transcript key -- which resolves the FILE and by its own docstring cannot carry a session -- would recover nothing.

The apply runs AFTER the restore has marked the slot clean, and leaves it dirty again whenever it recovered anything. A recovered flag exists only in memory; the claim it came from is swept at its 24h TTL, so a recovery that is never re-saved is a notice lost for good at the next restart. Recovering nothing leaves the slot clean, so an ordinary restore is not re-saved for no reason. Flags are all it writes -- it never unlinks or rewrites a claim -- so it is idempotent and a crash inside it leaves the state it started from; a row that already carries the flag is skipped so its lead marker stays exactly as the turn wrote it, and one lead is assigned per call among the rows it does recover. A LEGACY zero-byte claim lands in the unreadable branch and recovers nothing, which is what stops the pass scattering flags across a restored transcript -- an explicit emptiness check would be dead code, since an empty body is not JSON and reaches that branch on its own. The whole pass is best-effort behind `except Exception` in `chat_persistence`: it restores a display flag, so a failure must leave the restore untouched rather than lose a transcript. `TestARestoreRecoversAFlagItsClaimOutlived` pins the recovery, the slot scoping, the row scoping, the single lead, the untouched already-flagged row, the legacy claim, idempotence, and that the apply half reaches no file at all; `TestTheClaimIsReadWithTheKeyItWasWrittenUnder` pins all three choosers -- both wrappers and the pre-build derivation, including a BOUND channel slot reading its link and an UNBOUND one falling back to what the write used -- and `TestARecoveredFlagIsLeftToBeSaved` pins the dirty re-arm in both directions. Ten mutations are verified against a green baseline and are NAMED here rather than counted, because a restated kill count goes stale silently while the pinning test names above do not; the second five target the prefetch relocation and the pre-build derivation: reading after the build, awaiting the apply again, dropping the link from the derivation, taking the transcript key as the fallback, and making the shared rule ignore the link. The fallback mutation first SURVIVED, and that was a test aimed a layer too low rather than a weak assertion -- the derivation was pinned by calling it directly, so a call site swapped to the transcript key passed it untouched; the pin now sits at the call site, where the choice is actually made. `TestTargetedRehydrationRecoversToo` pins the eight-caller path by driving the REAL reader against a claim on disk, so a recovery removed from that function cannot pass by stubbing, and pins the live-slot return reading nothing; removing the recovery there fails 1 test, extending it to the live slot fails 1, and dropping the `None` guard is caught by `mypy` rather than by a test. The body is written by `_write_all` rather than one `os.write`, because a short write raises nothing and a truncated body reads later as an unreadable owner -- `"inert"` with the sentinel still in place, which is the same silence reached one step later. The temp comes from `tempfile.mkstemp` rather than a name this code composes, because the temp is private scratch and a file already sitting at its name must never decide whether the claim is taken. A composed name could: `<id>.claim.<pid>.tmp` is reproducible, so a hard kill between the open and the unlink leaves a residue that a respawn handed the same pid collides with on `O_CREAT|O_EXCL`, and every later claim for that record then answers `error` until the 24h sweep -- the app neither rendered nor recorded, the exact silence this seam removes. `mkstemp` retries internally on collision, so no pre-existing file is fatal rather than merely unlikely, and it already opens `O_CREAT|O_EXCL` at `0o600`; the `<id>.claim.` prefix keeps a leaked temp attributable to its record and the `.tmp` suffix is the one `sweep_spool` already ages out. `test_a_stale_claim_temp_does_not_block_the_claim` plants that residue under both the current pid and a neighbour, so the composed shape is blocked whichever pid the process is handed. The identity is what makes the durable sidecar SUFFICIENT ON ITS OWN, which is the crash-consistency property: the sidecar is durable while `meta["mcp_app"]` reaches disk only when the slot is next persisted, so a gateway death between the two would otherwise leave a spent claim with no flag -- the app unrenderable forever and nothing on the row saying it existed, the exact silence this module exists to remove. `_take_claim` therefore answers four outcomes rather than two: `took`, `spent` when an existing claim names THIS row, `inert` when it names a different one, and `error`. `spent` is reported as `app_on_row`, so re-processing the row after the crash puts its flag back with no ordering between the two writes and no restart-time scan for orphaned claims. `inert` is the replayed-marker case and flags nothing, which is why the attribution is load-bearing rather than cosmetic: a marker travels in tool-result text the model can echo into a LATER call, so flagging on the sidecar's mere existence would put "an app from this step is not viewable here" on a row that never had one. An unreadable or non-matching owner is treated as `inert`, so the failure direction is silence on the asking row rather than a false notice, and the owning row keeps what it already recorded. `test_a_spent_claim_on_the_same_row_recovers_the_flag` pins the recovery, `test_the_claim_records_the_row_that_owns_it` pins the durable attribution and that no claim temp leaks, and `test_an_unreadable_spent_claim_flags_nothing` pins the failure direction. `close` failing afterwards is logged and the descriptor given up, never reported as an unclaimed record: the earlier shape folded both calls into one `try`, so a created sidecar plus a deferred write error surfacing at `close()` -- the network/FUSE case this module plans for -- returned False and left the record permanently inert with no flag on the row. Releasing the sidecar there is not the alternative, because the caller strips the marker on both branches, so a released record has no replay left to render it. The identity narrows the residue that the release window leaves, and narrows it in the safe direction: a concurrent replay arriving between the claim and the unlink reads an owner that is not its own row, so it answers `inert` and draws NOTHING, rather than putting an absence notice on a row whose app is about to become renderable again. What it gives up is that one racing replay's chance at a record that becomes claimable a moment later, which a subsequent replay of the same marker takes instead. `_load_bound` is offloaded for the ordinary reason instead: it parses a record up to `MAX_SPOOL_BYTES`. `test_mcp_apps_render.test_the_claim_is_offloaded_to_a_worker_thread` pins the dispatch and `test_a_cancellation_during_the_claim_gives_the_claim_back` pins the release, the latter measuring the outcome because the sidecar provably exists at the moment the test cancels. `test_a_second_cancellation_still_gives_the_claim_back` pins the drain by holding the claim on an event the test owns, so the second cancellation provably lands while the claim is still in flight rather than after the unlink was already dispatched.

`handle_tool_result` sends `mcp_app_render` only through `state.broadcast_ws_owners` when that owner-only channel exists. It redacts every string key and value in the structured content, tool input, and result content before crossing into server-authored HTML. The callback capability therefore never enters marker text or a guest WebSocket, and credentials or exfiltration URLs in app-bound data are scrubbed. `test_mcp_apps_render.test_render_uses_owner_only_channel_not_generic` and `test_handle_tool_result_redacts_credentials_in_leaves` enforce those boundaries.

`dashboard.chat_runner._run_chat` invokes `handle_tool_result` for `EVENT_TOOL_RESULT`, passes the frontend slot separately from `effective_session_key`, and broadcasts the claimed payload. `website/src/hooks/useWebSocket.ts` stores that live event by tool-call id; `website/src/pages/chat/ToolCallLine.tsx` consumes it into `McpAppFrame`. This preserves canonical-session binding while associating the surface with its originating call. `test_mcp_apps_render.test_handle_tool_result_renders_in_bound_session` and `UseWebSocketCoverage.test.tsx` pin the handoff.

A spent claim is attributed by ROW MID -- not by `ts`, and not by `tool_call_id` -- and `_run_chat` resolves the owning rows from `slot.messages` before the seam so it can pass both identities in, derived from ONE row list so they cannot drift apart. `meta.mid` is minted once per row, so it names exactly one row for the life of the slot. A `ts` does not: only the rows that go through `monotonic_transcript_ts` are spaced by it, `_ChatSlot.append` preserves an explicit `ts` verbatim for a row replayed from a channel transcript because rewriting it would reorder the replay it came from, and a coarse clock stamps two appends in one tick identically -- which is the collision `meta.mid` exists to answer. The timestamps are recorded beside the ids as the fallback identity for a claim body that carries none, and both readers compare them as a set rather than for order, and the two are never MIXED: a claim carrying ids is matched on ids ALONE, or a foreign row that merely shares a claimed `ts` could answer for a row it is not, and answer durably, since the flag is never written back false. On the ts fallback -- a claim written before the ids -- a `ts` naming more than one restored row identifies neither, so neither is flagged: silence on a row is this module's failure direction and a false notice is not. `tool_call_id` is the BACKEND's own id and session-local in general, so a reset that preserves the transcript can hand a genuinely new call an id an older row already used. Attributing on the id would read a marker echoed into that new call as "spent by this row" and put the absence notice on a row that never had an app, which is the one outcome this attribution exists to prevent -- so the id is recorded for diagnostics only. `TestAClaimIsMatchedByRowIdentityNotTimestamp` pins the identity on both halves: a foreign row sharing the claimed `ts` is not flagged, a claim carrying ids ignores its own recorded `ts` (reachable once the claim's row has left the transcript, where the shared-ts guard cannot help), a claim written before the ids still recovers, an ambiguous `ts` on that fallback flags nothing, and the in-turn `spent` attribution answers `inert` to a row holding only the claimed `ts`. Five mutations are verified against a green baseline, named rather than counted for the same reason: reverting to ts matching, making the loader ignore the ids, making it MIX the two, dropping the ambiguity refusal, and making the attribution ignore the ids. The mixing mutation first SURVIVED, and that was a missing case rather than a weak assertion: in a transcript still holding both rows the shared-ts guard refuses the stranger for a different reason, so the mixing is observable only once the claimed row is gone.

Carrying the identity in the claim is necessary but not sufficient, because the WALK that gathers those rows still matches on the call id, and after a transcript-preserving reset that walk returns the preserved row alongside the new one. Both then take the flag -- durably, since it is never written `False` -- and because the client draws the notice on the first flagged row for an id, the stale row would answer for the app while the row that actually holds it is passed over. `_run_chat` therefore snapshots the `ts` of every row already in the slot when the turn begins, and both the claim's row list and the flag write skip any row in that set. A SET compared by membership rather than a high-water mark compared by order: `ts` is a string, so an ordering test would need it to sort numerically, whereas membership assumes nothing about the format. Taken once per turn before any tool row of that turn exists, which is what makes absence from it mean "appended since", and taken from the slot rather than recorded at each append site, so a site added later cannot be forgotten. Rows of the same turn are kept whatever their id, so an auto-approved call that appends a pre- and a post-approval row under one id keeps the flag on both. `test_mcp_app_absence_marked.TestAPreservedRowSharingTheIdIsNotFlagged` pins all three carriers -- the stored flag, the live patch, and the sidecar's own row list -- and dropping either gate, or emptying the snapshot, fails those tests with differing counts. The lookup is synchronous, which is what keeps the claim adjacent to the checks above it rather than reachable across a new suspension point. An empty intersection is `"inert"`, including when either side carried no rows at all: the flag loop is itself gated on finding a row for the call, so a claim taken without one has no flag a recovery could restore, and answering `"spent"` from the slot alone would hand it to whichever later row asked. `test_mcp_apps_render.test_a_reused_call_id_on_a_later_row_stays_inert` and `test_a_claim_taken_with_no_row_cannot_be_attributed_later` pin both halves, and reverting the match to the id fails exactly those two.

The same walk has a SECOND way to select a row it does not own, and it does not need a reset. `tool_call_id` reaches every reader already redacted -- `_run_chat`'s event preamble rewrites it in place before any handler sees it -- and credential redaction replaces the whole field with one constant rather than masking a span inside it, so two calls whose ids both look like a credential arrive as the same string. A row stores that string, so the walk hands one call's row to the other call, and the flag it receives is permanent. The gate cannot be a comparison of the redacted value against the id the handler holds, because that handler holds the redacted value too and the comparison is true even for a collapsed id; the multiplicity has to be recorded at the preamble, while the raw id still exists. `_run_chat` therefore counts the DISTINCT raw ids each redacted value has folded into, keeping a digest rather than the id so the turn retains no credential-shaped value, and both the claim's row list and the flag write are withheld where that count exceeds one. Withholding gives up the app's own row as well, deliberately: once the values are identical nothing tells the two rows apart, so flagging one would mean flagging both. Silence is repaired by rendering again; a flag on a row that never had an app is not, since it is never written `False`. `done` and `output` keep the id-wide walk they already had -- they describe the CALL, not a claim about which row once held an app. `test_mcp_app_absence_marked.TestACollapsedCallIdFlagsNothing` pins the unrelated row, that no row is flagged at all, the claim's own row list, and that an ordinary id still flags its row. Five mutations are verified against a green baseline and named rather than counted: reverting the owned-rows gate fails 1, reverting the flag gate fails 2, dropping the preamble's recording fails 3, loosening the count by one fails 3, and the full revert fails 3 -- the allow-direction test stays green under every one, which is what shows the gate is conditional rather than the feature turned off.

The frontend keeps render payloads only in live state and never persists app tabs, because a restored tab has no valid live payload or callback capability. `website/src/store/chatSlice.ts` and `mcpAppPanelTab.test.ts` enforce this lifecycle boundary.

That payload is the app's only carrier, so a transcript read after it is gone has nothing to rebuild the frame from, and an unmarked gap does not distinguish a degraded view from a turn that produced only text. `handle_tool_result` therefore returns a `ToolResultRender` stating whether this call consumed the record's single-use render claim, and `dashboard.chat_runner._run_chat` persists `meta["mcp_app"]` on every tool row of THIS TURN carrying that call id, so long as that id still names one call.

The flag follows the CLAIM, which is the irreversible half: past it the record's one render belongs to that call and no later frame can use it. It deliberately does not assert that a browser received the payload. `broadcast_ws_owners` drops the frame when no owner socket is attached and an unattended run has no viewer at all, which is precisely the case where a reader arriving later most needs to be told the app exists; gating on a delivered count would record nothing there. A dispatch that raises is recorded for the same reason: the claim is already spent, so that app can never be shown for that call. An inert replay, an expired or unreadable record, and a refused cross-session marker take no claim and leave the row unflagged, which is why marker presence is not the signal. The flag is never written false, so a row predating the field reads the same as a row that produced no app.

The flag is also pushed to open clients as a `chat_message_update` patch carrying that one key, because `chat.mcpApps` is a bounded cache: a session that opens many apps evicts an older payload while its row is still on screen, and a stored-only flag would leave that row blank until a reload. The reducer merges meta, and each patch is addressed by its row's own `ts` rather than by tool-call id: an auto-approved call has a pre- and a post-approval row sharing the id and the reducer patches only the newest of them, while the `ts` is the right ADDRESS for this send rather than a durable identity: it is resolved against the transcript the sender is holding, in the same turn that wrote these rows. The claim, which is read back in a later process, records `meta.mid` instead. `test_mcp_app_absence_marked.TestTheFlagAlsoReachesOpenClients` pins the payload and that an ordinary call patches nothing. The patch deliberately goes over `broadcast_ws` rather than the payload's owner-scoped `broadcast_ws_owners`: it carries one boolean saying an app existed on a row every client can already see, and no part of the payload -- not the HTML, not the tool data, and above all not `callback_secret` -- so there is nothing here a guest must be kept from. Sending it owner-only would instead leave a guest's row blank after an eviction, which is the silence this change removes.

`website/src/pages/chat/ToolCallLine.tsx` renders a plain line where the frame would have been whenever the flag is set and no live payload exists, including the side-panel build where no app tab survived. It draws on the row the BACKEND marked: `_run_chat` stamps `meta["mcp_app_lead"]` on the first row it flags for a call, both on the stored row and on the live patch, and `ToolCallLine` renders the notice only where that marker is true. An auto-approved call writes a pre- and a post-approval row and the flag is stored on both, so something must choose between them or one lost app reads as two.

The choice is the backend's because the client cannot make it. Two client-derived rules were implemented and each failed on a transcript-preserving reset, which leaves a historical row holding an id the backend later reissues: keying on the earliest row for the id picked that stale row, which is deliberately not flagged, so nothing drew at all; keying on the earliest FLAGGED row picked the stale row whenever IT had carried an app of its own, so the newer app's notice was suppressed and two lost apps read as one. A flat transcript does not record which rows belong to one call -- only the turn that appended them does, and `slot.messages` is in transcript order there, so the first row the flag loop reaches is the occurrence's earliest. The marker therefore needs no ordering comparison to read, and the client's transcript scan for this purpose is gone. Every row carrying `mcp_app` is written by the code that also writes the marker, so there is no earlier flagged row to keep a fallback for; a flagged row without it is a non-lead sibling and stays bare. `TestOneRowPerOccurrenceIsMarkedTheLead` drives a two-row occurrence -- with one row, writing the marker once and writing it on every row are indistinguishable, which let that mutation survive until the fixture grew a second row -- and the frontend suite pins both the pair drawing once and two reissued-id occurrences each drawing. The copy names the app when the row carries an identity: `app_not_viewable_here_named` interpolates `{{server}}` from `meta.mcp_server`, which `_tool_identity_fields` persists on the row and so survives the reload this notice exists for, and `app_not_viewable_here` covers the rows where the backend sent no identity at all. Two notices in one transcript therefore name two different apps instead of reading as one app reported twice. Its copy names the outcome and the way back rather than a cause, because reload, bounded-cache eviction, a guest socket and an unattended run all reach it while the remedy is one: ask the agent again. `test/test_mcp_app_absence_marked.py` and `website/src/test/ToolCallLine.mcpAppAbsent.test.tsx` pin the durable write, the zero-owner-socket case, and the four flag-and-payload combinations.

An inline app also makes its virtualized transcript row stateful. Once a live payload exists, `ChatPage` keys an app-bearing turn from the first app payload observed in that turn instead of the turn lead. An app-bearing loose row renders as a one-item `TurnBlock` from its first live payload, so later short-turn promotion updates that subtree instead of replacing it. Multiple loose siblings from the same app-bearing turn coalesce into that one synthetic `TurnBlock`, so later grouping changes its props instead of reparenting a sibling iframe. Payload insertion order stays stable when parallel calls complete out of transcript order, so a slower earlier call cannot replace the anchor chosen for an app already on screen. The selected anchor is latched by its session-scoped tool-call identity until the turn leaves the rendered transcript, so bounded payload eviction cannot promote a later app and remount the row. The app anchor key uses a session-and-tool-call namespace that ordinary row keys cannot enter, so history prepends and `uniqueRowKeys` suffixing cannot rename it. The preferred key still passes through `uniqueRowKeys`, preserving duplicate-key handling for the full display list. `ChatPage.steerKeyIdentity.test.tsx` pins the outer row and iframe nodes across payload arrival, reasoning insertion, history prepends, and retention eviction.

## Iframe policy and AppBridge

`website/src/components/McpAppFrame.tsx` renders a `srcdoc` iframe with `allow-scripts allow-forms` and without `allow-same-origin`. The missing same-origin permission forces the document to a null origin, preventing access to the dashboard DOM, cookies, storage, and same-origin APIs. The iframe can only use the host's postMessage bridge for privileged actions. `McpAppFrame.test.tsx` pins the missing `allow-same-origin` attribute.

`website/src/lib/mcpAppSrcdoc.ts` emits the per-app CSP meta tag and trusted navigation guard before every untrusted HTML byte, preserving only a leading doctype first. A `srcdoc` meta CSP starts enforcement where it appears and cannot provide every header CSP directive, so the null-origin sandbox remains the isolation boundary and the CSP limits the app's external capabilities. `mcpAppSrcdoc.test.ts` pins the injection order and strict default policy.

`buildMcpAppCsp` uses `default-src 'none'`, disables connection and nested frames unless the app declares valid domains, keeps form submission disabled, and limits script, style, image, font, media, and base sources to the policy defaults plus their corresponding declared domains. `sanitizeCspDomain` accepts only an HTTPS DNS origin, optional single wildcard subdomain, and optional port; it strips whitespace and rejects paths, non-HTTPS schemes, CSP separators, quoting, and embedded whitespace. This prevents a resource author from turning metadata into a second CSP directive. `mcpAppSrcdoc.test.ts` pins both domain sanitization and directive composition.

`buildAllowAttribute` grants only supported declared permissions. It may expose geolocation and clipboard write, but it does not advertise camera or microphone because those features are unusable in the opaque sandbox. The app cannot request broader iframe permissions through its HTML or CSP metadata.

`McpAppFrame` authenticates every inbound bridge message by the iframe `contentWindow`, answers `ui/initialize`, supplies the originating tool input and result after `ui/notifications/initialized`, handles size and display-mode negotiation, allows `ui/open-link` only for absolute HTTPS URLs with `noopener,noreferrer`, and logs app notifications with a server/tool label. It forwards only `tools/call` to the dashboard relay. Unsupported requests receive JSON-RPC method-not-found and unsupported notifications are ignored. A navigation-start signal and subsequent iframe load retire the bridge before a replacement document can use the host-held callback capability. `McpAppFrame.test.tsx` covers the supported bridge messages, unsupported requests, HTTPS link gate, and navigation retirement.

### Theming handoff

`McpAppFrame` populates SEP-1865's `hostContext.styles.variables` from the dashboard's own theme tokens, so an app on the SDK's `applyHostStyleVariables` paints in the user's active palette. `website/src/lib/mcpAppTheme.ts` is the token map's home: it declares the closed `McpUiStyleVariableKey` union, maps each protocol key to a dashboard theme token, and `readMcpAppStyleVariables()` resolves the values off `document.documentElement` via `getComputedStyle`, running every value through `sanitizeCssValue`. The map spells both namespaces out, so a rename on either side is a visible edit rather than a silent break. **Every mapped key reads a stored token**; a protocol key the dashboard has no token for is OMITTED rather than given a hardcoded value, because a literal has no source of truth — nothing distinguishes an app painting `14px` from what the dashboard renders, and the next change to the real scale would not move it. So the `--font-weight-*`, `--font-*-size`, `--font-*-line-height`, `--border-radius-xs`, `--border-radius-full`, `--border-width-regular` and `--shadow-hairline` keys are not sent: Kiro Crew stores no typography scale (the only `--font-*` properties in `index.css` are the two families) and its text sizes are per-call Tailwind utilities, so there is nothing to inherit. An app keeps its own type scale — a far thinner seam than the color one this handoff closes. `mcpAppTheme.test.ts` pins both the token-only rule and the exact omission list. The handoff adds **no** theme variable: `--color-background-info` is the one color key with no stored source, and it is derived as `INFO_WASH` of the resolved `--info` over `transparent` — the same derivation `website/src/tailwind-theme.css` already uses for `bg-info-subtle`, so the dashboard's own info surfaces and an app's info fill resolve from one definition. The customization surface stays at the 56 theme CSS variables described in [themes](themes.md).

The `--color-*` group is **all-or-nothing**: if any dashboard token feeding a color key fails to resolve or is rejected by the sanitizer, the whole color group is omitted, so an app never pairs a host background with its own fallback ink. The non-color keys that ARE mapped (the two font families, `--border-radius-sm/md/lg/xl`, `--shadow-sm/md/lg`) are delivered independently of each other and of the color group. When nothing resolves the `styles` key is omitted entirely rather than sent empty. `styles.css` is never sent, and `buildMcpAppSrcdoc` is untouched — theming is host-context data the app applies itself, not CSS injected into the srcdoc.

Delivery tracks `useTheme().themeVersion`, the single signal that bumps on a mode change, a color-theme change, an in-place theme-editor edit, and `loadCustomThemes` completion. `McpAppFrame` holds the mode name and the resolved palette in ONE snapshot memoized on `themeVersion` **alone**, and both wire payloads read both halves off that snapshot. That is a correctness requirement, not tidiness: `applyTheme` writes `data-theme` in a `ThemeProvider` effect while `theme` changes during render, and React flushes child effects before parent ones — so keying the palette read on `theme` resolved it one commit early and posted the new mode beside the old palette, which the app painted for a frame. `themeVersion` is bumped by the same effect that writes the attribute, so a snapshot taken on its render reads the palette that mode actually renders. When the serialized theme half actually changed, the frame re-delivers through the one outbound `notifyHostContext` post site — so a mounted app follows a theme switch without a re-render, and an identical palette posts nothing. `mcpAppTheme.test.ts` and the `McpAppFrame - host theme` block in `McpAppFrame.test.tsx` pin the map, the resolver, and the delivery gate.

## App-originated tool calls

The iframe posts `spool_id`, callback capability, requested tool name, arguments, and its session key to `POST /api/mcp-apps/call`. `dashboard.handlers.mcp_apps.api_mcp_apps_call` accepts only an object body with a tool name and object arguments, requires the authenticated dashboard owner rather than a client-supplied identity header, denies restricted sessions, and checks that the spool record belongs to the request session before it dials gatewayd. This prevents a leaked record id, app token, guest session, or another session from becoming a callback authority. `test_mcp_apps_call_endpoint.test_relay_rejects_non_owner_and_app_tokens`, `test_relay_rejects_restricted_session`, and `test_relay_rejects_session_mismatch` enforce the dashboard gates.

The dashboard is a relay, not the authorization authority. It sends one `app-call` frame over the uid-gated gateway socket and returns redacted backend results or errors to the iframe. It does not forward server names, pool identifiers, caller identity, malformed arguments, unrelated bridge methods, or a raw gateway response type. Unknown or expired records are rejected locally, and gateway unavailability, timeout, and unexpected frames have distinct HTTP failures as covered by `test_mcp_apps_call_endpoint` relay tests.

`mcp_gateway.app_call.handle_app_call` re-reads the spool record, requires a constant-time match of the owner-only callback capability, and resolves the backend only by the stored pool digest plus matching server name. A marker id alone therefore authorizes nothing, and a valid record cannot be redirected by a same-named backend in another pool partition. `test_mcp_apps_call_endpoint.test_app_call_requires_callback_secret` and `test_app_call_rejects_record_without_digest` pin those denials.

For each callback, `_tools_by_name` obtains a fresh caller-scoped `tools/list`; it is deliberately uncached because both tool visibility and input schema are authorization inputs that a server can revoke. `visibility_allows` is shared with model-side listing: absent visibility allows both model and app, an explicit app-only declaration hides the tool from the model but permits the app, a model-only declaration denies the app, and malformed declared visibility denies both audiences. `test_app_call_allows_tool_with_no_declared_visibility`, `test_app_call_still_denies_model_only_tool`, and `test_app_call_tools_list_is_fetched_fresh_per_call` pin the shipped semantics.

The gateway validates iframe-controlled arguments against that fresh tool schema before forwarding. It then applies the `mcp` governance decision to the canonical `@server/tool` reference with the producing backend agent name. Governance evaluation errors deny, while an ungoverned standalone host follows the same permit behavior as model-originated MCP calls. The forwarded request uses an ephemeral stub and `CallerContext(session_type="mcp-app")`, allowing backend routing and SEL auditing to distinguish app authority from model authority. `test_app_call_rejects_schema_violating_arguments`, `test_app_call_denied_by_governance_mcp_scope`, and `test_app_call_governance_evaluation_error_fails_closed` cover the critical gates.

`Backend._maybe_intercept_ui_result` never re-intercepts an `__app_call__` result, even when the called tool declares `ui://`; it returns the backend result to the requesting app verbatim instead of minting a nested spool record and replacing the callback result with a marker. `test_mcp_gateway_apps_spool.test_app_call_forward_never_reintercepted` pins this boundary.

`mcp_gateway.app_call._roundtrip` cancels in-flight work before detaching its ephemeral stub on timeout or cancellation. Detachment only removes routing state, so cancellation is necessary to reduce duplicate mutation risk when an iframe retries after a failed callback. `test_mcp_apps_call_endpoint.test_app_call_cancellation_is_audited` covers the cancellation audit path.
