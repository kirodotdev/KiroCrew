# Feature Map

One table per area, mapping every user-facing dashboard feature to **how a user
reaches it** and **where its code lives**. It exists so that "which page and
which handler own this?" is a lookup rather than a search, for a human or an
agent landing cold on a feature.

It is a **navigation index, not a contract**. Behavior contracts live in
[`../system-specs/`](../system-specs/README.md); this file says where to go and
deliberately says nothing about how a feature works.

## Maintenance contract

**A pull request that ADDS or REMOVES a feature updates this map in the same
PR. A pull request that only changes how an existing feature behaves does
not.** That line is drawn where it is because a map re-reviewed on every edit
stops being read: the cost has to land on the change that actually invalidates
a row.

`scripts/check_feature_map.py` enforces the mechanical half. It reads the
`base..HEAD` diff and fails only when a file is **added or deleted** under
`website/src/pages/` or `src/kiro_crew/dashboard/handlers/`, or a `<Route>`
entry is added or removed in `website/src/App.tsx`, while this file is
untouched. Editing existing files never trips it. The job row is in
[../ci/ci-and-reviews.md](../ci/ci-and-reviews.md).

The judgment half is reviewer-owned: the blocking `feature-map-correctness`
rule in root `AUTOSDE.yaml` verifies each changed row against the code diff and
rejects unrelated or cosmetic map churn. The mechanical check cannot tell
whether a row's *content* is still true, only that a structural change went by
without anyone looking at the map. When the check fires and the honest answer
is "no feature changed", update the row the new file belongs to so its columns
remain truthful; a whitespace or cosmetic edit does not count.

## How to read this

- **Reach it** is the user's path, written as the URL plus the tab or control
  that gets there. `?tab=` and `?view=` are real query parameters the page
  parses, not shorthand.
- **Page** is relative to `website/src/`.
- **Handler** paths resolve under `src/kiro_crew/`: `handlers/` is under
  `dashboard/`, other directory prefixes are literal, and `src/` paths are
  repo-relative. Bare module names resolve by unique basename; a short name after
  a full path inherits that path's directory. Per-app paths are relative to the
  app named in the row.
- **Endpoints** are representative routes, not the complete set. The full table is
  `src/kiro_crew/dashboard/routes/` plus the direct registrations in
  `dashboard/server.py`; `test/test_dashboard_route_table.py` pins its order.
- `TODO(verify)` marks a cell nobody has confirmed against code. Fix it or
  leave it; never replace it with a guess.

Sidebar entries come from `website/src/surfaces/builtins.tsx`, which is the
authoritative nav table (label, group, badge, preview gate). A surface marked
`hiddenFromNav` there has a working route but no rail row — it is reached from
somewhere else, noted per row below.

A Handler cell that names a facade (`chat_handlers.py`, `handlers/agents.py`, `handlers/artifacts.py`, `handlers/files.py`, `handlers/messaging.py`, `handlers/terminal.py`, `handlers/usage.py`, `handlers/security.py`, `handlers/memory.py`) points at the route surface; the code that owns the behaviour sits behind it in `chat_api/`, `agent_admin/` (and `handlers/agents_cc_model_rows.py`, the Claude model picker's row merge, which is not a feature of its own), `handlers/artifacts_parts/`, `file_api/`, `messaging_api/`, the `handlers/terminal_*.py` and `handlers/usage_*.py` owners, or the sibling owners the security and memory facades import (`security_audit.py`, `security_trusted_apps.py`, `security_governance_policy.py`, `security_trusted_registries.py`; `memory_services.py`, `memory_embeddings.py`, `memory_graph.py`).

`handlers/prompts.py` is such a facade too: the prompt and skill routes it names live in the `handlers/prompts_<role>.py` owners beside it.

`handlers/updates.py` and `handlers/knowledge.py` are such facades too: the update, log and stream routes and the Knowledge Library routes they name live in the `handlers/updates_<role>.py` and `handlers/knowledge_<role>.py` owners beside them.

The helpers every handler imports from `handlers/_shared.py` live in the `handlers/_shared_<role>.py` owners beside it; `_shared.py` is a facade that keeps no code of its own and is still the only import path.

`handlers/agent_panel.py`, `handlers/hooks.py` and `handlers/crew_log.py` are such facades too. The panel routes `handlers/agent_panel.py` names live in `handlers/agent_panel_read.py` (the drawer's read), `handlers/agent_panel_publish.py` (the publish routes) and `handlers/agent_panel_dashboard.py` (the dynamic dashboard's agent routes). `handlers/hooks.py` keeps the inbound webhook route and serves the script-hook routes from `handlers/hooks_scripts.py` and the webhook management routes from `handlers/hooks_webhooks.py`, with the webhook's limits and caller checks in `handlers/hooks_webhook_intake.py`. `handlers/crew_log.py` keeps its routes; who may read which crew log through the unit-keyed door lives in `handlers/crew_log_scope.py`.

`handlers/cron.py` is such a facade too: the cron job, run, lesson and cron-folder routes it names live in the `handlers/cron_<role>.py` owners beside it.

`handlers/core.py` is such a facade too: it keeps the page, health, theme, session sub-agent, logout, shutdown and app-token routes, and the STT, SEL, config and local token routes it names live in the `handlers/core_<role>.py` owners beside it.

`handlers/mcp.py` is such a facade too: it keeps the routes that take the mcp.json file lock (sync, toggle, remove, server detail and apply), and the other MCP server and gateway routes it names live in the owners beside it: `handlers/mcp_probe.py` (`/api/mcp`, `active`, `probe`, `measure`, `quarantine/clear`), `handlers/mcp_config_files.py` (`/api/mcp/scopes`), `handlers/mcp_gateway_routes.py` and `handlers/mcp_gateway_stubs.py` (`/api/mcp-gateway/*`, the stub route in the latter). `handlers/mcp_apps.py`, `handlers/mcp_custom.py` and `handlers/mcp_discover.py` are route modules of their own.

`apps/routes.py` is such a facade too: it keeps only the route table, and every app management route it names lives in the `apps/routes_<role>.py` owners beside it.

## Customize

One destination, pinned to the bottom of the rail, hosting nine tabs. Every tab
is a `?tab=` value on `/capabilities` (`pages/CapabilitiesPage.tsx`).

Any one of those tabs can also be **promoted to its own top-level rail row**, so
a sub-item someone uses daily is one click away instead of two. Each tab is
registered as a `pinnable` surface (`surfaces/builtins.tsx`,
`surfaces/registry.ts`), which keeps it OFF the rail until the user promotes it;
the promoted set is a per-browser preference held under `mc-nav-pinned` and
owned by `lib/navPinned.ts` (the sibling of `lib/appNavHidden.ts`, which does
the same job for app rows in the Apps group). Reach it from the pin control in
the Customize page header (`components/PinSurfaceButton.tsx`), which
resolves its subject from the current `?tab=` value. Promotions are capped at
`NAV_PINNED_LIMIT`, and the rail applies the filter in `shell/nav/appRail.tsx`. No handler and
no endpoint: the preference never leaves the browser.
