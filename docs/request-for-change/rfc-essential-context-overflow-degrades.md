# RFC: Essential-Context Overflow Degrades

> **Status:** `in-progress`. Nothing is on main. Verified at `f0be829003`:
> `render_essentials` in `src/kiro_crew/member_essential_context.py` raises
> `MemberEssentialContextError("V2 essential context exceeds 64000 characters;
> largest sources: ... Shorten these sources before continuing.")` whenever the
> rendered envelope is longer than `ESSENTIAL_MAX_CHARS` (64,000), and
> `build_v2_essentials` in `src/kiro_crew/context_assembly/member.py` lets it
> propagate, so the turn fails. `MemoryConfig` in
> `src/kiro_crew/config/memory_sections.py` has no field for the envelope size.
> The behaviour is specified in `docs/system-specs/modules/memory-skills-hooks.md`
> ("an over-budget or refused essential aborts context construction with a named
> reason rather than truncating its tail"). This document asks to change that
> specified default. At the maintainer's request it rides in the same PR as its
> implementation rather than landing first; the PR is named in
> `implementation-prs` above.

## Summary

When a member's V2 essential context is over its envelope, Kiro Crew stops
refusing the turn. It keeps the member's **core** (identity, persona prompt,
`SOUL.md`, `preferences.md`, `projects.md`) complete, drops whole **guide**
documents from the tail until the envelope fits, and puts one in-band notice in
their place that names every dropped source and its size. The turn runs and a
warning is logged. Nothing is ever cut mid-document, so the original "never
silently cut an essential" guarantee becomes "never silently omit one" rather
than "refuse".

The envelope size becomes a setting, `memory.essential_max_chars` (default
64,000), capped by the session's model window, so a user whose guides are left
out can raise it instead of editing files they did not write.

Hard refusal stays for one case: the core alone does not fit.

## Motivation

A Slack report on 2026-10-02 (jlaughli): a member whose agent spec's
`resources` array had picked up a batch of `file://.../context/*.md` entries
stopped working entirely with `V2 essential context exceeds 64000 characters`.
Deleting those entries by hand fixed it. Kiro Crew's own resource writers
(`dashboard/handlers/agents.py`, `dashboard/handlers/_shared.py`) only add
`skill://` URIs, so the entries most likely came from an external package
install or update (unverified). The user did nothing wrong in Crew and had no
in-product way out: every new turn of that agent failed until they found and
edited a JSON file.

Three properties of today's design make the refusal worse than the problem it
guards against:

1. **The failing input is usually not the user's own writing.** Agent specs are
   regenerated by package managers, IDE plugins and other tools. A refusal tells
   the user to "shorten these sources" when the sources are files they did not
   author and a spec they did not edit.
2. **The codebase already degrades in the adjacent cases.** Folder steering is
   fitted into the same envelope by `_fit_folder_steering_into_envelope`, which
   drops whole documents from the tail and adds a
   `FOLDER_STEERING_OMISSION_SOURCE` notice. Implicit project guides that cannot
   be read safely are replaced by `_omitted_guide`'s "PROJECT GUIDE NOT LOADED"
   note instead of failing the turn. Only the member's *declared* resources still
   fail closed, and the rationale given in `_read_implicit_guide` ("a guide the
   user can shorten") does not hold for regenerated specs.
3. **The budget may count bytes that never reach the wire.** For kiro-cli,
   `build_v2_essentials` also renders a native envelope in which documents
   kiro-cli loads itself are blanked to their header, and `essential_delivery.py`
   sends that one when the incarnation matches. The 64k check runs on the full
   envelope first, so a document the harness already carries natively can push a
   turn over a limit the delivered message would not have hit. (Read from code at
   `f0be829003`, not measured.)

## Goals

- An oversized essential context never stops a turn whose core fits.
- Every omission is visible to the model (in-band notice) and to the operator
  (logged warning), with the dropped source names and sizes.
- No document is ever truncated mid-body.
- The member's core is never dropped.
- A user can raise the limit without editing agent specs, and the raise cannot
  push a small-window model past a window-scaled ceiling.

## Non-goals

- Changing which documents count as essentials, or the per-source byte cap
  `_MAX_SOURCE_BYTES` (256,000 bytes) and the `_MAX_DOCUMENTS` count ceiling,
  which keep failing closed: they bound reads, not the prompt, so they stay tied
  to the default envelope whatever the setting.
- Fixing whatever external tool rewrote the spec.
- Refusing a profile save that fits on its own. Saving a
  `preferences.md`/`projects.md` that makes the *core* exceed the envelope keeps
  refusing, because that is the owner editing their own core; a save that only
  pushes guides out is accepted, and those guides drop at turn time with the
  notice.

## Design

### 1. Two tiers

| Tier | Documents | Over budget |
|---|---|---|
| Core | identity block; the template persona prompt (`<spec>#prompt` or its `file://` prompt); project `SOUL.md`; `<spec>#context-settings`; any `_omitted_guide` "not loaded" note; the member's `preferences.md` and `projects.md`; the "on-demand memory" note | never dropped; core alone over budget still raises |
| Guide | global and project always-steering, the conditional-guide index, implicit `AGENTS.md`, declared `file://` resources | dropped whole, from the tail, with a notice |
| Folder steering | `steering_dirs` documents | fitted afterwards by `_fit_folder_steering_into_envelope`, unchanged |

The readers report the core: `documents_for_member(..., core_sources_out=set)`
fills the set with the source label of every core document it returns, and
everything else it returns is a guide. The profile anchors and recall note are
appended by `build_v2_essentials` itself and are never droppable.

`SOUL.md`, the context settings and the "not loaded" note are core although the
first draft did not list them: `SOUL.md` is Crew's own persona file (it is the
one implicit document kept under kiro-cli's default-resources opt-out), the
context settings are a few hundred characters that describe the template, and
the note is the only record that a refused guide exists. Dropping any of them
saves little and loses identity.

### 2. Fitting

`fit_essential_documents` in `member_essential_context.py`, mirroring
`_fit_folder_steering_into_envelope`:

1. Measure core plus every guide. If it fits, return the list unchanged, so the
   rendered envelope is byte-identical to today's and a fitting member sees no
   diff.
2. Otherwise drop guides from the **tail of declaration order** until the
   envelope plus the omission notice fits. Declaration order is the user's only
   priority signal and is what the folder-steering fit already uses.
3. Reserve the notice's own cost before admitting the last guide, so the notice
   is the last thing to go: a guide that fits only without the notice is dropped
   too. When every guide is out and the full notice still does not fit, a
   minimal notice that only counts them is tried. If even that does not fit
   beside the core, raise -- naming the largest remaining sources and the
   setting.
4. Folder steering is fitted after this step, against what is left, as today.

`render_essentials` itself still only refuses; it gains a `max_chars` argument.

### 3. The notice

One essentials document, source `essential-context#omitted`, appended last,
worded like `_omitted_guide`:

> ESSENTIAL CONTEXT INCOMPLETE. N guide document(s) for this agent were not
> loaded because the essential context is limited to 64000 characters:
> `<source>` (12,345 characters), ... Do not assume their contents. If one
> matters for this task, read the file directly or ask the user. The user can
> raise the limit with the memory.essential_max_chars setting.

Because the envelope header says "This snapshot replaces ALL prior V2 essential
snapshots ... Do not keep applying removed sources", an omitted document must be
named as *omitted*, not left out of the list. The notice is what stops the model
from reading an omission as a removal.

A left-out guide whose exact body the harness already carries -- kiro-cli loads
an agent's declared resources itself, the same byte match that blanks it from
the native envelope -- is named in a separate sentence of the same notice: "not
repeated in this snapshot because this agent's harness loads them itself ...
They are not removed; keep applying them." Calling it "not loaded" would tell
the model to stop applying a document it holds. When every left-out guide is
harness-carried the notice opens with `ESSENTIAL CONTEXT SHORTENED` instead of
`INCOMPLETE`. This is a wording split only; counting such a guide at its header
cost is §4.

### 4. Native-envelope accounting (kiro-cli only) — deferred

Run the budget check against the envelope that is actually delivered: when
`native_documents` is present, a document whose body kiro-cli already loads
would count only its `[Essential source: ...]` header. Not in the first PR. The
full envelope is still what the full-envelope fallback sends, so fitting would
have to produce two document sets -- one for each envelope -- and keep their
omission notices consistent across a receipt change. That is a separate change
with its own tests; until it lands both envelopes are fitted from the same
documents, and the native one is never larger than the full one, so it always
fits.

### 5. User-visible signal

- `logger.warning` once per envelope build with the member, the limit, and every
  dropped source with its size. Shipped.
- A session-level warning chip in the dashboard ("Some agent context was not
  loaded — 3 files, 81k characters") linking to the agent's resources. Not in
  the first PR: no existing channel carries the folder-steering omission to the
  dashboard either, so this is a new `slot` field and its own PR.

### 6. Spec change

`memory-skills-hooks.md` replaces "an over-budget or refused essential aborts
context construction with a named reason rather than truncating its tail" with:
"an over-budget envelope drops whole guide documents from the tail and names
them in an in-band notice; only a core that alone exceeds the envelope, or a
refused source, aborts context construction". `providers.md` names the setting
where it quoted the fixed 64,000.

### 7. User-adjustable cap

A new config key, `memory.essential_max_chars` (int, default 64,000), on
`MemoryConfig` with the `_meta` label "Essential Context Limit".

- **Where it is set.** `~/.kiro/crew/config.json` under `memory`, or
  `PUT /api/memory/settings {"essential_max_chars": N}`, the route that already
  edits its peers `history_idle_hours` and `history_max_days`. Its GET reports
  it. There is no Settings → Memory page today: the memory settings card lives on
  the Overview page's Memory tab and renders only the consolidation fields, so a
  number input there is a follow-up (it needs strings in every locale).
- **Clamp.** Load and write both clamp to `[16,000, 500,000]`
  (`ESSENTIAL_MAX_CHARS_MIN` / `_MAX` in `config/memory_sections.py`, one pair of
  constants for both paths). The floor is above the largest member identity
  section -- the working protocol plus the 4,000-character
  `MEMBER_RULES_MAX_CHARS` and `MEMBER_BRIEFING_MAX_CHARS` layers, about 12,000
  characters -- plus the envelope frame, so a lowered setting cannot turn every
  turn into a core-overflow refusal. The ceiling is the window ceiling below at
  the 1M reference window; no window admits more, so a larger stored value would
  only ever behave as this one. A non-integer write is a 400; a non-integer hand
  edit loads as the default.
- **Effective size.** `effective_essential_max_chars(window)` =
  `min(configured, ceiling)` with `ceiling = max(3 * 33_000, floor(window * 4.0 *
  0.125))` -- one eighth of the window at four characters per token, never below
  three ordinary budgets. That is exactly `_ResolvedCaps.protected_context`, the
  ceiling `context_assembly/budget.py` already derives for protected context, and
  it is reused rather than spelled again. A window that is **unknown** (`None`,
  zero, negative) resolves to the 1M reference window, exactly as
  `budget._effective_window` does for every other budget, so its ceiling is
  500,000. The default deployment (`provider=acp`, `model="auto"`) resolves no
  window at a fresh session; capping it lower would make the setting a no-op
  where most members run, and the default of 64,000 keeps such a member's
  envelope unchanged until the user raises it. The window comes from
  the caller's existing `model_window` (`window_for_provider_client` /
  `resolve_model_window`), now passed to `_build_v2_essentials`.
- **Profile-save validation** knows no window, so it uses
  `smallest_essential_max_chars()`: the setting capped at the 99,000 floor,
  which is the ceiling of the smallest window. A profile it admits fits every
  session.
- **Raising admits.** A guide left out at 64,000 is loaded on the next turn
  after the setting is raised on a session whose window holds it; nothing is
  cached across turns.

## Security and safety

- **No new read.** Fitting only removes documents already read through `_read`
  with all its containment checks. Refused sources still fail closed, and they
  fail before fitting runs.
- **No trust widening.** Omission can only make the prompt smaller. The setting
  can make it larger, but only up to the window-scaled ceiling, and only for
  documents the readers already admit; the config file it lives in is already
  the operator's trust root for every other memory knob.
- **No privilege boundary moves.** Which sources are core is decided by the
  readers from where a document came from, not from its content or name, so a
  guide cannot promote itself into the core.
- **Silent-degradation risk.** The real cost is that a rule in a dropped guide
  stops applying. The notice and the logged warning are the mitigation; a
  user-authored rule that must always apply belongs in the core (preferences,
  persona) or in lessons, which have their own budget.

## Alternatives considered

1. **Keep refusing, improve the message.** Cheapest, but the user is still
   locked out of the agent until they edit a JSON file Crew did not write.
   Rejected as the primary fix; the improved message (it now names the setting)
   is kept for the core-overflow case.
2. **Truncate the tail document mid-body.** Rejected: a half document is worse
   than a missing one, because the model cannot tell what it lost.
3. **Drop largest-first.** Frees the budget with the fewest omissions, but it
   ignores declaration order and makes which file survives depend on sizes the
   user does not see. Kept as an open question.
4. **Only raise the cap.** A larger fixed cap moves the cliff without removing
   it, and a cap sized for a 1M window overflows a small one. Adopted *together
   with* degradation instead: the cap becomes a user setting bounded by the model
   window (§7), and degradation is what happens at whatever cap is in force.

## Rollout

1. This PR: tiering, fitting and notice in `member_essential_context.py` /
   `context_assembly/member.py`; `memory.essential_max_chars` with its clamp,
   window ceiling and `/api/memory/settings` field; profile-save validation on
   the effective size; spec text; tests below.
2. Follow-up: native-envelope accounting (§4).
3. Follow-up: dashboard session warning (§5) and a number input for the setting
   on the Memory tab.

### Tests (this PR)

- Fitting member: list returned unchanged, envelope byte-identical to the
  pre-change rendering.
- Guides over budget: tail documents dropped whole, notice lists exactly the
  dropped sources with sizes, envelope `<=` the limit, delivered native envelope
  carries the same notice inside the same bound.
- Core alone over budget: still raises `MemberEssentialContextError`, naming the
  largest remaining sources and `memory.essential_max_chars`.
- Notice cost reserved: a guide that fits only without the notice is dropped;
  the minimal notice stands in when the full list does not fit.
- Folder steering still fitted after guides, before the profile anchors.
- Refused source (outside root): still raises, even when the envelope is also
  over budget.
- The readers report exactly the core documents.
- Config: load clamp, write clamp, non-integer write refused; effective size per
  window (unknown, 32K, 200K, 1M); raising the setting admits a dropped guide on
  a 1M window and on an unknown one; profile validation uses the smallest
  size; every copy of the setting's help text states the measured caps.

## Open questions

1. **Drop order:** tail-of-declaration (proposed) or largest-first? Tail-first
   can drop several small guides declared after one huge one before reaching it.
2. **Core membership:** should the template `#prompt` be core? A huge persona
   prompt is the one thing the user can always shorten; keeping it core means a
   runaway prompt still refuses.
3. **Unknown window** -- resolved: it uses the 1M reference window the rest of
   `budget.py` assumes for `auto` (ceiling 500,000), because the conservative
   64,000 cap made the setting unable to raise anything in the default
   deployment (`provider=acp`, `model="auto"`), which resolves no window at a
   fresh session.
4. **Ship §4 next?** If native accounting alone would have kept jlaughli under
   64k, it is the next PR. Needs one measurement on a real oversized spec.
