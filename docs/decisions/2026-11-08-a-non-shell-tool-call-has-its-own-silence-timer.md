# A non-shell tool call has its own silence timer, and a call that outlives it is cancelled and handed back to the model as a timeout error

Decided by: Bolin Chen (bolichen97), Kiro Crew maintainer
Date: 2026-11-08
Supersedes: the rule in [`acp-client.md`](../system-specs/modules/acp-client.md), "Session-handle watchdog", that an in-flight tool whose oracle evidence carries no narrowing tag keeps the full build-scale suspect window (`watchdog.tool_stall_suspect_secs`, 90 min, under the 2 h hard cap). No earlier entry recorded it.

## Decision
Every non-shell tool call the harness identifies, except a built-in the harness never terminates, gets a silence timer that starts at dispatch and is restarted only by a frame attributable to that call; when it runs out the call is cancelled and, on the surfaces named below, the model is told it timed out, so it can retry. Each bound is a `watchdog.*` setting.

Fail open when activity may be invisible: a timer runs for a call only while the session can prove it would see that call's activity. Wherever it cannot, the call is not judged by its silence, and the liveness oracle and the hard cap judge it as they judged every call before this decision:

- A kiro-cli sub-agent call loses its timer once its sub-agent's frames may not have reached the session: the roster route is closed when the timer is read, or any frame naming a session reached no session on the runtime since the turn started (the runtime counts them). A co-tenant registered for less than one timer read closes the route and opens it again unseen; the count is what sees it.
- A call loses its timer when a frame of a kind the timer cannot read names it: an unknown `session/update` kind, a request this client does not serve, or a notification nothing reads.
- A call is not judged while an ask for it waits on a person (an approval, an MCP elicitation), whether or not the consumer holds the event meanwhile. The answer restarts its timer: what the call does next reaches the session as any call's frames do.
- No call is judged while an ask that names no call waits, or while a KAS hook runs (a hook can gate a call already dispatched, and no frame names which), and that time is not charged to any call afterwards. Time the consumer also spent holding an event meanwhile is subtracted once, not twice.
- No call is judged while a concurrent request reader holds the session's frames (a model switch or a command waiting for its own answer takes frames off the queue until it gets it).
- A call on Kiro Crew's own servers, its sub-agent calls included, is not judged on a session no keepalive can reach. Its heartbeat is its proof of activity, and the gateway's keepalive route delivers it only to a session the gateway's own registry holds; a session timing such a call is marked by that registry when it publishes the session. `kirocrew chat` and `kirocrew run` hold their session in their own process, and a sub-agent run on a shared session, a registry another command builds and an app's own runner hold theirs outside that registry, so none of them is marked. Such a session's other calls keep their timers.

- Non-shell built-ins (a file edit, a read, a search, a fetch): 5 minutes.
- Tools on an MCP server declared with a `url`: 5 minutes. Tools on any other MCP server, Kiro Crew's own included: 30 minutes. A frame the harness sends for the call restarts both, and so does the heartbeat of one of Kiro Crew's own tools. No capture shows kiro-cli or KAS turning a third-party server's MCP progress into such a frame, so that progress is not known to restart either.
- Sub-agent calls (the harness's own sub-agent tool, `spawn_run`, `spawn_continue`, `spawn_sub_agents`): 10 minutes, counted from the sub-agent's own frames. While a native sub-agent has any call open (a shell, a built-in, a Kiro Crew `wait` or `ask_question`, any other MCP call, its own sub-agent call) the parent's sub-agent call is not judged: no Kiro Crew watchdog times a native sub-agent's calls, and a running call sends nothing. The harness's own sub-agent call stops being timed once its sub-agent's frames may not have reached the session (above): kiro-cli streams a native sub-agent under its own session id, which reaches the parent only while the parent is the one session on its runtime.
- Kiro Crew's own tools that can block for minutes (`wait`, `ask_question`, `spawn_run`, `spawn_sub_agents`, the browser's hand-back and ask waits) send an MCP progress heartbeat about every 30 s with their current phase, instead of being on an exemption list.
- While a call waits on a person (an approval card, an MCP question) the timer is paused, the ask itself and its answer each restart it, and the approval caps stay as they are (600 s on the dashboard, 3600 s on a channel).
- A shell call keeps the oracle-driven rules. The hard cap stays as the backstop for every call.
- A built-in the harness never terminates gets no timer. kiro-cli dispatches `introspect` and never sends a result frame for it, and the model's next step can be another call with no text before it, or a sibling in the same batch, so nothing would ever mark it done and a timer on it would cut the healthy turn after it, a build streaming output included. It is named by the harness's own stamp (`_meta.kiro.toolName` is `introspect` on kiro-cli), never by the title, and the oracle and the hard cap judge it as before this decision.
- Any other call stops being timed once the model's own next text or thinking follows it: the model starts a new step only when every call of its batch has returned.
- These surfaces hand the call back the same way, on the same session: the dashboard chat and a sub-agent run as their tool-stall recovery; inside the turn, a messaging channel turn (Slack, Discord and every other channel's turn and nudge run through one turn driver), the native Slack turn, an agent channel member's turn, the CLI chat, a task-runner step, and every turn run through the shared background collector (cron, heartbeat, a workflow agent and the other background turns).

## Why
A built-in file edit dispatched next to a subagent launch was auto-approved and never ran, and the turn hung for 32 minutes. Nothing about a lost call can be seen from the client side: an MCP `tools/call` has no start acknowledgement and progress is optional, so the oracle read the call as an opaque tool and gave it the full 90-minute window, while the subagent's roster frames kept the empty-queue check from running at all.

The harnesses that do tell a slow call from a lost one use two clocks, an idle timer that output or progress restarts and a separate wall-clock cap. Claude Code's MCP idle timer is 5 minutes for a network server and 30 minutes for a stdio one, it counts from dispatch so a call that never starts is caught within the window, progress restarts it, and a stalled subagent is cut after 10 minutes. Gemini CLI times a shell command out after 5 minutes without output, OpenHands hands control back to the model after 30 seconds without new output, and Cursor's IDE resets an MCP idle timer on progress. The MCP specification lets a client restart its timeout on a matching progress notification and says it should still enforce a maximum. Most other harnesses (Codex, Goose, Cline, Roo Code, Continue, the TypeScript MCP SDK by default) use one fixed timer that progress does not restart, and none of the ones compared waits about 2 hours for one tool call by default. Built-in file edits have no timeout in most harnesses because they run in process; here the harness runs them in another process, so a lost one needs a bound like any other call.

ACP has no per-call cancel, so the cancel is the turn's `session/cancel` and the error reaches the model as the recovery prompt's statement that the call timed out and may be retried.

## Costs accepted
- A built-in that legitimately runs silent for more than 5 minutes (a large knowledge index, or kiro-cli's `code` intelligence on a cold large workspace) is cancelled. The setting raises it, and 0 turns a class off.
- A sub-agent that thinks silently for 10 minutes, with no frame and no tool in flight, ends its parent's sub-agent call.
- A call lost inside a native sub-agent holds its parent's sub-agent call until the oracle and the hard cap judge it, as every call waited before this decision, and so does a kiro-cli sub-agent call on a runtime another session shares. Timing the sub-agent's own calls, or the parent's call off frames the runtime dropped, would cut a sub-agent that is working.
- Every case where the session cannot prove it would see a call's activity (above) leaves that call to the oracle and the hard cap, so a call lost in one of them is recovered as late as before this decision: a kiro-cli sub-agent call on a runtime where any frame missed its session this turn, a call a frame of an unknown kind named, every call while a KAS hook runs or an ask naming no call waits, and every Kiro Crew call on a session no keepalive reaches (the CLI chat among them). Five review rounds each found a healthy turn cut where a call's activity was out of sight, one case at a time; the rule replaces those case-by-case fixes, and a session no keepalive reaches is one more case of the same rule, not a new decision. An ask that was answered restarts its call's timer instead of retiring it: after the answer the call's frames reach the session as any call's do, and the ticket's own edit was approved before it was lost, so retiring a call on any past ask would leave exactly that call uncut.
- Only kiro-cli and KAS frames say which calls an MCP server served, so other harnesses keep the oracle rules alone.
- A model that writes more text after a call within the same step retires that call's timer, so a call lost that way waits for the oracle and the hard cap, as every call did before this decision. A lost `introspect` waits for them the same way.
- The task planner's decomposition turn, the plan refine and eval runs stream their prompt themselves and do not hand the call back: a silence expiry ends them on the tool stall as before, and the model is not told the call timed out. Each is a short planning or measuring turn that a person starts and can run again. So does every other caller that streams a prompt itself outside the surfaces above (a webhook agent turn, the prompt optimizer, a built-in app's own runner). Agent channels and the CLI chat are among the surfaces that hand the call back.
